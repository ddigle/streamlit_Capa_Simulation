1한눈에 보기

앱은 코어와 모듈로 나뉩니다.

  • 코어 — HOME · Static · 실행 관리 · Dynamic · Admin 같은 원래 화면과 계산 전부입니다. 앱 관리자 쪽에서 만들고 고칩니다.
  • 모듈 — 동료가 만든 화면입니다. 사이드바의 「모듈」 상자 아래에 따로 섭니다. 켜진 모듈은 앱을 쓰는 모든 사람에게 보입니다.

사람은 셋입니다.

나담당자

무엇을 만들지 정해 에이전트에게 말합니다. 결과를 앱에서 봅니다. 승인 창을 읽고 허락합니다. 가지를 푸시하고 PR 을 엽니다.

내 에이전트Claude Code

내 모듈 폴더 안의 코드를 쓰고 점검을 돌립니다. 하는 일을 쉬운 말로 먼저 설명하고, 위험한 일은 먼저 묻습니다.

앱 관리자

새 모듈 등록과 성숙도 L2(9장)를 승인합니다. 내 PR 을 점검하고 합칩니다. 앱과 배포 서버에 올리고, 문제가 난 모듈을 끕니다.

내가 고칠 수 있는 곳은 내 모듈 폴더 하나뿐입니다(지침서 2장).

그 밖 전부 — 코어 · 다른 동료의 모듈 · 설정 파일남의 것읽기만 합니다

화면 여러 개(모듈 하나에 8개까지), 파일 올리기, 표와 그래프, 내 데이터 저장.

아직 못 한다

코어의 계산 결과 · 시나리오 · 기준정보를 내 화면에서 읽기. 다음 단계에서 열립니다(지침서 10장).

2시작 전에 — 한 번만

이 안내서에서 내가 치는 명령(git · uv · New-Item · notepad 로 시작하는 줄)은 PowerShell 창에 한 줄씩 치고 Enter 를 누릅니다(Claude Code 대화 칸이 아닙니다). 클론(2-2)을 만든 뒤로는 늘 클론 폴더에서 엽니다 — 파일 탐색기에서 클론 폴더를 열고 위쪽 주소 칸에 powershell 을 치고 Enter 를 누르면 그 폴더에서 열립니다.

2-1앱 관리자에게 등록 승인을 받는다

새 모듈은 앱 관리자의 승인이 먼저입니다(지침서 3-7).

승인은 사람끼리 주고받는 일입니다

PowerShell 명령도, 에이전트에게 하는 말도 아닙니다. 아래 네 줄을 복사해 평소 쓰는 메신저나 메일로 앱 관리자에게 보내고 답장을 기다립니다. 앱 관리자가 누구인지 모르면 이 안내서를 건넨 사람에게 묻습니다.

이 안내서에서 앱 관리자에게 「보낸다」 · 「알린다」 · 「전한다」 는 모두 이 길입니다(7장의 패키지 요청 · 8-6 도 같습니다).

메신저 · 메일로 보낼 글 — 명령 아님
모듈 등록 요청
- id: demo_memo
- 이름: 데모 메모
- 담당 역할: 데모 담당
- 하는 일: 합성 메모를 적어 두고 종류별로 센다

id 짓는 법(지침서 3-2) — id 는 화면 주소 · 데이터 폴더 · 커밋 제목에 두루 쓰이므로 처음에 잘 정합니다.

  • 영문 소문자로 시작하고 소문자 · 숫자 · 밑줄(_)만 씁니다. 2 ~ 24자입니다. 밑줄 둘을 잇거나 밑줄로 끝내지 않습니다.
  • 실제 제품 · 고객 · 공정 · 설비 · 사람 이름을 넣지 않습니다. 점검이 걸러 주지 못합니다.
  • 담당 역할은 사람 이름 · 사번이 아니라 역할 이름입니다(module.json 의 owner — 지침서 3-3). 오류 카드 · 관리 화면에 그대로 보입니다.

앱 관리자가 「승인」 이라고 답하면 그 답을 받은 날짜를 적어 둡니다. 첫 커밋과 PR 본문에 승인: 앱 관리자 <YYYY-MM-DD> 로 들어갑니다 — 에이전트에게 「<날짜> 에 앱 관리자 승인 받았어」 라고 알려 주면 에이전트가 적습니다. 앱 관리자가 「시작해도 된다」 고 한 뒤에 시작합니다(첫 판에는 기다려야 하는 까닭이 있습니다 — 지침서 2장 「첫 배포 주의」).

2-2내 작업 자리(클론)를 만든다

클론은 저장소를 내 PC 에 통째로 받은 폴더입니다. 앱 관리자가 배포에 쓰는 폴더와 다른, 나만의 폴더입니다(지침서 8-1).

  • 저장소 README.md 「초기 설정」 의 0 ~ 4단계를 따릅니다. 5 · 6단계는 앱 관리자 몫이라 하지 않습니다(지침서 6장).
  • 1 ~ 3단계의 시험(pytest)은 오래 걸릴 수 있습니다. 끝줄에 failed 가 없으면 됩니다.
  • 저장소 주소와 접근 권한은 앱 관리자에게 받습니다. 혼자 하기 어렵다면 앱 관리자와 함께 합니다.

2-3에이전트 설정을 넣는다

내 클론에 에이전트가 지킬 울타리를 칩니다(지침서 8-4). 클론 폴더에서 PowerShell 로 칩니다.

PowerShell
New-Item -ItemType Directory .claude -Force
notepad .claude\settings.json

메모장이 새 파일을 만들지 물으면 「예」 를 누르고, 지침서 8-4 의 JSON 블록을 그대로 붙여 넣고, 그 안의 <id> 한 곳을 내 id 로 바꿔 저장합니다. 블록은 클론의 docs\module_guide.md 를 메모장으로 열어 「8-4」 를 찾으면 있습니다 — { 로 시작해 } 로 끝나는 칸 전체입니다.

  • .claude\ 폴더는 git 에 올라가지 않는 내 PC 만의 설정이라 내가 만듭니다 — 1장의 「설정 파일(읽기만)」 은 저장소의 설정을 말합니다.
  • 설정을 넣거나 바꾼 뒤에는 Claude Code 를 새로 엽니다. 열려 있던 대화에는 듣지 않습니다.
  • 이 설정은 에이전트가 내 폴더 밖을 고치거나 · 패키지를 깔거나 · 푸시하는 것을 막고, 그 밖의 일은 할 때마다 나에게 묻게 합니다.
  • 배포 적용용 템플릿(docs/internal_claude_settings.json)은 쓰지 않습니다. 그것은 앱 관리자의 에이전트용입니다.
기본 모드(묻는 모드)로 엽니다

Claude Code 를 auto · bypass(권한 건너뛰기) 모드로 열지 않습니다. 설정이 모든 길을 막지는 못하므로, 내가 승인 창을 읽는 것이 마지막 울타리입니다(6-2).

3에이전트에게 줄 첫 지시

클론 폴더에서 Claude Code 를 열고, 새 대화를 열 때마다 아래 블록을 그대로 붙여 넣습니다(지침서 0장과 같은 글입니다).

  • 블록 안의 <id> 를 모두 내 id 로 바꿉니다. 메모장에 먼저 붙여 「바꾸기」(Ctrl+H)로 한 번에 바꾸면 편합니다.
  • <주제> · <무엇> · <패키지> · <판> · <까닭> · <YYYY-MM-DD> · <이름> 은 그대로 둡니다. 에이전트가 그때그때 채웁니다.
  • 그 밖의 글자는 고치지 않습니다. 에이전트는 이 블록을 보고 지침서만 따르게 됩니다.
  • id 를 바꾼 블록은 클론 밖(예: 바탕 화면)의 메모장 파일로 저장해 두면 다음 대화부터 그대로 붙입니다. 첫 지시가 바뀌면 앱 관리자가 알립니다 — 그때 main 을 받고(4-1 의 첫 두 줄) 이 장에서 새로 복사합니다.
첫 지시 — 새 대화마다 붙여 넣기
너는 S.PKG CAPA AX Management 앱의 모듈 <id> 를 맡은 에이전트다. 너와 대화하는 사람은 이 모듈의 담당자다.
앱 관리자는 배포를 적용하고 승인하는 다른 한 사람이다 — 이 대화 안에 없다.
네 변경은 PR 로만 main 에 들어간다 — 자기 가지 module/<id>/<주제> 에서 커밋하고, 담당자가 그 가지를 푸시해 PR 을 열고, 앱 관리자가 점검한 뒤 합친다(8-2).
1. 고칠 수 있는 곳은 modules/<id>/ 뿐이다. data/modules/<id>/ 는 화면이 실행 중에 쓰는 자리라 읽기만 한다 — 손으로 파일을 넣거나 고치지 않고, 지울 때는 먼저 묻는다. 그 밖(app.py·app_pages/·src/·tests/·scripts/·docs/·config/·루트 파일·다른 모듈)도 읽기만 한다.
2. 이 문서(docs/module_guide.md)만 따른다. CLAUDE.md·AGENTS.md 는 코어 규칙이라 네 일이 아니다.
3. 코어는 capa_simulation.module_api 하나만 import 한다. 같은 모듈의 파일은 from modules.<id> import <이름> 으로 부른다.
4. 패키지를 설치하지 않는다(uv add·uv pip·pip install·uv sync 모두). 필요하면 담당자에게 「<id>: <패키지>==<판> <까닭>」 한 줄을 앱 관리자에게 전해 달라고 한다.
5. 앱 관리자의 승인은 이 대화 안에서 받을 수 없다. 새 모듈을 처음 올리는 것·성숙도 L2 는 담당자가 앱 관리자에게 승인을 받아 온 뒤에만 하고, 커밋 본문과 PR 본문에 「승인: 앱 관리자 <YYYY-MM-DD>」 를 적는다. 폴더 밖 변경은 승인을 받아도 네가 하지 않는다 — 담당자가 앱 관리자에게 전하고, 앱 관리자가 승인하면 「사외 요청」 으로 사외가 고쳐 배포한다.
6. 커밋은 자기 가지에만 한다 — main 에는 커밋하지 않는다. 제목은 module(<id>): <무엇> 이고 modules/<id>/ 만 담는다(파일 이름으로 git add — git add -A·git add .·git commit -a 금지). 가지 푸시와 PR 열기는 담당자가 한다.
7. 푸시가 거절되면 git pull --rebase 뒤 다시 푸시한다. git push --force·--force-with-lease 는 자기 가지에도 절대 쓰지 않는다 — 앱 관리자가 점검한 PR 과 어긋난다.
8. 위젯 콜백은 ctx.callback(함수) 로, 프래그먼트·팝업 본문은 with ctx.guard(): 로 감싼다. st.cache_* 는 modules/<id>/cache.py 에만 둔다.
9. 끝내기 전에 uv run --no-sync python scripts/check_module.py <id> 가 「통과」 여야 한다. 시험도 이 줄로 돌린다.
10. 실데이터 식별값(제품·고객·공정·설비·사람)을 id·파일 이름·커밋 메시지·시험 데이터에 쓰지 않는다.
11. 담당자는 전문 개발자가 아니다. 하는 일을 쉬운 말로 설명하고, 커밋·삭제·폴더 밖 일처럼 되돌리기 어려운 것은 먼저 묻고, 시험과 check_module.py 는 담당자에게 맡기지 말고 네가 돌려 결과를 보여 준다.

이 지시 덕분에 에이전트는 내 폴더 밖을 고치지 않고, 패키지를 깔지 않고, 커밋 전에 묻고, 점검을 스스로 돌려 결과를 쉬운 말로 알려 줍니다.

4하루 작업 흐름

한 가지 일(예: 「종류별 필터 더하기」)은 늘 같은 일곱 걸음입니다(지침서 8-2).

  1. 가지를 만든다나
  2. 말로 설명한다나
  3. 에이전트가 만들고 점검한다에이전트
  4. 앱에서 화면을 본다나
  5. 커밋한다에이전트 · 내가 허락
  6. 푸시하고 PR 을 연다나
  7. 점검하고 합친다앱 관리자

4-1가지를 만든다

가지는 main(모두가 함께 쓰는 줄기)을 건드리지 않고 고치는 「내 작업 칸」 입니다. 새 일을 시작할 때마다 하나 만듭니다.

PowerShell
git switch main
git pull --rebase
git switch -c module/<id>/<주제>
  • <주제> 는 영문 소문자 · 숫자 · - 로 짧게 짓습니다(예: module/demo_memo/kind-filter).
  • 하던 일의 가지가 이미 있으면 셋째 줄 대신 git switch module/<id>/<주제> 로 돌아갑니다.
  • 직접 쳐도 되고, 에이전트에게 「새 일을 시작할게. 가지부터 만들어 줘」 라고 해도 됩니다(승인 창이 뜹니다).
  • 처음 한 번은 이 가지에서 에이전트가 뼈대(모듈의 첫 파일 넷)를 만듭니다. 뼈대 줄이 승인 창에 뜨면 id 와 이름이 맞는지 보고 허락합니다(지침서 3-7).

4-2말로 설명한다

무엇을 원하는지 말합니다. 잘 말하는 요령은 5장입니다.

4-3에이전트가 만들고 점검한다

에이전트는 코드를 고친 뒤 점검 줄 check_module.py 를 스스로 돌립니다(지침서 7장). 점검은 규칙 · 코드 모양 · 시험을 한 번에 봅니다. 끝에 모듈마다 이런 줄이 나옵니다.

점검 결과 예
- m1 demo_memo 통과 · L0 · API 1.0 · 화면 1 · 오류 0 · 경고 0 · ruff ok · 시험 2 통과
  • 「통과」 여야 다음 걸음으로 갑니다. 「실패」 면 에이전트가 고칩니다(읽는 법은 8-2).
  • 경고는 「통과」 를 막지 않습니다. 오류만 막습니다.
  • 에이전트가 결과를 말하지 않으면 「점검 돌렸어? 결과 줄 보여 줘」 라고 묻습니다.

4-4앱에서 화면을 본다

점검이 통과해도 화면은 눈으로 봐야 합니다. 다른 PowerShell 창을 열어 클론 폴더에서 앱을 띄웁니다.

PowerShell — 앱 띄우기
uv run --no-sync python -m streamlit run app.py --server.port 8510
  • 브라우저에서 http://localhost:8510 을 엽니다. 처음에는 입장 화면이 뜹니다 — 준비가 끝나 켜지는 「Detail」 단추를 누르면 앱으로 들어갑니다. 사이드바 「모듈」 상자에서 내 화면을 고릅니다.
  • 「Port 8510 is not available」 이 나오면 다른 번호(8511 등)로 바꿔 칩니다. 끌 때는 그 창에서 Ctrl+C 입니다.
  • 모듈을 새로 넣었거나 module.json(이름 · 화면 목록)을 바꿨으면 앱을 껐다 다시 띄워야 보입니다. 그 밖에도 화면이 이상하면 다시 띄워 봅니다.
  • 이렇게 확인합니다 — 화면이 뜨는가, 단추와 입력이 되는가, 데이터가 하나도 없을 때도 빈 화면으로 서는가, 조건을 고른 뒤 다른 화면(코어 화면 하나 포함)에 갔다 와도 조건이 남는가.
  • 무엇을 눌러 볼지 모르겠으면 에이전트에게 「앱에서 무엇을 눌러 보면 돼?」 라고 묻습니다.

4-5커밋한다

커밋은 지금까지 고친 것을 이름표를 붙여 저장하는 일입니다. 에이전트가 「커밋해도 될까요?」 라고 묻고 승인 창이 뜹니다.

  • 지금 가지가 module/<id>/… 인지 봅니다 — 에이전트에게 「지금 어느 가지야?」 라고 묻습니다. main 이면 허락하지 않고 4-1 의 셋째 줄로 가지부터 만듭니다(고친 것은 그 가지로 따라옵니다).
  • 담긴 파일이 모두 modules/<내 id>/ 아래인지 봅니다. 다른 폴더가 섞여 있으면 허락하지 않습니다.
  • 제목은 module(<id>): <무엇> 꼴입니다(예: module(demo_memo): 종류별 필터).
  • 새 모듈의 첫 커밋과 성숙도 L2(9장)로 올리는 커밋은 본문에 승인: 앱 관리자 <YYYY-MM-DD> 가 들어갑니다. 승인받은 날짜를 에이전트에게 알려 줍니다.

4-6내가 푸시하고 PR 을 연다

푸시는 내 가지를 GitHub 의 저장소로 올리는 일입니다. 에이전트는 푸시를 못 하게 막혀 있어 내가 칩니다.

PowerShell
git push -u origin module/<id>/<주제>

그 가지를 두 번째부터 올릴 때는 git push 만 칩니다. 그다음 GitHub 화면에서 PR(합쳐 달라는 요청)을 엽니다 — 첫 푸시 결과에 찍힌 주소를 열거나, 저장소의 GitHub 화면 위쪽에 뜨는 「Compare & pull request」 단추를 누릅니다.

  • 받는 쪽(base)은 main, 보내는 쪽은 내 가지입니다.
  • 제목은 커밋과 같은 꼴 module(<id>): <무엇> 입니다.
  • 본문은 에이전트에게 「PR 본문 만들어 줘」 라고 해서 받습니다 — 무엇을 바꿨는지 한두 줄, 점검 줄, (필요하면) 승인 줄이 들어갑니다.
  • 연 뒤 앱 관리자에게 PR 번호를 알리면 빠릅니다.
PR 은 「합쳐 달라는 요청서」 입니다

여는 것만으로는 main 이 바뀌지 않습니다 — 앱 관리자가 합칠 때 비로소 main 에 들어갑니다.

  • PR 화면에는 탭이 셋 있습니다 — 「Conversation」(본문과 주고받은 글), 「Commits」(이 가지의 커밋), 「Files changed」(바뀐 줄을 고치기 전 · 뒤로 나란히). 앱 관리자는 「Files changed」 로 바뀐 파일을 보고, 고칠 것은 「Conversation」 에 글로 남깁니다.
  • PR 은 내 가지를 가리킵니다. 같은 가지에 커밋을 더 푸시하면 PR 도 저절로 그 커밋까지 늘어납니다 — 그래서 고칠 때 새 PR 을 열지 않습니다.
  • 합쳐지면 PR 은 「Merged」 로 닫히고, 내 가지의 커밋들이 main 에 커밋 하나로 들어갑니다(Squash and merge). 합치지 않고 닫히면(「Closed」) main 은 그대로입니다 — 까닭이 PR 에 적혀 있으니 읽고 앱 관리자에게 묻습니다.

4-7앱 관리자가 점검하고 합친다

앱 관리자는 PR 이 내 폴더만 바꿨는지, 새 모듈이면 승인했는지 보고, PR 을 따로 떠서 점검을 다시 돌린 뒤 합칩니다(지침서 8-2 의 6).

  • 고칠 것이 PR 에 적혀 오면 같은 가지에서 고쳐 커밋하고 git push 만 다시 칩니다. PR 이 따라오므로 새 PR 을 열지 않습니다.
  • PR 을 연 뒤 더 올렸으면 앱 관리자에게 알립니다. 앱 관리자는 점검한 그대로만 합치므로 처음부터 다시 봅니다.
  • 「가지를 main 에 맞춰 달라」 고 하면 PR 화면의 「Update branch」 단추를 누르고, 내 PC 에서는 git pull --rebase 로 받습니다.
  • 합쳐진 뒤 다음 일은 4-1 부터 다시 합니다. 다 쓴 가지는 그대로 둬도 됩니다.

4-8언제 앱에 보이나

합쳐졌다고 곧바로 모든 사람에게 보이지는 않습니다.

어디언제 보이나
내 PC 에서 띄운 앱바로 — 지금 내 가지에 있는 그대로 보입니다
앱 관리자가 띄우는 앱PR 이 합쳐진 뒤 앱 관리자가 그 변경을 받아 점검을 한 번 더 돌리고 앱을 다시 띄울 때
배포 서버그 점검을 본 뒤 앱 관리자가 CI/CD 단추로 서버를 다시 만들 때

앱 관리자는 합친 모듈을 다음 배포 때 함께 올리거나, 그 전에 따로 올립니다(앱 관리자의 절차서 docs/internal_update_runbook.md 의 4-7). 언제 오르는지는 앱 관리자가 정하므로 앱 관리자에게 묻습니다. CI/CD 단추는 앱 관리자만 누릅니다 — 나는 누르지 않습니다.

  • 앱 관리자의 앱은 쓰는 사람이 없을 때만 다시 띄웁니다. 그래서 합쳐진 뒤 바로 보이지 않을 수 있습니다.
  • 모듈 변경만으로 배포 서버를 다시 만들 때는 앱 관리자가 먼저 알려 줍니다 — 「배포 서버의 모듈 데이터가 사라질 수 있다」 고요. 그 알림을 받으면 남겨야 할 자료를 챙기고(내려받기 등) 앱 관리자에게 챙겼다고 답합니다. 앱 관리자는 그 답을 받은 뒤 단추를 누릅니다.

5에이전트에게 말하는 요령

그림처럼 설명합니다. 화면의 위 · 아래 · 왼쪽 · 오른쪽에 무엇이 있는지 말합니다.

예
화면 맨 위에 조건 상자를 두고, 그 안에 「종류」 고르기와 「기간」 고르기를 넣어 줘.
그 아래 왼쪽에는 표(날짜 · 종류 · 수량), 오른쪽에는 종류별 수량 막대그래프를 그려 줘.

예시 데이터를 줍니다. 값은 지어낸 것으로 줍니다. 예시는 그대로 시험 데이터가 되어 저장소에 남습니다.

예
올릴 CSV 는 이런 모양이야(값은 지어낸 것):
날짜,종류,수량
2026-01-05,DEMO-A,12
2026-01-06,DEMO-B,7

한 번에 하나만 부탁합니다. 「표만 먼저. 그래프는 표가 되고 나서」 처럼 나눕니다. 한 걸음마다 앱에서 확인하면 어디서 틀렸는지 쉽게 찾습니다.

고치기 전에 계획을 묻습니다. 「고치기 전에 무엇을 어떻게 바꿀지 먼저 말해 줘」 라고 하면, 엉뚱한 방향을 일찍 잡을 수 있습니다.

끝나면 확인 질문을 합니다.

확인 질문
방금 무엇을 바꿨어? 어느 파일이야?
점검은 통과했어? 결과 줄 보여 줘.
앱에서 무엇을 눌러 보면 돼?

오류와 점검 결과는 그대로 붙여 넣습니다. 내 말로 옮기지 말고 화면의 글을 복사해 「이런 카드가 떴어: (붙여 넣기)」 라고 합니다.

이미 만든 독립 Streamlit 앱이 있으면 처음부터 다시 만들지 않고 옮깁니다(지침서 3-9). 사이드바 · 앱 꾸밈 · 큰 제목은 앱이 쓰므로 모듈 화면은 본문만 씁니다 — 그 고침은 에이전트가 합니다.

독립 앱 옮기기
내가 따로 만든 Streamlit 앱이 <폴더 위치> 에 있어. 지침서 3-9 차례대로 내 모듈로 옮겨 줘. 한 단계씩 하고 매번 알려 줘.

옛 앱 폴더는 클론 밖에 그대로 둡니다. 옛 앱이 쓰던 데이터 파일(실데이터)은 모듈 폴더로 옮기지 않습니다 — 옮긴 화면에서 올려 씁니다. 시험에 쓸 표본은 지어낸 값으로 새로 만듭니다(6-1).

자주 쓰는 부탁 — 복사해 쓰세요.

자주 쓰는 부탁
조건(종류 · 기간)이 다른 화면에 갔다 와도 남게 해 줘.
무거운 계산은 단추를 눌렀을 때만 돌게 해 줘.
입력한 것을 저장하는 단추를 두고, 저장 전에 화면을 옮기면 사라진다는 것을 그 단추 풍선에 적어 줘.
데이터 파일이 하나도 없을 때도 화면이 빈 상태로 서게 해 줘.
그건 하지 말고, 앱 관리자에게 보낼 한 줄로 정리해 줘.

마지막 줄은 에이전트가 내 폴더 밖을 고쳐야 한다고 할 때 씁니다(6장).

6하면 안 되는 것

6-1하지 않는 것과 까닭

하지 않는 것까닭대신
내 모듈 폴더 밖(코어 · 다른 동료의 모듈 · 설정 파일) 고치기코어는 다음 배포가 덮어씁니다. 다른 모듈은 그 담당자 몫입니다. 앱 관리자는 폴더 밖을 바꾼 PR 을 합치지 않습니다앱 관리자에게 한 줄로 전합니다(8-6)
data/modules/<id>/ 에 손으로 파일 넣기그 파일은 내 PC 에만 있습니다. 앱 관리자의 앱 · 배포 서버에는 없습니다화면에서 올리거나 저장해서 만듭니다. 작은 합성 표본은 modules/<id>/assets/(1 MB 아래)
패키지 마음대로 설치(pip install · uv add · uv pip)내 PC 에서만 돌고 배포 서버에서는 그 화면이 오류가 납니다7장의 요청
main 에 바로 커밋 · 푸시앱 관리자가 점검하지 않은 변경이 모두의 앱에 들어갑니다. 막혀 있지 않더라도 하지 않습니다가지 → PR(4장)
git push --force앱 관리자가 점검한 PR 과 어긋납니다거절되면 git pull --rebase 뒤 다시 git push
실제 제품 · 고객 · 공정 · 설비 · 사람 이름을 id · 파일 이름 · 커밋 · 시험 데이터 · 예시에 쓰기저장소와 기록에 남습니다지어낸 값(DEMO-A 등)
Claude Code 를 auto · bypass 모드로 열기승인 창이 마지막 울타리입니다기본 모드
모듈 시험을 pytest 로 따로 돌리기보호 장치가 걸리지 않아 내 진짜 데이터 폴더에 씁니다점검 줄 하나(check_module.py)가 시험까지 돌립니다
CI/CD 단추 누르기점검을 본 뒤에 앱 관리자만 누릅니다앱 관리자에게 부탁
모듈 데이터는 백업되지 않습니다

잃어도 되는 것만 둡니다. 배포 서버에서는 서버를 다시 만들 때(CI/CD)마다 사라집니다 — 앱의 DB 동기화가 켜진 뒤에도 모듈 데이터는 그 밖입니다(지침서 2장 「데이터」).

남겨야 하는 파일은 에이전트에게 「저장할 때 S3 에 올리고 화면이 처음 설 때 받게 해 줘」 라고 하면 앱의 도우미로 그렇게 만듭니다 — 배포 서버에서 앱 관리자가 DB 동기화를 켠 뒤에만 되고 파일 하나는 8 MiB 까지입니다(지침서 3-10).

내 화면은 다른 사람과 한 서버를 함께 씁니다

오래 걸리는 계산은 모두의 앱을 느리게 합니다. 무거운 계산은 단추를 눌렀을 때만 돌게 합니다(지침서 4장).

6-2승인 창 읽기

에이전트가 파일을 쓰거나 명령을 치려 하면 승인 창이 뜹니다. 읽고 나서 허락합니다.

대개 허락해도 되는 것
  • modules/<내 id>/ 안의 파일 쓰기
  • check_module.py <내 id> · ruff · git switch
  • git add modules/<내 id>…
  • 제목이 module(<내 id>): … 인 git commit
  • 처음 한 번의 뼈대 줄(new_module.py — id · 이름 확인)
거절할 것
  • 경로가 modules/<내 id>/ 밖인 쓰기 · 지우기
  • data/modules/ 에 파일 쓰기
  • 패키지 설치(pip · uv add · uv pip · uv sync — 7장의 uv sync --inexact 는 내가 내 창에서 칩니다)
  • git push --force · git reset · git clean
  • rm · Remove-Item · git add -A · git add .
모르겠으면

거절하고 「이 명령이 무엇을 하는지 쉬운 말로 설명해 줘」 라고 묻습니다. 설명을 듣고 다시 부탁하면 됩니다.

7새 패키지가 필요할 때

패키지는 남이 만든 기능 묶음입니다(예: 엑셀 읽기). 앱과 배포 서버에 깔린 것만 쓸 수 있습니다(지침서 6장).

바로 써도 된다

파이썬 기본 기능, streamlit, 앱이 직접 쓰는 패키지(pandas · numpy · plotly · altair · duckdb · pydantic 등). 에이전트가 압니다.

경고만 난다

pyarrow · pillow(PIL)처럼 다른 패키지를 따라 들어온 것. 점검은 통과하지만 언젠가 빠질 수 있습니다. 오래 쓸 거면 요청합니다.

bigdataquery — 조회는 앱의 도우미로 합니다(지침서 3-10) — 요청자 계정 · 토큰을 앱이 채워 배포 서버에서도 돕니다. 패키지를 직접 써도 점검은 경고뿐이지만 배포 서버에서 계정을 넘길 길이 없습니다. 계정 · 토큰 · S3 키를 코드에서 읽으면 점검 오류(M21)입니다 — 이미 그렇게 쓰던 모듈은 8-2 끝을 봅니다.

그 밖 — 요청

에이전트가 아래 꼴의 한 줄을 만들어 주면 앱 관리자에게 보냅니다. 꼴은 <id>: <패키지>==<판> <까닭 한 마디> 입니다.

요청 한 줄 예
demo_memo: openpyxl==3.1.5 엑셀 올리기

그 뒤 차례는 이렇습니다.

  1. 앱 관리자가 그 줄을 코어 쪽 요청(에이전트는 「사외 요청」 이라고 부릅니다)으로 넘깁니다.
  2. 코어 쪽이 앱의 패키지 목록에 넣어 배포합니다. 다음 배포까지 기다려야 합니다.
  3. 그 배포가 main 에 들어온 뒤 씁니다. 패키지 목록(pyproject.toml · uv.lock)이 바뀌었으면 main 을 받은 뒤(4-1 의 첫 두 줄) 내 클론에서 내가 칩니다.
PowerShell
uv sync --inexact
--inexact 를 빼지 않습니다

빼면 회사 전용 패키지(bigdataquery)가 지워집니다. 지워졌으면 README.md 「초기 설정」 4단계를 다시 합니다.

8문제가 생겼을 때

8-1화면에 오류 카드가 떴다

모듈 화면에서 오류가 나면 그 화면 자리에만 오류 카드가 섭니다. 사이드바와 다른 화면은 그대로 씁니다(지침서 9-1).

  • 카드에는 모듈 이름 · 화면 이름 · 오류 종류 · 메시지 첫 줄 · 멈춘 범위 · 담당 · 오류 위치가 적혀 있습니다. 끄는 법은 「이 화면만 멈춤」 줄에 마우스를 올리면 뜹니다.
  • 카드의 글을 그대로 복사해 에이전트에게 붙여 넣고 「이 카드가 떴어. 무엇이 잘못됐고 어떻게 고칠지 알려 줘」 라고 합니다.
  • 단추를 누른 뒤 「방금 한 동작에서 오류가 났습니다」 카드가 뜨면, 무엇을 눌렀는지도 함께 적습니다.
  • 카드가 「패키지가 없다」 고 하면 7장입니다.

8-2점검이 「실패」 다

점검 결과의 자세히 아래 줄이 고칠 곳입니다.

예
m1 demo_draft 오류 M19 page.py:19 `use_container_width=` 는 Streamlit 이 곧 지웁니다 — width="stretch" 또는 width="content" 로 바꿉니다

읽는 법 — 차례 번호(m1) · 모듈 id · 오류/경고 · 규칙 번호(M19) · 파일과 줄(page.py 19번째 줄) · 고칠 말. 에이전트가 이 줄을 보고 고칩니다. 「시험 안 돎 — 정적 오류 먼저」 가 보이면 다른 오류를 먼저 고쳐야 시험이 돕니다. 규칙 번호의 뜻은 지침서 부록 B 에 있습니다.

M21(자격 · 비밀)로 실패하면 — 내 모듈이 BigDataQuery 계정 · 토큰을 코드에서 직접 읽던 꼴입니다. 이제는 앱의 도우미로만 조회합니다. 앱 관리자가 「새 판(창구 1.3)을 적용했다」 고 알린 뒤 새 가지(4-1)에서 에이전트에게 「지침서 3-11 대로 BigDataQuery 조회를 앱 도우미로 옮겨 줘」 라고 말합니다. 그 전에는 옮길 수 없습니다 — 옛 판에는 도우미가 없습니다. 고친 뒤에는 평소처럼 커밋 · PR 입니다(4-5 · 4-6). 고침이 합쳐져 앱 관리자가 다시 켤 때까지 내 화면은 모두가 쓰는 앱에서 꺼져 있을 수 있습니다.

8-3내 PC 에서는 되는데 앱 관리자의 앱에서는 안 된다

흔한 까닭은 다섯입니다.

  • 데이터 폴더에 손으로 넣은 파일을 화면이 읽는다 — 그 파일은 내 PC 에만 있습니다(6-1).
  • 내 PC 에만 깐 패키지를 쓴다(7장).
  • 파일 이름에 대문자가 있다 — Windows 는 대소문자를 가리지 않지만 배포 서버는 가립니다(지침서 3-2).
  • 모듈을 넣거나 module.json 을 바꾼 뒤 앱을 다시 띄우지 않았다.
  • PR 이 아직 합쳐지지 않았거나, 앱 관리자가 아직 받지 않았다(4-8).

8-4모두가 쓰는 앱에서 내 모듈이 깨졌다

모듈을 숨기는 스위치는 둘입니다(지침서 9-2). 둘 다 앱을 다시 띄운 뒤부터 듣습니다.

  1. 급할 때 — 앱 관리자가 실행 환경변수로 바로 끕니다. 앱 관리자만 할 수 있습니다.
  2. 내가 하는 길 — module.json 의 "enabled": true 를 false 로 바꿔 PR 로 올립니다. 합쳐진 뒤 앱 관리자가 받아 앱을 다시 띄우면 꺼집니다(4-8). 그때까지 급하면 1 을 부탁합니다.

꺼진 모듈은 사이드바에서 사라지고 주소로도 열리지 않습니다. 고친 뒤 다시 true 로 올립니다.

8-5Admin 「모듈 상태」 — 앱 관리자에게 물어볼 것

앱 관리자는 Admin Area 안쪽 탭 줄 오른쪽 끝 「모듈 상태」 팝오버에서 모든 모듈을 봅니다(지침서 9-3). 운영 앱에서 무슨 일이 났는지 모를 때 「제 모듈 상태 칸을 알려 주세요」 라고 부탁합니다.

  • 상태(켜짐 · 꺼짐 · 실패)와 그 까닭 — 「실패 · 화면 이름 겹침」 같은 글이 여기 있습니다.
  • 마지막 오류(시각 · 종류 · 화면 본문인지 단추 동작인지).
  • 마지막 회차 시간(ms) — 화면 한 번 그리는 데 걸린 시간. 크면 내 화면이 모두를 느리게 하고 있다는 뜻입니다.

8-6누구에게 무엇을 보내나

오류 카드 · 점검 「실패」먼저 내 에이전트카드 글 · 점검 줄을 그대로
내 폴더 밖을 고쳐야 한다(코어 · 설정)앱 관리자에이전트가 정리한 한 줄 — 무엇이 왜 필요한지

9용어 풀이

코어
앱의 원래 화면과 계산 전부. 앱 관리자 쪽 몫이고, 배포가 통째로 덮어씁니다
모듈
동료가 만든 화면 묶음. 폴더 modules/<id>/ 하나가 모듈 하나입니다
id
모듈의 영문 이름표(예: demo_memo). 주소 · 데이터 폴더 · 커밋 제목에 쓰입니다
module.json
모듈의 이름 · 담당 역할 · 화면 목록 · 켜짐/꺼짐 · 성숙도를 적은 선언 파일(지침서 3-3)
지침서
docs/module_guide.md. 내 에이전트가 따르는 규칙서
에이전트
Claude Code. 대화로 코드를 쓰고 명령을 쳐 주는 도우미
승인 창
에이전트가 파일을 쓰거나 명령을 치기 전에 나에게 허락을 묻는 창
저장소 · 클론
저장소는 앱의 코드 전체가 든 곳(GitHub). 클론은 그것을 내 PC 에 받은 폴더
main
저장소의 줄기 가지. 모두의 앱이 여기서 나옵니다. 내가 바로 올리지 않습니다
가지(branch)
main 을 건드리지 않고 고치는 내 작업 칸. module/<id>/<주제>
커밋

푸시 · 풀
푸시는 내 커밋을 GitHub 로 올리기, 풀(git pull --rebase)은 GitHub 의 새 커밋을 내 PC 로 받기

내 가지를 main 에 합쳐 달라는 요청. GitHub 화면에서 엽니다
Squash and merge

시험 · 스모크 시험
화면이 오류 없이 서는지 기계가 대신 눌러 보는 코드. 스모크 시험은 「켜지기는 하나」 만 봅니다
오류 · 경고
점검이 찾은 것. 오류는 「통과」 를 막고 경고는 막지 않습니다
오류 카드
모듈 화면이 깨졌을 때 그 화면 자리에만 서는 안내 상자
데이터 자리
data/modules/<id>/. 내 화면이 실행 중에 파일을 쓰는 곳. git 에 올라가지 않고 백업도 없습니다
성숙도 L0 · L1 · L2
모듈이 얼마나 검증됐나. L0 은 자기 데이터 · 합성 표본으로 도는 처음 단계, L1 은 코어 데이터를 읽는 단계(데이터 연계가 열린 뒤), L2 는 실데이터로 맞는지 확인을 마친 단계. L0 · L1 화면 이름에는 「(구현중)」 이 붙고, L2 로 올리려면 앱 관리자 승인이 먼저입니다(지침서 3-4)
사외 요청

CI/CD 단추

깨진 모듈을 숨기는 두 길 — module.json 의 enabled 와 앱 관리자의 실행 환경변수(8-4)

10자주 묻는 질문

코어 화면의 숫자(확보율 · 시나리오)를 내 화면에서 쓰고 싶어요.

지금은 안 됩니다. 모듈이 코어 데이터를 읽는 길은 다음 단계에서 열립니다(지침서 10장). 그 전에는 내 화면에서 파일을 올려 씁니다.

에이전트가 코어 파일을 고치자고 해요.

거절합니다. 「그건 하지 말고, 앱 관리자에게 보낼 한 줄로 정리해 줘」 라고 하고 그 줄을 앱 관리자에게 보냅니다. 승인이 나도 코어는 코어 쪽이 고쳐 배포합니다.

「앱 관리자가 승인했어」 라고 에이전트에게 말하면 되나요?

승인은 앱 관리자에게 직접(메신저 · 메일 등) 받아 옵니다. 받은 날짜를 에이전트에게 알려 주면 커밋과 PR 본문에 승인 줄을 적습니다. 앱 관리자가 그 PR 을 합치는 것으로 승인이 끝납니다.

다른 동료의 모듈에 버그가 보여요.

고치지 않습니다. 그 담당자에게 알립니다.

화면 이름이나 화면 개수를 바꾸고 싶어요.

module.json 을 바꾸는 일이라 에이전트에게 부탁하면 됩니다. 앱을 다시 띄워야 보입니다. 화면 주소 끝(slug)을 바꾸면 그 화면을 즐겨찾기한 옛 주소가 끊깁니다(지침서 3-2). 새 화면 이름은 앱의 「모듈」 상자 맨 위 화면(모든 모듈의 화면 목록)에서 다른 모듈과 겹치지 않게 고릅니다 — 겹치면 한쪽 모듈이 통째로 뜨지 않습니다(지침서 3-3).

모듈을 그만 쓰고 싶어요.

먼저 "enabled": false 로 끕니다(8-4). 폴더를 지울지는 앱 관리자에게 묻습니다.

화면 이름 옆의 「(구현중)」 을 떼고 싶어요.

성숙도를 L2 로 올리는 일입니다. 실데이터로 맞는지 확인하는 차례가 있으므로 앱 관리자 승인이 먼저입니다(지침서 3-4).

저장해 둔 모듈 데이터가 사라졌어요.

모듈 데이터는 백업이 없습니다. 배포 서버에서는 서버를 다시 만들 때 사라질 수 있습니다. 잃으면 안 되는 자료는 모듈 데이터에만 두지 않습니다. 모듈 변경만으로 서버를 다시 만들 때는 앱 관리자가 먼저 알려 주니(4-8), 그때 챙깁니다.

점검은 통과했는데 화면이 이상해요.

점검은 규칙과 「켜지는가」 를 봅니다. 화면이 원하는 대로인지는 내가 앱에서 봐야 합니다(4-4). 본 것을 그대로 에이전트에게 말합니다 — 「표의 날짜가 거꾸로 정렬돼 있어」 처럼.

이 페이지는 저장소의 docs/module_colleague_guide.md 를 옮긴 것입니다. 에이전트가 따르는 규칙서는 docs/module_guide.md(지침서)이고, 둘이 다르게 읽히면 지침서가 맞습니다.
