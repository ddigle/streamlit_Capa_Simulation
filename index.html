발표자 노트

왜 만들었나

Capa Data 는 세 곳에 나뉘어 있다

같은 Capa 를 보는데 출처가 셋이고, 셋 다 제조 실무자가 바로 쓸 수 없다.

  • 제조팀의 Capa 업무 데이터는 엑셀로 산출·관리되고 EDM 에 올라간다.
  • 자원운영그룹의 Static Capa 는 CAMP 에서 관리된다 — 시스템은 있지만 일반 사용자 접근성이 떨어진다.
  • EDM 에 있어도 어떤 파일을 열어야 하는지 아는 사람만 안다.로컬 파일과 다르지 않다.
  • 그래서 생산·진도 담당자에게 Capa Data 가 닿지 않고, 제조 실무자들이 같은 눈높이로 일하기 어렵다.

EDM엑셀 Capa Data 보관어떤 파일인지 아는 사람만

생산 · 진도 담당자제조 실무자같은 눈높이로 볼 Capa 가 없다
발표자 노트

청중이 자기 경험으로 알아듣는 장이다. 시스템 이름을 설명하지 말고 '아는 사람만 안다' 에 멈춰라. 도식의 세 장벽이 서로 다른 이유라는 점을 짚는다.

왜 만들었나

확장성이 여기서 막힌다

엑셀은 늘릴 수 없고, CAMP DB 는 제조가 원하는 형태로 꺼내 쓸 수 없다.

  • 제조 데이터는 엑셀 기반이라 확장성이 떨어진다.
  • 투자·Static Capa 는 CAMP DB 에 있어 제조 입장에서 원하는 형태로 서비스하기 어렵다.
  • 생산실적·설비효율·신규설비 일정 같은 제조 실무 데이터와 Capa 를 결합해야 열리는 일이 있다 — 설비 생산성 관리, 재공 관리, 재공 기준 단기구간 목표 관리.
  • 두 축이 갈려 있어 이런 업무 서비스 개발을 시작조차 못 했다.

왜 만들었나

AI 도 이 데이터를 쓸 수 없다

업무에 AI 를 넣으려면 먼저 AI 가 읽을 수 있는 규격으로 데이터가 통합되어 있어야 한다.지금 Capa Data 는 그 반대다.

  • 엑셀 파일·EDM 폴더·CAMP 화면에 갇힌 데이터에는 어떤 AI 도 붙일 수 없다.키도, 규격도, 출처도 없다.
  • 그 데이터를 사람이 손으로 표준화·통합하는 것은 기존 업무 방식으로는 불가능하거나 자원이 매우 많이 든다.
  • 그래서 AI 로 그 기반을 만들었다.이 프로젝트의 정체는 Capa 계산 도구가 아니라 AX(AI Transformation)의 첫 발판이다 — AI 가 쓸 수 있는 업무 데이터를, AI 와 함께.

AI 와 함께 45일에 만들었다

초석 — 표준 Capa

기존 시뮬레이션이 오래 걸린 이유

CAMP 에 검토 데이터는 있지만 손댈 수가 없어, 결국 엑셀로 다시 산출해야 했다.

  • CAMP 에 시뮬레이션 검토 데이터가 정리되어 있지만, 커스터마이징하거나 필요한 기준정보만 골라 뽑기 어렵다.
  • 그래서 실질적으로는 엑셀 기반 수작업 산출이었다.
  • 숙련된 인원도 새 시나리오를 받아 LOB 자료화하고 검증까지 마치는 데 약 2일이 걸렸다.

'약 2일' 은 측정치가 아니라 숙련자 경험 기준이다. '수 분' 도 측정치가 아니라 사내에서 기간→목록→등록을 실제로 돌려 본 체감이고, 그 시간의 대부분은 원천 조회다. 앱 안의 기준정보 16종 적재는 1초 안(개발 PC 0.86초). 줄어든 것은 가운데 세 칸 — 엑셀로 옮기기, 기준정보 손 정리, 검증 — 이고 검증은 대조 도구가 대신한다. 정확한 공수 측정은 시범 적용에서 한다.

초석 — 표준 Capa

지금은 케이스를 고르면 끝난다

조회기간을 넣으면 시뮬레이션 케이스가 목록으로 뜨고, 한 줄을 고르면 기준정보 16종이 자동 등록된다.

  • SQL 을 쓰거나 CAMP 화면을 여는 과정이 사라졌다.
  • 원천 데이터는 컬럼 계약 검증을 거쳐 기준정보 16종으로 나뉘어 적재된다 — 계약을 어기면 변환이 아니라 위반으로 멈춘다.같은 업무 키에 값이 갈리면 충돌 목록 CSV 를 내주고 사람이 판정한다.
  • 계산은 부하량 → 대당 Capa → 소요대수 → 확보율 → B/N(병목) 으로 한 줄기로 흐른다.
  • 사내 원천에서 케이스 목록 조회와 상세 조회(약 3만 행) 모두 정상 동작을 확인했다.

발표자 노트

'멈추면 누가 고치나' — 위반 메시지가 어느 컬럼·어느 규칙인지 적는다. 원천 컬럼명이 바뀐 것이면 어댑터의 매핑 한 줄을 고치는 개발 쪽 일이고, 값이 계약을 어긴 것(같은 키에 다른 값)이면 충돌 목록 CSV 를 들고 CAMP 쪽에 정정을 묻는 업무 쪽 일이다. 앱이 값을 임의로 고쳐 넣는 경우는 없다. 이 그림을 4막에서 다시 쓴다.

초석 — 표준 Capa

같은 리비전이면 같은 결과

등록된 기준정보는 시나리오·리비전·공식버전으로 불변 보존된다.이 시나리오가 곧 표준 Capa 의 기준이다.

  • 시나리오 하나 = 원천과 기준정보를 그 시나리오 소유로 복제한 독립 데이터셋.새로 만들어도 기존 것을 덮지 않는다.
  • 저장할 때마다 과거 상태가 그대로 남는다.과거 리비전은 고치지 않는다.
  • 특정 리비전을 공식버전으로 발행하면 새로 접속한 사람은 항상 그것을 본다.
  • 이후 제조 실무 데이터는 활성 시나리오 위에서 결합되어 동작한다.이 구조가 AI 가 근거를 댈 수 있는 이유다 — 어떤 답이든 「어느 리비전의 어느 행」으로 되돌아간다.
r1→ r2→ r3 공식버전
└r4 r2 에서 갈라진 분기 — 과거 리비전은 고치지 않는다

리비전 하나 = 편집 대상 기준정보 14표 전체 스냅샷 + 조회기간·판정 기준 프리셋

발표자 노트

'표준 = 활성 시나리오' 가 핵심 개념이다. 결과를 테이블로 따로 저장하지 않는 이유 — 같은 리비전이면 언제든 같은 결과가 재현된다. '누가 언제' 중 '언제' 는 시각으로 남고 '누가' 는 지금 기록하지 않는다(사용자 식별 없음). 공용 서버·사번 권한이 열리면 함께 넣는다. 용량은 리비전이 전체 스냅샷이라 저장마다 늘지만 사내 실측 62.6 MiB 수준이고 중복 저장분 정리가 계획에 있다.

초석 — 표준 Capa

CAMP 와 같은 답을 낸다

CAMP 의 Capa 산출 로직을 그대로 구현했다.소요대수까지 기존 결과와 대조해 전량 일치를 확인했다.

  • 부하량 지표(Wafer 매수·Density)는 대조 스크립트로, 최종 소요대수는 앱이 내보낸 CSV 와 CAMP 결과를 사내에서 직접 대조했다.
  • 대조 중 나온 차이는 한 가지였다 — Pack Code 가 다른 계획 행이 등록 시 하나로 접히던 것.업무 키 승격으로 고쳤고 사내에서 다시 대조해 전량 일치했다.
  • 기준정보가 없거나 범위를 벗어난 행은 조용히 넘기지 않는다 — 제외 목록으로 보여주고 CSV 로 받을 수 있다.

Pack Code 를 숨기지 않고 말한다 — 차이를 찾아 원인을 규명하고 고친 뒤 다시 대조한 것이 검증이 실제로 돌았다는 증거다. ① 원인: Pack Code 만 다른 계획 행이 등록 시 첫 행만 남는 임시 정책으로 접혀 뒤 행의 생산수량이 빠졌다. ② 조치: 업무 키 승격으로 고쳤고 사내 재대조에서 전량 일치했다. 0013 이전에 저장한 옛 리비전은 재등록이 필요하다. ③ 범위: 확보율·B/N 은 소요대수와 가용대수의 비율이라 소요대수가 맞으면 따라온다.

내 화면에서 즉시, 팀에는 발행으로

편집은 내 브라우저 세션에만 산다.팀이 함께 볼 값만 리비전으로 저장하고 공식버전으로 발행한다.

  • UPEH·효율·여유율·측정률·일수·PKG PLAN·수율·설비대수를 화면에서 편집하면 내 결과에 즉시 반영된다.
  • 다른 사람의 결과는 건드리지 않는다 — what-if 를 마음껏 돌릴 수 있다.
  • 팀이 함께 볼 값은 리비전으로 저장하고 공식버전으로 발행한다.자동 저장은 없다.
세션 편집내 화면

  • 다른 사람에게 보이지 않음

AI 가 붙으면「12H 계획 10% 올려봐」를 편집안으로 바꿔 변경 전후 미리보기까지 — 적용 버튼은 사람이 누른다. 「확보율 100% 넘기려면 어느 공정에 몇 대」는 코드가 레버 조합을 반복 계산하고 AI 는 비교 문장만 쓴다.
발표자 노트

'옆자리가 보나' — 아니오, 발행해야 본다. 불편이 아니라 안심 재료다. '누가 발행할 수 있나' — 지금은 접속한 사람 누구나, 발행자 이름은 기록되지 않는다(시각만). 그래서 사번 권한을 요청한다. '잘못 발행하면' — 공식버전은 덧붙이기만 하므로 이전 리비전을 다시 발행해 되돌린다. '둘이 동시에 저장하면' — 한 서버 안에서는 잠금으로 줄을 서서 안전하지만 개인 PC 실행본이 여럿이면 각자의 DB 라 합쳐지지 않는다. 그래서 공용 서버가 다중 사용자의 전제다.

엑셀을 버리지 않는다

양식을 내려받아 익숙한 엑셀에서 값을 고치고 표를 그대로 붙여넣으면 즉시 반영된다.

  • 계산과 이력 관리만 웹이 맡는다.값을 고치는 자리는 그대로 엑셀이다.
  • 데이터 표를 파일로 올리는 경로가 없으므로 문서보안 환경에서 파일 바이트가 변형될 여지가 없다.양식은 내려받기만 한다.
  • 기준정보·표시순서·설비 호기 마스터·비가동 일정까지 같은 방식으로 통일했다.
앱: CSV 양식 내려받기→Excel: 값만 수정→표 전체 복사→앱: 붙여넣기 · 미리보기 · 적용
✕ 데이터 표의 파일 업로드 — 문서보안 환경에서 파일 바이트가 변형될 수 있어 데이터 입력 경로에는 두지 않았다. 층 배치 도면 이미지 하나만 예외다
발표자 노트

'엑셀 버리라는 얘기' 로 들리는 순간 실무자 저항이 시작된다. '파일 업로드를 두지 않았다' 는 데이터 표에 대한 말이고, Space 의 층 배경 도면 이미지만 업로드로 받는다 — 계산에 들어가는 값이 아니라 그림이라 왕복 무결성 문제가 없다. 붙여넣기 행 수 상한은 없고 사내 규모의 붙여넣기 시간은 시범 적용 때 측정한다.

03

실행 Capa

발표자 노트

실행 Capa — 설비 운영 현황을 이력으로 쌓고 라인 위에 올린다. 화면은 합성 샘플이다.

실행 Capa

설비 운영 현황을 이력으로 쌓는다

가용·비가동 설비 현황과 호기 생애주기 일정을 한 도구로 모았다.저장할 때마다 그 시점이 리비전으로 남는다.

  • 호기 마스터 31컬럼을 양식에 붙여넣어 등록한다 — 공정·분류·동·층·좌표, 그리고 제진대 → 물류 → 입고 → Qual → 반출/이설 일정.
  • 개발대여·공사·고장·이설 등 운영 비가동을 호기별 기간으로 관리한다.
  • 공정·분류별 주차 단위 총대수·가용대수·비가동대수를 집계한다.
  • 저장마다 전체 스냅샷 리비전이 남는다.이 누적 데이터를 Dynamic Capa 분석의 기반으로 삼을 계획이다.

발표자 노트

화면 캡처는 개발 PC 합성 샘플 7대다 — 사내에서는 실제 호기 마스터를 입력하는 중이다. 편의 도구의 목적은 둘 — 공수 절감과 현황 가시화. 여기서 쌓이는 가용대수는 아직 Capa 계산 입력이 아니고 전환 정책은 별도 결정이다. '누가 등록했는지 남나' — 등록자 식별·승인은 미구현, 저장 시각과 스냅샷만 남는다. '원천은' — 담당자가 관리하는 설비 리스트를 31컬럼 양식에 맞춰 붙여넣는 것이다. 이 표를 누가 어느 주기로 갱신할지 정하는 것이 실행 Capa 의 진짜 의존성이다.

04

Dynamic Capa

발표자 노트

표준과 실적을 잇는 단계. 산식과 화면은 있고 실적 데이터 연결이 남았다.

Dynamic Capa

표준과 실적을 잇는다

표준·실행 Capa 를 실적 효율·UPEH 와 결합한다.단계별 Gap 과 그 합이 만드는 Capa 차이를 본다.

  • 표준 Capa → 효율 반영 → 실효 Capa → 모델 실적 Capa(Rundown 반영) → 실제 실적.
  • 효율 Gap, UPEH Gap, 재공부족 미활용, 그리고 원인이 확정되지 않은 잔차를 나눠 본다.
  • 투자-실행 간 괴리가 큰 공정·설비를 골라 개선 대상 우선순위를 정한다.
표준 Capa기준정보에서 산출
실적 효율 반영효율 Gap
실적 UPEH 반영 = 실효 CapaUPEH Gap
Rundown 반영 = 모델 실적 Capa재공부족 미활용
실제 실적기타 정합성 Gap — 원인 미확정 잔차

막대 길이는 개념 도식이다 — 실제 비율은 실적 DB 연결 후 계산된다. Gap 이 큰 공정 · 설비가 개선 우선순위 후보가 된다.

AI 가 붙으면잔차의 원인 후보를 해석한다 — 같은 시점의 비가동·편집 이력·제외 목록을 붙여 가설을 순위화. 반드시 「후보」로, Gap 수치는 만들지 않는다.
발표자 노트

화면 골격과 산식은 구현되어 있고 실적효율·생산실적 DB 연결이 남았다. 현재 화면 수치는 구조 검토용 샘플이다. '우리가 어떤 컬럼을 줘야 하나' — 공정·제품·Stack·WF 속성 단위의 실적 효율, 실적 UPEH, 실가동시간, Rundown 시간. 정확한 컬럼 정의는 연결 때 확정한다. '기준은 누가' — 화면의 정상/관찰/개선 필요(90%/80%) 는 데모 임계값이고 운영 임계는 실데이터 분포를 본 뒤 제조팀 관리 정책으로 정한다.

Dynamic Capa

재공을 표준 Capa 기반 관리 및 전망한다

TAT 기반 cutoff 로 스텝별 일 목표를 세운다.재공 소진 전망에서 운영 필요대수를 낸다.

  • TAT DB 기반으로 공정·제품별 cutoff 테이블을 구성한다.
  • 이를 기준으로 스텝별 일 목표를 표준 Capa 로 세우고 일 실적과 비교한다.
  • 표준 또는 Dynamic Capa 기준으로 재공 소진 시나리오를 전망한다.
  • 제품별·차수별(Core 적층 단계별) 운영 필요대수를 산출해 제공한다.
TAT 기반 cutoff공정 · 제품별→스텝별 일 목표표준 Capa 기준→소진 시나리오표준 또는 Dynamic→운영 필요대수제품별 · 차수별
AI 가 붙으면재공 소진 시나리오 여러 개를 코드가 돌리고, AI 는 어느 제품·차수가 먼저 마르는지 비교 문장만 쓴다.
발표자 노트

설계 단계다. '화면이 있나' — 일별 재공·유입·Flow 를 일 표준 가능량과 비교하는 '표준 대비 재공 현황' 골격은 샘플 데이터로 돌고 있다. 이 장의 cutoff·소진 시나리오·필요대수는 그 위에 얹을 설계다. 'TAT 는' — 제품·단수별 Process 흐름 DB 에서 받을 계획이고 요청 항목에 있다. 재공 실적의 시점 정의(보유·유입·Flow 를 언제 자르나)는 데이터 담당과 확정한다.

05

AX 로 가는 길

발표자 노트

마지막 — Chatbot 이 왜 지금이 아니라 다음인지, AI 가 붙는 자리 여덟 곳, 현황과 요청, 그리고 이 방식을 템플릿으로.

AX 로 가는 길

Chatbot 은 신뢰할 수 있는 데이터 위에서만 신뢰할 수 있다

표준화된 데이터와 산출 로직 위에 설명·탐색·해석 층을 얹는다.AI 는 숫자를 만들지 않고 근거를 인용한다.

  • 계산은 기존 순수 함수가 한다.AI 가 하는 것은 셋 — 설명, 탐색, 해석.
  • 실체는 「승인된 읽기 전용 조회 도구」 집합이다.계산 결과에 이미 (리비전·기간) 키가 붙어 있어 답변마다 출처가 자동으로 따라온다 — 임베딩도 재학습도 필요 없다.
  • 답변 원칙은 이미 정해 두었다 — 활성 시나리오·조회기간 명시, 지표·단위·산식 표시, 근거 행 제시, 권한 밖 데이터 차단, 추정·확정 구분.
  • 사내 LLM(대형 언어모델) API 연결은 자체 진행 예정이다.
발표자 노트

'챗봇 만드나' 가 아니라 '도구 집합을 정의하면 챗봇이 된다'. 보여주기 챗봇은 하지 않는다 — 검증 안 된 데이터 위 LLM 은 그럴듯한 오답을 자신 있게 낸다. 초안 화면의 추천 질문 4개가 도구 8~10개와 1:1 대응한다. 도구는 읽기 전용으로 고정하고 쓰기 경로(편집·저장)는 사람 확인을 거친다. 마스킹·감사 이력 정책은 연결 전에 정한다.

AX 로 가는 길

AI 가 붙는 자리 — 단계별로

계산은 그대로 두고, 사람이 반복하던 설명·탐색·해석을 AI 가 맡는다.여덟 자리, 세 시점.

지금 가능 — 템플릿으로 먼저, LLM 은 문장층만 교체

  • ① 제외·충돌 보고 한 문단 — 세 화면에 흩어진 목록을 「B/N 공정에 걸린 제외 M건, 먼저 고칠 표」로
  • ② 부서별 우선순위 보고 문장 — 부족 표·B/N·로직 분석을 GO팀/기술팀/제조팀 문장으로. 숫자는 슬롯
  • ③ 등록 시 직전 대비 변화 해석 — 행수·월 범위·제품 집합 비교는 코드, 확인 항목 문장은 AI

사내 LLM 연결 후

  • ④ 붙여넣기 오류 행 단위 설명 — 규칙 21종의 위반을 모아서
  • ⑤ 읽기 전용 도구 집합 = Chatbot — 키 기반 캐시 래퍼 8개 + 순수 함수 5개를 도구 호출(function calling)로
  • ⑥ 자연어 → 편집안 → 변경 전후 미리보기 — 적용은 사람이
  • ⑦ 다중 레버 what-if 탐색 — 복사 테이블 위 ≤20회 반복, AI 는 비교 문장
