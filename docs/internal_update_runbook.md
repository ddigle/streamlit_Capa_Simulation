# 사내 업데이트 실행 절차 (사내 에이전트용)

이 문서는 **사내에서 배포 ZIP 을 받아 적용하는 한 번의 작업**을 처음부터 끝까지 적은
것이다. 위에서 아래로 그대로 따라가면 된다. 왜 이런 구조인지는 `docs/dual_env_workflow.md`
에 있고, 여기는 **무엇을 어떤 순서로 치는가**만 적는다. 사내 환경은 지금 사내 PC 다 — WebIDE 이관은
BigDataQuery → S3 Drive 전환이 끝날 때까지 보류다(2026-10-10 사용자). WebIDE 를 가리키는 줄은 그때를 위한 것이다.

**0장 · 0-1 · 1장 ~ 6장 · 8장은 배포마다 같다.** 사내에서 사용자와 정해 굴린 규칙(2026-10-06 ~ 10 사내 적용
다섯 번)을 여기 정본으로 옮겼다 — 사내 에이전트의 로컬 메모리에만 두면 환경을 옮길 때 사라진다. 이 문서에 없는
규칙을 메모리에서 꺼내 쓰지 말고, 필요하면 리뷰 문서의 「사외 요청」으로 낸다.

**이 문서를 읽고 있다면 먼저 확인한다.**

```powershell
git remote -v
```

`github.com` 이 나오면 **사외(개발 PC)다 — 이 문서는 네 것이 아니다.** 사내 GitHub 주소가
나올 때만 아래를 따른다.

---

## 0. 사내에서 절대 하지 않는 것

- **소스를 고치지 않는다.** `app.py`·`app_pages/`·`src/`·`tests/`·`scripts/`·`config/`·
  `.streamlit/`·`static/`·루트 문서 — 어느 것도 편집하지 않는다. 쓸 수 있는 곳은 `review/` 뿐이다.
  **예외는 하나 — 사용자가 직접 지시한 임시 수정**이다(2026-10-10 사용자 결정). 커밋하지 않고, 리뷰 문서에
  「임시 수정 있음 · 파일 N개 · 경로」 한 줄을 남기며, 다음 적용 전에 되돌린다 — 1-5 에 절차가 있다.
- **사내 커밋을 만들지 않는다** — `deploy:`(적용기)와 `review:`(리뷰 문서) 말고는 없다. 배포 세트 파일을 사내에서
  커밋하면 다음 적용이 덮거나(ZIP 에 있으면) 지운다(ZIP 에 없으면 「사외에서 지워짐」). 1-6 이 그것을 찾는다.
- **`git clean -x` 를 쓰지 않는다.** `-x` 는 무시된 파일까지 지우고, 거기에 **운영 DuckDB 와
  `data/input` 실데이터**가 들어 있다. 한 글자 차이로 사내 데이터가 날아간다.
- **`uv sync` 를 맨 것으로 돌리지 않는다.** 락에 없는 `bigdataquery` 를 지운다.
  항상 `uv sync --inexact` 다.
- **정체불명 파일을 스스로 지우지 않는다.** 사용자에게 묻고 고른 대로 한다.
- **`.gitignore` 를 고치지 않는다.** 권한에서도 막혀 있다. 넣어야 할 것이 있으면 리뷰
  문서에 적어 사외가 넣게 한다.
- **`git push` 는 에이전트가 하지 않는다.** 권한에서 막혀 있다(`Bash(git push*)` deny).
  푸시가 필요한 자리에서는 사용자에게 명령을 알려 주고 사용자가 친다.
- **사용자 앱을 끄지 않는다.** 다른 사람이 쓰고 있을 수 있다 — 꺼 달라고 요청하고 꺼진 것을 확인한다(1-1).
- **권한 판단이 막은 명령을 되풀이하거나 다른 길로 돌아가지 않는다.** 사용자에게 `!` 로 칠 한 줄을 준다(6장).

## 0-1. 진행 꼴 둘 — 사용자가 고른다

시작할 때 사용자에게 어느 꼴로 할지 묻는다. 대답이 없으면 기본 꼴이다.

| 꼴 | 차례 | 언제 |
|---|---|---|
| **기본** | 1장 → 2장 → 3장 → 4장 → 7장(화면 확인 · 7-8) → 8장 → 5장(리뷰 문서) | 사용자가 앱을 한동안 안 써도 될 때 |
| **적용 먼저, 확인 나중** | 1장 → 2장 → 4-1 → (사용자가 앱을 띄운다 — 4-2 의 마이그레이션이 이때 걸린다) → 4-3 → **멈춘다** · 사용자가 「사용 끝」을 알리면 → 7장 → 7-8 → 8장 → 5장 | 사용자가 새 배포를 바로 써야 할 때 |

- 「적용 먼저」에서도 **1장 ~ 2장 동안은 앱이 꺼져 있어야 한다** — 1-3 백업이 열린 DB 를 복사하면 사본이 깨질 수 있고,
  떠 있는 앱 아래에서 파일이 바뀌면 그 앱이 반쯤 새 코드를 읽어 오류로 선다.
- 앱이 떠 있는 동안 에이전트가 해도 되는 것은 **4-3 의 네 관문뿐**이다 — `pytest` 는 임시 DB 만 쓰고, 저장소의
  `data/*.duckdb` 를 열면 테스트가 실패로 끝나게 막혀 있다(`tests/conftest.py`). 7장의 화면 확인 스크립트(6-2)·7-8·8장은
  같은 DB 를 열어야 하므로 앱이 꺼진 뒤에 한다. 7장의 손 확인(사용자가 화면에서 하는 것)만 앱이 떠 있어야 한다.
- 리뷰 문서 머리에 「적용 먼저, 확인은 <YYYY-MM-DD>」 한 줄을 적는다.

## 1. 시작 전 점검 (5분)

### 1-1. 앱이 꺼졌는지 본다 — 에이전트가 끄지 않는다

```powershell
Get-CimInstance Win32_Process -Filter "Name = 'python.exe'" | Where-Object { $_.CommandLine -like '*app.py*' } | Select-Object ProcessId, CreationDate
```

한 줄이라도 나오면 **사용자에게 꺼 달라고 요청한다**(그 창에서 `Ctrl+C`). 에이전트가 프로세스를 죽이지 않는다 —
다른 사람이 쓰고 있을 수 있다. 사용자가 껐다고 하면 위 명령을 다시 쳐 빈 것을 확인한 뒤 진행한다. 명령줄에는 경로가
찍히니 리뷰 문서에 옮기지 않는다.

**DuckDB 는 프로세스 배타 잠금이라 앱이 살아 있으면 백업·7-8·8장이 전부 `duckdb.IOException` 으로 죽는다.**
적용기 자체는 DB 를 열지 않지만, 떠 있는 앱 아래에서 소스가 바뀌는 것도 막아야 하므로 1장 ~ 2장은 꺼진 채로 한다.

### 1-2. 쓰기 권한이 실제로 열리는지 한 번 본다

리뷰 문서를 못 쓰면 이번 작업의 산출물이 아예 나오지 않는다. 먼저 확인한다.

```powershell
New-Item -ItemType Directory -Force review | Out-Null
```

그리고 `review/_permission_test.md` 에 아무 한 줄이나 써 본다. 잘 써지면 사용자에게 그 파일을 지워 달라고 하고
넘어간다 — 에이전트 권한은 `Remove-Item`·`rm` 을 막는다(6-2). 사용자가 지우기 전에 리뷰 문서를 커밋하게 되면 그 파일은
스테이징하지 않는다.

**막히면 거기서 멈추고** 사용자에게 아래를 그대로 알린다 — 사외가 고쳐야 한다.

> 사내 `.claude/settings.json` 의 `Edit(*.md)` deny 가 `review/` 까지 막고 있습니다.
> 슬래시 없는 패턴은 gitignore 의미라 모든 깊이에 걸립니다. `Edit(/*.md)` 로 앵커하고
> allow 에 `Edit(review/**)` 를 더해야 합니다. **deny 는 allow 로 뚫을 수 없으므로**
> deny 쪽을 좁히는 것 말고는 방법이 없습니다.

설정 파일이 `docs/internal_claude_settings.json` 템플릿의 최신본과 같은지도 함께 본다 —
`.claude/` 는 배포가 덮지 않으므로 옛 템플릿이 남아 있을 수 있다. 이 시점의 템플릿은 **직전 배포의 것**이다 — 7장이
「권한 템플릿이 바뀌었다」고 적은 배포에서는 2-3 적용 뒤(8장 전) 한 번 더 견준다(7장이 그 자리를 적는다).

### 1-3. 운영 데이터를 저장소 밖으로 복사한다

**건너뛰지 않는다.** 아래 두 가지는 적용이 덮거나 지울 수 있다.

```powershell
$backup = "$HOME\deploy_backup\$(Get-Date -Format yyyyMMddHHmm)"
New-Item -ItemType Directory -Force $backup | Out-Null
Copy-Item data\*.duckdb $backup -ErrorAction SilentlyContinue
Copy-Item data\input\* $backup -Recurse -ErrorAction SilentlyContinue
```

`data/input/` 을 함께 챙기는 것은 보수적으로 두는 것이다. **배포 세트는 `data/input/` 아래를
보내지 않으므로**(`build_deploy_package.py` 의 `FORBIDDEN_PREFIXES`) 적용이 덮을 일은 없다.
다만 적용기의 `is_protected` 는 **삭제만** 막고 덮어쓰기는 막지 않는 구조라, 규칙이 바뀌면
조용히 덮인다 — 무시 파일이라 `git checkout -- .` 로도 돌아오지 않는다.

### 1-4. 저장소에 있으면 안 되는 것이 커밋돼 있는지 먼저 본다

**이 순서를 바꾸지 않는다.** 다음 단계(1-5)가 「수정된 파일을 되돌려라」라고 시키는데,
운영 DuckDB 나 `data/input` 실데이터가 **추적된 상태**라면 그 되돌리기가 실데이터를 커밋된
옛 버전으로 덮는다. 무엇이 추적 중인지 모르는 채로 1-5 에 들어가면 안 된다.

```powershell
git ls-files | Select-String -Pattern '\.duckdb|\.db$|\.wal$|^data/input/|^data/output/|^data/temp/|^\.agents/|^\.omo/|\.xlsx?$|\.xlsb$|\.tmp$'
```

**한 줄이라도 나오면 여기서 멈춘다.** `docs/dual_env_workflow.md` 8장의 정리를 먼저 끝내야
한다(앱 종료 → DB 를 저장소 밖으로 복사 → `git rm -r --cached` → 커밋). 그 정리는 사람이
한다 — `git rm` 은 에이전트 권한에서 막혀 있다. **단 `data/input/.gitkeep`·`data/output/.gitkeep`·
`data/temp/.gitkeep` 세 줄은 빼고 본다** — 배포가 싣는 빈 폴더 자리표라 늘 추적된다(데이터가 아니다). 2-1 의 `주의` 블록에도
같은 세 줄이 찍힌다. 그 셋 말고 한 줄이라도 나오면 멈춘다.

정리를 건너뛰고 적용하면 두 가지가 한꺼번에 일어난다. ① 그 파일들은 ZIP 에 없으므로
「사외에서 지워진 파일」로 판정돼 적용이 지운다. ② 1-5 의 되돌리기가 그 전에 실데이터를
덮는다.

### 1-5. 작업트리를 비운다

```powershell
git status --porcelain --untracked-files=no
```

**한 줄이라도 나오면 적용기가 멈춘다.** 사내에서 소스를 고쳤다면 커밋하지 말고 되돌린다.

```powershell
git checkout -- <경로>
```

**경로를 하나씩 확인하고 되돌린다.** `git checkout -- .` 처럼 전체를 쓰지 않는다. 경로에
`.duckdb`·`.wal`·`data/input`·`data/output`·`data/temp` 가 들어 있으면 **되돌리지 말고
사용자에게 알린다** — 그것은 소스 수정이 아니라 실데이터이고, 되돌리면 운영 데이터가
사라진다. 1-4 를 제대로 끝냈으면 이 목록에 그런 경로가 나올 수 없다.

`git checkout` 은 일부러 권한 allow 에 넣지 않았다. 매번 프롬프트가 떠서 **사람이 경로를
읽고 승인**하게 되어 있다.

되돌리기 전에 그 내용이 필요하면 리뷰 문서에 코드블록으로 옮겨 적는다 — 그것은 저장소 수정이
아니다. 아직 커밋하지 않은 `review/*.md` 가 있으면 **먼저 `review:` 로 커밋한다.** 그러지
않으면 이 단계에서 지워진다.

**사용자가 지시한 임시 수정(0장의 예외)이 남아 있을 때** — 그사이 사용자가 바로 써야 해서 고친 것이다.

1. 되돌리기 전에 diff 를 **저장소 밖**에 남긴다 — `git diff > $HOME\deploy_backup\<날짜>\temp_edit.diff`.
2. 이번 ZIP 이 같은 것을 정식으로 고쳤는지 본다(7장·2-1 의 변경 목록). 고쳤으면 사용자에게 「정식 반영됨」을, 아니면
   「적용하면 임시 수정이 사라집니다 — 계속 필요하면 사외 요청으로 내야 합니다」를 알린다.
3. `git checkout -- <경로>` 로 되돌린다(위 규칙대로 경로를 하나씩).
4. 리뷰 문서에 「임시 수정 있음 · 파일 N개 · <경로>」 한 줄을 남긴다(내용은 적지 않는다 — 경로는 실데이터가 아니다).
   그 수정이 걸린 채로 화면 확인·관문을 돌렸으면 그 사실도 같은 줄에 적는다 — 사외가 결과를 잘못 읽지 않게 한다.

임시 수정이 닿는 테스트를 배포본 기준으로 돌려야 하면 작업트리를 건드리지 않고 저장소 밖에 사본을 떠서 돌린다.

```powershell
git worktree add --detach <저장소 밖 경로> HEAD
$env:PYTHONPATH = "<저장소 밖 경로>/src"; uv run --no-sync python -m pytest <테스트 파일>   # 사본 폴더에서
git worktree remove <저장소 밖 경로>
```

### 1-6. 사내 커밋을 찾는다

```powershell
git log --format="%h %ad %s" --date=short -30 | Select-String -NotMatch ' (deploy|review): '
```

`deploy:`·`review:` 가 아닌 커밋이 나오면(예: 2026-10-08 `index.html` 발표자료) 그 커밋이 바꾼 파일을 본다 —
`git show --stat --format= <커밋>`. `review/`·`.deploy/`·`.claude/` 밖의 파일이면 **다음 적용이 덮거나(ZIP 에 있으면)
지운다(ZIP 에 없으면)** — 사용자에게 알리고, 계속 필요하면 리뷰 문서의 「사외 요청」에 적어 사외가 같은 것을 넣게
한다. 사외가 이미 같은 것을 넣었으면(사용자가 확인) 그대로 진행한다. 리뷰 문서의 「사내 데이터 변화」 절에 커밋
7자와 파일 수를 적는다.

## 2. 적용 (본 작업)

### 2-1. 먼저 보기만 한다

**그 전에 7장 머리의 stamp 확인(`.deploy/applied.json`)을 한다** — 2-3 의 적용이 그 파일을 덮는다.

```powershell
uv run --no-sync python scripts/apply_deploy_package.py <내려받은 ZIP 경로> --dry-run
```

**ZIP 경로는 슬래시로 쓴다** — `C:/Dev/.../202610021506.zip`. 에이전트의 셸이 Git Bash 면 역슬래시
(`C:\Dev\...`)가 사라져 「파일이 없다」로 끝난다(`202610021506` 리뷰). PowerShell 에서도 슬래시는
그대로 통한다.

`--dry-run` 은 **아무것도 바꾸지 않는다.** 깨끗한 작업트리도 요구하지 않는다. 출력에서 아래를
읽는다.

| 칸 | 뜻 | 할 일 |
|---|---|---|
| `사외에서 지워진 파일` | 추적 중인데 목록에 없다 | 적용이 지운다. 7장이 「예상된 삭제」로 적은 경로는 뜻밖이 아니다 — 그 밖의 것이 있으면 **여기서 멈추고** 사용자에게 묻는다 |
| `사내에만 있는 정체불명 파일` | 추적도 무시도 안 된다 | **스스로 지우지 않는다.** 아래 2-2 로 |
| `목록에 있는데 사내에 없는 파일` | 적용 전이면 정상 | ZIP 이 채운다 |

`--reconcile-only` 는 목록 대조만 본다(동작은 `--dry-run` 과 같은 자리에서 끝난다).

### 2-2. 정체불명 파일을 먼저 정리한다

**적용보다 먼저 한다.** 적용기의 커밋 단계는 이번 배포가 실제로 건드린 경로만 스테이징하므로
정체불명 파일을 빨아들이지는 않지만, 그래도 남겨 두면 다음 배포에서 다시 물어야 한다.

파일마다 사용자에게 묻고 셋 중 하나를 고른다.

1. **사내에서만 쓰는 것** → 그대로 둔다. `.gitignore` 에 넣을 필요가 있으면 **리뷰 문서에
   적어 사외가 넣게 한다** (사내에서 `.gitignore` 를 고치지 않는다)
2. **사외에도 있어야 하는 것** → 리뷰 문서에 적어 사외가 추가하게 한다
3. **옛 배포의 잔해** → 지운다

판단이 서지 않으면 (1)로 두고 리뷰 문서에 남긴다. 지우는 것은 되돌릴 수 없고, 남기는 것은
다음 배포에서 다시 물으면 된다.

**사내에서 쓴 기록 문서**(예: `HANDOFF_AUDIT_2026-09-17.md` — 사외 저장소에는 한 번도 없던 파일이다)는
(1)로 두는 대신 사용자에게 물어 **`review/` 로 옮겨 `review:` 로 커밋**하면 다음 배포부터 묻지 않는다.
`review/` 는 배포가 보내지도 지우지도 않는 사내 자리다. 옮기는 것도 사용자가 고른 뒤에만 한다.

아직 커밋하지 않은 `review/*.md` 가 있으면 **적용 전에 `review:` 로 먼저 커밋한다.**
`deploy:` 커밋과 섞이지 않게 하려는 것이다.

### 2-3. 적용한다

```powershell
uv run --no-sync python scripts/apply_deploy_package.py <내려받은 ZIP 경로>
```

끝나면 `deploy: <stamp> (<사외 커밋 7자>)` 로 자동 커밋된다.

**에이전트의 자동 권한 판단이 이 명령을 막으면** 같은 명령을 되풀이하지 않는다. 사용자에게 위 한 줄을
**ZIP 경로까지 채워(슬래시로)** 알려 주고, 사용자가 `! <명령>` 으로 직접 친 출력을 읽고 이어 간다
(`202610021506` 적용 때 두 번 막혀 이렇게 했다). 적용 결과의 대조·커밋은 스크립트가 같게 한다.

## 3. 적용 뒤 읽는 법 — 정상인데 이상해 보이는 줄

**아래는 결함이 아니다. 리뷰 문서에 결함으로 적지 않는다.**

### 3-1. `목록에 있는데 사내에 없는 파일` 은 비어 있어야 한다

적용 **뒤**에 이 칸에 무엇이든 있으면 이상이다(`해제가 덜 됐습니다`). 판정의 근거는 **바로
앞줄**이다.

```
대조    N/N 해시 일치
```

이 줄이 먼저 나왔으면 전 파일이 맞게 풀린 것이다.

> 예전 배포에서는 이 칸에 `data/input/RQ_DISPLAY_ORDER.csv` 한 줄이 **항상** 떴다. 그 파일이
> 배포 세트에 실리면서 동시에 `.gitignore` 에 걸려 대조가 쓰는 두 목록 어디에도 안 잡혔기
> 때문이다. 지금은 `data/input/` 아래를 아예 보내지 않으므로 그 오탐이 없다. 아직도 뜬다면
> **옛 ZIP 을 적용하고 있는 것이다.**

### 3-2. `pytest` 에서 `test_the_top_level_stays_the_declared_set` 실패

`['.deploy/', 'review/']` 때문에 실패하면 **옛 배포를 적용한 것이다.** 두 폴더는 사내에만
생기므로 사외에서는 재현되지 않고, 그래서 한동안 사내에서만 깨졌다. 지금 배포부터는 그 둘이
`INTERNAL_ONLY_TOP_LEVEL` 로 선언돼 있어 통과한다. 그래도 실패하면 **그 사실 자체를 리뷰
문서에 적는다.**

`static/`(글꼴, `202610061748` 배포부터)이 걸려 실패하면 꼴로 가른다. 「최상위에 선언되지 않은 항목이
있습니다 … ['static/']」이면 테스트 파일이 옛것이다 — 일부만 풀린 적용이다. 「선언에는 있는데 저장소에 없는
항목입니다 … ['static/']」이면 `static/` 이 풀리지 않았거나 커밋되지 않았다 — 3-1 의 `목록에 있는데 사내에 없는
파일` 을 함께 본다. 어느 쪽이든 고치지 말고 리뷰 문서에 적는다.

### 3-3. 루트의 `requirements.txt` 는 사내 WebIDE 컨테이너 전용이다

**손으로 적는 파일이 아니라 `uv.lock` 의 그림자다.** 개발 PC 와 CI 는 `uv sync` 로 잠금을
보지만, 사내 WebIDE 의 CI/CD 는 `docker/Dockerfile-prod` 로 이미지를 만들고 그 안에서
`pip install -r requirements.txt` 를 돈다. 둘이 갈라지면 **사내 컨테이너만 조용히 다른
버전을 쓴다** — 화면에 오류가 나지 않고 계산 결과만 달라질 수 있다.

- **사내에서 이 파일을 고치지 않는다.** `tests/test_requirements_export.py` 가 `uv.lock`
  과 대조하므로 고치면 검증에서 걸린다. 사외가 `uv export` 로 다시 뽑는다.
- **`uv sync` 를 이 파일로 대신하지 않는다.** 개발용 도구(ruff·mypy·pytest)가 빠져 있다.
- 이 파일에는 프로젝트 자신(`-e .`)이 **일부러 빠져 있다.** 그래서 컨테이너는
  `Dockerfile-prod` 의 `ENV PYTHONPATH=/project/src` 로 `src` 를 찾는다. 둘은 한 쌍이라
  한쪽만 보고 판단하지 않는다.

### 3-4. 지움이 있는 배포 — 적용 직후 재대조에 `사외에서 지워진 파일` 이 그대로 찍힌다

2-3 의 출력에서 `대조    N/N 해시 일치` 바로 아래 재대조가 2-1 에서 본 「사외에서 지워진 파일 k개 — 적용이 함께
지웁니다.」를 **한 번 더** 찍는다. 파일은 이미 지워졌다. 재대조가 읽는 `git ls-files` 는 작업트리가 아니라 인덱스를 보고,
적용기는 지운 경로를 그다음 커밋 단계에서야 인덱스에서 뺀다 — 그래서 커밋 바로 앞의 재대조는 지운 파일을 아직 「추적
중인데 목록에 없다」로 본다. **그 목록이 2-1 의 `지움` 목록과 같으면 결함이 아니다.** 커밋이 끝난 뒤 아래가 그 경로를 하나도
찍지 않으면 지워진 것이다.

```powershell
git ls-files <지움 목록의 경로>
```

2-1 의 `지움` 에 없던 경로가 이 칸에 있거나, 커밋 뒤에도 위 명령이 그 경로를 찍으면 이상이다 — 고치지 말고 리뷰 문서에
적는다.

## 4. 적용 뒤 할 일

### 4-1. 의존성 — 변경 목록에 `pyproject.toml` 이나 `uv.lock` 이 있을 때만

```powershell
uv sync --inexact
```

맨 `uv sync` 는 `bigdataquery` 를 지운다. 지웠으면 되돌린다.

```powershell
uv pip install -r requirements-company.txt
```

### 4-2. 마이그레이션은 앱이 알아서 한다

앱을 한 번 띄우면 `data/capa_simulation.duckdb` 와 `data/equipment_availability.duckdb` 에
새 마이그레이션이 적용된다. **적용된 마이그레이션은 버전 번호로 체크섬을 대조하므로, 사내에서
SQL 파일을 고치면 앱이 시작조차 못 한다.**

**이 명령은 사용자가 친다.** 서버는 끄기 전까지 안 끝나므로 에이전트가 띄우면 세션이 거기서
멈춘다. 그리고 브라우저로 한 번 들어가야 마이그레이션이 실제로 걸린다.

**두 DB 는 걸리는 때가 다르다.** 시뮬레이션 DB 는 첫 화면(HOME)에서 걸리지만 설비 DB 는
연결을 처음 쓸 때 만든다 — **`가용설비 현황`(또는 `Space 현황`) 페이지를 실제로 열어야** 설비
마이그레이션이 적용된다(`표준 목표`·`표준 대비 재공 현황 (구현중)` 도 설비 DB 를 열지만 확인은 앞의 둘로 한다).
설비 마이그레이션이 있는 배포면 그 페이지까지 열어 확인한다(`202609281727` 리뷰의 지적).

```powershell
uv run --no-sync python -m streamlit run app.py
```

화면이 뜨는 것까지 확인하면 `Ctrl+C` 로 끈다. 오류가 나면 **고치지 말고** 리뷰 문서에 적는데,
**원문을 그대로 붙이지 않는다** — 이 앱의 오류 문구에는 설계상 공정명·제품명 같은 식별값이
박혀 있다. 5장의 가명화 규칙을 그대로 적용해 옮겨 적는다.

### 4-3. 네 관문을 돌린다

```powershell
uv run --no-sync python -m ruff format --check .
uv run --no-sync python -m ruff check .
uv run --no-sync python -m mypy
uv run --no-sync python -m pytest
```

**넷을 차례로, `pytest` 는 다른 관문과 겹치지 않게 단독으로** 돌린다. 동시에 돌린 첫 실행에서 AppTest 가
`KeyError: 'client_state'` 로 간헐 실패한 적이 있다(Streamlit 의 끝남 판정 경쟁 — `202610070927` 부터 `tests/conftest.py`
가 막는다). 그래도 나오면 `pytest` 만 한 번 더 단독으로 돌리고, 두 번째도 실패하면 「발견」으로 적는다.

앱이 떠 있어도 된다 — 테스트는 임시 DB 만 쓰고, 저장소의 `data/*.duckdb` 를 새로 만들면 실패로 끝나게 막혀 있다
(0-1 의 「적용 먼저」가 이 점을 쓴다). 실패가 나오면 3-2 에 해당하는지 먼저 보고, 아니면 리뷰 문서의 「발견」으로 적는다.

## 5. 리뷰 문서 쓰기 (이 작업의 산출물)

경로는 `review/<ZIP 파일명>.md` — 예: `review/202609201530.md`. 양식과 「실데이터를 적지
않는다」 규칙은 `docs/dual_env_workflow.md` 4장에 있다. 핵심만 옮기면:

- **값의 「꼴」은 남기고 식별자는 가명으로 쓴다.** 이 문서는 **사내에서 사외로 나가는
  유일한 것**이다.
- 좋음 — 「`Pack Code` 에 `4.00E+02` 꼴인 값이 2종, 5행」
- 나쁨 — 실제 값을 그대로 적는 것

**실데이터로 취급하는 것 (컬럼 이름으로)**

`Customer` · `제품정보` · `Capa Code` · `CS` · `공정` · `Area_Name` · `설비명`(옛 `호기`) ·
`Main 설비`(옛 `모체호기`) · `Pack Code` · `WF 구분` · `Stack` · `양산구분` · `STEP_SEQ` · `MCP_SEQ` ·
설비 마스터의 자유 글 칸(`설비이력`·`반입/Qual 이력`·`메모1`~`메모3`) · 사람 이름과 사번 · 시뮬레이션
코드와 이름 · 파일 경로 안의 위 값들.

**무심코 붙여넣기 쉬운 자리** — 여기서 대부분 샌다.

- 오류 원문·스택트레이스 (앱 오류 문구에 공정명·제품명이 박혀 있다)
- `git diff`·`git log` 출력
- SQL 결과표, DataFrame 출력
- 화면 캡처와 그 파일 경로
- 적용기 출력의 파일 목록

**커밋 전에 스스로 한 번 돌린다.** 걸리면 그 줄을 가명으로 고친 뒤 다시 돌린다.

```powershell
Select-String -Path review\*.md -Pattern 'INTEL|AWS|BRCM|ARCM|BINTEL|HBM|DDR5|Pack ?Code *[=:] *[^ ]|[A-Z]{2,}-[0-9]{3,}'
```

한 줄도 안 나와야 한다. 이 패턴은 그물이지 보증이 아니다 — 걸리지 않아도 위 컬럼 목록을
눈으로 한 번 훑는다. **예외는 하나다** — 8장 출력 블록의 8-4 `사용기준` 줄(「- 사용기준(`equipment_contract.counts_for_capacity`,
… HBM … 행 · 다른 값 …」)은 계약 상수 `HBM` 을 실어 걸린다. 스크립트가 찍은 줄이라 고치지 않는다(8-6). 본문(7장 결과)에는
사용기준을 「사용기준 제외 N대」처럼 적어 그 글자를 쓰지 않는다 — 그러면 걸리는 줄은 그 한 줄뿐이다.

**적는 꼴** — 사외는 리뷰를 표와 수로 읽는다(2026-10-10 사내 요청으로 정본화, 양식은 `docs/dual_env_workflow.md` 4장).

- **값으로 적는다** — 수 · 있음/없음 · 같음/다름 · 「미기록 — 까닭」. 서술·반복·런북 인용은 뺀다.
- **확인자를 가른다** — 에이전트가 본 것과 사용자가 눈으로 본 것을 칸이나 머리말로 나눈다.
- **「사내 데이터 변화」 절을 따로 둔다.** 7-8 의 값이 기대와 다르면 대개 사내 사용자의 저장이다 — 화면의 저장 시각
  (캡션)과 에이전트가 확인한 시각을 견줘 에이전트의 쓰기가 아님을 가리고 「결함 아님」과 수만 적는다. 8-1 의
  리비전·호기 수 변화, 1-6 의 사내 커밋, 1-5 의 임시 수정도 이 절에 모은다.
- **「사외 요청」 절** — 런북·스크립트·규칙에 대한 요청은 여기에. 사내 메모리에만 둔 규칙은 이 절로 내 정본이 되게 한다.

**8장(실데이터 확인)을 돌렸으면** 리뷰 문서 끝에 「## 5. 실데이터 확인」 절을 더해 출력 블록을 그대로
붙인다 — 양식은 8-6 에 있다. 그 블록은 스크립트가 집계만 찍은 것이라 가명화하지 않고 고치지도 않는다.
블록 제목(`### 8-x.`)은 지키고, **직전 리뷰와 수가 하나도 다르지 않은 블록**은 본문 대신 「<stamp> 리뷰와 같음」 한
줄로 줄인다. BigDataQuery 실행 앞머리에 찍히는 서비스 공지(사람 이름이 든다)는 옮기지 않는다.

쓰고 나면 커밋한다.

```powershell
git add review
git commit -m "review: <ZIP 파일명>"
```

**푸시는 사용자가 한다.** 에이전트는 권한에서 막혀 있으므로 아래 명령을 알려 주고 멈춘다.

```powershell
git push
```

| `산출 결과` 에 `소요기준 PKG 는 Buffer 로만 셉니다` 안내, 제외 목록에 `PKG 기준은 Buffer 로만 계수` | PKG 공정은 스택된 Chip 을 Buffer 로만 센다(의도된 동작). 전에는 PKG 기준 소요대수가 늘 0 이었다 — 이제 값이 나온다 | 고칠 것 없다. `scripts/inspect_wf_division.py` 의 PKG 절 출력을 리뷰 문서에 옮긴다(EDP-TSV 의 PKG 행 WF 구분 확인용) |

되돌리는 법은 하나다 — **`git checkout -- .`**. 적용기는 파일을 다 풀고 대조까지 통과한 뒤에야
인덱스를 건드리므로, 중간에 멈춘 실행은 이 한 줄로 전부 돌아온다. 이미 커밋까지 갔으면
`git revert <커밋>` 이다.

## 6-2. 7장 화면 확인을 에이전트가 할 때

7장 화면 확인 가운데 `scripts/check_deploy_screens.py` 가 맡는 항목(7-0 표의 확인자 「에이전트(스크립트)」)은 에이전트가 이
스크립트로 한다. 스크립트는 이 저장소의 앱을 **별도 포트**(`127.0.0.1:8551`)에 따로 띄워 헤드리스 Chrome 으로 보고, 개수·있음/없음·
같음/다름만 적은 Markdown 블록을 낸다. 화면에서 읽은 이름은 판정에만 쓰고 옮기지 않으며 DB 에 쓰지 않는다. 끝나면(멈춰도) 띄운
앱을 스스로 끈다. 스크립트 밖 항목은 사용자가 화면에서 보고 에이전트가 값을 받아 적는다(확인자 「사용자」 — 6장 표).

**사용자 앱이 꺼져 있어야 한다.** 스크립트는 `streamlit run … app.py` 프로세스와 두 DB 잠금을 먼저 보고, 떠 있으면 미룬다(종료 3).
사용자에게 꺼 달라고 요청한다 — 에이전트가 끄지 않는다(0장 · 1-1).

**설치 — 처음 한 번, 저장소 밖에.** Playwright 는 이 저장소의 의존성이 아니다. 브라우저는 받지 않고 이미 깔린 Chrome 을 쓴다.

```powershell
uv pip install --target $HOME/pw playwright
```

`Test-Path $HOME/pw/playwright` 가 `True` 면 이미 깔린 것이다 — 다시 깔지 않는다. 권한 판단이 막으면 이 한 줄을 사용자에게 준다(6장 표).

**돌리기 — 백그라운드로 돌리고 `--output` 파일을 읽는다.** 사내 실데이터에서 몇 분 ~ 15분 걸려 에이전트의 한 번 호출 제한을 넘는다.

```powershell
uv run --no-sync python scripts/check_deploy_screens.py --playwright-dir $HOME/pw --output $HOME/screens.md
```

- 항목 목록만(Playwright 없이) — `uv run --no-sync python scripts/check_deploy_screens.py --list`. 첫 칸이 키다.
- 일부만 — 같은 줄 끝에 `--items <키>,<키>`(7장이 이번 몫의 키를 적는다). 미기록 항목만 다시 돌릴 때도 이것이다.
- `--output` 은 시작하자마자 「확인 시작 — 아직 항목 없음」으로 덮어쓰고, 항목이 끝날 때마다 블록 전체를 다시 쓴다 — 중간에
  끊겨도 그때까지의 칸이 남는다. 그 블록(머리 세 줄 + 표)을 리뷰 문서의 `## 7-<x> 화면 확인` 절에 **고치지 않고** 붙인다. 결과
  칸의 `|` 는 표가 깨지지 않게 `/` 로 바뀌어 찍힌다.
- **권한 템플릿(`docs/internal_claude_settings.json`)에 이 스크립트의 allow 는 일부러 없다** — 앱을 띄우고 브라우저를 모는 명령이라
  돌릴 때마다 사용자가 승인한다. 권한 판단이 막으면 위 한 줄을 사용자에게 `!` 로 주고, 사용자가 친 뒤 `--output` 파일을 읽는다.

**끝난 꼴은 종료 코드와 stdout 으로 가른다.**

| 종료 코드 | 뜻 | 할 일 |

|---|---|

**지키는 것.**

- **`--allow-writes` 는 사용자가 허락했을 때만 붙인다.** DB 에 쓰는 항목은 허락 없이는 「안 함(허락 없음)」으로 찍힌다. 지금 등록된
  항목에는 쓰는 것이 없다 — 쓰는 항목이 생기면 7장이 그 키와 허락을 따로 적는다.
- **스크린샷은 `--shots <저장소 밖 폴더>` 를 줄 때만 찍는다.** 화면의 이름이 그대로 담기므로 리뷰 문서에 붙이지 않고, **리뷰 커밋 전에
  사용자에게 그 폴더를 지워 달라고 한다**(에이전트 권한은 `Remove-Item`·`rm` 을 막는다). 평소에는 주지 않는다.
- **시간 예산은 15분**(`--budget-minutes` 기본값, 스크립트 시작부터 잰다). 사내 백그라운드 실행은 30분이면 죽으므로 늘리지 않는다.
- 끝에 「확인용 앱 프로세스가 남았을 수 있습니다 — 포트 N …」 이 찍히면 이 스크립트가 띄운 앱이다(명령줄에 `--server.port N`).
  1-1 명령으로 사용자와 함께 보고 사용자가 끈다.
- 블록 머리 둘째 줄의 「마이그레이션 n개를 이 확인이 걸었다」는 4-2 에서 앱을 열지 않아 이 확인의 앱이 건 것이다 — 결함이 아니다.

## 6-3. 사용자 앱을 끄지 않고 실 DB 사본으로 확인할 때 (사본 E2E)

사용자가 앱(8501)을 계속 써야 하는데 실데이터로 넓게 봐야 할 때 쓴다 — 전 리비전 계산 · 화면 순회 · HOME 시간.
`202610120655` 리뷰의 「실데이터 E2E」(전 리비전 54 계산 · 페이지 17 · 탭 49 · HOME cold/warm)가 이 꼴이었다. **7-8 ·
8장의 대신이 아니다** — 그 둘은 그대로 앱을 끈 채 운영 DB 로 한다. 사본 E2E 는 그 위에 더하는 확인이고, 할지는 7장이 적거나
사용자가 고른다.

**지키는 것.**

- **사용자 앱과 운영 DB(`data\*.duckdb`)는 건드리지 않는다.** 운영 DB 에 하는 일은 파일 복사뿐이다.
- **사본(트리·DB)은 저장소 밖에 둔다** — 실데이터라 커밋되면 안 된다. 끝나면 사용자에게 그 폴더와 zip 을 지워 달라고 한다(에이전트
  권한은 `Remove-Item`·`rm` 을 막는다).
- **사본 앱은 `127.0.0.1` 에만, 8501·8551 이 아닌 포트(8552 부터)에** 띄운다.
- **사본에서도 DB 에 쓰는 단추는 누르지 않는다**(7장 「세 가지」의 목록) — 사본이라 운영에 가지는 않지만 확인 범위 밖이다.
- 결과는 6-2 · 8장과 같은 꼴(개수·있음/없음·초)로만 적는다. 리뷰 문서에 `## 사본 E2E (런북 6-3)` 절을 두고 머리에 「사본 시각
  <YYYY-MM-DD HH:MM>」 을 적는다 — 사본 뒤 사용자가 저장한 것은 들어 있지 않다.

### 1) 사본 트리 — `git archive`

앱은 **자기 트리의** `data\` 의 DB 를 연다(`settings.DUCKDB_PATH`). 그래서 운영 트리 옆에 커밋된 트리를 하나 더 풀고 거기 `data\`
에 DB 사본을 둔다. `git worktree` 와 달리 저장소에 아무것도 등록하지 않는다. 사본 트리에는 가상환경도 `.git` 도 없다 — 파이썬은
**저장소의 `.venv` 를 경로로** 부르고(`uv run` 은 사본 안에 새 환경을 만들려 하므로 쓰지 않는다), git 이 드는 스크립트는 저장소에서
돌린다.

```powershell
$e2e = "$HOME\e2e_copy\$(Get-Date -Format yyyyMMddHHmm)"
New-Item -ItemType Directory -Force (Split-Path $e2e) | Out-Null
git archive --format=zip -o "$e2e.zip" HEAD
Expand-Archive "$e2e.zip" $e2e
$py = "$PWD\.venv\Scripts\python.exe"
```

`git archive -o` 는 상위 폴더를 만들지 않는다 — 둘째 줄이 없으면 처음 따라 할 때(`e2e_copy` 가 아직 없다) 「could not open
… for writing」으로 멈춘다. `git archive` 는 커밋된 것만 푼다 — 사용자가 지시한 임시 수정(1-5)은 사본에 없다. 그 수정이 걸린
채로 봐야 하면 이 확인은 하지 않는다.

### 2) DB 복사 — `.wal` 이 없을 때만

DuckDB 는 저장을 먼저 `<DB>.wal` 에 적고 나중에 본 파일로 옮긴다. `.wal` 이 있는 동안 본 파일만 복사하면 마지막 저장이 빠지거나 사본이
열리지 않는다. 앱은 rerun 하는 동안만 DB 를 쥐고 쉬는 동안에는 `.wal` 을 남기지 않으므로, **복사 앞뒤로 두 번** 본다. `.wal` 만
보면 복사 **도중에** 저장과 체크포인트가 다 끝난 경우(앞뒤 모두 `.wal` 없음)를 놓치므로 원본의 크기·마지막 쓴 시각도 앞뒤로 견준다.

```powershell
$db = "data\capa_simulation.duckdb", "data\equipment_availability.duckdb"
$wal = "data\capa_simulation.duckdb.wal", "data\equipment_availability.duckdb.wal"
$before = Get-Item $db | ForEach-Object { "$($_.Name) $($_.Length) $($_.LastWriteTimeUtc.Ticks)" }
Test-Path $wal
Copy-Item -Force $db "$e2e\data\"
Test-Path $wal
$after = Get-Item $db | ForEach-Object { "$($_.Name) $($_.Length) $($_.LastWriteTimeUtc.Ticks)" }
Compare-Object $before $after
```

`Test-Path` 는 두 번 다 `False` 둘이고 `Compare-Object` 는 아무것도 찍지 않아야 한다. 하나라도 어긋나거나 복사가 「다른 프로세스가
사용 중」으로 막히면 그사이 누가 저장(rerun)한 것이다 — 1분쯤 뒤 `$before` 줄부터 다시 한다. 사본 시각은 마지막으로 성공한 복사의
시각이다.

### 3) 사본이 맞는지 — 띄우기 전에 둘을 본다

```powershell
$env:PYTHONPATH = "$e2e\src"
& $py -c "import capa_simulation.settings as s; print(s.DUCKDB_PATH.resolve())"
& $py -c "import duckdb, capa_simulation.settings as s; [print(p.name, duckdb.connect(str(p), read_only=True).execute('SELECT count(*) FROM duckdb_tables()').fetchone()[0]) for p in (s.DUCKDB_PATH, s.EQUIPMENT_DUCKDB_PATH)]"
```

- 첫 줄이 찍는 경로가 **`$e2e\data\` 아래여야 한다.** 저장소의 `data\` 가 찍히면 멈춘다 — 그대로 띄우면 사본 앱이 사용자 DB 를 연다
  (`PYTHONPATH` 가 안 먹었다).
- 둘째 줄은 두 사본이 열리는지만 본다(읽기 전용으로 열어 표 수만 센다 — 몇 초). 파일 이름과 표 수 두 줄이 나와야 하고, 오류가
  나면 2) 를 다시 한다. 전 리비전 계산은 여기서 하지 않는다 — 수 분이 걸리고 4-a 가 한다.

### 4) 확인 셋 — 고른 것만, 이 차례로

차례를 지킨다 — a 는 사본 DB 를 읽기만 하고, b·c 는 사본 앱이 마이그레이션을 걸 수 있어 사본을 바꾼다. 같은 사본 DB 를 동시에 열면
`duckdb.IOException` 이니 하나씩 돌린다.

**a. 전 리비전 계산** — `scripts/inspect_revision_calculations.py`. 모든 리비전을 앱과 같은 길로 읽어 대당 Capa → 소요대수 → 확보율을
돌리고 상태·개수만 찍는다(이름 대신 `S3 r2` 차례 번호). 리비전이 많으면 수 분이라 백그라운드로 돌리고 `--output` 을 읽는다. 오래
걸리면 `--active-only`(시나리오마다 활성 리비전과 공식버전 대상만).

```powershell
& $py "$e2e\scripts\inspect_revision_calculations.py" --database "$e2e\data\capa_simulation.duckdb" --output $HOME\revisions.md
```

`--database` 는 기본값이 없다 — 늘 사본 경로를 준다. 운영 DB(`data\capa_simulation.duckdb`)는 앱이 쉬는 동안 열리기도 하지만, 이
스크립트가 쥐는 수 분 동안 사용자 앱의 연결이 막힌다.

출력 블록을 고치지 않고 붙인다. 읽는 법은 블록 끝에 있다 — `멈춤` 이 0 이 아니면 그 줄의 원천 묶음·단계·표 이름을 「발견」에 옮긴다.

**b. HOME 시간** — `scripts/benchmark_home.py --data-dir`. **저장소에서** 돌린다(출력 머리의 커밋을 git 으로 읽는다). 저장소의
`data\` 는 받지 않는다 — 사본 폴더만.

```powershell
& $py scripts\benchmark_home.py --data-dir "$e2e\data" --output $HOME\home_bench.json
```

`>` 로 받지 않는다 — 출력은 UTF-8 인데 PowerShell 5.1 의 `>` 는 그것을 콘솔 코드페이지(cp949)로 읽어 한글을 깨뜨린다. `--output`
파일은 UTF-8 이고 먼저 비운다. `phases` 의 단계마다 `seconds`·`figure_count`, 그리고 `skipped`(입력이 없어 잠긴 토글)·`note`(프로필이
없어 켠 비용만 잰 토글)를 옮긴다.

실패하면 스크립트가 한 줄만 찍고(표준 오류와 `--output` 파일) 1 로 멈춘다. 그 한 줄은 둘 중 하나다.

- 스크립트 자신의 문장 — 예: `cold_summary의 Figure 수가 8개가 아닙니다: 4`.
- HOME 이 멈췄을 때 **줄인 줄** — `<단계> 실행 실패 — <예외 종류> <수> · 문구가 가리키는 표 <RQ_*> (사본이라 문구는 찍지
  않는다)`. 사본 모드는 HOME 의 오류 문구(공정·제품 이름, DB 오류면 사본 경로가 실린다)를 찍지 않는다.

**그 한 줄만** 그대로 적는다. 원문이 필요하면 c 의 사본 앱 화면에서 보고, 리뷰에는 옮기지 않는다.

**c. 화면** — 둘 중 하나.

- 7장 스크립트 항목을 사본으로 — 사본 트리의 `check_deploy_screens.py` 에 `--ignore-other-apps` 와 빈 포트를 준다. **이 옵션은 사본
  트리에서만 붙인다** — 프로세스 검사는 사용자 앱(8501)을 보고 미루는데, 사본 트리의 스크립트는 사본 DB 만 열고 잠금 확인도 사본
  DB 로 한다. 저장소에서 돌릴 때는 6-2 그대로다(1-1 확인 없이는 붙이지 않는다).

  ```powershell
  & $py "$e2e\scripts\check_deploy_screens.py" --ignore-other-apps --port 8552 --playwright-dir $HOME/pw --output $HOME/screens_copy.md
  ```

- 전 화면 순회 — 사본 앱을 손수 띄워(백그라운드) 페이지·탭을 차례로 연다. 세는 것은 연 페이지·탭 수와 예외·오류 화면 수뿐이고, 화면의
  이름·값은 옮기지 않는다. 열지 못한 탭(감춘 패널 안 등)은 수만 적는다.

  ```powershell
  Set-Location $e2e
  & $py -m streamlit run app.py --server.address 127.0.0.1 --server.port 8553 --server.headless true
  ```

  주소는 `http://127.0.0.1:8553` 이다. 끝나면 이 프로세스(명령줄에 `--server.port 8553`)만 끈다 — 사용자 앱이 아니다.

### 5) 끝내기

4) **설비 마스터 일부 열 붙여넣기 — 미리보기까지**(2026-10-10 사용자 결정). `가용설비 현황` → `RawData` 탭 → 입력.

6) **Space 이름 바꾸기 — `적용` 뒤 `모두 버리기`**(2026-10-10 사용자 결정). `적용` 은 DB 에 쓰지 않고 이 세션의 편집본에만 넣는다.

     바뀜/안 바뀜」).
   - 같은 칸에 다른 호기의 이름(도면이나 서랍에 보이는 것)을 적어 Enter → 바꾸지 않고 바로 알리는지(「겹친 이름 막음/안 막음」).
     `Esc` 로 고치던 글자를 버린다.

     같아 넓어지지 않을 수 있다. 그래도 넓어졌다면 지금 날짜가 조회 달 밖에 있는 호기가 있는 것이다), 축 양 끝에 잘려 붙은 ○·●

### 7-8. 마지막 — 앱을 끄고 개수로 확인한다

사용자에게 앱을 꺼 달라고(`Ctrl+C`) 한 다음 아래 한 줄을 돌린다. 두 DB 를 `read_only` 로 열고, 값은 찍히지 않고 개수만
나온다. 7-14 를 건너뛰었어도 이 줄은 돌린다. **끝나면 앱을 끈 채로 바로 8장을 돌린다.** 기대하는 꼴은 시뮬레이션 `0033` 이
걸린 뒤의 것이다. 줄은 직전(`202610081500`) 7-8 줄 끝에 이번 배포에서 `ref_copies` 하나를 더했다 — `ref_data` 의 리비전 표 14개 행 수의

```powershell

```

  쪽인지 가릴 수 없다. 이번 확인에서 이름을 바꾸지는 않는다.
- `ref_copies N` — `ref_data` 에 남은 리비전 표 14개 사본의 행 수 합. `0033` 은 **리비전 1 과 행 단위로 같은 사본만** 지우므로 모두
  같았다면 **`0`** 이다. **0 이 아니어도 결함이 아니다** — 리비전 1 과 한 행이라도 다르거나 리비전 1 이 없는 데이터셋의 사본은 다른 곳에
  없는 값일 수 있어 일부러 남긴다. 수를 그대로 적고 8-1 의 「`ref_data` 에 리비전 표 사본이 남은 데이터셋 … (사본 M행 — …)」 의 M 과
  같은지 본다. 1,484,071(`202610071831` 리뷰의 적용 전 수)에 가까우면 `0033` 이 걸리지 않은 것이다 — `migration` 이 33 인지 먼저 본다.
- **직전 값(2026-10-10, `202610081500` 리뷰)** — `migration 31 equipment_migration 21 shortening_filter [0, 0] baselines [0, 0, 0]
  advance_shipment [1, 3] thresholds [1, 0] fab [1, 37] layout_marks 14 dup_names 0`(`ref_copies` 는 이번에 더했다).
- `duckdb.IOException` 이면 앱이 아직 떠 있다.

이 줄 다음에 **8장 「실데이터 확인」** 을 그대로 돌리고 출력 블록을 리뷰 문서 「실데이터 확인」 절에 붙인다(8-0 · 8-6).
앱은 끈 채로 둔다. 8-1 · 8-2 · 8-4 · 8-5 는 이번 배포에서 꼴이 바뀌어 직전 리뷰와 견줄 수 없으니 「같음」 한 줄로 줄이지 않고 그대로
붙인다(8-3 은 같으면 줄여도 된다). 그 뒤 7-7 을 알린다.

## 8. 실데이터 확인 (배포마다 반복)

**이 장은 배포마다 그대로 쓴다.** 7장은 그 배포 하나만의 확인이지만, 이 장은 stamp 와 상관없이 매번
같은 명령을 돌린다. 사외에는 합성 표본밖에 없어 답이 안 나오는 질문이 있다 — 기존 앱 결과와 신규 계산이
맞는지, 원천 `RQ_REQB` 의 소요기준이 어떻게 갈리는지, BigDataQuery 의 등록일이 어떤 꼴인지 같은 것이다
(`docs/TODO.md` 의 「사내 실데이터 확인 절차 준비됨 — 결과 대기」 항목). 사내에서
`scripts/inspect_real_data_checks.py` 로 재고, **개수·비율·dtype·초만** 리뷰 문서로 돌려보낸다. 그 결과를
보고 사용자와 사외가 다음 일을 대화로 정한다(2026-10-06 사용자 결정).

이 스크립트는 **읽기만 한다** — 두 DB 를 `read_only` 로 열고, 출력에는 제품·고객·공정·설비·시나리오
이름과 시뮬레이션 코드, 키별 값, 오류 원문이 나오지 않는다. 그래서 출력 블록은 **고치지 않고 그대로**
리뷰 문서에 붙인다. 사내에서 찍힌 수는 실데이터 집계라 사외가 그대로 근거로 쓴다.

### 8-0. 언제 · 무엇을 치나

**7장(그 배포의 확인)을 마친 뒤, 앱을 끈 채로 돌린다.** 앱이 떠 있으면 「DB 를 열지 못했습니다. 앱이 떠
있으면 먼저 끄세요 …」 한 줄을 찍고 멈춘다(종료 코드 1) — 사용자에게 `Ctrl+C` 를 부탁하고 다시 친다.
앱이 꺼져 있는데도 그 줄이 나오면 파일 손상일 수 있다 — 고치려 하지 말고 그 사실을 리뷰 문서에 적는다.
설비 DB 는 `가용설비 현황` 을 한 번 연 뒤라야 마이그레이션이 다 걸려 있다(4-2). 7장을 했다면 이미 걸렸다.

```powershell
uv run --no-sync python scripts/inspect_real_data_checks.py --output $HOME/real_data_check.md
uv run --no-sync python scripts/inspect_real_data_checks.py --only bdq --output $HOME/real_data_check_bdq.md
```

**이 두 줄은 처음부터 사용자에게 준다**(`! ` 를 앞에 붙여 치게) — 에이전트의 권한 판단이 이 스크립트를 매번 막았다(6장).
사용자가 친 뒤 에이전트는 두 `--output` 파일을 읽어 리뷰 문서에 옮긴다. 파일은 저장소 밖이라 커밋되지 않는다.

- **첫 줄** — DB 확인 넷(8-1 ~ 8-4). 사내 원천 크기에 따라 수십 초 ~ 몇 분이다(가장 최근 데이터셋의 원천을
  읽어 부하량·소요대수를 다시 계산한다).
- **둘째 줄** — BigDataQuery(8-5). 사내 DB 에 직접 묻는다. WebIDE 처럼 요청자 계정이 필요한 환경이면 먼저
  `export CAPA_BDQ_USER_NAME="<AD 계정>"` 을 넣은 셸에서 친다
  ([`bigdataquery_webide_setup.md`](bigdataquery_webide_setup.md)). 묻는 것은 기본값에서 — 목록 조회 두
  번(오늘−30일 ~ 오늘, 366일), 전 코드 적재일 GROUP BY 한 번, 표본 다섯 코드마다 상세 조회 두 번·적재일
  조회 한 번, 사본 확인(여러 날 코드 둘 × 적재일 조회 한 번·하루치 상세 조회 넷 = 하루치 상세 **최대
  8번**)이다 — 상세 조회는 모두 최대 18번(표본 10 · 사본 8)이고 적재일 조회가 최대 7번이다. 사내 상세 조회 한 번이
  3~26초라(`202610081500` 리뷰) 상세만 1~8분이고, 전 코드 GROUP BY 와 적재일 조회는 사내에서 잰 적이 없어 **10분
  안팎, 길면 20분**으로 잡는다. 리뷰 문서의 「걸린 시간」 줄에 실제 분을 적는다(직전 리뷰는 적지 않았다). 줄이는 법 —
  366일 목록이 너무 오래 걸리면 `--bdq-no-max-window`, 표본을 줄이려면 `--bdq-sample 2`(`0` 이면 표본
  적재일과 사본 확인을 모두 건너뛴다), 사본 확인을 줄이려면 `--bdq-copy-codes 1` · `--bdq-copy-days 2`
  (0 이면 끈다), 전 코드 GROUP BY 를 빼려면 `--bdq-no-code-days`. 붙였으면 리뷰 문서의 「돌린 명령」 줄에
  적는다.
- **블록은 끝나는 대로 찍힌다.** `--output` 파일은 시작할 때 비우고 머리 한 줄부터 쓴 뒤, 화면과 함께
  블록(8-5 는 표 머리·줄)마다 바로 덧붙인다. 시간 제한이나 `Ctrl+C` 로 멈춰도 앞 블록은 남고 끝에
  「`8-x` 블록이 멈췄다 — …」 한 줄이 붙는다 — 남은 것까지 그대로 붙인다.
- 하나만 다시 볼 때는 `--only env` · `legacy` · `reqb` · `equipment` 를 쉼표로 고른다. 다른 데이터셋을
  보려면 `--dataset-id <ID>`(ID 는 앱이 만든 무작위 값이라 적어도 된다). 고르지 않으면 원천에서 온
  데이터셋 가운데 가장 최근 것을 본다 — 복제·월 병합·연도 이동으로 만든 데이터셋은 건너뛴다.
- 출력은 Markdown 이다. 처음부터 끝까지 리뷰 문서에 붙인다(8-6). 표가 넓어 터미널 스크롤에서 잘리면
  `--output` 으로 **저장소 밖** 파일에도 받아 거기서 복사한다 — 예: `--output $HOME/real_data_check.md`,
  `--only bdq --output $HOME/real_data_check_bdq.md`. 저장소 안(`review/` 포함)에 따로 두지 않는다.

각 블록에서 「읽지 못함」·「실패(예외 종류)」 가 나와도 **스크립트는 다음 블록으로 계속한다.** 실패한 줄도
그대로 옮긴다 — 그것도 사외에는 답이다.

### 8-1. `env` — 두 DB 와 적용 배포

- `적용 배포` — `.deploy/applied.json` 의 stamp 와 사외 커밋. 2-3 에서 적용한 ZIP 과 같아야 한다.
- `마이그레이션 … (최고 N · 코드 M, …)` — **「코드와 같다」가 정상이다.** 「코드보다 낮다」면 그 DB 를 여는
  화면을 열지 않은 것이다(4-2) — 앱을 띄워 HOME 과 `가용설비 현황` 을 연 뒤 끄고 다시 돌린다. 「코드보다
  높다」면 옛 ZIP 을 적용했을 수 있다 — 그대로 적는다.
- 행 수 표 — 데이터셋·시나리오·리비전·공식버전·원천 행 수와 데이터셋 원천 종류(`BIGDATAQUERY` 등 앱이 붙인
  이름).
- `ref_data 에 리비전 표 사본이 남은 데이터셋` — 2026-10-06 결정(B3) 전에 만든 데이터셋은 리비전 표 14개를 리비전 1
  과 `ref_data` 에 두 번 들고 있었다(읽는 곳은 없다). 시뮬레이션 `0033`(2026-10-10 사용자 승인)이 **리비전 1 과 행
  단위로 같은 사본만** 지운다. 줄 끝이 「리비전 1 과 달라 `0033` 이 남긴 사본. 0 이 아니어도 결함 아님」이면 남은 수는
  일부러 남긴 것이다 — 다른 곳에 없는 값일 수 있다. 「`0033` 적용 전 — …」 이면 앱이 아직 `0033` 을 걸지 않은 것이다(4-2).
  `사본 M행` 은 7-8 의 `ref_copies` 와 같다. 지운 자리는 파일 안 빈 블록으로 돌아갈 뿐 **DB 파일 크기는 줄지 않는다** —
  공간을 돌려받는 재구축은 하지 않았다(결함 아님).

### 8-2. `legacy` — 기존 결과 대조

원천 Core Data 에는 기존 앱이 계산해 실어 보낸 값(`WF수(매)` 등)이 그대로 있다. 이 블록은 그 값과 이
앱의 계산을 맞대어 **차이의 분포**만 찍는다. 기준은 가장 최근에 적재한 데이터셋의 원천과 그 시나리오의
**리비전 1**(원천 그대로)이다 — 사내에서 고친 리비전은 대조에 들지 않는다.

- **원천 컬럼 표** — 여섯 컬럼이 얼마나 차 있는지. 대조할 컬럼이 비어 있으면 그 아래 대조는 「비어 있어
  대조 불가」로 끝난다. **그것도 답이다**(사외 표본은 `소요대수` 가 비어 있다). `GOOD_DIE` 는 채움만 본다 —
  부하량이 아니라 대조하지 않는다(2026-10-08 결정).
- **부하량 표**(`WF수(매)`·`EQ(억Gb)`·`Plan_Chip(K개)`) — 키마다 |신규 − 기존| ÷ |기존|. Wafer·Density 는
  `월 × 제품정보 × Stack × WF 구분`, Chip 은 계획 줄(Pack Code 합산) × WF 구분으로 맞댄다(Chip 은
  `202610071831` 리뷰의 비율 탐색에서 1,264키 중 1,248키 ≈1 이라 정식 대조로 올렸다).
  - `차이율 중앙`·`p95`·`최대`, `>0.1%`·`>1%` 는 그 비율을 넘는 키 수다. **최대가 0.5% 안이면 산식이 맞다.**
  - `기존 0·신규 있음` — 기존이 0 을 적은 키(비율을 구할 수 없다). 사외 표본에서는 전부 `WF 구분 = Dummy`
    였다 — 기존 앱이 Dummy Wafer 를 0 으로 두었다는 뜻이다.
  - `값 불일치` — 기존 값이 계획 줄 × WF 구분 안에서 경로마다 갈려 접을 수 없었던 키. 0 이 아니면 대조
    단위를 다시 설계해야 한다는 신호다. Wafer 는 그래서 아래 경로 값 절이 따른다.
  - `신규에만`·`기존에만` — 한쪽에만 있는 키. `기존에만` 이 0 이 아니면 신규가 놓친 자리가 있다.
- **Wafer `WF수(매)` 경로 값** — `202610071831` 리뷰에서 Wafer 296키 가운데 287키가 `값 불일치` 였다. 같은
  계획 줄 × WF 구분 안에서도 경로 행마다 `WF수(매)` 가 갈린다 — 계획 줄 값이 아니라 **경로 값**이다. 위 계획
  줄 표는 연속성으로 남기고 경로 단위로 다시 본다(2026-10-10 결정). 신규 계산에는 경로마다 갈리는 Wafer
  값이 없다 — WF 경로의 `부하량` 은 계획 줄 Wafer 부하량 그대로이고, 측정률은 대당 Capa 의 분모로만 든다.
  그래서 원천 경로 값이 **무엇으로 갈리는지**를 개수로 가른다.
  - 첫 줄 — 계획 줄 × WF 구분 칸 수와 그 가운데 갈리는 칸(위 `값 불일치` 가 여기서 난다), 경로 행·양수만
    남겨 ±0.1% 를 넘게 갈리는 칸. 앞이 뒤보다 크면 그 차는 계획 행(Area_Name 빈 행)이나 0 값이 만든 갈림이다.
    아래 두 표는 뒤의 칸만 본다.
  - **무엇이 가르나 표** — 갈리는 칸 안에서 소요기준·Main/MI·공정·STEP·MCP·Step수·Para 값마다
    `WF수(매)` 가 한 값이면 `가름`. `소요기준` 이 가르면 WF·CHIP·PKG 경로가 서로 다른 값을 싣는 것이다.
    공정·STEP 처럼 경로마다 다른 칸은 대개 `자명`(저절로 갈린 것이라 증거가 못 된다).
  - **나누거나 곱하면 한 값이 되나 표** — 후보 경로 칸(측정률 둘과 그 곱·Side반영률·MCP_Chip_Ratio·
    CUM_수율·Step수·Para·Shot수)마다, 갈리는 칸에서 `WF수(매) ÷ 그 칸` 이 한 값이 되는 칸 수. **`÷ 로 한 값`
    이 `값이 다 있는 칸` − `칸 안에서 한 값` 과 같으면 원천 경로 값 = 계획 줄 값 × 그 칸이다.** 칸 안의 비만
    보므로 그 칸이 % 로 적혔든 비율로 적혔든 상관없다. `× 로 한 값` 이면 계획 줄 값 ÷ 그 칸(수율 같은 칸).
    `칸 안에서 한 값` 이 `값이 다 있는 칸` 과 같으면 그 칸은 가르지 못한다.
  - **결과 칸 표** — `일 필요`·`TEST WF수(매)` 는 기존 시스템이 경로마다 실어 보낸 **결과**라 원천 경로 값에서
    만들어졌을 수 있다(인과 방향을 모른다). 그래서 후보와 따로 센다. `TEST WF수(매)` 는 같은 단위(매)라
    빼기·더하기로 본다. `값과 같은 칸` 은 그 칸이 곧 경로 값인 칸이라 나머지 칸에서 뺐다.
  - **주의 — 「한 값이 된다」·「따라간다」는 같이 움직인다는 뜻이지 원인이라는 뜻이 아니다.** 원천 경로 값이 그
    칸에서 만들어졌을 수도, 그 칸이 원천 경로 값에서 만들어졌을 수도 있다. 결론은 사외가 사용자와 정한다.
  - **경로 키 13 맞대기** — 소요기준 WF 경로만 원천 `WF수(매)` 를 신규 `부하량`(둘째 줄은 `× Lot 측정률 ×
    WF측정률`, 소요대수가 실제로 나누는 부하)과 소요대수와 같은 접기로 맞댄다. 한 줄의 차이율이 0 에 붙으면
    그 줄의 신규 값이 원천 경로 값의 정의다.
  - **기존÷신규가 경로 칸을 따라가나 표** — 경로 키마다 기존÷신규 를 그 칸 값과 견준다(**이 표의 ≈ 는
    ±0.1%**). `칸 ≠1 인 키` 가운데 `≈ 칸` 이 거의 전부면 원천 경로 값 = 신규 계획 줄 Wafer × 그 칸이다 — 사외가
    신규 쪽에 그 칸을 곱한 경로 값을 만들어 정식 대조로 올린다. `≈ 1÷칸` 이면 나눈 것이고, `≈1` 이 거의
    전부면 그 칸과 무관하다. 어느 칸도 따라가지 않으면 그대로 옮긴다 — 사외가 다른 후보를 더한다.
- **소요대수** — 먼저 `키 연결` 줄(신규 경로 키 가운데 원천 경로에도 있는 키의 비율, **100% 가 정상**).
  원천에 값이 있으면 세 줄로 대조한다. 기존 값이 경로 행마다 어떻게 실리는지 사외가 모르기 때문이다.
  - `경로 키 13 · 같은 경로 반복을 접음` / `월×공정×소요기준 · 접음` — 같은 경로에 반복된 값을 한 번만 센다.
  - `월×공정×소요기준 · 접지 않고 행마다 더함` — 원천 행마다 따로 더한다.
  - 둘 중 **한쪽만 맞으면 그쪽이 원천의 실리는 방식**이다. `└ 접음 · 소요기준 …` 줄은 소요기준별로 나눈
    것이다 — PKG 만 어긋나면 「PKG 는 Buffer 로만 센다」(6장 표) 규칙 차이다.
- **소요대수 ≈60 배 가르기** — `202610071831`·`202610080745` 리뷰에서 경로 키 절반이 기존 = 신규 × 60 이었다
  (분↔시간 같은 단위 어긋남으로 보이나 **어느 쪽이 틀렸는지 모른다**). `경로 키 13` 대조의 키를 기존÷신규
  `≈60`·`≈1`(각 ±5%)·`그 밖` 세 무리로 나눠 개수와 분포로만 가른다. ≈60 무리가 없으면 한 줄로 끝난다.
  - 첫 줄 — 무리별 키 수와 `60 ±0.1% 안`(딱 60 이면 단위 상수, 퍼져 있으면 다른 원인이다).
  - **속성 표** — 무리마다 소요기준·Main/MI 경로·WF 구분별 키 수. 한 줄에 몰리면 그 속성이 가른다. WF 구분은
    계약 어휘(`BUFFER`·`CORE` 등)만 이름을 적고 나머지는 `그 밖(n종)` 이다.
  - **공정 줄** — 키가 전부 ≈60 · 전부 ≈1 · 섞인 공정 수. 섞인 공정이 있으면 **가르는 칸 표**가 따른다 —
    공정 안에서 그 칸(달·제품·Stack·STEP·설비 `메이커`·`모델명` 등) 값마다 무리가 하나뿐이면 `가름`.
  - **산식 인자 표** — 소요대수 산식의 인자(부하량·구분_Chip·Net Die·수율·UPEH·ST·CAPA_RUN_RATE·편중률·
    모듈수·RUN_DAY·측정률)마다 무리별 p5·중앙·p95 와 `중앙 ≈60÷≈1`(60 이나 0.0167 근처면 그 인자가 단위째
    다르다). 부하량은 물량이라 비만 찍는다. `60 배로 고침` 은 그 인자 값 가운데 ≈1 키가 쓰지 않는 값만 60 배로
    고쳐 다시 계산했을 때 ≈1 이 되는 ≈60 키, `같이 어긋남` 은 ≈60 키가 쓰는 값을 모두 고치면 함께 ≈1 을
    벗어나는 ≈1 키다 — **고침이 전부이고 어긋남이 0 인 인자만** 혼자서 60 배를 설명한다. 아래 `원천 …` 줄은
    기존 시스템이 실어 보낸 값(`일 필요`·`Side반영률`·`MCP_Chip_Ratio`)이다.
  - **원천 범주 칸 표** — `메이커`·`모델명`·`Para`·`Step수`·`Shot Time`·`Shot수`·`Index Time` 의 무리별 값
    종류 수와 겹침. 값은 찍지 않는다.
- **PCB수(K매)** — 신규 계산이 없다(산식 미구현). 값이 계획 줄 단위인지(`갈리는 칸 0`)와 `생산수량 ÷
  PCB수(K매)`(PCB 한 매당 Unit)의 분포만 본다.

### 8-3. `reqb` — 원천 RQ_REQB 소요기준 분포

리비전 1 의 `RQ_REQB` 를 소요기준(`PKG`·`CHIP`·`WF`·`BOX`·`PCB`)마다 센다 — 행 수, 공정 수, `Main`·`MI`
공정 수, WF 구분이 하나뿐인 공정과 그 하나가 `BUFFER` 인 공정. 사외가 표본 생성기의 공정 목록을 업무
사실로 잘못 읽은 적이 있어(`docs/TODO.md` 3-5 「Stack 이후 Wafer 공정」) **실데이터로 다시 센다.**

- `그 밖의 소요기준 N종` — 계약 밖 이름이다. 이름은 찍지 않는다. 0 이 아니면 그대로 적는다.
- `소요기준이 둘 이상인 공정` — 업무 규칙상 **0** 이어야 한다(한 공정은 한 소요기준).

### 8-4. `equipment` — 설비 DB

최신 설비 리비전에서 세 가지를 센다. **값은 고치지 않는다** — 고칠 행이 있으면 사용자가 `가용설비 현황`
RawData 에서 고쳐 저장한다. 에이전트는 수만 적는다.

- `Qual일정 = 2262-04-11` — 옛 리비전 변환이 빈 Qual 을 먼 미래로 채우던 자리표다. 이제는 빈 Qual 로 읽혀
  「일정 미정」에 잡힌다. 사용자가 Qual 날짜를 넣어야 할 행 수다.
- `모듈 행 환산비 0.2` — 직접 편집 칸이 0.25 를 0.2 로 자르던 결함의 흔적이다. **사용자가 다시 입력할 행**이다.
  `Main 설비 없이 환산비 0.2` 는 Main 설비를 적기 전의 모듈일 수 있다. `묶음 / 합이 1 이 아닌 묶음` 의 둘째
  수가 0 이 아니면 그 설비의 능력이 한 대가 안 되게 세어지고 있다.
- `일정 미정` — 반입·Qual 일정이 비어 가용대수에 들지 못하는 설비 대수. `가용설비 현황` 의 「일정 미정 N대」
  알림과 같은 셈이다(사용기준이 HBM·EDP 인 행만 센다). 「건너뜀: 설비 DB 마이그레이션이 코드보다 낮다」면 8-0 대로 화면을 연 뒤
  다시 돌린다.
- `사용기준` — 최신 리비전 설비 마스터의 사용기준이 `HBM` 인 행·`EDP` 인 행(따로 센다)·다른 값인 행·빈 칸인 행의 수와, 그
  때문에 Dynamic 가용대수에서 빠지는 설비 대수(설비 전체 대수 중). Dynamic 은 사용기준이 HBM·EDP 인 호기만 한 가용대수로 센다
  (2026-10-08 사용자 결정). 세는 값 둘의 이름 말고 사용기준 글자 자체는 찍지 않는다. 빈 칸이 많으면 옛 리비전에서 사용기준을 채우지 않은 것이다 — 사용자에게 알린다(`202610080745` 리뷰가 알렸다). 이 줄은
  계약 상수 `HBM` 을 실으므로 5장 자가 점검에 걸린다 — **고치지 않고 그대로 둔다**(8-6).

### 8-5. `bdq` — BigDataQuery

- `준비` 줄 — 패키지·SQL·요청자 계정(값은 찍지 않고 있음/없음만). 「패키지가 없다」면 4-1 의 되돌리기,
  「요청자 계정 필요」면 8-0 의 `export` 를 넣고 새 셸에서 다시 친다.
- **목록 조회 표** — 기간마다 성공 여부, 걸린 초, 목록 행 수(`SELECT DISTINCT` 결과), 코드·PLAN 수, 코드 수,
  화면이 느려지는 3,000 을 넘는지. 기본 기간(오늘−30일 ~ 오늘)은 `BigDataQuery 등록` 화면의 첫 값과 같다.
- **`reg_date`** — dtype, 값의 종류, 숫자면 자릿수, 문자열이면 꼴(숫자는 `9`, 영문은 `A` 로 바꾼 모양),
  원천 등록시각으로 읽지 못하는 값 수. 숫자형은 앱이 일부러 버린다(1970 년으로 읽히는 것을 막는다).
  `코드·PLAN 하나의 서로 다른 등록시각 수` 가 1 보다 크면 `reg_date` 가 행 단위 적재 시각이다.
- **`catb_sim_info_id` 규칙 위반** — `^[A-Za-z0-9._-]+$` 를 벗어나 화면에서 저장이 막히는 코드 수와 까닭의
  종류.
- **전 코드 적재일 표** — 목록 창(366일, `--bdq-no-max-window` 면 31일) 안의 규칙을 지키는 **모든 코드**를
  GROUP BY 한 번으로 세어 분포만 찍는다(코드는 찍지 않는다). 이것도 **사외에서 돌려 보지 못한 SQL** 이라
  실패하면 그 한 줄만 남고 나머지는 계속된다.
  - `적재일 1일 · 2–5일 · 6일 이상` — 1일이 거의 전부면 여러 날 적재는 드문 예외다.
  - `여러 날 코드의 적재일 수 ÷ 폭` — 1 에 붙으면 하루도 빠짐없이 매일 적재한 것이다. `끝 적재일이 목록 창
    끝날(오늘)인 코드` 는 지금도 매일 다시 적재되고 있는 코드다.
  - `여러 날 코드가 차지하는 행` — 원천 테이블 행 가운데 그런 코드의 몫. 크면 기본 창의 득실이 크다.
- **표본 적재일 표** — 규칙을 지키는 코드 가운데 첫 등록일 순으로 고르게 다섯을 골라, 상세 조회 기본 창
  (원천 등록일 −7 ~ +3일)과 넓은 창(±30일)의 행 수를 견준다. **`기본 창 행 = 넓은 창 행` 이 전부면 기본
  창으로 충분하다.** `기본 창이 놓친 행` 이 0 이 아니면 사외가 기본 창을 넓힐지, 같은 코드를 다시 받는 길을
  둘지 정한다(`docs/TODO.md` 결정 대기) — 그 판단은 아래 사본 표가 한다. 아래 적재일 줄은 **사외에서 돌려
  보지 못한 SQL**(적재 시각의 날짜별 행 수)이다 — 사내 엔진이 받지 않으면 「조회 실패(예외 종류)」 한 줄만
  남고 나머지는 계속된다.
- **여러 날 적재 — 날마다 무엇이 같고 다른가** — `202610081500` 리뷰에서 표본 한 코드가 32일 동안 적재돼
  기본 창이 그 코드 행의 84.38% 를 놓쳤다. 84.38% 는 정확히 1 − 5/32 라 **매일 같은 크기로 통째 다시 적재된
  꼴**이다. 놓친 것이 사본인지, 나눠 실은 것인지, 값이 바뀐 것인지를 가를 **사실**을 찍는다.
  **판정은 사외가 한다 — 에이전트는 수만 옮긴다.** (자동 판정은 갈래마다 반례가 있어 뺐다.)
  - 고르는 것 — 표본의 여러 날 코드(적재일이 많은 순)를 먼저, 모자라면 전 코드 표의 여러 날 코드에서 고르게
    채워 **최대 둘**(`--bdq-copy-codes`). 코드마다 **최대 넷**(`--bdq-copy-days`)의 날을 앱과 같은 상세 SQL 로
    하루씩 다시 받는다 — 기준 날 → 끝 앞날 → 첫 적재일 → 그 사이 차례로 고른다.
  - **기준 날** — 끝 적재일. 끝 적재일이 **오늘**이면 아직 적재 중일 수 있어 오늘을 먼저 빼고 「오늘 전 마지막
    적재일」을 기준 날로 삼는다. 오늘은 `--bdq-copy-days` 가 3 이상일 때만 견주는 날로 넣고 `오늘 — 적재 중일
    수 있음` 을 단다. 전 코드 표가 실패해 등록일 창으로만 셌는데 기준 날이 창 끝날이면 코드 줄에 「기준 날이 창
    끝날에 닿음」 이 붙는다(창 밖에 더 뒤 적재가 있을 수 있다).
  - 코드마다 머리 한 줄(`- 코드 n · 표본|여러 날 코드 더함 — 적재일 · 날별 행 최소 · 중앙 · 최대 · 기준 날`)과
    고른 날마다 한 줄의 표가 찍힌다. 코드는 번호로만 적는다. `자리` 의 `(k/n)` 은 그날이 n 개 적재일 가운데
    몇째인지다 — 고른 날이 창의 어디에 있는지 본다.
  - 견주는 단위 — **계획 줄 키**(`RQ_PKG_PLAN` 업무 키)와 **가장 잘게 나눈 키**(계획 줄 키 ∪ 경로 키 13,
    `Pack Code` 포함 — 원천이 Pack Code 마다 같은 경로를 되풀이한다). 키 칸이 하나라도 없으면 그 키로 세지 않고
    `칸 없음` 이라고 찍는다. 행은 **RQ 16 표가 읽는 업무 칸**으로만 견준다(`기준정보년월`·기존 결과 `WF수(매)`
    같은 칸만 바뀐 행은 따로 센다). 숫자 칸은 숫자로 맞춰 견주고 글자 칸은 글자 그대로 견준다.

  | 칸 | 무엇을 세나 | 이런 꼴이면 의심한다(행동 지시가 아니다) |
  |---|---|---|
  | `행` · `고유 행(업무 칸)` | 그날 받은 행, 업무 칸이 같은 행을 하나로 접은 수 | `고유 행` 이 `행` 보다 크게 작으면 같은 날 같은 내용을 여러 번 실었다 |
  | `계획 줄 키` · `가장 잘게 나눈 키` | 그날의 키 수(기준 날 줄은 기준 날 자체의 수) | 날마다 크게 다르면 날마다 다른 범위를 실었다 |
  | `그날에만 있는 키 — 계획 줄 · 잘게` | 그날엔 있고 기준 날엔 없는 키 | 이것만 0 이 아니면 **나눠 적재**(날마다 다른 계획 줄·경로) 또는 **뒤 적재에서 빠짐**을 의심한다 — 그날이 첫 적재일이면 기준 날이 키를 잃었을 수 있다 |
  | `기준 날에만 있는 키 — 계획 줄 · 잘게` | 기준 날엔 있고 그날엔 없는 키 | 이것만 0 이 아니면 **누적 적재**(앞 날이 기준 날의 일부)를 의심한다. 그날에만·기준 날에만이 둘 다 있으면 **나눠 적재**다 |
  | `두 날 모두 있는 키 가운데 행이 다른 키` | 같은 가장 잘게 나눈 키의 업무 칸 행이 두 날에 다른 키 | **값 바뀜**(다시 계산해 다시 실음)을 의심한다. 방향은 없다 — 어느 날이 맞는지 이 칸으로는 모른다 |
  | `업무 칸은 같고 그 밖 칸만 다른 행` | 업무 칸으로는 기준 날에 있는데 모든 칸으로는 없는 행 | 계산에 들지 않는 스냅샷 칸만 흔들렸다 — 계산 결과는 같다 |
  | `하루 안 충돌 키` | 그날 안에서 같은 가장 잘게 나눈 키에 업무 칸이 다른 행이 둘 이상인 키 | **같은 날 두 번 적재**(다른 값으로)를 의심한다 — 그날 하나만 받아도 업무 키 충돌이 난다 |

  - **날마다 모든 견준 칸이 0 이면 통째 사본**으로 읽힌다 — 기본 창이 놓친 행은 사본이다. 그 밖의 꼴은 수 그대로
    옮기면 사외가 사용자와 창(그대로·끝 적재일을 덮게·넓히기·최신 적재만)을 정한다.
  - 기준 날의 `행` 이 다른 날보다 크게 작으면 그날 적재가 덜 끝났을 수 있다 — 사내 메모에 적고 다음 배포에 다시
    본다.

### 8-6. 리뷰 문서에 옮기는 법

리뷰 문서(5장) 끝에 아래 절을 더하고, 출력 블록 `8-1` ~ `8-5` 를 **그대로** 붙인다. 블록 제목(`### 8-1. …`)
까지 함께 붙인다 — 사외는 그 제목으로 블록을 찾는다.

```markdown
## 5. 실데이터 확인 (런북 8장)

- 돌린 명령 : `inspect_real_data_checks.py` · `inspect_real_data_checks.py --only bdq` (붙인 옵션: 없음)
- 돌린 때 : 7장 뒤 · 앱 끔 · <YYYY-MM-DD HH:MM KST>
- 걸린 시간 : DB 넷 <N초> · BigDataQuery <N분>
- 출력은 고치지 않고 붙였다 · 더한 것은 아래 「사내 메모」 뿐이다 : 확인함 ☐

### 사내 메모 (선택)
```

### 8-7. 하지 않는 것

- **DB 를 SQL 로 고치지 않는다.** 2262-04-11 자리표·환산비 0.2·`ref_data` 사본이 보여도 그대로 둔다 — 리비전은
  append-only 이고, 고칠 길은 사용자가 화면에서 저장하거나 사외가 후속 마이그레이션을 만드는 것뿐이다.
- **스크립트를 고치지 않는다**(0장). 출력이 이상하거나 실패하면 그 줄을 그대로 적는다.
- **출력에 없는 값을 더 찾아 적지 않는다.** 「어느 제품이 어긋났나」·「어느 코드가 규칙을 어겼나」가 궁금해도
  키별 값, 제품·공정·설비 이름, 시뮬레이션 코드, 오류 원문은 적지 않는다. 사외가 필요하면 가명 규칙(5장)으로
  따로 묻는다.
- **`scripts/compare_legacy_results.py` 를 대신 돌려 옮기지 않는다** — 그 스크립트는 허용을 넘은 키의 제품·
  Stack 을 그대로 찍는다(사외 디버깅용이다).
- **확인을 위해 쓰지 않는다** — 데이터셋을 새로 등록하거나 원천을 다시 받거나 리비전을 저장하지 않는다.
  앱을 띄운 채 돌리지 않는다.

### 8-8. 사외가 답하는 법

사외는 리뷰의 「실데이터 확인」 절을 블록마다 읽고 **사용자와 대화로** 다음 일을 정한다. 정한 것은 다음
배포의 7장(사내가 따로 할 일)과 `docs/TODO.md` 에 적는다. 예를 들면 —

- 8-2 에서 기존 결과 컬럼의 비율이 `≈1` 에 몰리면 대조 목록(`services/legacy_comparison.py` 의
  `COMPARISONS`)에 넣고, `≈1000` 이면 단위를 맞춘 뒤 넣는다(`Plan_Chip(K개)` 가 그렇게 들어갔다). 소요대수
  ≈60 배 가르기에서 혼자 60 배를 설명하는 인자나 속성이 나오면 어느 쪽 단위가 맞는지 사용자와 정한다.
- 8-4 에서 0.2 행이 있으면 사용자에게 다시 입력할 행 수를 알리는 문장을 7장에 싣는다.
- 8-5 에서 기본 창이 행을 놓치면 기본 창·같은 코드 다시 받기를 정한다.

**확인이 끝난 블록은 사외가 스크립트에서 빼고 이 장도 함께 고친다.** 새로 실데이터로만 답이 나오는 질문이
생기면 블록을 더한다. 사내는 이 장을 고치지 않는다.
