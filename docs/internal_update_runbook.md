# 사내 업데이트 실행 절차 (사내 에이전트용)

이 문서는 **사내(WebIDE)에서 배포 ZIP 을 받아 적용하는 한 번의 작업**을 처음부터 끝까지 적은
것이다. 위에서 아래로 그대로 따라가면 된다. 왜 이런 구조인지는 `docs/dual_env_workflow.md`
에 있고, 여기는 **무엇을 어떤 순서로 치는가**만 적는다.

**이 문서를 읽고 있다면 먼저 확인한다.**

```powershell
git remote -v
```

`github.com` 이 나오면 **사외(개발 PC)다 — 이 문서는 네 것이 아니다.** 사내 GitHub 주소가
나올 때만 아래를 따른다.

---

## 0. 사내에서 절대 하지 않는 것

- **소스를 고치지 않는다.** `app.py`·`app_pages/`·`src/`·`tests/`·`scripts/`·`config/`·
  `.streamlit/`·루트 문서 — 어느 것도 편집하지 않는다. 쓸 수 있는 곳은 `review/` 뿐이다.
- **`git clean -x` 를 쓰지 않는다.** `-x` 는 무시된 파일까지 지우고, 거기에 **운영 DuckDB 와
  `data/input` 실데이터**가 들어 있다. 한 글자 차이로 사내 데이터가 날아간다.
- **`uv sync` 를 맨 것으로 돌리지 않는다.** 락에 없는 `bigdataquery` 를 지운다.
  항상 `uv sync --inexact` 다.
- **정체불명 파일을 스스로 지우지 않는다.** 사용자에게 묻고 고른 대로 한다.
- **`.gitignore` 를 고치지 않는다.** 권한에서도 막혀 있다. 넣어야 할 것이 있으면 리뷰
  문서에 적어 사외가 넣게 한다.
- **`git push` 는 에이전트가 하지 않는다.** 권한에서 막혀 있다(`Bash(git push*)` deny).
  푸시가 필요한 자리에서는 사용자에게 명령을 알려 주고 사용자가 친다.

---

## 1. 시작 전 점검 (5분)

### 1-1. 앱을 끈다

```powershell
Get-Process python -ErrorAction SilentlyContinue | Where-Object { $_.Path -like "*streamlit_project*" }
```

떠 있으면 그 창에서 `Ctrl+C`. **DuckDB 는 프로세스 배타 잠금이라 앱이 살아 있으면 이후
검증·마이그레이션이 전부 `duckdb.IOException` 으로 죽는다.** 적용기 자체는 DB 를 열지 않지만
적용 뒤 확인이 막히므로 먼저 끈다.

### 1-2. 쓰기 권한이 실제로 열리는지 한 번 본다

리뷰 문서를 못 쓰면 이번 작업의 산출물이 아예 나오지 않는다. 먼저 확인한다.

```powershell
New-Item -ItemType Directory -Force review | Out-Null
```

그리고 `review/_permission_test.md` 에 아무 한 줄이나 써 본다. 잘 써지면 그 파일은 지우고
넘어간다.

**막히면 거기서 멈추고** 사용자에게 아래를 그대로 알린다 — 사외가 고쳐야 한다.

> 사내 `.claude/settings.json` 의 `Edit(*.md)` deny 가 `review/` 까지 막고 있습니다.
> 슬래시 없는 패턴은 gitignore 의미라 모든 깊이에 걸립니다. `Edit(/*.md)` 로 앵커하고
> allow 에 `Edit(review/**)` 를 더해야 합니다. **deny 는 allow 로 뚫을 수 없으므로**
> deny 쪽을 좁히는 것 말고는 방법이 없습니다.

설정 파일이 `docs/internal_claude_settings.json` 템플릿의 최신본과 같은지도 함께 본다 —
`.claude/` 는 배포가 덮지 않으므로 옛 템플릿이 남아 있을 수 있다.

### 1-3. 운영 데이터를 저장소 밖으로 복사한다

**건너뛰지 않는다.** 아래 두 가지는 적용이 덮거나 지울 수 있다.

```powershell
$backup = "$HOME\deploy_backup\$(Get-Date -Format yyyyMMddHHmm)"
New-Item -ItemType Directory -Force $backup | Out-Null
Copy-Item data\*.duckdb $backup -ErrorAction SilentlyContinue
Copy-Item data\input\* $backup -Recurse -ErrorAction SilentlyContinue
```

`data/input/` 을 함께 챙기는 것은 보수적으로 두는 것이다. **배포 세트는 `data/input/` 아래를
보내지 않으므로**(`build_deploy_package.py` 의 `FORBIDDEN_PREFIXES`) 적용이 덮을 일은 없다.
다만 적용기의 `is_protected` 는 **삭제만** 막고 덮어쓰기는 막지 않는 구조라, 규칙이 바뀌면
조용히 덮인다 — 무시 파일이라 `git checkout -- .` 로도 돌아오지 않는다.

### 1-4. 저장소에 있으면 안 되는 것이 커밋돼 있는지 먼저 본다

**이 순서를 바꾸지 않는다.** 다음 단계(1-5)가 「수정된 파일을 되돌려라」라고 시키는데,
운영 DuckDB 나 `data/input` 실데이터가 **추적된 상태**라면 그 되돌리기가 실데이터를 커밋된
옛 버전으로 덮는다. 무엇이 추적 중인지 모르는 채로 1-5 에 들어가면 안 된다.

```powershell
git ls-files | Select-String -Pattern '\.duckdb|\.db$|\.wal$|^data/input/|^data/output/|^data/temp/|^\.agents/|^\.omo/|\.xlsx?$|\.xlsb$|\.tmp$'
```

**한 줄이라도 나오면 여기서 멈춘다.** `docs/dual_env_workflow.md` 8장의 정리를 먼저 끝내야
한다(앱 종료 → DB 를 저장소 밖으로 복사 → `git rm -r --cached` → 커밋). 그 정리는 사람이
한다 — `git rm` 은 에이전트 권한에서 막혀 있다.

정리를 건너뛰고 적용하면 두 가지가 한꺼번에 일어난다. ① 그 파일들은 ZIP 에 없으므로
「사외에서 지워진 파일」로 판정돼 적용이 지운다. ② 1-5 의 되돌리기가 그 전에 실데이터를
덮는다.

### 1-5. 작업트리를 비운다

```powershell
git status --porcelain --untracked-files=no
```

**한 줄이라도 나오면 적용기가 멈춘다.** 사내에서 소스를 고쳤다면 커밋하지 말고 되돌린다.

```powershell
git checkout -- <경로>
```

**경로를 하나씩 확인하고 되돌린다.** `git checkout -- .` 처럼 전체를 쓰지 않는다. 경로에
`.duckdb`·`.wal`·`data/input`·`data/output`·`data/temp` 가 들어 있으면 **되돌리지 말고
사용자에게 알린다** — 그것은 소스 수정이 아니라 실데이터이고, 되돌리면 운영 데이터가
사라진다. 1-4 를 제대로 끝냈으면 이 목록에 그런 경로가 나올 수 없다.

`git checkout` 은 일부러 권한 allow 에 넣지 않았다. 매번 프롬프트가 떠서 **사람이 경로를
읽고 승인**하게 되어 있다.

되돌리기 전에 그 내용이 필요하면 리뷰 문서에 코드블록으로 옮겨 적는다 — 그것은 저장소 수정이
아니다. 아직 커밋하지 않은 `review/*.md` 가 있으면 **먼저 `review:` 로 커밋한다.** 그러지
않으면 이 단계에서 지워진다.

## 2. 적용 (본 작업)

### 2-1. 먼저 보기만 한다

```powershell
uv run --no-sync python scripts/apply_deploy_package.py <내려받은 ZIP 경로> --dry-run
```

**ZIP 경로는 슬래시로 쓴다** — `C:/Dev/.../202610021506.zip`. 에이전트의 셸이 Git Bash 면 역슬래시
(`C:\Dev\...`)가 사라져 「파일이 없다」로 끝난다(`202610021506` 리뷰). PowerShell 에서도 슬래시는
그대로 통한다.

`--dry-run` 은 **아무것도 바꾸지 않는다.** 깨끗한 작업트리도 요구하지 않는다. 출력에서 아래를
읽는다.

| 칸 | 뜻 | 할 일 |
|---|---|---|
| `사외에서 지워진 파일` | 추적 중인데 목록에 없다 | 적용이 지운다. 뜻밖의 것이 있으면 **여기서 멈추고** 사용자에게 묻는다 |
| `사내에만 있는 정체불명 파일` | 추적도 무시도 안 된다 | **스스로 지우지 않는다.** 아래 2-2 로 |
| `목록에 있는데 사내에 없는 파일` | 적용 전이면 정상 | ZIP 이 채운다 |

`--reconcile-only` 는 목록 대조만 본다(동작은 `--dry-run` 과 같은 자리에서 끝난다).

### 2-2. 정체불명 파일을 먼저 정리한다

**적용보다 먼저 한다.** 적용기의 커밋 단계는 이번 배포가 실제로 건드린 경로만 스테이징하므로
정체불명 파일을 빨아들이지는 않지만, 그래도 남겨 두면 다음 배포에서 다시 물어야 한다.

파일마다 사용자에게 묻고 셋 중 하나를 고른다.

1. **사내에서만 쓰는 것** → 그대로 둔다. `.gitignore` 에 넣을 필요가 있으면 **리뷰 문서에
   적어 사외가 넣게 한다** (사내에서 `.gitignore` 를 고치지 않는다)
2. **사외에도 있어야 하는 것** → 리뷰 문서에 적어 사외가 추가하게 한다
3. **옛 배포의 잔해** → 지운다

판단이 서지 않으면 (1)로 두고 리뷰 문서에 남긴다. 지우는 것은 되돌릴 수 없고, 남기는 것은
다음 배포에서 다시 물으면 된다.

**사내에서 쓴 기록 문서**(예: `HANDOFF_AUDIT_2026-09-17.md` — 사외 저장소에는 한 번도 없던 파일이다)는
(1)로 두는 대신 사용자에게 물어 **`review/` 로 옮겨 `review:` 로 커밋**하면 다음 배포부터 묻지 않는다.
`review/` 는 배포가 보내지도 지우지도 않는 사내 자리다. 옮기는 것도 사용자가 고른 뒤에만 한다.

아직 커밋하지 않은 `review/*.md` 가 있으면 **적용 전에 `review:` 로 먼저 커밋한다.**
`deploy:` 커밋과 섞이지 않게 하려는 것이다.

### 2-3. 적용한다

```powershell
uv run --no-sync python scripts/apply_deploy_package.py <내려받은 ZIP 경로>
```

끝나면 `deploy: <stamp> (<사외 커밋 7자>)` 로 자동 커밋된다.

**에이전트의 자동 권한 판단이 이 명령을 막으면** 같은 명령을 되풀이하지 않는다. 사용자에게 위 한 줄을
**ZIP 경로까지 채워(슬래시로)** 알려 주고, 사용자가 `! <명령>` 으로 직접 친 출력을 읽고 이어 간다
(`202610021506` 적용 때 두 번 막혀 이렇게 했다). 적용 결과의 대조·커밋은 스크립트가 같게 한다.

## 3. 적용 뒤 읽는 법 — 정상인데 이상해 보이는 두 줄

**이 둘은 결함이 아니다. 리뷰 문서에 결함으로 적지 않는다.**

### 3-1. `목록에 있는데 사내에 없는 파일` 은 비어 있어야 한다

적용 **뒤**에 이 칸에 무엇이든 있으면 이상이다(`해제가 덜 됐습니다`). 판정의 근거는 **바로
앞줄**이다.

```
대조    N/N 해시 일치
```

이 줄이 먼저 나왔으면 전 파일이 맞게 풀린 것이다.

> 예전 배포에서는 이 칸에 `data/input/RQ_DISPLAY_ORDER.csv` 한 줄이 **항상** 떴다. 그 파일이
> 배포 세트에 실리면서 동시에 `.gitignore` 에 걸려 대조가 쓰는 두 목록 어디에도 안 잡혔기
> 때문이다. 지금은 `data/input/` 아래를 아예 보내지 않으므로 그 오탐이 없다. 아직도 뜬다면
> **옛 ZIP 을 적용하고 있는 것이다.**

### 3-2. `pytest` 에서 `test_the_top_level_stays_the_declared_set` 실패

`['.deploy/', 'review/']` 때문에 실패하면 **옛 배포를 적용한 것이다.** 두 폴더는 사내에만
생기므로 사외에서는 재현되지 않고, 그래서 한동안 사내에서만 깨졌다. 지금 배포부터는 그 둘이
`INTERNAL_ONLY_TOP_LEVEL` 로 선언돼 있어 통과한다. 그래도 실패하면 **그 사실 자체를 리뷰
문서에 적는다.**

### 3-3. 루트의 `requirements.txt` 는 사내 WebIDE 컨테이너 전용이다

**손으로 적는 파일이 아니라 `uv.lock` 의 그림자다.** 개발 PC 와 CI 는 `uv sync` 로 잠금을
보지만, 사내 WebIDE 의 CI/CD 는 `docker/Dockerfile-prod` 로 이미지를 만들고 그 안에서
`pip install -r requirements.txt` 를 돈다. 둘이 갈라지면 **사내 컨테이너만 조용히 다른
버전을 쓴다** — 화면에 오류가 나지 않고 계산 결과만 달라질 수 있다.

- **사내에서 이 파일을 고치지 않는다.** `tests/test_requirements_export.py` 가 `uv.lock`
  과 대조하므로 고치면 검증에서 걸린다. 사외가 `uv export` 로 다시 뽑는다.
- **`uv sync` 를 이 파일로 대신하지 않는다.** 개발용 도구(ruff·mypy·pytest)가 빠져 있다.
- 이 파일에는 프로젝트 자신(`-e .`)이 **일부러 빠져 있다.** 그래서 컨테이너는
  `Dockerfile-prod` 의 `ENV PYTHONPATH=/project/src` 로 `src` 를 찾는다. 둘은 한 쌍이라
  한쪽만 보고 판단하지 않는다.

## 4. 적용 뒤 할 일

### 4-1. 의존성 — 변경 목록에 `pyproject.toml` 이나 `uv.lock` 이 있을 때만

```powershell
uv sync --inexact
```

맨 `uv sync` 는 `bigdataquery` 를 지운다. 지웠으면 되돌린다.

```powershell
uv pip install -r requirements-company.txt
```

### 4-2. 마이그레이션은 앱이 알아서 한다

앱을 한 번 띄우면 `data/capa_simulation.duckdb` 와 `data/equipment_availability.duckdb` 에
새 마이그레이션이 적용된다. **적용된 마이그레이션은 버전 번호로 체크섬을 대조하므로, 사내에서
SQL 파일을 고치면 앱이 시작조차 못 한다.**

**이 명령은 사용자가 친다.** 서버는 끄기 전까지 안 끝나므로 에이전트가 띄우면 세션이 거기서
멈춘다. 그리고 브라우저로 한 번 들어가야 마이그레이션이 실제로 걸린다.

**두 DB 는 걸리는 때가 다르다.** 시뮬레이션 DB 는 첫 화면(HOME)에서 걸리지만 설비 DB 는
연결을 처음 쓸 때 만든다 — **`가용설비 현황`(또는 `Space 현황`) 페이지를 실제로 열어야** 설비
마이그레이션이 적용된다. 설비 마이그레이션이 있는 배포면 그 페이지까지 열어 확인한다
(`202609281727` 리뷰의 지적).

```powershell
uv run --no-sync python -m streamlit run app.py
```

화면이 뜨는 것까지 확인하면 `Ctrl+C` 로 끈다. 오류가 나면 **고치지 말고** 리뷰 문서에 적는데,
**원문을 그대로 붙이지 않는다** — 이 앱의 오류 문구에는 설계상 공정명·제품명 같은 식별값이
박혀 있다. 5장의 가명화 규칙을 그대로 적용해 옮겨 적는다.

### 4-3. 네 관문을 돌린다

```powershell
uv run --no-sync python -m ruff format --check .
uv run --no-sync python -m ruff check .
uv run --no-sync python -m mypy
uv run --no-sync python -m pytest
```

**앱을 끈 뒤에 돌린다** — DuckDB 배타 잠금 때문이다. 실패가 나오면 3-2 에 해당하는지 먼저 보고,
아니면 리뷰 문서의 「발견」으로 적는다.

## 5. 리뷰 문서 쓰기 (이 작업의 산출물)

경로는 `review/<ZIP 파일명>.md` — 예: `review/202609201530.md`. 양식과 「실데이터를 적지
않는다」 규칙은 `docs/dual_env_workflow.md` 4장에 있다. 핵심만 옮기면:

- **값의 「꼴」은 남기고 식별자는 가명으로 쓴다.** 이 문서는 **사내에서 사외로 나가는
  유일한 것**이다.
- 좋음 — 「`Pack Code` 에 `4.00E+02` 꼴인 값이 2종, 5행」

  단추 **`Summary`** 가 선다(Guide 가 없는 화면에서는 테마 단추 왼쪽). 누르면 화면이 그 단추 속으로 접히며 요약이
  다시 조립된다. 모든 페이지에 서고, 같은 탭을 새로고침한 뒤에도 선다.
- 공식버전이 없거나 요약을 만들지 못하면 입장 화면의 `Summary` 가 흐리게 꺼지고(마우스를 올리면 까닭이 뜬다)
  헤더 `Summary` 도 서지 않는다 — 결함이 아니고 앱은 그대로 쓴다. 그 까닭을 원문 그대로 옮기지 않고 「꺼짐」으로만
  적는다.
- **한 탭에 한 번이다.** 같은 탭에서는 새로고침·헤더 `Dark`/`Light` 를 눌러도 입장 화면이 다시 뜨지 않는다. 새
  탭에서는 다시 뜬다. 입장 화면의 `Summary` 만 보고 `Detail` 을 누르지 않은 채 새로고침하면 다시 뜬다.
- 주소의 테마 인자(`?theme=`)가 없거나 그 브라우저에 저장된 테마와 다르면 앱이 처음에 한 번 새로고침한다.
  그동안은 **앱 바탕색 한 장만** 보이다가 새로고침 뒤 인트로가 시작한다 — 몇 초 빈 화면처럼 보여도 결함이
  아니다(최대 10초).
- HOME 이 아닌 화면 주소로 처음 들어가도 뜬다. 그때는 `요약` 다음 단계들이 실행이 끝날 때 한꺼번에 찬다.
- 계산이 60초 넘게 끝나지 않으면 `Detail` 이 먼저 켜지고 「계산이 길어지고 있습니다. 들어가면 HOME 진행 막대로
  이어서 볼 수 있습니다.」가 뜬다 — 결함이 아니다. 들어가면 HOME 맨 위 진행 막대가 이어서 찬다.
- 타이틀·`S.PKG CAPA`·`Detail`·`Summary`·요약 시트의 달(`26.10` 꼴)은 **저장소에 든 글꼴**(Archivo, 좁고 굵은
  글꼴), 선 위 값·막대 위 %·시트 수치는 저장소에 든 **숫자 글꼴**(Archivo 굵은 보통 폭)로 그린다. 두 글꼴은 함께
  올라가므로 **시트의 달이 좁은 글꼴이면 숫자 글꼴도 뜬 것이다**(숫자는 기본 글꼴로 떨어져도 굵은 보통 폭이라 눈으로
  가를 수 없다). 사내망에서 외부 글꼴을 받지 않으므로 이 글꼴들이 뜨는지가 이번 확인의 핵심이다. 단계·상태 문구,
  축 눈금(`N억Gb`)·기준선 %, 차트의 한글은 앱 본문 글꼴이다.
- 원이 퍼지고 접히는 움직임은 브라우저 기능(`CSS.registerProperty`·`mask-image`)을 쓴다. 사내 Chrome 이 이를
  모르면 움직임 없이 **한 번에** 열리고 닫힌다 — 동작은 같다. 또 브라우저가 OS 의 「움직임 줄이기」를 따르면
  심볼·워드마크 없이 웨이퍼가 바로 펼쳐지고, 요약은 조립 없이 끝 모습으로 바로 뜨며, 들어가고 나올 때는 원 대신
  짧게 **흐려진다** — 둘 다 결함이 아니다. 오래된 Chrome 이 화면 뒤 그리기(OffscreenCanvas 워커)를 모르면 같은
  장면을 앞에서 그려 로딩 중 움직임이 잠깐씩 끊길 수 있다 — 이것도 결함이 아니다.

**확인해 올 것.** 저장하지 않는다(이 화면은 아무것도 쓰지 않는다).

1) 앱을 띄운 뒤 브라우저에 **새 탭**을 열고 앱 주소를 직접 친다(4-2 에서 이미 열어 둔 탭은 들어간 탭이라
   다시 뜨지 않을 수 있다). 덮개가 뜨는지(「뜸/안 뜸」), 상단 바·사이드바까지 다 가리는지(「다 가림/일부
   보임」) 적는다.
2) **웨이퍼 심볼이 나타난 때부터** 단계 막대 여섯이 차고 상태 줄이 「준비 완료」가 될 때까지 대략 몇 초인지(손으로
   잰 **약 N초**) 적는다(그 앞의 바탕색 대기는 세지 않는다). 타이틀 `S.PKG CAPA SIMULATION` 이 **좁고 굵은
   글꼴**인지, 넓은 기본 글꼴(맑은 고딕 같은)인지 적는다(「좁은 글꼴/기본 글꼴」). 60초 안내가 떴으면 그것도 적는다.
   `Summary` 가 흐리게 꺼져 있으면 「꺼짐」으로 적고 3)·5) 를 건너뛴다 — 그때 4) 는 입장 화면의 `Detail` 로 하고,
   6) 은 입장 화면이 다시 뜨는지만 본다(헤더 `Summary` 가 없는 것이 정상이다 — 「안 뜸·없음」).
3) `Summary` 를 누른다. 세 줄(선·막대·시트)이 다 그려지는지(「셋 다/빠진 것 있음」), 오른쪽 위 공식버전 이름이
   사용자가 아는 **최신 공식버전**인지 사용자에게 물어 적는다(「맞음/다름」 — 이름은 적지 않는다). 시트의 달
   (`26.10` 꼴)이 타이틀처럼 좁고 굵은 글꼴인지(「좁은 글꼴/기본 글꼴」 — 좁으면 숫자 글꼴도 뜬 것이다), 막대 하나에
   마우스를 올려 말풍선이 뜨는지(「됨/안 됨」) 적는다.
4) 요약의 `Detail` 을 누른다. 원이 퍼지며 HOME 이 보이고 사이드바·탭을 누를 수 있는지(「정상/이상」), 원이
   부드럽게 퍼졌는지 한 번에 바뀌었는지 흐려지며 바뀌었는지(「부드럽게/한 번에/흐려짐」) 적는다.
5) 헤더 오른쪽 위에 `Summary` 가 보이는지(「보임/안 보임」) 적고, 누른다 → 요약이 다시 그려지는지(「됨/안 됨」)
   → `Esc` 로 돌아온다.
6) 같은 탭에서 새로고침(F5) → 입장 화면이 **다시 뜨지 않고** 헤더 `Summary` 는 그대로 서는지(「안 뜸·섬/그 밖」).
   헤더 `Dark` → 다시 뜨지 않는지 보고 `Light` 로 돌린다(이 단추는 페이지를 새로 읽어 사이드바 상자·시나리오
   선택·조회기간이 기본값으로 돌아간다 — 결함이 아니다).

### 7-2. Space 현황 — 배치·공간만 보고, 층 상세에 배치 편집기가 붙었다

**Space 현황은 배치·공간만 본다**(2026-10-01 사용자 결정).

- FAB 전체 화면의 카드는 **`배치 설비`·`미배치`·`레이아웃 제외`** 셋이다. `미배치` 는 레이아웃표시가 `Y` 인데
  좌표가 없는 호기, `레이아웃 제외` 는 `N` 인 호기다. 반출·이설을 마친 호기는 어디에도 세지 않는다. 동 화면은
  `선택 동`·`배치 설비`·`미배치`·`배치 도면`(도면을 등록한 층 수 / 층 수)이고 층 표에 **점유율**(호기 면적 ÷
  캔버스 면적)이 붙는다. 층 화면에는 카드가 없고 도면 위 요약 줄에 점유율이 붙는다.
- 예전의 `기간 내 설비 단계 전환 현황`(카드·막대·표)은 **가용설비 현황 Main 의 볼 내용 `단계 전환`** 으로
  옮겼다(7-3). 상태별 대수는 층 배치도 범례에 붙는다. 본문의 「Data확보중」 배지와 적용 이력 줄은 걷었다
  (사이드바 메뉴 이름은 그대로).
- **층 상세**는 카드 대신 도면 위 한 줄 요약(`배치 N대 · 미배치 N대 · 점유율 x%`)이고, 머리 줄에 제목·
  `도면·캔버스 편집`·**`배치 편집`** 토글·상태 범례가 선다. 도면은 **보기 전용 뷰어**다 — `+`·`−` 확대·축소(100% 에서는 `−` 가
  잠긴다), `전체 보기`, **확대한 뒤** 끌어서 이동, 더블클릭 확대/전체 보기, 호기를 누르면 정보 한 줄.
- **`배치 편집` 을 켜면 끌어 놓아 고치는 편집기**가 선다: 호기를 끌어 옮기고 크기를 바꾼다(격자 `0.1`·`0.5`·
  `1`·`2`), 도면 요소(영역·반입구·문·기둥·글자·동선)를 그린다, 편집 영역 크기를 바꾼다, 오른쪽 트레이의 미배치
  호기를 도면에 놓는다, 다른 층으로 보낸다, 호기를 더한다. **`적용` 은 편집본에만 넣는다**(저장 전) — 그러면
  화면 위에 저장하지 않은 배치 상자(`변경 메모`·`배치 저장`·`버리기`)가 어느 단계 화면에서나 뜬다.
  `배치 저장` 이 새 설비 리비전을 만든다. 저장된 도면 요소는 층 뷰어에도 그려진다.
- 레이아웃표시 `Y` 인데 좌표가 없는 호기는 **미배치**로 트레이에 뜬다(오류가 아니다). 층이 정해지지 않은
  미배치 호기는 그 동 어느 층 편집기에서나 트레이에 보인다.

**확인해 올 것.** **저장하지 않는다**(`배치 저장`·팝업 저장을 누르지 않는다). RawData 를 고친 채로 하지 않는다
— 3) 의 `모두 버리기` 는 설비 편집본 전체를 버린다.

본문에 `합성 샘플` 배지나 「호기 마스터가 비어 있어 데모 fleet 을 표시합니다」가 보이면 호기 마스터가 비어 있는
것이다 — 1) 의 대수는 「샘플」로 적고, 3) 은 `배치 편집` 토글이 서지 않으니 「호기 마스터 비어 있음 — 편집기
없음」으로 적고 건너뛴다. 샘플 스위치는 바꾸지 않는다. 7-3 의 결과도 「샘플」로 적는다.

1) `Space 현황` 을 연다(설비 마이그레이션 `0011` 은 앞 배포에서 이미 걸렸다 — 7-8 이 센다). 오류 없이 뜨는지(「정상/오류」 — 오류면
   원문을 옮기지 않고 가명화한다), 카드 셋의 대수만 적는다.
2) 동 하나 → **배치된 호기가 있는 층 하나**로 들어간다. 도면이 뜨는지, 요약 줄이 보이는지 본 뒤 이 순서로
   해 본다 — `+`(또는 도면 더블클릭)로 확대 → **확대한 채** 끌어서 이동 → `−` 나 `전체 보기` 로 처음 크기 →
   호기 하나 누르기(도구 줄에 정보 한 줄). 각각 「됨/안 됨」으로 적는다. 100% 에서 `−` 가 잠겨 있고 끌어도
   움직이지 않는 것은 정상이다 — 「안 됨」이 아니다. 배치된 호기가 있는 층이 없으면 「배치된 층
   없음」으로 적고 3) 은 아무 층에서 편집기가 뜨는지만 본다.
3) `배치 편집` 토글을 켠다. 편집기가 뜨는지 보고, 호기 하나를 끌어 옮긴 뒤 `적용` → 화면 위에 저장하지 않은
   배치 상자가 뜨는지 본다. 그다음 **`버리기` → `모두 버리기`** 로 버린다. 상자가 사라지고 호기가 원래 자리로
   돌아오는지(「돌아옴/안 돌아옴」) 적는다. 토글을 끈다.

### 7-3. 가용설비 현황 Main — 볼 내용 `단계 전환`

Space 현황에서 옮겨 온 단계 전환 현황이 **가용설비 현황 Main 의 다섯째 볼 내용 `단계 전환`** 이 됐다. 기간과
기준일, 전환단계·일정상태·Qual 확정상태와 추가 조건이 함께 걸리고, 보기는 `단계별 건수`·`전환 일정 목록` 둘이다.
Space 와 달리 레이아웃과 무관하게 **호기 마스터 전체**를 센다 — 예전 Space 화면의 숫자와 달라도 결함이 아니다.

**확인해 올 것.** `가용설비 현황` → Main → 볼 내용 `단계 전환` 을 고르고 두 보기가 오류 없이 뜨는지(「정상/오류」)만
적는다. 목록의 호기·공정은 적지 않는다.

### 7-4. 그 밖에 보이는 변화

- **HOME 주요공정 히트맵 제목** — 프리셋이 있으면 **`주요공정 - <프리셋 이름>`** 이다(예전 `주요공정 확보율 ·
  <프리셋>`). 긴 이름은 한 줄로 줄이고(`…`) 마우스를 올리면 전체 이름이 나온다 — 예전에는 긴 이름이 줄을
  바꿔 구분 칸과 월 칸의 행이 어긋났다.
- **헤더 `Guide`·`Dark`/`Light` 단추** — 단추를 싣는 틀을 바꿨다(서버 터미널에 찍히던 `st.components.v1.html`
  폐기 예고가 사라진다). 기능은 같다.
- **가용설비 현황 RawData 의 저장 규칙** — Space 배치 편집기와 **한 편집본**을 쓴다. 아래는 결함이 아니라 의도한
  막힘·문구다.
  - 다른 사용자가 먼저 저장했으면 `저장`(과 Space `배치 저장`)이 「다른 사용자가 먼저 rN을 저장해 저장하지
    않았습니다. 화면을 다시 불러와 최신 저장본 위에서 고친 뒤 저장하세요.」로 막힌다. 그다음 화면에서는 「다른
    사용자가 rN을 저장해, 이 화면에서 저장하지 않은 설비 편집(RawData·Space 배치)을 버리고 최신 저장본으로 다시
    열었습니다.」가 뜨고, 그 회차의 제출은 「다른 사용자가 먼저 저장해 이번 제출은 반영하지 않았습니다. …」로
    버려진다.
  - 레이아웃표시 `Y` 인데 좌표가 없는 행, 크기만 있는 행이 **이제 저장된다**(Space 트레이의 미배치 호기가 된다).
    예전의 「… 동·층·좌표·크기를 모두 입력해야 합니다」 대신 「X좌표·Y좌표는 함께 넣거나 함께 비워야
    합니다」·「레이아웃표시 Y 호기에 좌표를 넣으면 동·층도 넣어야 합니다」 같은 문구로 막힌다.
  - 좌표 칸의 `12,5`·`12m` 같은 글자는 빈칸으로 흘리지 않고 「X좌표를 숫자로 읽을 수 없습니다: …」로 막는다.
  - RawData `저장` 은 그 세션에서 적용만 하고 저장하지 않은 Space 캔버스·도면 요소도 함께 쓴다(「층 캔버스·도면
    요소도 함께 저장했습니다」). Space 의 `모두 버리기` 는 저장하지 않은 RawData 편집도 함께 버린다.

**확인해 올 것.** HOME `Main` 의 주요공정 히트맵 제목 꼴(「`주요공정 - …`/그 밖」 — 프리셋 이름은 적지 않는다)과
제목 칸과 월 칸 행이 맞는지(「맞음/어긋남」), 헤더 `Guide` 가 열리고 `Esc` 로 닫히는지(「됨/안 됨」)를 적는다.

### 7-5. 직전 배포에서 이어지는 것

- **설비 DB 마이그레이션은 가용설비 현황(또는 Space) 페이지를 열어야 걸린다**(4-2). 이번 배포에는 새 것이 없다 —
  직전 배포의 `0011` 이 걸려 있으면 7-8 이 `equipment_migration 11` 로 센다.
- **`requirements.txt` 용도** — 3-3 절에 적었다. 사내 WebIDE 컨테이너 전용이고 `uv.lock` 의
  그림자다. **사내에서 고치지 않고** `uv sync` 를 대신하지도 않는다.
- **`Pack Code` 업무 키 승격의 후속** — `0013` 이전에 저장한 리비전은 `Pack Code` 가 비어
  있어 `생산 계획` 화면이 「RQ_PKG_PLAN의 편집 테이블 식별 컬럼에 누락값이 있습니다: Pack Code …」로
  선다(사이드바 `편집 되돌리기` 로도 풀리지 않는다). 실데이터를 **다시 등록**해야 하고, 승격 전에 내려받은 PKG PLAN CSV
  양식도 못 쓰므로 **양식을 다시 받는다.**
- **BigDataQuery 조회** — `export CAPA_BDQ_USER_NAME="<AD 계정>"` 를 넣고 앱을 다시 띄운다.
  자세한 것은 [`bigdataquery_webide_setup.md`](bigdataquery_webide_setup.md).
- **WebIDE 환경 두 가지를 확인해 온다** — `aws` 가 PATH 에 있는가, WebIDE 재시작 주기·디스크
  영속성은 어떻게 되는가. 답을 `docs/objectstore_setup.md` 의 표에 적을 수 있게 리뷰 문서에
  남긴다.
- `202609291101` 의 화면 양식 변경(조건 카드·Guide·작업 줄·탭 아이콘과 주황 점)과 편집 확인
  체크는 그대로다. 사내 리뷰에서 문제 없음으로 확인됐다. 다만 `신규 리비전 저장` 단추는 체크 전에도
  잠기지 않는다 — 체크 없이 누르면 저장하지 않고 「신규 리비전을 저장하지 않았습니다…」를 띄운다(7-6-3).
  결함이 아니다.
- **BigDataQuery 기본 상세 조회 창(−7 ~ +3)** — 7-7-3 은 건너뛴다(7-0 표, 2026-10-02 정상 조회 확인). 사용자가
  따로 잰 초가 있으면 리뷰 문서에 적는다.

### 7-6. 앞 배포 `202610010952` 분 — 7-0 표 5~8번

아래는 `202610010952` 배포의 7장(7-1~7-4)을 번호만 바꿔 그대로 옮긴 것이다. 그 배포를 적용해 7장 확인을

먼저 끝낸 뒤 한다. 7-6-4 4) 의 `Dark` 단추는 7-1 6) 처럼 같은 탭이라 입장 화면이 다시 뜨지 않는다.

**이 묶음과 7-7 에 걸리는 규칙**(그 배포 7장 머리의 규칙 그대로다).

- **새 오류문은 식별값을 그대로 적는다.** 리뷰 문서에는 원문을 옮기지 않고 **건수·년월·표 이름과

  팝업의 `신규 리비전 저장` 도 하지 않는다(7-6-3 1) 은 **저장이 막히는 것**을 보는 확인이다 — 체크 칸을 켜지
  않고 `새 리비전명` 도 비워 둔다). 이 묶음에서 남기는 쓰기는 **7-6-1 의 1월 시나리오 등록**(사용자가 원래
  하려던 운영 등록, 물을 수 없으면 시험용 `시험-7-1`)과 7-7 의 시험 프리셋·시험 시나리오뿐이고, 시험용은
  끝에 지운다. **기존(운영) 시나리오는 보관도 영구 삭제도 하지 않는다.**

#### 7-6-1. CS 코드 `CB` — 막혔던 1월 시나리오를 다시 등록한다

사내 1월 시나리오를 BigDataQuery 로 등록하다 「RQ_PKG_PLAN 업무 키에 null 또는 빈값이 있습니다:
양산구분」으로 막혔다. 원천에 처음 보는 CS 코드 `CB` 가 있었고, CS → 양산구분 규칙에 없어 그 행의
양산구분이 비었던 것이다.

- CS → 양산구분 규칙을 한 곳에 모았다: **`MP`·`CS`·`CB` → 양산, `ER` → ER**(`CB` 는 2026-09-30
  사용자 결정). CS 값은 앞뒤 공백을 떼고 대문자로 맞춰 읽는다.
- `CB` 행은 양산으로 센다 — HOME 생산계획·Density·표준 목표 Capa 에 들어가고, 효율·여유율은 같은
  달·공정의 양산 값과 한 칸을 쓴다.
- 규칙에 없는 코드가 또 오면 등록이 **「원천 CS 코드 중 양산구분(양산·ER) 규칙에 없는 값이 있습니다:
  `XX` N행(계획 M행) …」**으로 멈춘다(전처럼 「업무 키에 null …」로 멈추지 않는다). 계획 M행은 PKG
  PLAN 에 실리는 행 수다. 사외가 규칙에 더해 다시 배포해야 등록된다.

**확인해 올 것.**

1) 1월 시나리오를 `시나리오 관리 → BigDataQuery 등록` 으로 다시 등록한다. **실제 이름으로 남길지
   사용자에게 먼저 묻는다** — 사용자가 원래 하려던 등록이다. 물을 수 없으면 `저장할 시나리오명` 을
   `시험-7-1` 로 두고 등록한 뒤 7-6-1 4) 대로 지운다. 실제 이름이 이미 있으면(보관본 포함) 조회 전에 「같은
   이름의 시나리오가 이미 있습니다. 이름을 바꿔 저장하세요.」로 막힌다 — 사용자에게 다른 이름을 받아 다시
   누른다. 상세 조회 기간은 폼이 채운 기본값(원천 등록일 7일 전 ~ 3일 뒤)을 쓰고, 0행으로 막히면 `상세
   조회 종료일` 을 오늘로 늘려 다시 누른다(7-7-3 참고). **실제 이름으로 남길 때는** 처음부터 `상세 조회
   종료일` 을 오늘로 두거나 사용자에게 기간을 받는다 — 창 밖에 적재된 행은 오류 없이 빠지고, 한 번 저장한
   코드는 기간을 넓혀 다시 받을 수 없다(원천 코드 불변 — 그 운영 시나리오를 보관·영구 삭제해야 풀리는데
   이번 확인에서는 하지 않는다). 기본 창이 충분한지는 아직 7-7-3 으로 재는 중이다. 결과는 셋 중 하나로
   적는다 — 「저장됨」 / 「CS 규칙 밖 코드로 막힘 — `코드` N행(계획 M행)」(코드와 행 수는 그대로) /
   「다른 오류」(문구는 가명화).
2) 저장되면 등록 화면에 **「N개 업무 키 그룹에서 값 충돌을 확인했습니다」** 경고가 뜨는지 본다. 뜨면
   아래 요약 표의 `RQ테이블` 별 `충돌 업무키 그룹수` 만 옮긴다(CSV 는 받지 않는다 — 식별값이 든다).
   특히 **`RQ_RUN_RATE`·`RQ_VITAL`** 줄이 있는지 적는다. 그 두 표에 충돌이 있으면 같은 달·공정의
   양산 행(`MP`·`CS`·`CB` 를 모두 양산으로 센다) 사이에 효율·여유율 값이 둘 이상이라 값이 있는 첫 행을 임시로
   썼다는 뜻이다. 이 배포 전에도 양산 행끼리 생길 수 있던 충돌이라 `CB` 행 때문인지는 이 요약 표로 가릴 수
   없다 — 사외가 `CB` 를 양산으로 묶은 것이 맞는지 다시 볼 근거로만 쓴다.
3) PKG PLAN 표에서 `CB` 행이 표 맨 뒤나 같은 제품의 `MP`·`CS` 행 뒤에 서도 결함이 아니다 — 공용 표시순서에
   CS `사용자지정` 규칙이 있으면 거기에 없는 `CB` 는 그 정렬 단계에서 맨 뒤로 간다. 순서를 바꾸려면 Admin 의
   표시순서 관리에서 더한다(이번 확인에서는 하지 않는다).
4) `시험-7-1` 로 등록했으면 **지금 지우지 않는다** — 영구 삭제는 그 원천 행까지 지워, 먼저 지우면 그 `CB`
   행이 7-8 의 `cb_rows` 에서 빠져 `CB` 가 계획 행에만 있는지 셀 수 없다. 사이드바에서 원래 보던 시나리오를
   다시 불러와 7-6-2 로 간다. 7-8 의 조회를 돌린 뒤에 7-7-3 4) 의 두 단계(보관 → 영구 삭제)를 **이름만
   `시험-7-1` 로 바꿔** 그대로 따라 지운다(7-8). 실제 이름으로 남긴 시나리오와 `시험-7-1` 밖의 시나리오는
   보관·삭제하지 않는다.

`CB` 가 계획 행에만 있는지(설비 수요를 만드는 행이 없는지)는 7-8 의 조회 한 줄이 센다.

#### 7-6-2. 사이드바 상자를 접고 펼 때 본문이 다시 돌지 않는다

사이드바의 조회 조건 상자(시나리오·리비전, 조회기간, B/N 집계 공정)·조건 카드·메뉴 그룹 상자를 접거나
펼 때 **본문의 계산과 그림을 다시 하지 않는다**(2026-09-30 사용자 요청). 0.3초 안에 끝나는 짧은
실행은 본문을 흐리지 않는다. 상자를 여닫는 같은 순간에 다른 칸을 바꿨으면 그때는 본문이 다시 돈다
— 그 변경을 잃지 않기 위해서다.

**확인해 올 것.** HOME `Main` 이 그려진 뒤 사이드바 상자를 대여섯 번 접고 편다. 본문이 흐려졌다
돌아오거나 그림이 다시 그려지는지(「안 함/함」)와 체감(「즉시/잠깐 멈춤」)만 적는다. 기준 정보의
아무 편집표 칸 하나를 고쳐 둔 채(적용하지 않는다) 상자를 접고 펴도 그 탭 이름 옆 **주황 점**이 남는지
본다 — 끝나면 표 위 `편집 취소`.

#### 7-6-3. 브라우저 E2E 점검에서 고친 것

사외가 2026-09-30~10-01 에 실제 브라우저로 흐름 80개를 돌려 찾은 결함 18건을 고쳤다. 사내에서 다르게
보일 수 있는 것만 적는다. **아래는 오류가 아니라 의도한 동작이다.**

**저장·불러오기**
- 사이드바 `신규 리비전 저장` 단추를 **잠그지 않는다.** 적용하지 않은 편집이 있는데 `적용하지 않은 편집을
  버리고 저장` 을 체크하지 않고 누르면 저장하지 않고 **「신규 리비전을 저장하지 않았습니다. … 에 적용하지
  않은 편집이 있습니다 — …」**를 팝업 안과 상자 아래에 띄운다. 전에는 단추가 잠긴 채 눌린 클릭이 말없이
  사라져, 저장한 줄 알았는데 리비전이 없었다.
- 생산 계획의 PKG PLAN 을 적용해도 **수율 탭의 적용하지 않은 편집**이 사라지지 않는다.
- 적용한 직후 사이드바가 방금 적용한 표를 「적용 전 편집」으로 세지 않는다.

**시나리오 이름**
- **같은 이름의 시나리오를 새로 만들 수 없다**(보관본 포함, 앞뒤 공백을 뗀 완전 일치). BigDataQuery 등록·
  복제·이름 수정·월 머지·연도 Shift 가 모두 **「같은 이름의 시나리오가 이미 있습니다. 이름을 바꿔
  저장하세요.」**로 막힌다(2026-10-01 사용자 결정). 지금 이름 그대로 이름 수정을 저장하는 것은 된다.
- **이 규칙 전에 생긴 같은 이름은 그대로 둔다**(지우거나 바꾸지 않는다). 7-8 의 조회가 그런 이름이 몇
  개인지 센다 — 있으면 사용자가 하나씩 이름을 바꾼다(이번 확인에서는 하지 않는다).
- 복제 폼은 저장에 성공하면 비워진다(다시 누르면 같은 시나리오가 또 생기던 것).

**가용설비 GAP**
- Static·Dynamic **한쪽에만 있는 공정은 GAP 을 내지 않는다**(2026-10-01 사용자 결정). 그런 공정을 고르면
  「「…」는 기준정보(Static)에 없는 공정이라 GAP 을 내지 않습니다.」 또는 「… Dynamic 이 나오지 않은
  공정(Cut-off·설비 없음)이라 GAP 을 내지 …」가 뜬다. 조회 달 중 한쪽 자료만 있는 달도 GAP 이 없다.
- 확보율 교차검증은 기준정보에 없는 공정을 비교한 공정으로 세지 않는다. 호기 필터 캡션의 호기 수는
  고른 공정 안의 호기만 센다.

**화면**
- 편집표의 빈칸에 `None` 글자가 찍히지 않는다.
- 조회기간 월 칸을 키보드로 고쳐도 되돌려지지 않는다 — 입력을 멈추고 잠깐 뒤 반영된다.
- 헤더 `Guide` 로 연 창이 `Esc` 로 닫힌다.
- 펼친 상자가 알림·탭 이동에 접히지 않는다: 산출 결과 히트맵, 시나리오 관리 보관함, VOC 의 편 글.
  VOC 작성자 칸은 다른 화면에 갔다 와도 남는다. 가용설비 RawData 안쪽 탭이 제출 뒤에도 고른 탭에 머문다.
- 표준 목표 `표시 항목` 은 고른 항목을 다시 눌러도 선택이 풀리지 않는다.
- HOME Wafer 계획 증감은 `+0K` 로 적지 않는다(한 자리 더 적거나 적지 않는다). Past Data 탭도 읽어 두고
  저장하지 않은 표가 있으면 주황 점이 찍힌다. Space 현황에서 샘플을 끄고 호기가 없으면 카드에 까닭이
  한 줄 뜬다.

#### 7-7-3. BigDataQuery 상세 조회 기간 — 폼에서 정한다

`시나리오 관리 → BigDataQuery 등록` 의 등록 폼에 **`상세 조회 시작일`·`상세 조회 종료일`** 두 칸이
생겼다(2026-09-29 사용자 결정). 예전 상세 조회는 최근 90일 ∪ 목록 기간이라 옛 코드일수록 길었다.

- 목록에서 코드를 고르면 **원천 등록일 7일 전 ~ 3일 뒤**로 채운다. 목록에 그 코드의 등록일이 여러 날
  보였으면(PLAN 이 여럿인 줄 포함) 가장 이른 날 7일 전 ~ 가장 늦은 날 3일 뒤다. 끝은 오늘을 넘지
  않는다. 상세 조회는 PLAN 을 가리지 않고 코드 전체를 받는다.
- 등록 뒤에도 원천이 **계속 수정·재적재된** 시뮬레이션은 **처음 등록할 때** 종료일을 넉넉히 늘린다.
  창 밖에 적재된 행은 **오류 없이 빠진다.** 적재분이 **모두** 창 밖이면 저장이 「시뮬레이션 코드 … 의
  조회 결과가 0행입니다」로 멈춘다 — 결함이 아니다, 기간을 넓혀 다시 누른다.
- **같은 코드는 원천이 다르면 다시 등록되지 않는다**(원천 코드 불변, 보관본 포함). 한 번 저장한 코드를
  기간을 넓혀 다시 받으면 「동일 시뮬레이션 코드에 다른 원천 데이터가 이미 저장되어 있습니다」로
  막힌다 — 앱 결함이 아니다. 다시 받으려면 그 코드의 시나리오를 모두 보관한 뒤 영구 삭제해야 한다.
- 코드를 직접 적을 때는 두 칸을 비우고(칸의 지우기 단추) `원천 DB 등록시점` 을 채우거나 날짜를
  고른다. 둘 다 없거나 한 칸만 채우면 저장이 막힌다. 목록에서 고른 뒤 **코드만 바꿔 적으면**, 고른
  코드가 채운 날짜 두 칸이나 `원천 DB 등록시점` 을 그대로 두는 한 「… 다른 코드의 …」로 막힌다.
- 실제로 조회한 기간이 리비전 메모에 `상세 조회기간 YYYY-MM-DD ~ YYYY-MM-DD` 로 남는다.

**확인해 올 것.** 사외 표본은 합성이라 아래는 사내에서만 잴 수 있다. **7-7-2·7-7-1 을 끝낸 뒤** 한다.
값·코드·이름은 적지 않고 결과 종류·초·개수만 적는다.

1) **7-6-1 에서 등록한 1월 코드는 고르지 않는다** — 같은 기본 창으로 막 받은 원천이라 2) 가 언제나 「같음」이
   되고, 7-6-1 이 종료일을 늘렸다면 측정이 섞인다(`202609300745` 배포 뒤 기본 창 그대로 등록한 코드도 같은 까닭으로 뺀다).

   없음」으로 적는다. 7-6-1 1) 에서 기본 창이 0행이라 `상세 조회 종료일` 을 늘렸는지(예/아니오)도 이 측정의 한

2) 그 코드를 골라 기본 창(−7일 ~ +3일) 그대로 두고 `저장할 시나리오명` 을 **`시험-7-5-3`** 으로 바꾼다

   찍히지 않는다). 결과 문구가 곧 판정이다.

   - 「동일 시뮬레이션 코드에 다른 원천 데이터가 이미 저장되어 있습니다…」 — 기본 창이 받은 원천이

     누른다. 누가 만든 것인지 모르면 지우지 말고 사용자에게 묻는다.
   - 「원천 CS 코드 중 양산구분(양산·ER) 규칙에 없는 값이 있습니다…」 — 7-6-1 의 CS 규칙에 막혔다. 7-6-1 1)

3) 2) 가 「다름」이면 폼을 그대로 두고 `상세 조회 종료일` 만 오늘로 바꿔 다시 누른다. 성공하면 「등록일

   번 모두 초를 적는다. **이 결과로 사외가 기본 창(−7 ~ +3)을 유지할지 정한다.**
4) `시험-7-5-3` 이 저장됐으면 지운다 — 단추 하나가 아니라 두 단계다. 사이드바에서 원래 보던 시나리오를
   먼저 불러온다. `시나리오 관리` 탭의 `시나리오 작업` 을 `목록 관리` 로 두고, 표에서 `시험-7-5-3` 행의
   `선택` 을 켜 `시나리오 보관` → 「시험-7-5-3 을 보관합니다」 체크 → `보관 실행`. 이어서 `보관된
   시나리오 N건` 을 펴 `보관본` 에서 `시험-7-5-3` 을 고르고, `영구 삭제하려면 시나리오명을 그대로
   입력하세요` 에 `시험-7-5-3` 을 적은 뒤 `영구 삭제 실행`. 보관만 하면 원천이 남는다. 공식버전으로
   지정하지 않는다(최신 공식은 보관·삭제가 막힌다). 지워도 DuckDB 파일 크기는 줄지 않는다.
   `시험-7-5-3`(과 7-6-1 4) 의 `시험-7-1`) 말고는 아무것도 보관·삭제하지 않는다.

### 7-8. 마지막 — 앱을 끄고 개수로 확인한다

7-7 을 했으면 그 시험용을 지운 뒤(`시험-7-1` 은 아직 둔다 — 아래 `cb_rows` 가 그 원천을 센다), 사용자에게 앱을
꺼 달라고(`Ctrl+C`) 한 다음 아래 한 줄을 돌린다. 값은 찍히지 않고 개수만 나온다. `시험-7-1` 이 남아
있으면 출력을 리뷰 문서에 옮긴 뒤 사용자에게 4-2 의 명령으로 앱을 다시 띄워 달라고 해 7-6-1 4) 대로 지우고,
지운 뒤 다시 꺼 달라고 한다(이 한 줄은 다시 돌리지 않는다 — 지운 뒤의 `cb_rows` 는 새로 알려 주는 것이
없다). 7-6·7-7 을 건너뛰었어도 이 줄은 돌린다.

```powershell
uv run --no-sync python -c "import duckdb; c = duckdb.connect('data/capa_simulation.duckdb', read_only=True); e = duckdb.connect('data/equipment_availability.duckdb', read_only=True); q = lambda s, p=None: c.execute(s, p or []).fetchall(); print('migration', q('SELECT max(version) FROM app_meta.schema_migration')[0][0], 'equipment_migration', e.execute('SELECT max(version) FROM equipment_meta.schema_migration').fetchall()[0][0], 'layout_marks', e.execute('SELECT count(*) FROM equipment_ops.floor_layout_mark').fetchall()[0][0], 'dup_names', q('SELECT count(*) FROM (SELECT scenario_name FROM app_meta.scenario GROUP BY scenario_name HAVING count(*) > 1)')[0][0], 'cb_rows', q('SELECT coalesce(nullif(upper(trim(계획기초정보여부)), ?), ?), count(*) FROM raw_data.core_data WHERE upper(trim(cs)) = ? GROUP BY 1 ORDER BY 1', ['', '-', 'CB']), 'presets', [q(f'SELECT count(*) FROM app_meta.{t} WHERE profile_id = 1')[0][0] for t in ('global_key_process_item', 'global_key_process_preset', 'global_key_process_preset_item')])"
```

읽는 법(출력 한 줄을 그대로 리뷰 문서에 옮긴다).

- `migration 28` — 시뮬레이션 DB 마이그레이션 번호. 28 이 아니면 4-2 로 돌아간다.
- `equipment_migration 11` — 설비 DB 마이그레이션 번호. 11 이 아니면 `Space 현황`(또는 `가용설비 현황`)을 열지 않은
  것이다 — 4-2 대로 앱을 띄워 그 페이지를 연 뒤 끄고 이 줄을 다시 돌린다. `Catalog Error`(표가 없다)가 나와도
  같은 까닭이다.
- `layout_marks N` — 저장된 Space 도면 요소 수. 이번 확인은 저장하지 않으므로 **0** 이어야 한다. 0 이 아니면
  누군가 도면 요소를 저장한 것이다 — 결함이 아니니 수만 적는다.
- `dup_names N` — 이름이 겹치는 시나리오 이름의 수(7-6-3). 0 이 아니면 사용자에게 알린다 — 겹친 이름은
  사이드바·보관함에서 어느 쪽인지 가릴 수 없다. 이번 확인에서 이름을 바꾸지는 않는다.
- **직전 값(2026-10-02, `202610021506` 리뷰)** — `migration 28 equipment_migration 11 layout_marks 0 dup_names 0
  cb_rows [('N', 3110), ('Y', 190)] presets [11, 4, 18]`. 이번 출력이 이것과 다르면 그 줄만 따로 적는다(원천을
  새로 등록했거나 프리셋을 고쳤으면 달라지는 것이 정상이다).
- `cb_rows [('N', a), ('Y', b)]` — 저장된 원천 전체(보관본 포함)에서 CS 가 `CB` 인 행 수를 계획 행 여부(`Y`·`N`,
  비었거나 빈 글자면 `-`)별로 센다(7-6-1). `[]` 이면 `CB` 행이 저장된 원천이 없다(1월 시나리오를 저장하지 않았거나
  등록이 막혔다 — `시험-7-1` 을 이 조회 전에 지우면 그 행이 빠지므로 7-6-1 4) 의 순서를 지킨다). **`Y` 만 있으면** 그
  사실을 따로 적는다 — 사외가 `CB` 의 설비 수요 경로를 다시 본다.
- `presets [N, M, K]` — 7-7-1 의 프리셋 표 행 수(옛 목록 공정 N, 프리셋 M, 프리셋에 든 공정의 합 K). `0028`
  이 이번에 처음 걸렸고 그 뒤 아무도 프리셋을 고치지 않았으면 `[N, 1, N]`(옛 목록 N개가 「기본」으로 옮겨졌다)
  또는 `[0, 0, 0]`(옛 목록이 비어 있었다)이다. 앞 배포를 이미 적용해 써 왔으면 사내 사용자가 만들거나 고친
  프리셋 때문에 M 이 1 보다 크거나 K 가 N 과 달라도 정상이다. **이번에 7-7-1 3) 을 했으면** M 을 7-7-1 2) 에서
  적은 `N개 프리셋` 과 맞대어 본다 — 하나 많으면 시험 프리셋이 남은 것이니 사용자에게 4-2 의 명령으로 앱을 다시
  띄워 달라고 해 7-7-1 3) 대로 `시험` **만** 지우고, 앱을 끈 뒤 이 줄을 다시 돌린다. `시험` 이 아닌 프리셋은
  지우지 않는다. 7-7 을 건너뛰었어도 세 수를 그대로 옮긴다.
- `duckdb.IOException` 이면 앱이 아직 떠 있다.
