# 사내 업데이트 실행 절차 (사내 에이전트용)

이 문서는 **사내(WebIDE)에서 배포 ZIP 을 받아 적용하는 한 번의 작업**을 처음부터 끝까지 적은
것이다. 위에서 아래로 그대로 따라가면 된다. 왜 이런 구조인지는 `docs/dual_env_workflow.md`
에 있고, 여기는 **무엇을 어떤 순서로 치는가**만 적는다.

**이 문서를 읽고 있다면 먼저 확인한다.**

```powershell
git remote -v
```

`github.com` 이 나오면 **사외(개발 PC)다 — 이 문서는 네 것이 아니다.** 사내 GitHub 주소가
나올 때만 아래를 따른다.

---

## 0. 사내에서 절대 하지 않는 것

- **소스를 고치지 않는다.** `app.py`·`app_pages/`·`src/`·`tests/`·`scripts/`·`config/`·
  `.streamlit/`·`static/`·루트 문서 — 어느 것도 편집하지 않는다. 쓸 수 있는 곳은 `review/` 뿐이다.
- **`git clean -x` 를 쓰지 않는다.** `-x` 는 무시된 파일까지 지우고, 거기에 **운영 DuckDB 와
  `data/input` 실데이터**가 들어 있다. 한 글자 차이로 사내 데이터가 날아간다.
- **`uv sync` 를 맨 것으로 돌리지 않는다.** 락에 없는 `bigdataquery` 를 지운다.
  항상 `uv sync --inexact` 다.
- **정체불명 파일을 스스로 지우지 않는다.** 사용자에게 묻고 고른 대로 한다.
- **`.gitignore` 를 고치지 않는다.** 권한에서도 막혀 있다. 넣어야 할 것이 있으면 리뷰
  문서에 적어 사외가 넣게 한다.
- **`git push` 는 에이전트가 하지 않는다.** 권한에서 막혀 있다(`Bash(git push*)` deny).
  푸시가 필요한 자리에서는 사용자에게 명령을 알려 주고 사용자가 친다.

---

## 1. 시작 전 점검 (5분)

### 1-1. 앱을 끈다

```powershell
Get-Process python -ErrorAction SilentlyContinue | Where-Object { $_.Path -like "*streamlit_project*" }
```

떠 있으면 그 창에서 `Ctrl+C`. **DuckDB 는 프로세스 배타 잠금이라 앱이 살아 있으면 이후
검증·마이그레이션이 전부 `duckdb.IOException` 으로 죽는다.** 적용기 자체는 DB 를 열지 않지만
적용 뒤 확인이 막히므로 먼저 끈다.

### 1-2. 쓰기 권한이 실제로 열리는지 한 번 본다

리뷰 문서를 못 쓰면 이번 작업의 산출물이 아예 나오지 않는다. 먼저 확인한다.

```powershell
New-Item -ItemType Directory -Force review | Out-Null
```

그리고 `review/_permission_test.md` 에 아무 한 줄이나 써 본다. 잘 써지면 그 파일은 지우고
넘어간다.

**막히면 거기서 멈추고** 사용자에게 아래를 그대로 알린다 — 사외가 고쳐야 한다.

> 사내 `.claude/settings.json` 의 `Edit(*.md)` deny 가 `review/` 까지 막고 있습니다.
> 슬래시 없는 패턴은 gitignore 의미라 모든 깊이에 걸립니다. `Edit(/*.md)` 로 앵커하고
> allow 에 `Edit(review/**)` 를 더해야 합니다. **deny 는 allow 로 뚫을 수 없으므로**
> deny 쪽을 좁히는 것 말고는 방법이 없습니다.

설정 파일이 `docs/internal_claude_settings.json` 템플릿의 최신본과 같은지도 함께 본다 —
`.claude/` 는 배포가 덮지 않으므로 옛 템플릿이 남아 있을 수 있다.

### 1-3. 운영 데이터를 저장소 밖으로 복사한다

**건너뛰지 않는다.** 아래 두 가지는 적용이 덮거나 지울 수 있다.

```powershell
$backup = "$HOME\deploy_backup\$(Get-Date -Format yyyyMMddHHmm)"
New-Item -ItemType Directory -Force $backup | Out-Null
Copy-Item data\*.duckdb $backup -ErrorAction SilentlyContinue
Copy-Item data\input\* $backup -Recurse -ErrorAction SilentlyContinue
```

`data/input/` 을 함께 챙기는 것은 보수적으로 두는 것이다. **배포 세트는 `data/input/` 아래를
보내지 않으므로**(`build_deploy_package.py` 의 `FORBIDDEN_PREFIXES`) 적용이 덮을 일은 없다.
다만 적용기의 `is_protected` 는 **삭제만** 막고 덮어쓰기는 막지 않는 구조라, 규칙이 바뀌면
조용히 덮인다 — 무시 파일이라 `git checkout -- .` 로도 돌아오지 않는다.

### 1-4. 저장소에 있으면 안 되는 것이 커밋돼 있는지 먼저 본다

**이 순서를 바꾸지 않는다.** 다음 단계(1-5)가 「수정된 파일을 되돌려라」라고 시키는데,
운영 DuckDB 나 `data/input` 실데이터가 **추적된 상태**라면 그 되돌리기가 실데이터를 커밋된
옛 버전으로 덮는다. 무엇이 추적 중인지 모르는 채로 1-5 에 들어가면 안 된다.

```powershell
git ls-files | Select-String -Pattern '\.duckdb|\.db$|\.wal$|^data/input/|^data/output/|^data/temp/|^\.agents/|^\.omo/|\.xlsx?$|\.xlsb$|\.tmp$'
```

**한 줄이라도 나오면 여기서 멈춘다.** `docs/dual_env_workflow.md` 8장의 정리를 먼저 끝내야
한다(앱 종료 → DB 를 저장소 밖으로 복사 → `git rm -r --cached` → 커밋). 그 정리는 사람이
한다 — `git rm` 은 에이전트 권한에서 막혀 있다.

정리를 건너뛰고 적용하면 두 가지가 한꺼번에 일어난다. ① 그 파일들은 ZIP 에 없으므로
「사외에서 지워진 파일」로 판정돼 적용이 지운다. ② 1-5 의 되돌리기가 그 전에 실데이터를
덮는다.

### 1-5. 작업트리를 비운다

```powershell
git status --porcelain --untracked-files=no
```

**한 줄이라도 나오면 적용기가 멈춘다.** 사내에서 소스를 고쳤다면 커밋하지 말고 되돌린다.

```powershell
git checkout -- <경로>
```

**경로를 하나씩 확인하고 되돌린다.** `git checkout -- .` 처럼 전체를 쓰지 않는다. 경로에
`.duckdb`·`.wal`·`data/input`·`data/output`·`data/temp` 가 들어 있으면 **되돌리지 말고
사용자에게 알린다** — 그것은 소스 수정이 아니라 실데이터이고, 되돌리면 운영 데이터가
사라진다. 1-4 를 제대로 끝냈으면 이 목록에 그런 경로가 나올 수 없다.

`git checkout` 은 일부러 권한 allow 에 넣지 않았다. 매번 프롬프트가 떠서 **사람이 경로를
읽고 승인**하게 되어 있다.

되돌리기 전에 그 내용이 필요하면 리뷰 문서에 코드블록으로 옮겨 적는다 — 그것은 저장소 수정이
아니다. 아직 커밋하지 않은 `review/*.md` 가 있으면 **먼저 `review:` 로 커밋한다.** 그러지
않으면 이 단계에서 지워진다.

## 2. 적용 (본 작업)

### 2-1. 먼저 보기만 한다

```powershell
uv run --no-sync python scripts/apply_deploy_package.py <내려받은 ZIP 경로> --dry-run
```

**ZIP 경로는 슬래시로 쓴다** — `C:/Dev/.../202610021506.zip`. 에이전트의 셸이 Git Bash 면 역슬래시
(`C:\Dev\...`)가 사라져 「파일이 없다」로 끝난다(`202610021506` 리뷰). PowerShell 에서도 슬래시는
그대로 통한다.

`--dry-run` 은 **아무것도 바꾸지 않는다.** 깨끗한 작업트리도 요구하지 않는다. 출력에서 아래를
읽는다.

| 칸 | 뜻 | 할 일 |
|---|---|---|
| `사외에서 지워진 파일` | 추적 중인데 목록에 없다 | 적용이 지운다. 뜻밖의 것이 있으면 **여기서 멈추고** 사용자에게 묻는다 |
| `사내에만 있는 정체불명 파일` | 추적도 무시도 안 된다 | **스스로 지우지 않는다.** 아래 2-2 로 |
| `목록에 있는데 사내에 없는 파일` | 적용 전이면 정상 | ZIP 이 채운다 |

`--reconcile-only` 는 목록 대조만 본다(동작은 `--dry-run` 과 같은 자리에서 끝난다).

### 2-2. 정체불명 파일을 먼저 정리한다

**적용보다 먼저 한다.** 적용기의 커밋 단계는 이번 배포가 실제로 건드린 경로만 스테이징하므로
정체불명 파일을 빨아들이지는 않지만, 그래도 남겨 두면 다음 배포에서 다시 물어야 한다.

파일마다 사용자에게 묻고 셋 중 하나를 고른다.

1. **사내에서만 쓰는 것** → 그대로 둔다. `.gitignore` 에 넣을 필요가 있으면 **리뷰 문서에
   적어 사외가 넣게 한다** (사내에서 `.gitignore` 를 고치지 않는다)
2. **사외에도 있어야 하는 것** → 리뷰 문서에 적어 사외가 추가하게 한다
3. **옛 배포의 잔해** → 지운다

판단이 서지 않으면 (1)로 두고 리뷰 문서에 남긴다. 지우는 것은 되돌릴 수 없고, 남기는 것은
다음 배포에서 다시 물으면 된다.

**사내에서 쓴 기록 문서**(예: `HANDOFF_AUDIT_2026-09-17.md` — 사외 저장소에는 한 번도 없던 파일이다)는
(1)로 두는 대신 사용자에게 물어 **`review/` 로 옮겨 `review:` 로 커밋**하면 다음 배포부터 묻지 않는다.
`review/` 는 배포가 보내지도 지우지도 않는 사내 자리다. 옮기는 것도 사용자가 고른 뒤에만 한다.

아직 커밋하지 않은 `review/*.md` 가 있으면 **적용 전에 `review:` 로 먼저 커밋한다.**
`deploy:` 커밋과 섞이지 않게 하려는 것이다.

### 2-3. 적용한다

```powershell
uv run --no-sync python scripts/apply_deploy_package.py <내려받은 ZIP 경로>
```

끝나면 `deploy: <stamp> (<사외 커밋 7자>)` 로 자동 커밋된다.

**에이전트의 자동 권한 판단이 이 명령을 막으면** 같은 명령을 되풀이하지 않는다. 사용자에게 위 한 줄을
**ZIP 경로까지 채워(슬래시로)** 알려 주고, 사용자가 `! <명령>` 으로 직접 친 출력을 읽고 이어 간다
(`202610021506` 적용 때 두 번 막혀 이렇게 했다). 적용 결과의 대조·커밋은 스크립트가 같게 한다.

## 3. 적용 뒤 읽는 법 — 정상인데 이상해 보이는 두 줄

**이 둘은 결함이 아니다. 리뷰 문서에 결함으로 적지 않는다.**

### 3-1. `목록에 있는데 사내에 없는 파일` 은 비어 있어야 한다

적용 **뒤**에 이 칸에 무엇이든 있으면 이상이다(`해제가 덜 됐습니다`). 판정의 근거는 **바로
앞줄**이다.

```
대조    N/N 해시 일치
```

이 줄이 먼저 나왔으면 전 파일이 맞게 풀린 것이다.

> 예전 배포에서는 이 칸에 `data/input/RQ_DISPLAY_ORDER.csv` 한 줄이 **항상** 떴다. 그 파일이
> 배포 세트에 실리면서 동시에 `.gitignore` 에 걸려 대조가 쓰는 두 목록 어디에도 안 잡혔기
> 때문이다. 지금은 `data/input/` 아래를 아예 보내지 않으므로 그 오탐이 없다. 아직도 뜬다면
> **옛 ZIP 을 적용하고 있는 것이다.**

### 3-2. `pytest` 에서 `test_the_top_level_stays_the_declared_set` 실패

`['.deploy/', 'review/']` 때문에 실패하면 **옛 배포를 적용한 것이다.** 두 폴더는 사내에만
생기므로 사외에서는 재현되지 않고, 그래서 한동안 사내에서만 깨졌다. 지금 배포부터는 그 둘이
`INTERNAL_ONLY_TOP_LEVEL` 로 선언돼 있어 통과한다. 그래도 실패하면 **그 사실 자체를 리뷰
문서에 적는다.**

`static/`(글꼴, `202610061748` 배포부터)이 걸려 실패하면 꼴로 가른다. 「최상위에 선언되지 않은 항목이
있습니다 … ['static/']」이면 테스트 파일이 옛것이다 — 일부만 풀린 적용이다. 「선언에는 있는데 저장소에 없는
항목입니다 … ['static/']」이면 `static/` 이 풀리지 않았거나 커밋되지 않았다 — 3-1 의 `목록에 있는데 사내에 없는
파일` 을 함께 본다. 어느 쪽이든 고치지 말고 리뷰 문서에 적는다.

### 3-3. 루트의 `requirements.txt` 는 사내 WebIDE 컨테이너 전용이다

**손으로 적는 파일이 아니라 `uv.lock` 의 그림자다.** 개발 PC 와 CI 는 `uv sync` 로 잠금을
보지만, 사내 WebIDE 의 CI/CD 는 `docker/Dockerfile-prod` 로 이미지를 만들고 그 안에서
`pip install -r requirements.txt` 를 돈다. 둘이 갈라지면 **사내 컨테이너만 조용히 다른
버전을 쓴다** — 화면에 오류가 나지 않고 계산 결과만 달라질 수 있다.

- **사내에서 이 파일을 고치지 않는다.** `tests/test_requirements_export.py` 가 `uv.lock`
  과 대조하므로 고치면 검증에서 걸린다. 사외가 `uv export` 로 다시 뽑는다.
- **`uv sync` 를 이 파일로 대신하지 않는다.** 개발용 도구(ruff·mypy·pytest)가 빠져 있다.
- 이 파일에는 프로젝트 자신(`-e .`)이 **일부러 빠져 있다.** 그래서 컨테이너는
  `Dockerfile-prod` 의 `ENV PYTHONPATH=/project/src` 로 `src` 를 찾는다. 둘은 한 쌍이라
  한쪽만 보고 판단하지 않는다.

## 4. 적용 뒤 할 일

### 4-1. 의존성 — 변경 목록에 `pyproject.toml` 이나 `uv.lock` 이 있을 때만

```powershell
uv sync --inexact
```

맨 `uv sync` 는 `bigdataquery` 를 지운다. 지웠으면 되돌린다.

```powershell
uv pip install -r requirements-company.txt
```

### 4-2. 마이그레이션은 앱이 알아서 한다

앱을 한 번 띄우면 `data/capa_simulation.duckdb` 와 `data/equipment_availability.duckdb` 에
새 마이그레이션이 적용된다. **적용된 마이그레이션은 버전 번호로 체크섬을 대조하므로, 사내에서
SQL 파일을 고치면 앱이 시작조차 못 한다.**

**이 명령은 사용자가 친다.** 서버는 끄기 전까지 안 끝나므로 에이전트가 띄우면 세션이 거기서
멈춘다. 그리고 브라우저로 한 번 들어가야 마이그레이션이 실제로 걸린다.

**두 DB 는 걸리는 때가 다르다.** 시뮬레이션 DB 는 첫 화면(HOME)에서 걸리지만 설비 DB 는
연결을 처음 쓸 때 만든다 — **`가용설비 현황`(또는 `Space 현황`) 페이지를 실제로 열어야** 설비
마이그레이션이 적용된다(`표준 목표`·`표준 대비 재공 현황 (구현중)` 도 설비 DB 를 열지만 확인은 앞의 둘로 한다).
설비 마이그레이션이 있는 배포면 그 페이지까지 열어 확인한다(`202609281727` 리뷰의 지적).

```powershell
uv run --no-sync python -m streamlit run app.py
```

화면이 뜨는 것까지 확인하면 `Ctrl+C` 로 끈다. 오류가 나면 **고치지 말고** 리뷰 문서에 적는데,
**원문을 그대로 붙이지 않는다** — 이 앱의 오류 문구에는 설계상 공정명·제품명 같은 식별값이
박혀 있다. 5장의 가명화 규칙을 그대로 적용해 옮겨 적는다.

### 4-3. 네 관문을 돌린다

```powershell
uv run --no-sync python -m ruff format --check .
uv run --no-sync python -m ruff check .
uv run --no-sync python -m mypy
uv run --no-sync python -m pytest
```

  `계획 · LOB 요약`(행 넷 — `Density (억Gb)` · `Wafer 계획` · `Dynamic B/N 확보율 현재` · `Dynamic B/N 확보율 단축 후`), 그

  월 표(`가용대수` · `소요대수` · `확보율` · `과부족 (목표 110%)`), 호기 줄(왼쪽 이름, 가운데 ● 기존 Qual ◀ 목표 Qual
  타임라인, 오른쪽 `−N일` 또는 「신규」)이다. 공정을 고르지 않으면 **고른 목표에서 한 달이라도 모자란 공정만** 카드로 선다.
- **CSV 셋** — 범위는 셋 다 화면과 같다(조건 카드의 `공정`, 비우면 맞댄 공정 전체 · 고른 달).
  - `호기별 단축 일정 CSV` — 고른 목표에서 호기마다 한 줄(당긴 호기와 「추가N」). **27칸** — `목표 확보율(%)` · `공정` ·
    `Cut-off(일)` · `호기` · `구분`, 호기 마스터 속성 열둘(`공정대분류` · `공정소분류` · `Model` · `동` · `층` ·
    `투자구분` · `Main 설비` · `설비명` · `모듈 수` · `환산비` · `반입일정` · `확정상태`), `기존 Qual 완료일` ·
    `기존 기여 시작일` · `목표 Qual 완료일` · `목표 기여 시작일`(기여는 Qual 다음 날부터), `단축일수` ·
    `늘어난 환산대수` · `대상 월` · `대상 월 부족 대수(단축 전)` · `대상 월 부족 대수(단축 후)` · `해소 기여 월`.
    「추가N」 줄은 마스터 칸·기존 일정·단축일수가 빈칸이다. 부족 대수 「단축 후」는 그 목표의 단축·신규를 모두 반영한
    뒤의 값이라 호기 하나의 몫이 아니다.
  - `호기별 단축 일정 CSV · 목표 전체` — 같은 27칸 표를 다섯 목표(90~130%) 한 파일로 잇는다(`목표 확보율(%)` 칸으로
    가른다).
  - `공정·월 CSV` — 고른 목표의 공정 × 월, **12칸**(`목표 확보율(%)` 과 공정 · 생산계획년월 · 소요 · 목표 · 가용 전/후 ·
    확보율 전/후 · 과부족 전/후 · 상태).
  - 호기별 두 파일에는 설비명·Main 설비·Model·동·층 같은 실데이터 칸(5장)이 들어 있다 — 아래 8) 대로 **행 수·칸 수만**
    적는다.
- **DB 에 쓰지 않는다.** 이 탭에는 저장 단추가 없다 — 단추는 CSV 받기 셋뿐이고, 받기는 화면을 다시 계산하지도 않는다.
  호기 마스터의 Qual 일정은 바뀌지 않는다.
- **결함이 아닌 것.**
  - **「기한 지남」** — 그 달 W/D 구간 `(전월 말일 − Cut-off, 당월 말일 − Cut-off]` 이 오늘로 이미 끝났으면 당겨서 채울 수
    없어, 과부족 칸 아래에 「→ … · 기한 지남」으로 남는다. 사내 Cut-off 는 30~42일이라 구간이 달력보다 한 달 남짓 앞선다 —
    조회기간 첫 달부터 **이번 달까지(월말이 가깝고 Cut-off 가 길면 다음 달까지)는 모자라면 「기한 지남」이다.** 그런 달만
    모자란 공정도 KPI 의 `부족 공정` 에 들고 카드로 선다.
  - **진행 중인 달의 「추가N」 여러 대** — 오늘이 구간 안에 든 달(대개 다음 달)은 가상 호기 한 대가 **남은 날만큼만** 덮는다.
    그래서 작은 부족에도 여러 대가 붙고, 그 대수가 뒤 달에는 한 대씩 온전히 기여해 뒤 달 가용이 필요보다 크게 넘칠 수 있다
    (2026-10-07 사용자 결정 「지금대로」). 한 달 50대를 넘어야 하면 그 달의 가상 호기를 걷고 「→ … · 남은 날 부족」으로 남긴다.
  - **호기 줄이 없거나 「추가N」 뿐** — 당길 후보는 Qual 이 오늘 뒤인 신규 호기뿐이다. 사내에 그런 호기가 적으면 카드 아래가
    「부족한 달이 모두 지난 구간이라 당길 수 있는 호기가 없습니다.」(빈 카드)이거나 「추가N」 줄만 선다.
  - 목표에서 모자란 공정이 하나도 없으면 카드 대신 초록 상자 「목표 110% 에서 모자란 달이 있는 공정이 없습니다. …」가 선다(카드 0).

**확인해 올 것.** 읽기만 한다. **이름을 옮기지 않는다** — 카드 머리의 공정 이름, 호기 줄의 이름, `계획 · LOB 요약` 확보율 칩
아래의 작은 공정 이름, 맞대지 못한 공정 상자를 폈을 때의 목록, 내려받은 CSV 의 내용 모두. 수(KPI 넷·카드 수·줄 수·조각
수, CSV 의 행 수·칸 수)와 % 만 적는다. Density·Wafer·가용·소요 값도 적지 않는다.

1) `가용설비 현황` → `필요단축일정` 탭을 연다(설비 DB 마이그레이션은 이 페이지를 여는 순간 걸린다 — 4-2). 먼저 조건 셋을
   적는다 — KPI 수가 이 셋에 따라 바뀐다. 사이드바 조회기간의 처음·끝 달(「YY.MM–YY.MM」), `설비 조회 조건` 카드를 펴
   `시작 월`·`끝 월` 이 그 조회기간 전체와 같은지(「전체/다름 — YY.MM–YY.MM」 — 소요대수가 없는 달은 빠진다), 본문 머리 띠
   첫 줄 끝 조각이 `공식 vN` 인지(「공식 vN/저장된 리비전/미저장 변경」 — 시나리오명·리비전명은 옮기지 않는다).
   `시작 월`·`끝 월`·`공정` 은 처음 값 그대로 둔다(공정 비움).
2) 오류 없이 뜨는지(「정상/오류」). 노란 「활성 시나리오의 소요대수를 읽지 못해 필요단축일정을 계산하지 않았습니다 …」나 빨간
   「필요단축일정을 계산하지 못했습니다 — …」면 그 앞머리 꼴만 적고 뒤에 붙는 까닭은 옮기지 않는다. 파란 「시나리오
   소요대수와 Dynamic 가용대수에 같은 이름으로 함께 있는 공정이 없습니다 …」면 「맞댄 공정 0」으로 적고 6) 만 이어 한다 —
   이름 규칙의 문제이지 앱 결함이 아니다.
3) `목표 확보율` 목록을 펴 항목이 `90%` · `100%` · `110%` · `120%` · `130%` 다섯인지, 처음 값이 `110%` 인지(「다섯 · 110%/
   다름 — 그 꼴」). 이 세션에서 전에 바꿨으면 그 값이 남는다 — 처음 여는 탭에서 본다.
4) **`110%`** 에서 적는다.
   - KPI 넷 — 「부족 공정 a/b · 단축 대상 n대 · 최대 단축 d일 · 신규 m대」.
   - 공정 카드 수와, 그 가운데 「부족한 달이 모두 지난 구간이라 …」 문구만 선 빈 카드 수(「카드 N개(빈 카드 k개)」). 공정을
     고르지 않았으므로 **카드 수는 KPI 의 a 와 같아야 한다** — 다르면 그 사실을 적는다.
   - 호기 줄 — 「호기 행 N개 · 추가N 행 M개」. 오른쪽에 `−N일` 이 붙은 줄이 호기 행, 이름이 「추가」로 시작하고 「신규」 표가
     붙은 줄이 추가N 행이다. 같은 셈이라 **N 은 KPI 의 n, M 은 m 이다** — 카드마다 세지 말고 KPI 로 적되, 줄이 실제로
     보이는지는 눈으로 본다(n·m 이 0 이 아닌데 줄이 하나도 없거나, 0 인데 줄이 보이면 그 사실을 적는다). 사내에 Qual 이
     오늘 뒤인 신규 호기가 적으면 호기 행 0 이 정상일 수 있다.
   - 과부족 칸 아래 「기한 지남」 이 붙은 칸이 있는지, 「남은 날 부족」 이 있는지(각각 「있음/없음」).
5) `목표 확보율` 을 **`100%`** 로 바꿔 4) 의 KPI 넷 · 카드 수 · 「호기 행 · 추가N 행」을 같은 꼴로 적는다. 본 뒤 `110%` 로 돌려
   둔다.
6) KPI 위 「맞대지 못한 공정 — …」 접힌 상자가 있는지. 있으면 **제목 줄의 수만** 「시나리오에만 a · 설비에만 b · Cut-off
   미기재 c」(없는 조각은 0)로 적는다. 상자를 펴서 나오는 이름은 옮기지 않는다. 없으면 「상자 없음」.
7) `계획 · LOB 요약` 에 행 이름 넷이 다 있는지(「넷 있음/빠짐 — 그 이름」). 상자 아래 「계획 값을 읽지 못했습니다 — …」 줄이
   있으면 그 사실만 적는다(뒤의 까닭은 옮기지 않는다).
8) KPI 아래 단추 셋 — `호기별 단축 일정 CSV` · `호기별 단축 일정 CSV · 목표 전체` · `공정·월 CSV` — 이 다 있는지
   (「셋 있음/그 밖 — 보이는 단추 이름」). **받기는 선택이다** — DB 에 쓰지 않고 화면을 다시 계산하지도 않는다. 받았으면
   파일마다 **데이터 행 수(머리 줄 뺀)와 머리 칸 수만** 「호기별 행 N · 칸 27」 꼴로 적는다. 값과 이름은 한 칸도 옮기지
   않는다.
   - 파일은 사용자의 브라우저가 받는다. 사용자가 Excel 로 열어 마지막 행 번호 − 1 과 마지막 머리 칸의 열(27칸은 `AA`,
     12칸은 `L`)을 알려 준다. 에이전트는 그 파일을 열거나 복사·요약하지 않고, 7-1 2) 의 옛 양식 파일처럼 **저장소
     안(`review/`·`data/`·루트)에 두지 않는다.**
   - 맞대어 볼 것(110% 에서 받았을 때, 수로만). `호기별 단축 일정 CSV` 의 행은 4) 의 KPI **n + m** 이다(당긴 호기와
     「추가N」이 한 줄씩). `공정·월 CSV` 의 행은 KPI 「부족 공정 a / b」의 **b × 고른 달 수**(`계획 · LOB 요약` 의 달
     칸 수)다. `· 목표 전체` 의 행은 다섯 목표의 n + m 을 더한 수라 110% 파일의 행보다 적을 수 없다 — 수만 적는다.
     다르면 「다름」과 두 수를 적는다.
   - 받지 않았으면 「안 받음」.

### 7-10. 앱 정보 카드 — 모든 화면 사이드바 맨 아래 (이번 배포)

7-9 바로 뒤에 한다(7-0 차례 2). 읽기만 하는 2분짜리 확인이다.

- **자리가 바뀌었다**(2026-10-07 사용자 결정). 직전 배포까지 앱 정보는 `Admin Area` 본문 맨 아래, 구분선 아래의 작은 글 세
  줄이었다. 이제는 **모든 화면 사이드바 맨 아래의 작은 카드**이고, `Admin Area` 본문에는 없다.
- **두 줄이다** — 첫 줄은 앱 이름·버전·빌드일(「… v… · 빌드 …」), 둘째 줄은 개발 팀·문의처(「개발 … · …」)다. **셋째 줄(보안
  등급·인증번호(유효기간)·반출·사외 공유 금지)은 걷었다.** 문의처 메일은 누를 수 있는 링크라 강조색이다. 사이드바를 좁히면
  (220px 꼴) 글이 접혀 네 줄처럼 보인다 — **줄은 보이는 줄이 아니라 글로 센다**(앱 줄 하나 · 개발 줄 하나).
- **사이드바 바닥에 붙어 있다.** 사이드바 목록이 길면 목록이 카드 **밑으로 지나간다** — 카드가 목록에 밀려 내려가지도,
  목록이 카드를 덮지도 않는다. 끝까지 내리면 맨 아래 `Support` 상자가 카드 위에 다 보인다. 목록이 짧은 화면(`Admin Area`·
  VOC 게시판)에서도 마지막 상자 바로 아래가 아니라 **사이드바 바닥**에 선다.
- **결함이 아닌 것.** 사이드바를 접으면 카드도 함께 화면 밖이다. 앱이 시작하다 멈춘 부트스트랩 오류 화면은 사이드바를
  세우기 전에 멈추므로 카드가 없다(그 화면만 문의처가 보이지 않는다). 인쇄에는 사이드바가 찍히지 않으므로 카드도 없다.

**확인해 올 것.** 읽기만 한다. **카드의 글은 옮기지 않는다** — 버전·빌드일·팀·메일 모두(문의처 메일은 사람 이름이다, 5장).
「있음/없음 · 두 줄/그 밖」만 적는다. 사이드바 상자 펴기와 스크롤은 이 세션의 보기 조건이라 써도 된다.

1) **HOME** — `Main` 탭을 연 채 사이드바 맨 아래, 창 바닥에 카드가 붙어 있는지(「HOME 바닥 있음/없음」). 사이드바가 스크롤되지
   않을 만큼 짧으면 사이드바의 접힌 상자를 펴서 길게 만든다. 사이드바를 위아래로 굴려 목록이 카드 밑으로 지나가고 끝까지
   내렸을 때 `Support` 가 카드 위에 다 보이는지(「밑으로 지나감 있음/없음」 — 카드가 목록에 밀려 움직이거나, 목록이 카드
   위에 겹쳐 보이거나, `Support` 가 카드에 가려 끝까지 보이지 않으면 「없음」).
2) 카드가 **두 줄**인지 — 첫 줄은 앱 이름으로 시작해 「· 빌드 …」로 끝나고, 둘째 줄은 「개발 …」로 시작한다. 보안 등급·
   인증번호·반출 금지 글이 보이면 「그 밖」이다 — 그때는 옛 파일이 남은 것일 수 있으니 3-1 의 대조 줄을 함께 적는다
   (「두 줄/그 밖」).
3) **Admin Area**(목록이 짧은 화면) — 사이드바 `Support` 상자의 `Admin Area` 로 간다. 카드가 마지막 상자 바로 아래가 아니라
   사이드바 바닥에 서는지(「Admin Area 바닥 있음/없음」). 본문을 맨 아래까지 내려 예전의 구분선과 앱 정보 세 줄이 **없는지**
   (「Admin Area 본문 앱 정보 없음/있음」). Admin Area 의 탭은 열어 보기만 하고 아무것도 저장하거나 붙여넣지 않는다.

### 7-2. Space 현황 — 기둥 이름표 · 글자 크기/색 · 미배치 서랍 · FAB 블록 색

- **기둥 이름표** — 층 도면의 기둥에 이름을 주면 이름표가 **기둥 위 가운데에 가로로** 선다(반입구·문·동선의 바깥 이름표와
  같은 규칙). 편집기와 보기 화면이 같다.
- **도면 요소의 글자 크기·글자 색** — 편집기에서 도면 요소(영역·반입구·문·기둥·글자·동선, FAB 의 층 블록)를 고르면 도면 위
  `선택` 칸의 `이름` 옆에 **`글자 크기`**(`자동` · `9px`~`24px`)와 **`글자 색`**(`기본` · 영역 색 여섯)이 선다. **호기
  상자에는 없다.** `자동`·`기본` 은 예전 그림 그대로다 — 이미 저장된 요소는 모두 그것으로 읽힌다(`0017`).
- **미배치 서랍은 호기를 놓아도 열린 채다** — 이어서 놓을 수 있게. 놓은 호기가 서랍 아래에 들면 화면이 옆으로 옮겨 그
  호기를 보인다. 닫는 것은 전처럼 `접기`·Esc 다.
- **색을 고른 FAB 층 블록은 불투명하다** — 블록 뒤의 영역·격자가 비치지 않는다(빈 캔버스 위에서는 전과 같은 색이다).
  색을 고르지 않은 블록 — 기본 배치의 블록 전부 — 은 그대로다.
- **직전 사내 요약은 「배치 0대 · 미배치 31대 · 레이아웃 제외 865대」였다.** 배치된 층이 없어도 아래 확인은 된다 — 기둥은
  그려 넣고, 서랍의 미배치 호기를 하나 놓아 본 뒤, 둘 다 `처음 상태로` 지운다.

**확인해 올 것.** **저장하지 않고 `적용` 도 누르지 않는다.** 편집기는 모두 **`처음 상태로`**(편집기 도구 줄의 `실행 취소`
옆)로 되돌린 뒤 토글을 꺼서 끝낸다 — `적용` 을 누르지 않았으면 화면 위 `저장 안 한 배치 변경` 상자가 생기지 않는다.
실수로 `적용` 을 눌렀으면 그 상자의 **`버리기` → `FAB 배치만 버리기`**(FAB 만 적용했을 때) 또는 `모두 버리기` 로 버리고
그 사실을 적는다 — 7-1 에서 편집본을 바꾸지 않았으므로 버릴 설비 편집은 없다. `배치 저장` 은 누르지 않는다. 7-1 2) 의
미리보기를 지운 뒤에 한다.

1) `Space 현황` 을 연다. 오류 없이 뜨는지(「정상/오류」), FAB 도면 위 요약 줄의 세 수(「배치 N대 · 미배치 N대 · 레이아웃
   제외 N대」 — 대수만, 넷째 조각 「· 미배치 중 동·층 미정 N대」가 있으면 그것도)를 적는다. FAB 도면이 기본 배치인지
   저장본인지는 화면에 표시가 없다 — 7-8 의 `fab [p, m]` 으로 적는다(`[0, 0]` 이면 기본 배치).
2) **층 열기·F5·손잡이 — 직전 미기록.** 배치된 호기가 있는 층의 블록을 누른다. 없으면 **블록에 미배치 수가 적힌 층**을
   누르고 「배치된 층 없음」으로 적는다. 그 층 상세가 한 번에 열리는지(「열림/안 열림」). 새로고침(F5) → 같은 층에
   머무는지(「머묾/FAB 로 돌아감」). 도면 아래 가로 막대를 끌면 높이가 바뀌고 두 번 누르면 돌아오는지(「됨/안 됨」 —
   높이는 그 브라우저만 기억한다, DB 에 쓰지 않는다).
3) **층 편집기.** 그 층 머리 줄의 `배치 편집` 을 켠다.
   - 도면 위 `도면 요소` 칸의 `기둥` 을 누르면 화면 가운데에 기둥이 선다. 그 옆 `선택` 칸의 `이름` 에 아무 글자(`T1` 꼴)를
     넣고 Enter → 이름표가 **기둥 위 가운데에 가로로** 서는지(「위 가운데/그 밖」).
   - 같은 `선택` 칸에 `글자 크기`·`글자 색` 이 있는지, `글자 크기` 를 `20px`·`글자 색` 을 아무 색으로 바꾸면 이름표가
     바뀌는지(「칸 있음·바뀜/칸 없음/안 바뀜」).
   - 도면 오른쪽 가장자리의 `미배치 N` 탭을 눌러 서랍을 연다. 호기 하나를 끌어 도면에 놓는다 → **서랍이 열린 채인지**
     (「열린 채/닫힘」). 놓은 호기를 눌러 고르면 `선택` 칸에 `글자 크기`·`글자 색` 이 **없는지**(「호기에 칸 없음/있음」).
   - **`처음 상태로`** 를 누른다 → 기둥이 사라지고 놓은 호기가 서랍으로 돌아오는지(「돌아옴/안 돌아옴」). **`적용` 을
     누르지 않은 채** `배치 편집` 을 끈다.
4) **FAB 편집기.** 경로 줄의 `S.PKG FAB 전체` 로 돌아가 FAB 머리 줄의 `배치 편집` 을 켠다.
   - 층 블록 하나를 누른다(편집 중에는 고르기다 — 열리지 않는다). `선택` 칸에 `이름`·`글자 크기`·`글자 색` 과 `연결`·
     `색`·`열기` 가 서는지(「섬/안 섬」). **`열기` 는 누르지 않는다**(편집 중 다른 화면으로 간다).
   - 그 블록의 `색` 을 아무 색으로 고른다 → 블록 면이 한 색으로 칠해지고 뒤의 영역 테두리·격자 줄이 비치지 않는지
     (「불투명/비침」).
   - **`처음 상태로`** → 블록이 원래대로 돌아오는지 보고, **`적용` 을 누르지 않은 채** `배치 편집` 을 끈다. 화면 위에
     `저장 안 한 배치 변경` 상자가 없는지(「상자 없음/뜸」 — 「뜸」이면 위 안내대로 버리고 적는다).

### 7-3. 확보율 판정 — 기준과 같으면 확보 · 범례 · 산출 결과 히트맵

- **확보율이 확보 기준과 같으면 확보다**(2026-10-06 사용자 결정). 확보·경고 모두 기준 **이상**이다 — 경고는 전부터
  이상이었고, 바뀐 것은 확보 쪽(전에는 기준을 **넘어야** 확보)이다. HOME LOB 칸·B/N·Top5·결론 문장, 사이드바 `B/N 집계
  공정` 의 `공정 선택` 팝업(구역 이름 「기준 초과」 → **「확보 기준 충족」**), `산출 결과` 히트맵, Summary 가 같은 판정을
  쓴다. `Static Capa` 부족 현황은 이미 이 쪽이었다.
- **그래서 색이 바뀌는 칸은 확보율이 그 달의 확보 기준과 정확히 같은 칸뿐이다**(경고 → 확보). 사내는 공용 판정 기준이
  이미 저장돼 있다(직전 7-8 `thresholds [1, 3]` — 기본 1행 · 월별 3행). 판정은 그 값으로 하고, 이번 배포는 그 값을 바꾸지
  않는다.
- **범례는 「확보 · 경고 · 부족」** 세 이름이다(「초과 확보」가 「확보」로 줄었다). HOME `Capa LOB 현황` 제목 줄과
  Summary `B/N 확보율` 줄에만 있다.
- **`산출 결과` → `확보율` 탭의 히트맵은 `히트맵` 접힘 상자 하나다**(처음에는 접혀 있다). 행은 위 확보율 표와 같다 —
  사이드바 `표 조건` 카드의 필터가 히트맵에도 걸린다. 따로 고르던 「히트맵 주요 공정」 목록, 부족 공정 수·가장 이른
  부족 문구, 부족 요약 표, 범례는 모두 없어졌다. 상자 이름도 「주요 공정 × 월 히트맵」에서 `히트맵` 으로 줄었다.

**확인해 올 것.** **저장하지 않는다** — `판정 기준 저장` 을 누르지 않고 두 칸·월별 표에 아무것도 적지 않는다.
Preference 탭의 다른 상자(특히 고르는 즉시 쓰는 `비교 시나리오`·`비교 리비전`)는 건드리지 않는다.

1) **범례** — HOME `Main` 의 `Capa LOB 현황` 제목 줄 오른쪽, 사이드바 `S.PKG CAPA` 로 연 Summary 의 `B/N 확보율` 줄
   (`Esc` 로 닫는다). 둘 다 「확보 · 경고 · 부족」인지(각각 「셋/그 밖」).
2) **판정 기준 — 직전 미기록.** HOME → `Preference` → `확보율 판정 기준` 상자. 캡션은 저장본이 있으므로 「공용 버전 vN ·
   …」 꼴일 것이다 — **N 과 저장 날짜만** 적는다(가운데의 구성·출처 글은 옮기지 않는다 — 메모라 이름이 들 수 있다). `기본 확보 기준(%)`·`기본 경고 기준(%)`
   두 값(% 숫자는 식별값이 아니다), 월별 표에서 값이 든 칸 수(「확보 N칸 · 경고 N칸」 — 조회기간 밖 저장분은 보이지
   않으니 보이는 것만).
3) **히트맵** — `산출 결과` → `확보율` 탭. 표 아래 `히트맵` 상자가 하나뿐이고(「상자 하나/그 밖」), 펴면 공정 × 월 그림만
   있는지 — 공정 고르는 목록·부족 요약·범례가 없는지(「없음/있음」). 사이드바 `표 조건` 카드에서 필터 하나(공정대분류
   하나 꼴)를 고르면 표와 히트맵이 **같이** 줄어드는지(「같이 줄어듦/히트맵 그대로」). 본 뒤 `필터 초기화` 를 누른다.
   상자 펴기·필터는 쓰기가 아니다.
4) 사용자에게 이번 배포 뒤 판정 색이 바뀐 칸을 봤는지 묻는다(「못 봄/봄」). 봤으면 그 칸의 확보율이 그 달 확보 기준과
   같았는지 적는다(「같음/다름/모름」 — 공정 이름·값은 적지 않는다). 「같음」이면 이 배포의 의도다. 「다름」이면 그사이
   사내에서 공식버전·활성 리비전·판정 기준이 바뀌지 않았는지도 함께 적는다.

### 7-4. 선행 B/O · 선행 입고 실적

- **「선행 전망」 → 「선행 B/O」** — 이름만 바뀌었다. 사이드바 `LOB 표시 조건` 카드의 토글과 Preference 의 상자(옛
  「선행 투입 물량」)가 「선행 B/O」다. 계산·저장 자리·세션 값은 그대로다 — 저장해 둔 값은 그대로 보이고, 켜 둔 토글도
  그대로다. 저장 단추는 `선행 B/O 저장`, hover 는 「Density (선행 B/O 전)」이다.
- **새 공용 설정 「선행 입고 실적」(억Gb)** — 계획보다 앞서 입고한 물량이다. 생산계획에 이미 들어 있어 **계산을 바꾸지
  않고** Density 가운데 얼마가 선행 입고였는지 보이기만 한다. Preference 의 `선행 B/O` 상자 바로 아래이고(상자 차례는
  `비교 시나리오` → `확보율 판정 기준` → `선행 B/O` → `선행 입고 실적` → …), 달은 LOB 월 축 그대로다(Past Data 를 켜면
  과거 달도). 저장은 `선행 입고 저장` — 시뮬레이션 `0031` 공용 프로필이라 **사내 모든 사람 화면에 같이 보인다.**
- **토글 「선행 입고」** — `LOB 표시 조건` 카드에서 `선행 B/O` 바로 아래, **기본 끔**. 켜면 저장된 달의 Density 칸 **오른쪽
  끝, 값과 같은 높이에** `+#.#` 글자(12px — 밝은 테마는 검정, 어두운 테마는 본문 글자색)가 선다. 0 으로 보이는 값과 연간
  Total 칸에는 적지 않는다. hover 는 「선행 입고 실적 +1.2억Gb」 꼴이다. Summary 에는 없다.
- **값이 길면 이 글자가 Density 값과 겹칠 수 있다** — 사용자가 겹침을 받아들이고 정한 자리다(2026-10-07 결정). 결함으로
  적지 않는다.

**확인해 올 것.** **읽기만 한다.** 「선행 입고 실적」은 공용 프로필이다 — `선행 입고 저장`·`선행 B/O 저장` 을 누르지 않고
표에 아무것도 적지 않는다.

1) HOME → `Preference` 에 `선행 B/O` 상자와 그 바로 아래 `선행 입고 실적` 상자가 있는지(「둘 다 있음/옛 이름 남음/없음」).
   `선행 입고 실적` 의 캡션은 저장본이 없으면 **「공용 버전 없음 · 아직 넣은 선행 입고 실적이 없습니다」** 다(「저장본
   없음/공용 버전 vN」). 표 맨 앞 `구분` 칸의 행 이름 「선행 입고 실적」이 잘리지 않고 다 보이는지(「다 보임/잘림」).
2) HOME `Main` 탭에서 사이드바 `LOB 표시 조건` 카드의 토글 차례가 `선행 B/O` · `선행 입고` · `실행 Loss` · `GAP` · `상세
   계획` · `EDP 포함` · `Past Data 포함`(그 아래 `제품별 비중 단위`)인지, 처음에 `선행 입고` 가 꺼져 있는지(「차례 같음/다름 · 꺼짐/켜짐」 — 이 세션에서 전에 켠 적이
   있으면 켜져 있을 수 있다). `선행 입고` 를 켠다 — 저장본이 없으면 **Density 칸에 아무 글자도 생기지 않는 것이
   정상이다**(「글자 없음/`+#.#` N칸」). 누가 이미 저장했으면 그 달 칸 오른쪽 끝에 `+#.#` 이 선다 — 칸 수만 적는다. 본 뒤
   토글을 끈다(토글은 이 세션의 보기 조건이라 DB 에 쓰지 않는다).

사용자에게 앱을 꺼 달라고(`Ctrl+C`) 한 다음 아래 한 줄을 돌린다. 두 DB 를 `read_only` 로 열고, 값은 찍히지 않고 개수만

AND table_name = ? AND column_name IN (?, ?)', ['equipment_ops', t, 'font_size', 'font_color']); print('migration', q('SELECT max(version) FROM app_meta.schema_migration'), 'equipment_migration', r('SELECT max(version) FROM equipment_meta.schema_migration'), 'advance_shipment', [q('SELECT count(*) FROM app_meta.global_advance_shipment'), q('SELECT count(*) FROM app_meta.global_advance_shipment_month')], 'font_columns', [f('floor_layout_mark'), f('fab_layout_mark')], 'thresholds', [q('SELECT count(*) FROM app_meta.global_securement_threshold'), q('SELECT count(*) FROM app_meta.global_securement_threshold_month')], 'fab', [r('SELECT count(*) FROM equipment_ops.fab_layout_profile'), r('SELECT count(*) FROM equipment_ops.fab_layout_mark')], 'layout_marks', r('SELECT count(*) FROM equipment_ops.floor_layout_mark'), 'dup_names', q('SELECT count(*) FROM (SELECT scenario_name FROM app_meta.scenario GROUP BY scenario_name HAVING count(*) > 1)'))"

- `font_columns [a, b]` — `0017` 이 더한 열(`font_size`·`font_color`)이 층 도면 요소 표와 FAB 요소 표에 각각 몇 개

- `thresholds [h, m]` — 공용 판정 기준의 기본값 행(0 또는 1)과 월별 행 수. **직전 `[1, 3]` 과 같아야 한다**(이번 확인은
  읽기만 했다). 다르면 그사이 누가 `판정 기준 저장` 을 누른 것이다 — 결함이 아니니 수만 적고 사용자에게 알린다.
- `fab [p, m]` — 저장된 FAB 캔버스 행(0 또는 1)과 FAB 요소 수. 이번 확인은 `처음 상태로` 되돌렸으므로 **`[0, 0]`** 이어야

  누가 도면 요소를 저장한 것이다 — 결함이 아니니 수만 적는다.
- `dup_names N` — 이름이 겹치는 시나리오 이름의 수. 0 이 아니면 사용자에게 알린다 — 겹친 이름은 사이드바·보관함에서

  줄에서 뺐다.
- `duckdb.IOException` 이면 앱이 아직 떠 있다.

## 8. 실데이터 확인 (배포마다 반복)

(`docs/TODO.md` 의 「사내 실데이터 확인 절차 준비됨 — 결과 대기」 항목). 사내에서

### 8-0. 언제 · 무엇을 치나

**7장(그 배포의 확인)을 마친 뒤, 앱을 끈 채로 돌린다.** 앱이 떠 있으면 「DB 를 열지 못했습니다. 앱이 떠
있으면 먼저 끄세요 …」 한 줄을 찍고 멈춘다(종료 코드 1) — 사용자에게 `Ctrl+C` 를 부탁하고 다시 친다.
앱이 꺼져 있는데도 그 줄이 나오면 파일 손상일 수 있다 — 고치려 하지 말고 그 사실을 리뷰 문서에 적는다.
설비 DB 는 `가용설비 현황` 을 한 번 연 뒤라야 마이그레이션이 다 걸려 있다(4-2). 7장을 했다면 이미 걸렸다.

```powershell
uv run --no-sync python scripts/inspect_real_data_checks.py
uv run --no-sync python scripts/inspect_real_data_checks.py --only bdq
```

- **첫 줄** — DB 확인 넷(8-1 ~ 8-4). 사내 원천 크기에 따라 수십 초 ~ 몇 분이다(가장 최근 데이터셋의 원천을
  읽어 부하량·소요대수를 다시 계산한다).
- **둘째 줄** — BigDataQuery(8-5). 사내 DB 에 직접 묻는다. WebIDE 처럼 요청자 계정이 필요한 환경이면 먼저
  `export CAPA_BDQ_USER_NAME="<AD 계정>"` 을 넣은 셸에서 친다
  ([`bigdataquery_webide_setup.md`](bigdataquery_webide_setup.md)). 목록 조회 두 번(오늘−30일 ~ 오늘,
  366일)과 표본 다섯 코드마다 상세 조회 두 번·적재일 조회 한 번이라 **몇 분 걸릴 수 있다.** 366일 목록이

  보려면 `--dataset-id <ID>`(ID 는 앱이 만든 무작위 값이라 적어도 된다). 고르지 않으면 원천에서 온
  데이터셋 가운데 가장 최근 것을 본다 — 복제·월 병합·연도 이동으로 만든 데이터셋은 건너뛴다.
- 출력은 Markdown 이다. 처음부터 끝까지 리뷰 문서에 붙인다(8-6). 표가 넓어 터미널 스크롤에서 잘리면
  `--output` 으로 **저장소 밖** 파일에도 받아 거기서 복사한다 — 예: `--output $HOME/real_data_check.md`,
  `--only bdq --output $HOME/real_data_check_bdq.md`. 저장소 안(`review/` 포함)에 따로 두지 않는다.

각 블록에서 「읽지 못함」·「실패(예외 종류)」 가 나와도 **스크립트는 다음 블록으로 계속한다.** 실패한 줄도
그대로 옮긴다 — 그것도 사외에는 답이다.

### 8-1. `env` — 두 DB 와 적용 배포

- `적용 배포` — `.deploy/applied.json` 의 stamp 와 사외 커밋. 2-3 에서 적용한 ZIP 과 같아야 한다.
- `마이그레이션 … (최고 N · 코드 M, …)` — **「코드와 같다」가 정상이다.** 「코드보다 낮다」면 그 DB 를 여는
  화면을 열지 않은 것이다(4-2) — 앱을 띄워 HOME 과 `가용설비 현황` 을 연 뒤 끄고 다시 돌린다. 「코드보다
  높다」면 옛 ZIP 을 적용했을 수 있다 — 그대로 적는다.
- 행 수 표 — 데이터셋·시나리오·리비전·공식버전·원천 행 수와 데이터셋 원천 종류(`BIGDATAQUERY` 등 앱이 붙인
  이름).
- `ref_data 에 리비전 표 사본이 남은 데이터셋` — 2026-10-06 결정(B3) 전에 만든 데이터셋은 같은 표를 두 번
  들고 있다. 읽는 곳은 없고 파일만 키운다 — 정리할지는 사외가 이 수를 보고 정한다.

### 8-2. `legacy` — 기존 결과 대조

원천 Core Data 에는 기존 앱이 계산해 실어 보낸 값(`WF수(매)` 등)이 그대로 있다. 이 블록은 그 값과 이
앱의 계산을 맞대어 **차이의 분포**만 찍는다. 기준은 가장 최근에 적재한 데이터셋의 원천과 그 시나리오의
**리비전 1**(원천 그대로)이다 — 사내에서 고친 리비전은 대조에 들지 않는다.

- **원천 컬럼 표** — 여섯 컬럼이 얼마나 차 있는지. `소요대수`·`PCB수(K매)`·`GOOD_DIE` 가 비어 있으면 그
  아래 대조는 「비어 있어 대조 불가」로 끝난다. **그것도 답이다**(사외 표본은 셋 다 비어 있다).
- **부하량 표**(`WF수(매)`·`EQ(억Gb)`) — 키마다 |신규 − 기존| ÷ |기존|.
  - `차이율 중앙`·`p95`·`최대`, `>0.1%`·`>1%` 는 그 비율을 넘는 키 수다. **최대가 0.5% 안이면 산식이 맞다.**
  - `기존 0·신규 있음` — 기존이 0 을 적은 키(비율을 구할 수 없다). 사외 표본에서는 전부 `WF 구분 = Dummy`
    였다 — 기존 앱이 Dummy Wafer 를 0 으로 두었다는 뜻이다.
  - `값 불일치` — 기존 값이 계획 줄 × WF 구분 안에서 경로마다 갈려 접을 수 없었던 키. 0 이 아니면 대조
    단위를 다시 설계해야 한다는 신호다.
  - `신규에만`·`기존에만` — 한쪽에만 있는 키. `기존에만` 이 0 이 아니면 신규가 놓친 자리가 있다.
- **소요대수** — 먼저 `키 연결` 줄(신규 경로 키 가운데 원천 경로에도 있는 키의 비율, **100% 가 정상**).
  원천에 값이 있으면 세 줄로 대조한다. 기존 값이 경로 행마다 어떻게 실리는지 사외가 모르기 때문이다.
  - `경로 키 13 · 같은 경로 반복을 접음` / `월×공정×소요기준 · 접음` — 같은 경로에 반복된 값을 한 번만 센다.
  - `월×공정×소요기준 · 접지 않고 행마다 더함` — 원천 행마다 따로 더한다.
  - 둘 중 **한쪽만 맞으면 그쪽이 원천의 실리는 방식**이다. `└ 접음 · 소요기준 …` 줄은 소요기준별로 나눈
    것이다 — PKG 만 어긋나면 「PKG 는 Buffer 로만 센다」(6장 표) 규칙 차이다.
- **PCB수(K매)** — 신규 계산이 없다(산식 미구현). 값이 계획 줄 단위인지(`갈리는 칸 0`)와 `생산수량 ÷
  PCB수(K매)`(PCB 한 매당 Unit)의 분포만 본다.
- **Plan_Chip(K개) · GOOD_DIE** — 신규 Chip 부하량(K개)에 대한 비율의 분포. `≈1` 이 대부분이면 정의와 단위가
  같고, `≈1000`·`≈0.001` 이 많으면 단위만 1000 배 다르며, 흩어지면 정의가 다르다. 아래의 `… ÷ (생산수량 ×
  구분_Chip)`·`GOOD_DIE ÷ Net Die` 같은 줄은 원천 행 안에서 본 정의 후보다 — 어느 줄이 `≈1` 에 몰리는지가
  답이다. 마지막 줄은 `GOOD_DIE` 가 제품마다 값 하나인 속성인지 본다.

### 8-3. `reqb` — 원천 RQ_REQB 소요기준 분포

리비전 1 의 `RQ_REQB` 를 소요기준(`PKG`·`CHIP`·`WF`·`BOX`·`PCB`)마다 센다 — 행 수, 공정 수, `Main`·`MI`
공정 수, WF 구분이 하나뿐인 공정과 그 하나가 `BUFFER` 인 공정. 사외가 표본 생성기의 공정 목록을 업무
사실로 잘못 읽은 적이 있어(`docs/TODO.md` 3-5 「Stack 이후 Wafer 공정」) **실데이터로 다시 센다.**

- `그 밖의 소요기준 N종` — 계약 밖 이름이다. 이름은 찍지 않는다. 0 이 아니면 그대로 적는다.
- `소요기준이 둘 이상인 공정` — 업무 규칙상 **0** 이어야 한다(한 공정은 한 소요기준).

### 8-4. `equipment` — 설비 DB

최신 설비 리비전에서 세 가지를 센다. **값은 고치지 않는다** — 고칠 행이 있으면 사용자가 `가용설비 현황`
RawData 에서 고쳐 저장한다. 에이전트는 수만 적는다.

- `Qual일정 = 2262-04-11` — 옛 리비전 변환이 빈 Qual 을 먼 미래로 채우던 자리표다. 이제는 빈 Qual 로 읽혀
  「일정 미정」에 잡힌다. 사용자가 Qual 날짜를 넣어야 할 행 수다.
- `모듈 행 환산비 0.2` — 직접 편집 칸이 0.25 를 0.2 로 자르던 결함의 흔적이다. **사용자가 다시 입력할 행**이다.
  `Main 설비 없이 환산비 0.2` 는 Main 설비를 적기 전의 모듈일 수 있다. `묶음 / 합이 1 이 아닌 묶음` 의 둘째
  수가 0 이 아니면 그 설비의 능력이 한 대가 안 되게 세어지고 있다.
- `일정 미정` — 반입·Qual 일정이 비어 가용대수에 들지 못하는 설비 대수. `가용설비 현황` 의 「일정 미정 N대」
  알림과 같은 셈이다. 「건너뜀: 설비 DB 마이그레이션이 코드보다 낮다」면 8-0 대로 화면을 연 뒤 다시 돌린다.

### 8-5. `bdq` — BigDataQuery

- `준비` 줄 — 패키지·SQL·요청자 계정(값은 찍지 않고 있음/없음만). 「패키지가 없다」면 4-1 의 되돌리기,
  「요청자 계정 필요」면 8-0 의 `export` 를 넣고 새 셸에서 다시 친다.
- **목록 조회 표** — 기간마다 성공 여부, 걸린 초, 목록 행 수(`SELECT DISTINCT` 결과), 코드·PLAN 수, 코드 수,
  화면이 느려지는 3,000 을 넘는지. 기본 기간(오늘−30일 ~ 오늘)은 `BigDataQuery 등록` 화면의 첫 값과 같다.
- **`reg_date`** — dtype, 값의 종류, 숫자면 자릿수, 문자열이면 꼴(숫자는 `9`, 영문은 `A` 로 바꾼 모양),
  원천 등록시각으로 읽지 못하는 값 수. 숫자형은 앱이 일부러 버린다(1970 년으로 읽히는 것을 막는다).
  `코드·PLAN 하나의 서로 다른 등록시각 수` 가 1 보다 크면 `reg_date` 가 행 단위 적재 시각이다.
- **`catb_sim_info_id` 규칙 위반** — `^[A-Za-z0-9._-]+$` 를 벗어나 화면에서 저장이 막히는 코드 수와 까닭의
  종류.
- **표본 적재일 표** — 규칙을 지키는 코드 가운데 첫 등록일 순으로 고르게 다섯을 골라, 상세 조회 기본 창
  (원천 등록일 −7 ~ +3일)과 넓은 창(±30일)의 행 수를 견준다. **`기본 창 행 = 넓은 창 행` 이 전부면 기본
  창으로 충분하다.** `기본 창이 놓친 행` 이 0 이 아니면 사외가 기본 창을 넓힐지, 같은 코드를 다시 받는 길을
  둘지 정한다(`docs/TODO.md` 결정 대기). 아래 적재일 줄은 **사외에서 돌려 보지 못한 SQL**(적재 시각의
  날짜별 행 수)이다 — 사내 엔진이 받지 않으면 「조회 실패(예외 종류)」 한 줄만 남고 나머지는 계속된다.

### 8-6. 리뷰 문서에 옮기는 법

리뷰 문서(5장) 끝에 아래 절을 더하고, 출력 블록 `8-1` ~ `8-5` 를 **그대로** 붙인다. 블록 제목(`### 8-1. …`)
까지 함께 붙인다 — 사외는 그 제목으로 블록을 찾는다.

- 출력은 고치지 않고 붙였다 · 더한 것은 아래 「사내 메모」 뿐이다 : 확인함 ☐

### 8-7. 하지 않는 것

- **DB 를 SQL 로 고치지 않는다.** 2262-04-11 자리표·환산비 0.2·`ref_data` 사본이 보여도 그대로 둔다 — 리비전은
  append-only 이고, 고칠 길은 사용자가 화면에서 저장하거나 사외가 후속 마이그레이션을 만드는 것뿐이다.
- **스크립트를 고치지 않는다**(0장). 출력이 이상하거나 실패하면 그 줄을 그대로 적는다.
- **출력에 없는 값을 더 찾아 적지 않는다.** 「어느 제품이 어긋났나」·「어느 코드가 규칙을 어겼나」가 궁금해도
  키별 값, 제품·공정·설비 이름, 시뮬레이션 코드, 오류 원문은 적지 않는다. 사외가 필요하면 가명 규칙(5장)으로
  따로 묻는다.
- **`scripts/compare_legacy_results.py` 를 대신 돌려 옮기지 않는다** — 그 스크립트는 허용을 넘은 키의 제품·
  Stack 을 그대로 찍는다(사외 디버깅용이다).
- **확인을 위해 쓰지 않는다** — 데이터셋을 새로 등록하거나 원천을 다시 받거나 리비전을 저장하지 않는다.
  앱을 띄운 채 돌리지 않는다.

### 8-8. 사외가 답하는 법

사외는 리뷰의 「실데이터 확인」 절을 블록마다 읽고 **사용자와 대화로** 다음 일을 정한다. 정한 것은 다음
배포의 7장(사내가 따로 할 일)과 `docs/TODO.md` 에 적는다. 예를 들면 —

- 8-2 에서 `Plan_Chip(K개)` 가 `≈1` 에 몰리면 대조 목록(`services/legacy_comparison.py` 의 `COMPARISONS`)에
  넣고, `≈1000` 이면 단위를 맞춘 뒤 넣는다. 소요대수의 한쪽 줄이 맞으면 그 방식으로 대조에 넣는다.
- 8-4 에서 0.2 행이 있으면 사용자에게 다시 입력할 행 수를 알리는 문장을 7장에 싣는다.
- 8-5 에서 기본 창이 행을 놓치면 기본 창·같은 코드 다시 받기를 정한다.

**확인이 끝난 블록은 사외가 스크립트에서 빼고 이 장도 함께 고친다.** 새로 실데이터로만 답이 나오는 질문이
생기면 블록을 더한다. 사내는 이 장을 고치지 않는다.
