# 사내 업데이트 실행 절차 (사내 에이전트용)

이 문서는 **사내(WebIDE)에서 배포 ZIP 을 받아 적용하는 한 번의 작업**을 처음부터 끝까지 적은
것이다. 위에서 아래로 그대로 따라가면 된다. 왜 이런 구조인지는 `docs/dual_env_workflow.md`
에 있고, 여기는 **무엇을 어떤 순서로 치는가**만 적는다.

**이 문서를 읽고 있다면 먼저 확인한다.**

```powershell
git remote -v
```

`github.com` 이 나오면 **사외(개발 PC)다 — 이 문서는 네 것이 아니다.** 사내 GitHub 주소가
나올 때만 아래를 따른다.

---

## 0. 사내에서 절대 하지 않는 것

- **소스를 고치지 않는다.** `app.py`·`app_pages/`·`src/`·`tests/`·`scripts/`·`config/`·
  `.streamlit/`·`static/`·루트 문서 — 어느 것도 편집하지 않는다. 쓸 수 있는 곳은 `review/` 뿐이다.
- **`git clean -x` 를 쓰지 않는다.** `-x` 는 무시된 파일까지 지우고, 거기에 **운영 DuckDB 와
  `data/input` 실데이터**가 들어 있다. 한 글자 차이로 사내 데이터가 날아간다.
- **`uv sync` 를 맨 것으로 돌리지 않는다.** 락에 없는 `bigdataquery` 를 지운다.
  항상 `uv sync --inexact` 다.
- **정체불명 파일을 스스로 지우지 않는다.** 사용자에게 묻고 고른 대로 한다.
- **`.gitignore` 를 고치지 않는다.** 권한에서도 막혀 있다. 넣어야 할 것이 있으면 리뷰
  문서에 적어 사외가 넣게 한다.
- **`git push` 는 에이전트가 하지 않는다.** 권한에서 막혀 있다(`Bash(git push*)` deny).
  푸시가 필요한 자리에서는 사용자에게 명령을 알려 주고 사용자가 친다.

---

## 1. 시작 전 점검 (5분)

### 1-1. 앱을 끈다

```powershell
Get-Process python -ErrorAction SilentlyContinue | Where-Object { $_.Path -like "*streamlit_project*" }
```

떠 있으면 그 창에서 `Ctrl+C`. **DuckDB 는 프로세스 배타 잠금이라 앱이 살아 있으면 이후
검증·마이그레이션이 전부 `duckdb.IOException` 으로 죽는다.** 적용기 자체는 DB 를 열지 않지만
적용 뒤 확인이 막히므로 먼저 끈다.

### 1-2. 쓰기 권한이 실제로 열리는지 한 번 본다

리뷰 문서를 못 쓰면 이번 작업의 산출물이 아예 나오지 않는다. 먼저 확인한다.

```powershell
New-Item -ItemType Directory -Force review | Out-Null
```

그리고 `review/_permission_test.md` 에 아무 한 줄이나 써 본다. 잘 써지면 그 파일은 지우고
넘어간다.

**막히면 거기서 멈추고** 사용자에게 아래를 그대로 알린다 — 사외가 고쳐야 한다.

> 사내 `.claude/settings.json` 의 `Edit(*.md)` deny 가 `review/` 까지 막고 있습니다.
> 슬래시 없는 패턴은 gitignore 의미라 모든 깊이에 걸립니다. `Edit(/*.md)` 로 앵커하고
> allow 에 `Edit(review/**)` 를 더해야 합니다. **deny 는 allow 로 뚫을 수 없으므로**
> deny 쪽을 좁히는 것 말고는 방법이 없습니다.

설정 파일이 `docs/internal_claude_settings.json` 템플릿의 최신본과 같은지도 함께 본다 —
`.claude/` 는 배포가 덮지 않으므로 옛 템플릿이 남아 있을 수 있다.

### 1-3. 운영 데이터를 저장소 밖으로 복사한다

**건너뛰지 않는다.** 아래 두 가지는 적용이 덮거나 지울 수 있다.

```powershell
$backup = "$HOME\deploy_backup\$(Get-Date -Format yyyyMMddHHmm)"
New-Item -ItemType Directory -Force $backup | Out-Null
Copy-Item data\*.duckdb $backup -ErrorAction SilentlyContinue
Copy-Item data\input\* $backup -Recurse -ErrorAction SilentlyContinue
```

`data/input/` 을 함께 챙기는 것은 보수적으로 두는 것이다. **배포 세트는 `data/input/` 아래를
보내지 않으므로**(`build_deploy_package.py` 의 `FORBIDDEN_PREFIXES`) 적용이 덮을 일은 없다.
다만 적용기의 `is_protected` 는 **삭제만** 막고 덮어쓰기는 막지 않는 구조라, 규칙이 바뀌면
조용히 덮인다 — 무시 파일이라 `git checkout -- .` 로도 돌아오지 않는다.

### 1-4. 저장소에 있으면 안 되는 것이 커밋돼 있는지 먼저 본다

**이 순서를 바꾸지 않는다.** 다음 단계(1-5)가 「수정된 파일을 되돌려라」라고 시키는데,
운영 DuckDB 나 `data/input` 실데이터가 **추적된 상태**라면 그 되돌리기가 실데이터를 커밋된
옛 버전으로 덮는다. 무엇이 추적 중인지 모르는 채로 1-5 에 들어가면 안 된다.

```powershell
git ls-files | Select-String -Pattern '\.duckdb|\.db$|\.wal$|^data/input/|^data/output/|^data/temp/|^\.agents/|^\.omo/|\.xlsx?$|\.xlsb$|\.tmp$'
```

**한 줄이라도 나오면 여기서 멈춘다.** `docs/dual_env_workflow.md` 8장의 정리를 먼저 끝내야
한다(앱 종료 → DB 를 저장소 밖으로 복사 → `git rm -r --cached` → 커밋). 그 정리는 사람이
한다 — `git rm` 은 에이전트 권한에서 막혀 있다.

정리를 건너뛰고 적용하면 두 가지가 한꺼번에 일어난다. ① 그 파일들은 ZIP 에 없으므로
「사외에서 지워진 파일」로 판정돼 적용이 지운다. ② 1-5 의 되돌리기가 그 전에 실데이터를
덮는다.

### 1-5. 작업트리를 비운다

```powershell
git status --porcelain --untracked-files=no
```

**한 줄이라도 나오면 적용기가 멈춘다.** 사내에서 소스를 고쳤다면 커밋하지 말고 되돌린다.

```powershell
git checkout -- <경로>
```

**경로를 하나씩 확인하고 되돌린다.** `git checkout -- .` 처럼 전체를 쓰지 않는다. 경로에
`.duckdb`·`.wal`·`data/input`·`data/output`·`data/temp` 가 들어 있으면 **되돌리지 말고
사용자에게 알린다** — 그것은 소스 수정이 아니라 실데이터이고, 되돌리면 운영 데이터가
사라진다. 1-4 를 제대로 끝냈으면 이 목록에 그런 경로가 나올 수 없다.

`git checkout` 은 일부러 권한 allow 에 넣지 않았다. 매번 프롬프트가 떠서 **사람이 경로를
읽고 승인**하게 되어 있다.

되돌리기 전에 그 내용이 필요하면 리뷰 문서에 코드블록으로 옮겨 적는다 — 그것은 저장소 수정이
아니다. 아직 커밋하지 않은 `review/*.md` 가 있으면 **먼저 `review:` 로 커밋한다.** 그러지
않으면 이 단계에서 지워진다.

## 2. 적용 (본 작업)

### 2-1. 먼저 보기만 한다

```powershell
uv run --no-sync python scripts/apply_deploy_package.py <내려받은 ZIP 경로> --dry-run
```

**ZIP 경로는 슬래시로 쓴다** — `C:/Dev/.../202610021506.zip`. 에이전트의 셸이 Git Bash 면 역슬래시
(`C:\Dev\...`)가 사라져 「파일이 없다」로 끝난다(`202610021506` 리뷰). PowerShell 에서도 슬래시는
그대로 통한다.

`--dry-run` 은 **아무것도 바꾸지 않는다.** 깨끗한 작업트리도 요구하지 않는다. 출력에서 아래를
읽는다.

| 칸 | 뜻 | 할 일 |
|---|---|---|
| `사외에서 지워진 파일` | 추적 중인데 목록에 없다 | 적용이 지운다. 뜻밖의 것이 있으면 **여기서 멈추고** 사용자에게 묻는다 |
| `사내에만 있는 정체불명 파일` | 추적도 무시도 안 된다 | **스스로 지우지 않는다.** 아래 2-2 로 |
| `목록에 있는데 사내에 없는 파일` | 적용 전이면 정상 | ZIP 이 채운다 |

`--reconcile-only` 는 목록 대조만 본다(동작은 `--dry-run` 과 같은 자리에서 끝난다).

### 2-2. 정체불명 파일을 먼저 정리한다

**적용보다 먼저 한다.** 적용기의 커밋 단계는 이번 배포가 실제로 건드린 경로만 스테이징하므로
정체불명 파일을 빨아들이지는 않지만, 그래도 남겨 두면 다음 배포에서 다시 물어야 한다.

파일마다 사용자에게 묻고 셋 중 하나를 고른다.

1. **사내에서만 쓰는 것** → 그대로 둔다. `.gitignore` 에 넣을 필요가 있으면 **리뷰 문서에
   적어 사외가 넣게 한다** (사내에서 `.gitignore` 를 고치지 않는다)
2. **사외에도 있어야 하는 것** → 리뷰 문서에 적어 사외가 추가하게 한다
3. **옛 배포의 잔해** → 지운다

판단이 서지 않으면 (1)로 두고 리뷰 문서에 남긴다. 지우는 것은 되돌릴 수 없고, 남기는 것은
다음 배포에서 다시 물으면 된다.

**사내에서 쓴 기록 문서**(예: `HANDOFF_AUDIT_2026-09-17.md` — 사외 저장소에는 한 번도 없던 파일이다)는
(1)로 두는 대신 사용자에게 물어 **`review/` 로 옮겨 `review:` 로 커밋**하면 다음 배포부터 묻지 않는다.
`review/` 는 배포가 보내지도 지우지도 않는 사내 자리다. 옮기는 것도 사용자가 고른 뒤에만 한다.

아직 커밋하지 않은 `review/*.md` 가 있으면 **적용 전에 `review:` 로 먼저 커밋한다.**
`deploy:` 커밋과 섞이지 않게 하려는 것이다.

### 2-3. 적용한다

```powershell
uv run --no-sync python scripts/apply_deploy_package.py <내려받은 ZIP 경로>
```

끝나면 `deploy: <stamp> (<사외 커밋 7자>)` 로 자동 커밋된다.

**에이전트의 자동 권한 판단이 이 명령을 막으면** 같은 명령을 되풀이하지 않는다. 사용자에게 위 한 줄을
**ZIP 경로까지 채워(슬래시로)** 알려 주고, 사용자가 `! <명령>` 으로 직접 친 출력을 읽고 이어 간다
(`202610021506` 적용 때 두 번 막혀 이렇게 했다). 적용 결과의 대조·커밋은 스크립트가 같게 한다.

## 3. 적용 뒤 읽는 법 — 정상인데 이상해 보이는 두 줄

**이 둘은 결함이 아니다. 리뷰 문서에 결함으로 적지 않는다.**

### 3-1. `목록에 있는데 사내에 없는 파일` 은 비어 있어야 한다

적용 **뒤**에 이 칸에 무엇이든 있으면 이상이다(`해제가 덜 됐습니다`). 판정의 근거는 **바로
앞줄**이다.

```
대조    N/N 해시 일치
```

이 줄이 먼저 나왔으면 전 파일이 맞게 풀린 것이다.

> 예전 배포에서는 이 칸에 `data/input/RQ_DISPLAY_ORDER.csv` 한 줄이 **항상** 떴다. 그 파일이
> 배포 세트에 실리면서 동시에 `.gitignore` 에 걸려 대조가 쓰는 두 목록 어디에도 안 잡혔기
> 때문이다. 지금은 `data/input/` 아래를 아예 보내지 않으므로 그 오탐이 없다. 아직도 뜬다면
> **옛 ZIP 을 적용하고 있는 것이다.**

### 3-2. `pytest` 에서 `test_the_top_level_stays_the_declared_set` 실패

`['.deploy/', 'review/']` 때문에 실패하면 **옛 배포를 적용한 것이다.** 두 폴더는 사내에만
생기므로 사외에서는 재현되지 않고, 그래서 한동안 사내에서만 깨졌다. 지금 배포부터는 그 둘이
`INTERNAL_ONLY_TOP_LEVEL` 로 선언돼 있어 통과한다. 그래도 실패하면 **그 사실 자체를 리뷰
문서에 적는다.**

`static/`(글꼴, `202610061748` 배포부터)이 걸려 실패하면 꼴로 가른다. 「최상위에 선언되지 않은 항목이
있습니다 … ['static/']」이면 테스트 파일이 옛것이다 — 일부만 풀린 적용이다. 「선언에는 있는데 저장소에 없는
항목입니다 … ['static/']」이면 `static/` 이 풀리지 않았거나 커밋되지 않았다 — 3-1 의 `목록에 있는데 사내에 없는
파일` 을 함께 본다. 어느 쪽이든 고치지 말고 리뷰 문서에 적는다.

### 3-3. 루트의 `requirements.txt` 는 사내 WebIDE 컨테이너 전용이다

**손으로 적는 파일이 아니라 `uv.lock` 의 그림자다.** 개발 PC 와 CI 는 `uv sync` 로 잠금을
보지만, 사내 WebIDE 의 CI/CD 는 `docker/Dockerfile-prod` 로 이미지를 만들고 그 안에서
`pip install -r requirements.txt` 를 돈다. 둘이 갈라지면 **사내 컨테이너만 조용히 다른
버전을 쓴다** — 화면에 오류가 나지 않고 계산 결과만 달라질 수 있다.

- **사내에서 이 파일을 고치지 않는다.** `tests/test_requirements_export.py` 가 `uv.lock`
  과 대조하므로 고치면 검증에서 걸린다. 사외가 `uv export` 로 다시 뽑는다.
- **`uv sync` 를 이 파일로 대신하지 않는다.** 개발용 도구(ruff·mypy·pytest)가 빠져 있다.
- 이 파일에는 프로젝트 자신(`-e .`)이 **일부러 빠져 있다.** 그래서 컨테이너는
  `Dockerfile-prod` 의 `ENV PYTHONPATH=/project/src` 로 `src` 를 찾는다. 둘은 한 쌍이라
  한쪽만 보고 판단하지 않는다.

## 4. 적용 뒤 할 일

### 4-1. 의존성 — 변경 목록에 `pyproject.toml` 이나 `uv.lock` 이 있을 때만

```powershell
uv sync --inexact
```

맨 `uv sync` 는 `bigdataquery` 를 지운다. 지웠으면 되돌린다.

```powershell
uv pip install -r requirements-company.txt
```

### 4-2. 마이그레이션은 앱이 알아서 한다

앱을 한 번 띄우면 `data/capa_simulation.duckdb` 와 `data/equipment_availability.duckdb` 에
새 마이그레이션이 적용된다. **적용된 마이그레이션은 버전 번호로 체크섬을 대조하므로, 사내에서
SQL 파일을 고치면 앱이 시작조차 못 한다.**

**이 명령은 사용자가 친다.** 서버는 끄기 전까지 안 끝나므로 에이전트가 띄우면 세션이 거기서
멈춘다. 그리고 브라우저로 한 번 들어가야 마이그레이션이 실제로 걸린다.

**두 DB 는 걸리는 때가 다르다.** 시뮬레이션 DB 는 첫 화면(HOME)에서 걸리지만 설비 DB 는
연결을 처음 쓸 때 만든다 — **`가용설비 현황`(또는 `Space 현황`) 페이지를 실제로 열어야** 설비
마이그레이션이 적용된다(`표준 목표`·`표준 대비 재공 현황 (구현중)` 도 설비 DB 를 열지만 확인은 앞의 둘로 한다).
설비 마이그레이션이 있는 배포면 그 페이지까지 열어 확인한다(`202609281727` 리뷰의 지적).

```powershell
uv run --no-sync python -m streamlit run app.py
```

화면이 뜨는 것까지 확인하면 `Ctrl+C` 로 끈다. 오류가 나면 **고치지 말고** 리뷰 문서에 적는데,
**원문을 그대로 붙이지 않는다** — 이 앱의 오류 문구에는 설계상 공정명·제품명 같은 식별값이
박혀 있다. 5장의 가명화 규칙을 그대로 적용해 옮겨 적는다.

### 4-3. 네 관문을 돌린다

```powershell
uv run --no-sync python -m ruff format --check .
uv run --no-sync python -m ruff check .
uv run --no-sync python -m mypy
uv run --no-sync python -m pytest
```

### 7-1. 설비 마스터 컬럼 개편 — 새 36컬럼, 옛 양식은 그대로 읽힌다

호기 마스터의 컬럼이 **새 36개 순서·이름**이 됐다(2026-10-06 사용자 결정). 화면·양식·CSV·Space 편집기가 모두 이
차례를 쓴다.

| 1–6 | 7–12 | 13–18 | 19–24 | 25–30 | 31–36 |
|---|---|---|---|---|---|
| 1 `구분` | 7 `공정구분` | 13 `담당자` | 19 `제진대일정` | 25 `이설일` | 31 `레이아웃표시` |
| 2 `공정대분류` | 8 `투자Capa` | 14 `설비가동현황` | 20 `물류일정` | 26 `반입/Qual 이력` | 32 `환산비` |
| 3 `공정소분류` | 9 `투자구분` | 15 `X좌표` | 21 `반입일정` | 27 `호기이력` | 33 `Main 설비` |
| 4 `Maker` | 10 `사용기준` | 16 `Y좌표` | 22 `Qual일정` | 28 `설비이력` | 34 `메모1` |
| 5 `Model` | 11 `동` | 17 `Xsize` | 23 `확정상태` | 29 `보관유무` | 35 `메모2` |
| 6 `설비명` | 12 `층` | 18 `Ysize` | 24 `반출일정` | 30 `기존설비여부` | 36 `메모3` |

- **이름이 바뀐 것(옛 → 새)** — `분류1` → `구분`, `모델` → `Model`, `호기` → `설비명`, `라인구분` → `공정구분`,
  `활용구분` → `투자구분`, `분류2` → `사용기준`, `분류3` → `설비가동현황`, `입고일정` → `반입일정`, `비고` → `설비이력`,
  `장기보관여부` → `보관유무`, `모체호기` → `Main 설비`. 비가동 일정의 `호기` 도 `설비명` 이다. 기존 보유대수의 `비고`
  와 비가동 일정의 `비고` 는 그대로다.
- **새 컬럼 다섯** — `투자Capa`(글자 값, 계산에는 쓰지 않는다)·`반입/Qual 이력`·`메모1`~`메모3`. 모두
  선택 칸이고, 기존 리비전에서는 빈칸이다(`0015`).
- **`투자기준` 은 빠졌다.** 화면·양식·CSV 에서 사라지고 읽지도 쓰지도 않는다. DB 의 `investment_basis` 값은 지우지
  않는다 — 옛 리비전은 값을 그대로 갖고, **이 배포 뒤 처음 저장하는 설비 리비전부터는 빈칸**이다(7-7). `투자Capa` 는
  그 값을 이어받지 않는 별개의 컬럼이다.
- **옛 머리 이름 파일은 그대로 올려도 된다.** 붙여넣기·CSV 올리기 모두 옛 이름을 새 이름으로 바꿔 읽는다(공백·
  대소문자 무시). 미리보기 위에 알림(ℹ) 줄이 붙는다.
  - `투자기준` 열이 있으면 — 「호기 마스터의 「투자기준」 열은 빠진 컬럼이라 읽지 않았습니다(새 컬럼 「투자Capa」 는
    별개의 컬럼입니다).」
  - 새 선택 컬럼이 없으면 — 「호기 마스터에 투자Capa · 반입/Qual 이력 · 메모1 · 메모2 · 메모3 열이 없어 빈칸으로
    읽었습니다. 이 파일로 바꾸는 행은 그 칸의 저장된 값이 지워집니다 — 「변경컬럼」을 확인하세요.」 **새 다섯 칸에
    한해서는** 걱정할 문구가 아니다 — 사내 저장본은 그 다섯 칸이 모두 빈칸이라 지워질 값이 없다.
  - **목록에 `Main 설비` 가 들면 다르다.** 옛 파일에 `모체호기` 열이 없으면 목록에 `Main 설비` 가 함께 든다. 사내가
    `0010` 배포(2026-09-28) 뒤 `모체호기`(지금 `Main 설비`) 값을 저장한 적이 있다면, **이 파일로 실제 저장할 때 대체되는
    행의 저장된 `Main 설비` 가 빈칸이 된다.** 미리보기는 쓰지 않으니 이번 확인에는 해가 없다 — 「있음」이면 리뷰
    문서에 적고 사용자에게 알린다(7-7). 저장할지는 사용자가 정하고, 에이전트는 저장하지 않는다.
  - 막히는 꼴(빨간 오류) 둘 — 옛 이름과 새 이름이 함께 오면 「호기 마스터에 같은 컬럼을 가리키는 옛 이름과 새 이름이
    함께 있습니다(…). 하나만 남기세요.」, 선택 컬럼 이름이 조금 틀리면(`Main 설비(선택)` 꼴) 「호기 마스터의 <컬럼> 열
    이름이 다릅니다: … — 머리글을 「<컬럼>」로 고치세요.」. 둘 다 앱 결함이 아니라 파일의 머리 줄 문제다.
- **직접 편집 표** — `설비명` 은 이제 왼쪽에 고정되지 않고 계약 차례(6번째)에 선다. 맨 앞 `선택` 체크 칸은 화면 전용
  (저장되지 않는다)이라 **머리 칸은 37개**(`선택` + 36)로 보인다. `선택` 은 `직접 편집` 의 **세 탭(호기 마스터·기존
  보유대수·비가동 일정) 모두 맨 앞에 고정**된다 — 머리 칸은 늘 `선택` 다음부터 센다.
- Space `저장 안 한 배치 변경` 상자의 `바뀐 호기` 표에서 종류 열 이름은 `변경` 이다(`구분` 과 겹치지 않게).

**확인해 올 것.** **저장하지 않는다** — `확인 후 리비전 저장`·`설비 데이터 저장` 을 누르지 않는다. 표의 값은 고치지
않는다.

1) `가용설비 현황` 을 연다(설비 마이그레이션 `0013`·`0015` 가 여기서 걸린다). 오류 없이 뜨는지(「정상/오류」 — 오류면
   원문을 옮기지 않고 가명화한다). `RawData` 탭 → `직접 편집` → `호기 마스터` 탭. 표 머리 칸을 왼쪽부터 읽어 위 36
   차례와 맞대어 본다 — 맨 앞 `선택` 은 빼고 세고, 표가 넓으면 가로로 끝까지 민다. 「같음」 또는 「다름 — N번째 자리가
   <컬럼 이름>」으로 적는다. 보이는 칸이 36 보다 적으면 `호기 마스터 · 표 보기 설정` 을 펴 `볼 컬럼` 에서 감춘 것이
   있는지 본다(고정 컬럼 다섯 — `설비명`·`공정소분류`·`보관유무`·`기존설비여부`·`레이아웃표시` — 은 그 목록에 없고
   늘 보인다). 호기 마스터가 비어 있으면 「저장본 없음」으로 적고 머리 칸만 본다.
2) RawData 위 `입력 양식 · 현재 데이터 내려받기` 를 펴 `호기 마스터 양식`(`equipment_master_template.csv`)을 받는다.
   첫 줄 머리를 위 36 차례와 맞대어 「같음/다름 — N번째」로 적는다. 둘째 줄은 합성 예시라 옮기지 않는다. 받기는 DB 에
   쓰지 않는다.
3) **사내가 지금 쓰는 옛 양식 파일**(옛 머리 이름 — `호기`·`라인구분`·`활용구분`·`투자기준`·`분류1`~`분류3`·
   `모델`·`입고일정`·`비고`·`장기보관여부`·`모체호기` 가 든 호기 마스터 엑셀이나 CSV)을 사용자에게 받는다. 앱의
   `현재 데이터` 받기는 이제 새 이름으로 나오므로 옛 양식 시험이 되지 않는다 — 옛 파일이 없으면 「옛 양식 파일 없음 —
   건너뜀」으로 적는다.
   - **그 파일은 사용자가 두는 자리에 그대로 둔다 — 저장소 안(`review/`·`data/`·루트)에 복사하지 않는다.** `review/` 는
     5장에서 통째로 커밋돼 사외로 나가고, CSV 는 `.gitignore` 의 Excel 규칙에도 걸리지 않는다. 붙여넣기·올리기는
     **사용자가 브라우저에서** 한다. 에이전트는 그 파일을 복사·열기·출력·요약하지 않고, 리뷰 문서에는 미리보기 화면의
     수와 컬럼 이름만 옮긴다.
   - `입력` 탭 → `등록할 표` 를 `호기 마스터` 로 둔다. **기본 길은 붙여넣기다** — 옛 파일을 Excel 로 열어 **머리 줄을
     포함해 표 전체**를 복사하고 `Excel 표 붙여넣기` 칸에 붙인다. `또는 CSV 파일 업로드` 는 붙여넣기를 못 할 때만 쓴다 —
     **둘 중 하나만**(둘 다 있으면 「붙여넣기와 CSV 파일이 함께 있습니다…」로 막힌다).
   - **사내 DRM 은 올린 파일의 바이트를 바꾼다.** CSV 를 올렸는데 머리 이름이나 글자가 깨져 막히면 앱 결함이 아니라 DRM
     변환이다 — 오류로 적지 않고, 올린 파일을 `×` 로 내린 뒤 붙여넣기로 다시 한다. 붙여넣기에서도 막힐 때만 아래 「막힌
     꼴」로 적는다.
   - `변경 미리보기` 를 누른다. **옆의 `확인 후 리비전 저장`(색이 든 주 단추)이 이제 켜진다 — 누르지 않는다.**
   - 정상은 이렇다 — 굵은 제목 「호기 마스터 · 저장할 변경 N행」, 그 아래 ℹ 알림 줄(위의 두 문구), `신규`·`기존 대체`
     건수, 변경 표(맨 앞 `Import구분`·`변경컬럼`·`변경내용`), 맨 아래 「저장 후: 기존 보유대수 N행 · 호기 N행 · 비가동
     N행」.
   - 적을 것 — 저장할 변경 행 수, `신규` N건·`기존 대체` N건, 알림 두 줄 각각 「있음/없음」, 「빈칸으로 읽었습니다」
     줄의 목록에 `Main 설비` 가 드는지(「Main 설비 있음/없음」 — 「있음」이면 위 알림 설명대로 사용자에게 알린다),
     변경 표에서 `변경컬럼` 이 「변경 없음」이 아닌 행 수와 그 행들의 `변경컬럼` 에 나온 **컬럼 이름**(값과 `변경내용`
     은 적지 않는다). 막혔으면 빨간 오류의 **꼴**만(「옛 이름과 새 이름이 함께」·「열 이름이 다릅니다」·그 밖은 가명화해 한 줄).
   - 지금 저장본과 같은 내용의 옛 파일이면 `신규` 0 에 거의 모두 「변경 없음」이 정상이다. 파일이 저장본보다 오래됐거나
     새로우면 그만큼 `신규`·변경 행이 생기는 것도 정상이다 — 그 수를 그대로 적는다.
   - **미리보기를 지운다.** 미리보기는 편집본도 DB 도 바꾸지 않고, 저장 단추를 눌러야만 들어간다. 이 화면에는 미리보기
     전용 `버리기`·`취소` 단추가 없다 — 지우는 길은 이것이다: `Excel 표 붙여넣기` 칸을 비우고(Ctrl+A → Delete), 올린
     CSV 는 파일 이름 옆 `×` 로 내린 뒤 `변경 미리보기` 를 한 번 더 누른다. 「Excel 표를 붙여넣거나 CSV 파일을 올린 뒤
     미리보세요.」가 **RawData 맨 위(`입력 양식 · 현재 데이터 내려받기` 위)에 빨간 오류 상자로** 뜨고 미리보기 표가
     사라지며 `확인 후 리비전 저장` 이 다시 꺼진다. **이 빨간 상자는 미리보기를 지웠다는 정상 표시다 — 위의 「막힌 꼴」로
     적지 않는다.** 결과는 「꺼짐/남음」 하나만 적는다.
4) `직접 편집` → `비가동 일정` 탭에서 맨 앞 `선택` 다음 첫 머리 칸이 `설비명` 인지(「설비명/그 밖」).

### 7-2. Space 현황 — S.PKG FAB 전체 → 층 2단

**동 단계가 없어졌다.** 화면은 **S.PKG FAB 전체 → 층 상세** 두 단계이고, 경로 줄은 `S.PKG FAB 전체` › `층 바로
가기`(목록) 두 칸이다.

- **FAB 전체** — 카드가 없어지고 도면 위 도구 줄 오른쪽 한 줄 요약(`배치 N대 · 미배치 N대 · 레이아웃 제외 N대`)이
  대신한다. 도면 아래는 30개 층의 층 목록 표(`동`·`층`·`배치대수`·`미배치대수`·`점유율`·`배치 도면`·`캔버스`)이고, 행을
  고르면 그 층이 열린다.
- **FAB 도면** 은 층 도면과 같은 뷰어(보기 전용)다. **저장한 FAB 배치가 없으면 기본 배치가 그려진다** — 동마다 위에서
  아래로 층 블록 여섯이 서고, 독립동·연결 구간 영역과 동 이름 글자가 꾸밈으로 붙는다. 사내는 아직 FAB 배치를 저장한
  적이 없을 것이므로 **이 기본 배치가 보이는 것이 정상**이다(빈 화면이 아니다). 블록에는 배치 대수(있으면 미배치 대수)가
  적히고, 올려 두면 강조 테두리와 「<동> <층> · 누르면 열기」가 뜬다. **블록을 누르면 그 층 상세가 바로 열린다.** 끌기는
  화면만 옮기고 열지 않는다.
- **연 층은 주소에 남는다**(`?floor=` 꼴) — 새로고침해도 그 층에 머문다. FAB 로 돌아가면 주소에서 빠진다. 브라우저
  뒤로/앞으로로는 층을 오가지 않는다(알려진 한계, 결함 아님).
- **층 도면이 열 폭을 채우고**, 도면 아래 가로 막대(손잡이)를 끌어 **높이만** 바꾼다. 두 번 누르면 처음 높이로 돌아오고,
  고른 높이는 그 브라우저가 기억한다(화면을 다시 그리지 않는다).
- **미배치 트레이는 접히는 서랍이다.** 층 `배치 편집` 을 켜면 도면 오른쪽 가장자리에 `미배치 N` 탭이 서고, 누르면
  서랍이 열린다(`접기`·Esc 로 닫힌다).
- **FAB 배치 편집** — FAB 머리 줄(`S.PKG FAB 전체 배치`)에 `도면·캔버스 편집` 과 `배치 편집` 토글이 선다. 켜면 층
  블록·영역·글자를 끌어 고치고, 층 블록을 고르면 아래 선택 칸에 `연결`(연결 층)·`색`·`열기` 가 선다. 색은 자리 구분
  색이다(상태 색이 아니다). `적용` 은 이 세션에만 넣고, 화면 위 `저장 안 한 배치 변경` 상자에 「S.PKG FAB 전체 배치」가
  붙는다. 그 상자의 `배치 저장` 이 FAB 를 설비 리비전 없이 따로 쓴다 — 이번 확인에서는 누르지 않는다. 호기 마스터가 비어
  샘플을 보는 화면에서는 FAB 편집이 꺼진다.

**확인해 올 것.** **저장하지 않는다**(`배치 저장`·`도면·캔버스 편집` 팝업의 `도면·캔버스 저장`·`도면·캔버스 삭제` 를
누르지 않는다). 7-1 3) 의 미리보기를 지운 뒤에 한다.

1) `Space 현황` 을 연다. 오류 없이 뜨는지(「정상/오류」), 경로 줄이 두 칸이고 동 단계가 없는지(「2단/그 밖」), FAB
   도면이 무엇인지(「기본 배치/저장본/빈 화면」), 요약 줄의 세 수(배치·미배치·레이아웃 제외 대수만)를 적는다. 본문에
   `합성 샘플` 배지나 「호기 마스터가 비어 있어 데모 fleet 을 표시합니다.」가 보이면 대수를 「샘플」로 적고 3)·4) 는
   건너뛴다(샘플 스위치는 바꾸지 않는다).
2) **배치된 호기가 있는 층의 블록**을 누른다 → 그 층 상세가 한 번에 열리는지(「열림/안 열림」). 새로고침(F5) → 같은
   층에 머무는지(「머묾/FAB 로 돌아감」 — 같은 탭이라 입장 화면은 다시 뜨지 않는다). 도면이 화면 폭을 채우는지, 도면
   아래 가로 막대를 끌면 높이가 바뀌고 두 번 누르면 돌아오는지(「됨/안 됨」). 배치된 층이 없으면 「배치된 층 없음」으로
   적고 아무 블록이나 누른다.
3) 그 층에서 `배치 편집` 을 켠다 → 도면 오른쪽에 `미배치 N` 탭이 보이는지, 누르면 서랍이 열리고 `접기`(또는 Esc)로
   닫히는지(「됨/안 됨」). **아무것도 옮기지 않고 `적용` 을 누르지 않은 채** 토글을 끈다.
4) 경로 줄의 `S.PKG FAB 전체` 로 돌아가 FAB 머리 줄의 `배치 편집` 을 켠다. 층 블록 하나를 누르면(편집 중에는 고르기다
   — 열리지 않는다) 아래 선택 칸에 `연결`·`색`·`열기` 가 서는지(「섬/안 섬」) — 값은 바꾸지 않는다. 그 블록을 조금 끌어
   옮기고 `적용` → 화면 위 `저장 안 한 배치 변경` 상자에 「S.PKG FAB 전체 배치」가 붙는지(「뜸/안 뜸」). 그다음 상자의
   **`버리기` → `FAB 배치만 버리기`** 로 버린다(그 단추가 없으면 `모두 버리기` — 7-1 에서 편집본을 바꾸지 않았으므로 버릴
   설비 편집은 없다). 상자가 사라지고 블록이 원래 자리로 돌아오는지(「돌아옴/안 돌아옴」) 적고 토글을 끈다.

### 7-3. 확보율 판정 기준 — HOME → Preference 의 공용 월별 설정

확보·경고 기준을 **시나리오와 무관한 공용 설정 한 곳**에서 정한다(2026-10-06 사용자 결정, 시뮬레이션 `0029`).

- **사이드바의 입력 칸이 없어졌다** — HOME·`Static Capa` 사이드바에는 확보·경고 기준을 고치는 칸이 없고 「판정
  기준은 HOME → Preference 에서 정합니다.」 한 줄이 선다. HOME 은 사이드바 `B/N 집계 공정` 상자(기본 접힘) 안이고,
  `Static Capa` 는 `판정 기준` 조건 카드 안에 지금 쓰는 기준을 읽기 전용으로 적은 캡션(`확보 기준 110%` 꼴, 기간 안에
  월별 예외가 있으면 `· 월별 예외 N개월`)과 함께 선다.
- **HOME → `Preference` 탭의 `확보율 판정 기준` 상자** — `기본 확보 기준(%)`·`기본 경고 기준(%)` 두 칸과 달마다의 표
  (`구분` 열 + 조회기간의 달, 행은 `확보 기준`·`경고 기준`). 비워 둔 달은 기본값을 따른다. 한 번도 저장하지 않았으면
  캡션이 「공용 버전 없음 · 아직 저장하지 않아 <출처> 값(확보 x% · 경고 y%)을 씁니다」이고, 출처는 셋 중 하나다.
  - `공식 vN 프리셋` — 최신 공식버전 리비전의 프리셋 값. 지금까지 공식 시나리오를 열면 사이드바에 서던 값과 같은
    근원이다.
  - `코드 기본값` — 공식버전이 없을 때. 확보 109.5% · 경고 99.5%.
  - `코드 기본값(공식 vN 프리셋 값은 쓸 수 없어 대신)` — 그 프리셋 짝이 규칙에 어긋나(경고 0, 확보 = 경고 등) 기본값을
    쓴다. **이때는 판정이 전과 달라질 수 있다.**
- 판정은 **달마다 그 달의 기준**으로 한다 — HOME LOB·B/N·Top5·결론 문장·공정 선택, `Static Capa`, `산출 결과` 확보율
  히트맵, Summary. **월별 표가 비어 있고 기본값이 전에 쓰던 짝과 같으면 결과는 전과 같다.**
- **범례는 % 없이 「초과 확보 · 경고 · 부족」 셋**이고 「과거 구간」 칩은 없다 — HOME `Capa LOB 현황`, `산출 결과` →
  `확보율` 히트맵, Summary.
- 기준을 글로 적는 곳(Summary 기준선 이름표, B/N 공정 선택 팝업)은 사사오입 정수 %(109.5 → 110%, 99.5 → 100%)로 적는다.
  판정·저장값·입력 칸은 정확한 값 그대로다.

**확인해 올 것.** **저장하지 않는다** — `판정 기준 저장` 을 누르지 않고, 두 칸과 월별 표에 아무것도 적지 않는다.
Preference 탭의 다른 상자(특히 고르는 즉시 쓰는 `비교 시나리오`·`비교 리비전`)는 건드리지 않는다.

1) HOME 사이드바(`B/N 집계 공정` 상자를 편다 — 펴기는 쓰기가 아니다)와 `Static Capa` 사이드바(`판정 기준` 카드)에
   확보·경고 기준을 고치는 칸이 없고 위 안내 한 줄이 보이는지(각각 「없음·안내 보임/칸 남음」).
2) HOME → `Preference` → `확보율 판정 기준` 상자의 캡션 꼴(「공식 vN 프리셋/코드 기본값/코드 기본값(… 대신)/공용 버전
   vN — 누가 이미 저장함」)과 두 칸의 값(% 숫자 — 기준값은 식별값이 아니다), 월별 표가 비었는지(「빈칸/값 있음 N칸」)를
   적는다. 그 두 값이 전에 사이드바에서 쓰던 기준과 같은지 사용자에게 묻는다(「같음/다름/모름」).
3) 범례 — HOME `Main` 의 `Capa LOB 현황`, `산출 결과` → `확보율` 탭의 히트맵, 사이드바 `S.PKG CAPA` 로 연 Summary 의
   `B/N 확보율` 줄. 셋 다 「초과 확보 · 경고 · 부족」이고 % 와 「과거 구간」이 없는지(각각 「셋/그 밖」). Summary 기준선
   이름표가 정수 %(「110%」 꼴)인지(「정수/소수」). Summary 는 `Esc` 로 닫는다.
4) 2) 가 「같음」이고 월별 표가 비었으면 HOME 결론 줄(「가장 낮은 확보율은 …」)이 직전 배포 때와 같아야 한다. 사용자에게
   판정 색과 부족 공정 수가 전에 본 것과 같은지 묻는다(「같음/다름/비교 못 함」 — 공정 이름·값은 적지 않는다). 그사이
   사내에서 공식버전이나 활성 리비전이 바뀌었으면 「다름」은 데이터 때문일 수 있다 — 그때는 「비교 못 함」으로 적는다.

### 7-4. 머리 띠 · 사이드바 라벨 · 툴바 · 인쇄 · 글꼴

- **머리 띠**(화면 맨 위 띠)가 **이 세션에 적용 중인 시나리오**를 싣는다(2026-10-06 사용자 결정).
  - 위 줄(굵게) — `시나리오명 · rN 리비전명 · 상태`. 상태는 `공식 vN`·`저장된 리비전`·`미저장 변경` 중 하나다.
  - 아래 줄(옅게) — `시뮬레이션 코드 · 적용 YY.MM–YY.MM · 원천 YY.MM.DD 등록`(공식버전이 아니면 `YY.MM.DD 저장`).
    적용 기간은 생산계획의 첫 달·끝 달이지 조회기간이 아니다.
  - 활성 시나리오가 없는 저장소면 앱 이름 한 줄로 물러난다.
- **사이드바 머리 맨 앞에 웨이퍼 심볼 + `S.PKG CAPA` 라벨**(옆에 작게 `Summary`). 누르거나 Enter 로 Summary 가 열리고,
  닫으면 초점이 라벨로 돌아온다. **툴바의 `Summary` 단추는 없어졌다**(직전 배포에서 확인한 그 단추). 공식버전이 없거나
  요약을 못 만들면 라벨이 흐리게 꺼진다(올려 두면 까닭).

  없다** — 인쇄와 테마는 툴바 단추가 맡는다.
- **`Print`** — 지금 화면을 인쇄한다. 사이드바·머리 띠·툴바·입장 화면 덮개는 늘 빠지고 본문이 종이 폭을 쓴다. 어두운
  테마에서는 먼저 「어두운 테마로 인쇄합니다. 밝은 테마(Light)로 바꾼 뒤 인쇄하면 잉크가 덜 듭니다. 그대로 인쇄할까요?」를
  묻는다. 가로로 넓은 표(HOME `Capa LOB 현황` 등)는 보이는 부분만 찍힌다 — 인쇄 창에서 가로 방향을 고르거나 인쇄 전에
  조회기간을 좁히는 것이 안내된 방법이다(결함 아님, HOME Guide 의 `인쇄` 절).
- **테마는 앱 전체에 하나로 유지된다** — 하위 페이지에서 고른 `Dark` 도 한 번에 듣고, 다른 페이지에서 F5 해도 그대로다.

  이 변경이 사라집니다. 계속할까요?」를 묻는다.
- **사이드바 접기 `<<`** 가 마우스를 올리지 않아도 늘 보인다.
- **개발·인증 정보**는 `Admin Area` 맨 아래(구분선 아래 캡션 세 줄)로 옮겼다.
- **글꼴** — 페이지 제목은 Archivo 800, 상자·구획 제목과 큰 숫자(`st.metric` 값, HOME 결론 줄의 확보율)는 Archivo 700

   코드는 적지 않는다).
2) 사이드바 머리의 `S.PKG CAPA` 라벨이 보이는지, 누르면 Summary 가 열리고 `Esc` 로 닫히는지(「됨/안 됨/꺼짐」). 툴바에

   않아도 보이는지(「보임/안 보임」), `Admin Area` 맨 아래 캡션 세 줄이 보이는지(「보임/안 보임」 — 내용은 옮기지
   않는다).
3) 테마 — HOME 에서 `Dark` → 사이드바로 `산출 결과` 로 옮겨 F5 → 어두운 채인지(「유지/밝게 돌아감」). 미저장 확인 창이
   뜨면 「물음」으로 적고 `취소` 한다(이 확인에서는 편집을 하지 않았으므로 뜨지 않는 것이 정상이다). 테마는 4) 까지
   `Dark` 로 둔다.
4) 인쇄 — 어두운 테마에서 `Print` → 위 확인 문구가 먼저 뜨는지(「물음/바로 인쇄 창」) 보고 **`취소`** → 아무 일도
   없는지. `Light` 로 돌린 뒤 `Print` → 묻지 않고 브라우저 인쇄 창이 뜨는지, 미리보기에서 사이드바·머리 띠·툴바가
   빠졌는지(「빠짐/남음」) 보고 **`취소`**.
5) 글꼴(오프라인) — **먼저 HOME 으로 간다.** 글꼴은 영문·숫자에만 걸려(`unicode-range`) 제목이 한글뿐인 화면 — 4) 를 마친
   자리인 `산출 결과` 등 — 에서는 브라우저가 파일을 아예 부르지 않을 수 있다. HOME 은 제목 `Capa LOB Summary` 가 800, 큰 숫자가
   700 을 부른다. HOME 에서 Chrome 개발자 도구(F12) → `Network` → 필터에 `woff2` → F5. `archivo-700.woff2`·
   `archivo-800.woff2` 두 줄의 상태를 적는다(「200(캐시·`304`·`(memory cache)`·`(disk cache)` 포함 — 받은 것이다)/404/줄
   없음」). 개발자 도구를 쓸 수 없거나 HOME 에서도 「줄 없음」이면 새 탭에 앱 주소(WebIDE 면 `/proxy/<포트>/`
   까지) 끝에 `app/static/fonts/archivo-800.woff2` 를 붙여 연다 — 파일이 내려받아지거나 깨진 글자가 보이면 「됨」,
   `404`·`File not found` 면 「안 됨」. 주소는 적지 않는다. 「안 됨」이면 `.streamlit/config.toml` 에 `enableStaticServing =
   true` 가 있는지와 `static/fonts/` 에 파일 셋이 있는지만 보고(「있음/없음」) 고치지 않는다.

### 7-5. 그 밖에 보이는 변화 — 확인 없음, 보이면 결함이 아니다

- **가상 제품이 든 리비전의 공식버전 지정** — 경고와 함께 「가상 제품이 포함된 것을 확인했습니다」를 체크해야 `선택
  리비전을 공식버전으로 지정` 이 풀린다. 체크는 리비전마다 따로 받는다. 가상 제품이 없는 리비전은 전과 같다.
- **가상 제품 이력을 물려받는다** — 사이드바 `신규 리비전 저장`·시나리오 관리 `새 리비전 저장` 은 불러온 리비전의,
  `현재 활성 RQ 복제` 는 활성 리비전의 가상 제품 이력에 이 세션의 등록을 더해 저장한다(같은 제품정보 + Stack 은 한 건).
  저장 알림의 건수는 합친 수다.
- **DB 가 코드보다 새 버전이면 막지 않고 경고한다** — 화면 위에 「… 가 이 코드보다 새 버전입니다(DB N · 코드 M). 예전
  배포로 되돌린 상태일 수 있습니다. …」 한 줄. 이번 적용 뒤에는 뜨지 않아야 한다 — 뜨면 옛 ZIP 을 적용한 것이니 리뷰
  문서에 그 사실(어느 DB 인지, 두 번호)을 적는다.
- **큰 월별 편집표(칸 1만 개 넘는 표)는 분류 칸 배경색이 없다** — rerun 마다 드는 시간을 줄이려는 것이다(2026-10-05
  사용자 결정). 작은 표는 전과 같다.
- **VOC** — 작성자를 빠뜨려 거절된 새 글·답변은 적은 글이 남고, 성공한 뒤에만 비워진다. 첫 답변 뒤 옛 글 상자의 회색
  사본이 남지 않는다.
- **조사** — 값 뒤의 을/를·은/는·으로/로 를 값의 끝소리로 고른다(「r2를」 꼴). 시나리오·리비전·Stack·데이터셋 이름 알림.
- **Summary** — 달 이름·공정 이름·상태 글자가 커지고 설명이 줄었다. 기준선 이름표는 `110%`·`100%` 꼴이다. 입장 화면·
  Summary 가 떠 있는 동안 Tab 은 덮개 안 단추만 돈다.
- **산출 결과 확보율 히트맵** — 행마다 공정 이름이 붙고(공정이 많으면 그래프가 길어진다), 월 눈금은 가로/세로를 스스로
  고른다.
- **재실행이 빨라진 화면**(표준 목표·산출 결과·생산 계획·기준 정보·가용설비 현황) — 계산 결과와 그림은 같다.
- **운영 스크립트** — `scripts/bootstrap_initial_duckdb_scenario.py` 의 기존 시나리오 분기는 활성 리비전에 가상 제품이
  있으면 `--allow-virtual-products` 없이 발행하지 않고 목록을 찍은 뒤 멈춘다. `scripts/compact_duckdb.py` 는 살아 있는 앱을
  보면 멈추지만 쉬는 앱은 못 본다 — 그래도 **서버를 내린 뒤에만** 돌린다.

### 7-6. 늘 걸리는 것

- **`requirements.txt` 용도** — 3-3 절. 사내 WebIDE 컨테이너 전용이고 `uv.lock` 의 그림자다. **사내에서 고치지 않고**
  `uv sync` 를 대신하지도 않는다.
- **`Pack Code` 업무 키 승격의 후속** — 시뮬레이션 `0013` 이전에 저장한 리비전은 `Pack Code` 가 비어 있어 `생산 계획`
  화면이 「RQ_PKG_PLAN의 편집 테이블 식별 컬럼에 누락값이 있습니다: Pack Code …」로 선다. 실데이터를 **다시 등록**하고,
  승격 전에 내려받은 PKG PLAN CSV 양식은 **다시 받는다.**
- **BigDataQuery 조회** — `export CAPA_BDQ_USER_NAME="<AD 계정>"` 를 넣고 앱을 다시 띄운다. 자세한 것은

- **WebIDE 환경 두 가지** — `aws` 가 PATH 에 있는가, WebIDE 재시작 주기·디스크 영속성은 어떤가. 아직 답하지 않았으면

### 7-7. 사용자에게 알릴 것 — `투자기준` · `Main 설비`

리뷰 문서에 적고, 사용자에게도 아래 한 줄을 그대로 알린다(수만 채운다).

> 이 배포 뒤 처음 설비 데이터를 저장하면(가용설비 현황 RawData 저장, 또는 호기 배치가 바뀐 Space `배치 저장`) 새
> 리비전에는 `투자기준` 이 빈칸으로 들어갑니다. 지금 최신 리비전에서 투자기준 값이 든 행은 `basis` 첫 수, 전체 행은 둘째
> 수입니다. 옛 리비전의 값은 DB 에 남아 있으니 이 열을 되살릴지(계속 둘지) 정해 주세요.

`basis` 의 첫 수·둘째 수는 **이 배포 뒤 첫 설비 저장 전까지만** 뜻이 있다(저장하면 최신 리비전은 0 이 된다). 셋째 수(모든
리비전의 합)는 저장 뒤에도 남는다.

7-1 3) 이 「Main 설비 있음」이었으면 아래 한 줄도 그대로 알린다.

> 사내에서 쓰는 옛 호기 마스터 파일에는 `모체호기`(지금 `Main 설비`) 열이 없습니다. 이 파일을 그대로 붙여넣어 저장하면
> 파일에 든 호기 중 이미 저장돼 있던 호기의 `Main 설비` 값이 모두 빈칸이 됩니다. 저장하기 전에 `현재 데이터` 를 새 양식으로 받아 쓰거나 옛
> 파일에 `Main 설비` 열을 더해 주세요(이번 확인에서는 저장하지 않았습니다).

### 7-8. 마지막 — 앱을 끄고 개수로 확인한다

사용자에게 앱을 꺼 달라고(`Ctrl+C`) 한 다음 아래 한 줄을 돌린다. 두 DB 를 `read_only` 로 열고, 값은 찍히지 않고 개수만
나온다. 7-1 ~ 7-4 를 건너뛰었어도 이 줄은 돌린다.

```powershell
uv run --no-sync python -c "import duckdb; c = duckdb.connect('data/capa_simulation.duckdb', read_only=True); e = duckdb.connect('data/equipment_availability.duckdb', read_only=True); q = lambda s, p=None: c.execute(s, p or []).fetchall()[0][0]; r = lambda s, p=None: e.execute(s, p or []).fetchall()[0][0]; m = 'FROM equipment_ops.equipment_master_snapshot WHERE revision_id = (SELECT revision_id FROM equipment_ops.revision ORDER BY revision_no DESC LIMIT 1)'; print('migration', q('SELECT max(version) FROM app_meta.schema_migration'), 'equipment_migration', r('SELECT max(version) FROM equipment_meta.schema_migration'), 'new_columns', r('SELECT count(*) FROM information_schema.columns WHERE table_schema = ? AND table_name = ? AND column_name IN (?, ?, ?, ?, ?)', ['equipment_ops', 'equipment_master_snapshot', 'investment_capa', 'arrival_qual_history', 'memo_1', 'memo_2', 'memo_3']), 'basis', [r('SELECT count(nullif(trim(investment_basis), ?)) ' + m, ['']), r('SELECT count(*) ' + m), r('SELECT count(nullif(trim(investment_basis), ?)) FROM equipment_ops.equipment_master_snapshot', [''])], 'thresholds', [q('SELECT count(*) FROM app_meta.global_securement_threshold'), q('SELECT count(*) FROM app_meta.global_securement_threshold_month')], 'fab', [r('SELECT count(*) FROM equipment_ops.fab_layout_profile'), r('SELECT count(*) FROM equipment_ops.fab_layout_mark')], 'layout_marks', r('SELECT count(*) FROM equipment_ops.floor_layout_mark'), 'dup_names', q('SELECT count(*) FROM (SELECT scenario_name FROM app_meta.scenario GROUP BY scenario_name HAVING count(*) > 1)'))"
```

기대하는 꼴은 `migration 29 equipment_migration 15 new_columns 5 basis [a, b, c] thresholds [0, 0] fab [0, 0] layout_marks 0
dup_names 0` 이다. 읽는 법(출력 한 줄을 그대로 리뷰 문서에 옮긴다).

- `migration 29` — 시뮬레이션 DB 마이그레이션 번호. 29 가 아니면 4-2 로 돌아간다.
- `equipment_migration 15` — 설비 DB 마이그레이션 번호. 15 가 아니면 설비 DB 를 여는 화면(`가용설비 현황`·`Space
  현황`)을 열지 않은 것이다 — 4-2 대로 앱을 띄워 그 페이지를 연 뒤 끄고 이 줄을 다시 돌린다. `Catalog Error`(표가 없다)가
  나와도 같은 까닭이다.
- `new_columns 5` — `0015` 가 더한 설비 마스터 열 다섯이 다 있는지. 5 가 아니면 위 `equipment_migration` 과 함께 본다.
- `basis [a, b, c]` — `a` 는 최신 설비 리비전에서 `투자기준` 값이 든 행 수, `b` 는 그 리비전의 전체 행 수, `c` 는 모든
  리비전에서 값이 든 행의 합이다. 정답이 정해진 수가 아니다 — 7-7 대로 사용자에게 알린다. 설비 저장본이 없으면
  `[0, 0, 0]`.
- `thresholds [h, m]` — 공용 판정 기준의 기본값 행(0 또는 1)과 월별 행 수. 이번 확인은 저장하지 않으므로 **`[0, 0]`**
  이어야 한다. 아니면 누군가 Preference 에서 판정 기준을 저장한 것이다 — 결함이 아니니 수만 적고 사용자에게 알린다(그
  뒤로는 저장한 값이 판정 기준이다).
- `fab [p, m]` — 저장된 FAB 캔버스 행(0 또는 1)과 FAB 요소 수. 이번 확인은 버렸으므로 **`[0, 0]`** 이어야 한다. 아니면
  누가 FAB 배치나 FAB 도면·캔버스를 저장한 것이다 — 수만 적는다.
- `layout_marks N` — 저장된 층 도면 요소 수. 이번 확인은 층 편집기에서 적용하지 않으므로 직전 값(0)과 같아야 한다. 다르면
  누가 도면 요소를 저장한 것이다 — 결함이 아니니 수만 적는다.
- `dup_names N` — 이름이 겹치는 시나리오 이름의 수. 0 이 아니면 사용자에게 알린다 — 겹친 이름은 사이드바·보관함에서
  어느 쪽인지 가릴 수 없다. 이번 확인에서 이름을 바꾸지는 않는다.
- **직전 값(2026-10-03, `202610031034` 리뷰)** — `migration 28 equipment_migration 11`. 그보다 앞(2026-10-02)에는
  `layout_marks 0 dup_names 0` 이었다. 앞 배포의 `cb_rows`·`presets` 는 확인이 끝나 이번 줄에서 뺐다.
- `duckdb.IOException` 이면 앱이 아직 떠 있다.

### 8-0. 언제 · 무엇을 치나

**7장(그 배포의 확인)을 마친 뒤, 앱을 끈 채로 돌린다.** 앱이 떠 있으면 「DB 를 열지 못했습니다. 앱이 떠
있으면 먼저 끄세요 …」 한 줄을 찍고 멈춘다(종료 코드 1) — 사용자에게 `Ctrl+C` 를 부탁하고 다시 친다.
설비 DB 는 `가용설비 현황` 을 한 번 연 뒤라야 마이그레이션이 다 걸려 있다(4-2). 7장을 했다면 이미 걸렸다.

```powershell
uv run --no-sync python scripts/inspect_real_data_checks.py
uv run --no-sync python scripts/inspect_real_data_checks.py --only bdq
```

- **첫 줄** — DB 확인 넷(8-1 ~ 8-4). 사내 원천 크기에 따라 수십 초 ~ 몇 분이다(가장 최근 데이터셋의 원천을

- **둘째 줄** — BigDataQuery(8-5). 사내 DB 에 직접 묻는다. WebIDE 처럼 요청자 계정이 필요한 환경이면 먼저
  `export CAPA_BDQ_USER_NAME="<AD 계정>"` 을 넣은 셸에서 친다
  ([`bigdataquery_webide_setup.md`](bigdataquery_webide_setup.md)). 목록 조회 두 번(오늘−30일 ~ 오늘,
  366일)과 표본 다섯 코드마다 상세 조회 두 번·적재일 조회 한 번이라 **몇 분 걸릴 수 있다.** 366일 목록이
  너무 오래 걸리면 `--bdq-no-max-window`, 표본을 줄이려면 `--bdq-sample 2` 를 붙인다 — 붙였으면 리뷰

  보려면 `--dataset-id <ID>`(ID 는 앱이 만든 무작위 값이라 적어도 된다).
- 출력은 Markdown 이다. 터미널에 찍힌 것을 처음부터 끝까지 복사해 리뷰 문서에 붙인다(8-6).

각 블록에서 「읽지 못함」·「실패(예외 종류)」 가 나와도 **스크립트는 다음 블록으로 계속한다.** 실패한 줄도
그대로 옮긴다 — 그것도 사외에는 답이다.

### 8-1. `env` — 두 DB 와 적용 배포

- `적용 배포` — `.deploy/applied.json` 의 stamp 와 사외 커밋. 2-3 에서 적용한 ZIP 과 같아야 한다.
- `마이그레이션 … (최고 N · 코드 M, …)` — **「코드와 같다」가 정상이다.** 「코드보다 낮다」면 그 DB 를 여는
  화면을 열지 않은 것이다(4-2) — 앱을 띄워 HOME 과 `가용설비 현황` 을 연 뒤 끄고 다시 돌린다. 「코드보다
  높다」면 옛 ZIP 을 적용했을 수 있다 — 그대로 적는다.
- 행 수 표 — 데이터셋·시나리오·리비전·공식버전·원천 행 수와 데이터셋 원천 종류(`BIGDATAQUERY` 등 앱이 붙인
  이름).
- `ref_data 에 리비전 표 사본이 남은 데이터셋` — 2026-10-06 결정(B3) 전에 만든 데이터셋은 같은 표를 두 번
  들고 있다. 읽는 곳은 없고 파일만 키운다 — 정리할지는 사외가 이 수를 보고 정한다.

### 8-2. `legacy` — 기존 결과 대조

원천 Core Data 에는 기존 앱이 계산해 실어 보낸 값(`WF수(매)` 등)이 그대로 있다. 이 블록은 그 값과 이
앱의 계산을 맞대어 **차이의 분포**만 찍는다. 기준은 가장 최근에 적재한 데이터셋의 원천과 그 시나리오의
**리비전 1**(원천 그대로)이다 — 사내에서 고친 리비전은 대조에 들지 않는다.

- **원천 컬럼 표** — 여섯 컬럼이 얼마나 차 있는지. `소요대수`·`PCB수(K매)`·`GOOD_DIE` 가 비어 있으면 그
  아래 대조는 「비어 있어 대조 불가」로 끝난다. **그것도 답이다**(사외 표본은 셋 다 비어 있다).
- **부하량 표**(`WF수(매)`·`EQ(억Gb)`) — 키마다 |신규 − 기존| ÷ |기존|.
  - `차이율 중앙`·`p95`·`최대`, `>0.1%`·`>1%` 는 그 비율을 넘는 키 수다. **최대가 0.5% 안이면 산식이 맞다.**
  - `기존 0·신규 있음` — 기존이 0 을 적은 키(비율을 구할 수 없다). 사외 표본에서는 전부 `WF 구분 = Dummy`
    였다 — 기존 앱이 Dummy Wafer 를 0 으로 두었다는 뜻이다.
  - `값 불일치` — 기존 값이 계획 줄 × WF 구분 안에서 경로마다 갈려 접을 수 없었던 키. 0 이 아니면 대조
    단위를 다시 설계해야 한다는 신호다.
  - `신규에만`·`기존에만` — 한쪽에만 있는 키. `기존에만` 이 0 이 아니면 신규가 놓친 자리가 있다.
- **소요대수** — 먼저 `키 연결` 줄(신규 경로 키 가운데 원천 경로에도 있는 키의 비율, **100% 가 정상**).
  원천에 값이 있으면 세 줄로 대조한다. 기존 값이 경로 행마다 어떻게 실리는지 사외가 모르기 때문이다.
  - `경로 키 13 · 같은 경로 반복을 접음` / `월×공정×소요기준 · 접음` — 같은 경로에 반복된 값을 한 번만 센다.
  - `월×공정×소요기준 · 접지 않고 행마다 더함` — 원천 행마다 따로 더한다.
  - 둘 중 **한쪽만 맞으면 그쪽이 원천의 실리는 방식**이다. `└ 접음 · 소요기준 …` 줄은 소요기준별로 나눈
    것이다 — PKG 만 어긋나면 「PKG 는 Buffer 로만 센다」(6장 표) 규칙 차이다.
- **PCB수(K매)** — 신규 계산이 없다(산식 미구현). 값이 계획 줄 단위인지(`갈리는 칸 0`)와 `생산수량 ÷
  PCB수(K매)`(PCB 한 매당 Unit)의 분포만 본다.
- **Plan_Chip(K개) · GOOD_DIE** — 신규 Chip 부하량(K개)에 대한 비율의 분포. `≈1` 이 대부분이면 정의와 단위가
  같고, `≈1000`·`≈0.001` 이 많으면 단위만 1000 배 다르며, 흩어지면 정의가 다르다. 아래의 `… ÷ (생산수량 ×
  구분_Chip)`·`GOOD_DIE ÷ Net Die` 같은 줄은 원천 행 안에서 본 정의 후보다 — 어느 줄이 `≈1` 에 몰리는지가
  답이다. 마지막 줄은 `GOOD_DIE` 가 제품마다 값 하나인 속성인지 본다.

### 8-3. `reqb` — 원천 RQ_REQB 소요기준 분포

리비전 1 의 `RQ_REQB` 를 소요기준(`PKG`·`CHIP`·`WF`·`BOX`·`PCB`)마다 센다 — 행 수, 공정 수, `Main`·`MI`
공정 수, WF 구분이 하나뿐인 공정과 그 하나가 `BUFFER` 인 공정. 사외가 표본 생성기의 공정 목록을 업무
사실로 잘못 읽은 적이 있어(`docs/TODO.md` 3-5 「Stack 이후 Wafer 공정」) **실데이터로 다시 센다.**

- `그 밖의 소요기준 N종` — 계약 밖 이름이다. 이름은 찍지 않는다. 0 이 아니면 그대로 적는다.
- `소요기준이 둘 이상인 공정` — 업무 규칙상 **0** 이어야 한다(한 공정은 한 소요기준).

### 8-4. `equipment` — 설비 DB

최신 설비 리비전에서 세 가지를 센다. **값은 고치지 않는다** — 고칠 행이 있으면 사용자가 `가용설비 현황`
RawData 에서 고쳐 저장한다. 에이전트는 수만 적는다.

- `Qual일정 = 2262-04-11` — 옛 리비전 변환이 빈 Qual 을 먼 미래로 채우던 자리표다. 이제는 빈 Qual 로 읽혀
  「일정 미정」에 잡힌다. 사용자가 Qual 날짜를 넣어야 할 행 수다.
- `모듈 행 환산비 0.2` — 직접 편집 칸이 0.25 를 0.2 로 자르던 결함의 흔적이다. **사용자가 다시 입력할 행**이다.
  `Main 설비 없이 환산비 0.2` 는 Main 설비를 적기 전의 모듈일 수 있다. `묶음 / 합이 1 이 아닌 묶음` 의 둘째
  수가 0 이 아니면 그 설비의 능력이 한 대가 안 되게 세어지고 있다.
- `일정 미정` — 반입·Qual 일정이 비어 가용대수에 들지 못하는 설비 대수. `가용설비 현황` 의 「일정 미정 N대」
  알림과 같은 셈이다. 「건너뜀: 설비 DB 마이그레이션이 코드보다 낮다」면 8-0 대로 화면을 연 뒤 다시 돌린다.

### 8-5. `bdq` — BigDataQuery

- `준비` 줄 — 패키지·SQL·요청자 계정(값은 찍지 않고 있음/없음만). 「패키지가 없다」면 4-1 의 되돌리기,
  「요청자 계정 필요」면 8-0 의 `export` 를 넣고 새 셸에서 다시 친다.
- **목록 조회 표** — 기간마다 성공 여부, 걸린 초, 목록 행 수(`SELECT DISTINCT` 결과), 코드·PLAN 수, 코드 수,
  화면이 느려지는 3,000 을 넘는지. 기본 기간(오늘−30일 ~ 오늘)은 `BigDataQuery 등록` 화면의 첫 값과 같다.
- **`reg_date`** — dtype, 값의 종류, 숫자면 자릿수, 문자열이면 꼴(숫자는 `9`, 영문은 `A` 로 바꾼 모양),
  원천 등록시각으로 읽지 못하는 값 수. 숫자형은 앱이 일부러 버린다(1970 년으로 읽히는 것을 막는다).
  `코드·PLAN 하나의 서로 다른 등록시각 수` 가 1 보다 크면 `reg_date` 가 행 단위 적재 시각이다.
- **`catb_sim_info_id` 규칙 위반** — `^[A-Za-z0-9._-]+$` 를 벗어나 화면에서 저장이 막히는 코드 수와 까닭의
  종류.
- **표본 적재일 표** — 규칙을 지키는 코드 가운데 첫 등록일 순으로 고르게 다섯을 골라, 상세 조회 기본 창
  (원천 등록일 −7 ~ +3일)과 넓은 창(±30일)의 행 수를 견준다. **`기본 창 행 = 넓은 창 행` 이 전부면 기본
  창으로 충분하다.** `기본 창이 놓친 행` 이 0 이 아니면 사외가 기본 창을 넓힐지, 같은 코드를 다시 받는 길을
  둘지 정한다(`docs/TODO.md` 결정 대기). 아래 적재일 줄은 **사외에서 돌려 보지 못한 SQL**(적재 시각의
  날짜별 행 수)이다 — 사내 엔진이 받지 않으면 「조회 실패(예외 종류)」 한 줄만 남고 나머지는 계속된다.

### 8-6. 리뷰 문서에 옮기는 법

리뷰 문서(5장) 끝에 아래 절을 더하고, 출력 블록 `8-1` ~ `8-5` 를 **그대로** 붙인다. 블록 제목(`### 8-1. …`)
까지 함께 붙인다 — 사외는 그 제목으로 블록을 찾는다.

- 걸린 시간 : DB 넷 <N초> · BigDataQuery <N분>
- 출력은 고치지 않고 붙였다 · 더한 것은 아래 「사내 메모」 뿐이다 : 확인함 ☐

### 8-7. 하지 않는 것

- **DB 를 SQL 로 고치지 않는다.** 2262-04-11 자리표·환산비 0.2·`ref_data` 사본이 보여도 그대로 둔다 — 리비전은
  append-only 이고, 고칠 길은 사용자가 화면에서 저장하거나 사외가 후속 마이그레이션을 만드는 것뿐이다.
- **스크립트를 고치지 않는다**(0장). 출력이 이상하거나 실패하면 그 줄을 그대로 적는다.
- **출력에 없는 값을 더 찾아 적지 않는다.** 「어느 제품이 어긋났나」·「어느 코드가 규칙을 어겼나」가 궁금해도
  키별 값, 제품·공정·설비 이름, 시뮬레이션 코드, 오류 원문은 적지 않는다. 사외가 필요하면 가명 규칙(5장)으로
  따로 묻는다.
- **`scripts/compare_legacy_results.py` 를 대신 돌려 옮기지 않는다** — 그 스크립트는 허용을 넘은 키의 제품·
  Stack 을 그대로 찍는다(사외 디버깅용이다).
- **확인을 위해 쓰지 않는다** — 데이터셋을 새로 등록하거나 원천을 다시 받거나 리비전을 저장하지 않는다.
  앱을 띄운 채 돌리지 않는다.

### 8-8. 사외가 답하는 법

사외는 리뷰의 「실데이터 확인」 절을 블록마다 읽고 **사용자와 대화로** 다음 일을 정한다. 정한 것은 다음
배포의 7장(사내가 따로 할 일)과 `docs/TODO.md` 에 적는다. 예를 들면 —

- 8-2 에서 `Plan_Chip(K개)` 가 `≈1` 에 몰리면 대조 목록(`services/legacy_comparison.py` 의 `COMPARISONS`)에
  넣고, `≈1000` 이면 단위를 맞춘 뒤 넣는다. 소요대수의 한쪽 줄이 맞으면 그 방식으로 대조에 넣는다.
- 8-4 에서 0.2 행이 있으면 사용자에게 다시 입력할 행 수를 알리는 문장을 7장에 싣는다.
- 8-5 에서 기본 창이 행을 놓치면 기본 창·같은 코드 다시 받기를 정한다.

**확인이 끝난 블록은 사외가 스크립트에서 빼고 이 장도 함께 고친다.** 새로 실데이터로만 답이 나오는 질문이
생기면 블록을 더한다. 사내는 이 장을 고치지 않는다.
