# AGENTS 10-1장 — 로컬 데이터는 합성 표본이다 — 관측을 업무 사실로 적지 않는다

## 10-1. 로컬 데이터는 합성 표본이다 — 관측을 업무 사실로 적지 않는다

`data/input/Core_Data.csv` 와 거기서 적재된 `data/capa_simulation.duckdb` 는 **실제 운영
데이터가 아니라 합성 데모 표본**이다. 공정 목록·소요기준(WF/CHIP)·성능·수율은
`scripts/generate_sample_core_data.py` 의 `PROCESS_SPECS` 리터럴에 사람이 써 넣은 값이고,
행의 팬아웃(계획 1행 × 전 공정)도 `process_rows()` 가 계획 행을 전 공정에 복제해서
생기는 구조적 산물이다. `equipment_samples.py`, `dynamic_capacity.py` 의 `DemoProfile`,
`builtin_seed.py` 도 같다.

검수용 합성 샘플(`scripts/generate_review_sample.py` — 화면 검수 · 가이드 예시판 시드, `docs/review_sample.md`)도 같다. 그 이야기
칸 · 판정 분포 · B/N 차례는 `review_sample_story.py` 의 리터럴에 맞춘 **이야기 꼴**이고, 생성기가 끝 점검(시뮬레이션 52 · 설비 22)으로
지킨다. 이야기에는 CUSTOM 이 둘인 제품 하나(`TWO_PART` — 한 변형만 수율 · UPEH 편차가 다른 부품)가 든다. 부품은 `review_sample_sim.py`(시뮬레이션 DB — 앱 저장 · 등록 · 자동 갱신 공개 함수만, 준비 자리에서 다 만든 뒤 옮김) ·
`review_sample_equip.py`(설비 DB — 시뮬레이션 DB 사본의 최신 공식 소요 · 가용에서) · `review_sample_modules.py`(시험 견본
`tests/fixtures/modules/` 여섯 복사) · `review_sample_story.py`(이야기 상수 · 산출 자리 지킴 `refuse_place` — git 작업 트리 안은
거절) · `review_sample_core_frame.py`(78컬럼 원천)다. 산출은 늘 저장소 밖이고(`git archive` 사본은 받는다) 저장소에 `data/` ·
`modules/` 를 만들지 않는다. 계약은 `tests/test_review_sample.py`.

따라서 다음을 지킨다.

- **로컬 DB·CSV 를 쿼리해 나온 값으로 업무 구조를 판단하거나 설계를 바꾸지 않는다.**
  쿼리는 코드 경로가 도는지 확인하는 용도다. 「데이터가 이러하니 업무가 이러할 것」은
  표본 생성기 저자의 선택을 업무 사실로 착각하는 것이다.
- **`실측` 이라는 말은 데이터와 무관한 측정에만 쓴다** — 브라우저 픽셀 폭, Streamlit
  위젯 동작, 소요시간 같은 것. 데이터를 집계해 얻은 수치는 `샘플 관측` 이라고 적고
  출처(어느 파일의 어느 리터럴에서 나온 값인지)를 함께 남긴다.
- **표본 고유 수치를 계약처럼 적지 않는다.** 「키 하나에 31행」, 「WF 기준 공정 6개」,
  「소요대수는 전부 NULL」 같은 문장은 공정 수와 생성기 설정이 바뀌면 전부 달라진다.
  코드가 그런 수치에 의존하면 그것은 결함이다.
- 근거가 사내 실데이터에서 온 것이면 **그렇다고 명시한다**. 예: `Pack Code` 충돌과
  `MPGA TEST` 의 소수 `모듈수` 는 사내 BigDataQuery 관측이라 근거가 있다.
- **실데이터로만 답이 나오는 질문은 사내에서 잰다.** `scripts/inspect_real_data_checks.py` 가 두 DB 를
  `read_only` 로 열어(저장소 `initialize()` 는 마이그레이션을 걸어 쓰므로 부르지 않는다) 기존 결과 대조
  분포(ST 정의 대조 UPEH × ST ÷ 60 — 리비전 1 에 그런 MI 행이 없으면 가장 최근에 저장한 리비전 가운데 그런 것을 저장 차례
  k/N 으로 대신 본다 — ·소요대수 ≈60 배 무리 가르기 포함. 8-2 끝의 「계획 행으로 접음」 대조 · 원천 집계 대비 달 비 · 환산 탭
  두 집계 기준의 달 합 · Dummy 계열 행(요약 `8-2P`)과 업무 키 충돌 키밖 / 그 밖 · Capa Code 하나에 CUSTOM 둘 이상(`8-2K`) — 두 줄 머리
  `종류 n` 은 원천 CUSTOM 종류이고 리비전에 맞추기(`source_custom_aligned`) **앞**의 원천으로 센다(`SourceData.custom`))·원천
  `RQ_REQB` 소요기준·설비 DB·
  BigDataQuery(8-9 HOME 월 축 블록은 닫을 조건이 서서 걷었다 — 번호는 다시 쓰지 않는다)와
  「지금대로」 로 정한 결정마다 그 꼴이 저장 리비전에 몇 개 있는지(8-10 센서스 — 기본은 활성·공식버전 대상 리비전, `--census-all-revisions`
  면 전부. 줄마다 근거가 되는 `docs/TODO.md` 결정 번호와 그 가운데 잰 부분을 꼬리표로 단다 — 수는 근거일 뿐이라 0 이어도 결정을
  닫지 않고 사외가 사용자에게 묻는다. BigDataQuery 가 있어야 답이 나는 것은 넣지 않는다. 같은 블록 표 아래 객체 칸 한 줄(요약 키 `8-10T` —
  2026-11-17 메모리 보드)은 같은 리비전 묶음의 리비전 표를 `load_frame` 그대로 읽어 객체 칸을 `글자만` · `섞임` · `빈` 으로 세어 글자 공유 R1 의
  「글자 칸만」 조건을 실데이터로 본다 — 결정의 꼴이 아니라 머리의 `0 아님` · `합` 에 넣지 않고 따로 낸다), 기준 정보 편집 표 아홉의 실데이터 크기(8-11
  `grid` — 같은 리비전 묶음을 화면과 같은 양식 함수로 펴 줄 · 달 · 칸 수와 껍데기 본문 바이트를 큰 표 상한 `reference_grid.CAP_*` 에
  견준다. 상한 · 값 형식 · 분류 칸은 화면 모듈을 부르지 않고 옮겨 두고 시험이 화면과 맞댄다 — 2026-11-03), 남는 경로의 빈 칸으로 대당 Capa 가 멈춘
  리비전의 꼴(8-12 `blank` — 6-3 a 와 같은 저장된 모든 리비전. 빈 칸을 남은 경로 · 빠질 경로만 · 안 붙음으로 가르고 분포 · 원천 형제 · 부하를 센다. 메모리 사본의 빈 칸에 자리값을 넣어 계산을
  끝까지 돌리고 그 값은 찍지 않는다 — 사내 리뷰 `202611041000` 발견 1)을 재고,
  **개수·비율·dtype·초만** Markdown 블록으로 찍는다 — 이름·코드·키별 값·합계 물량·파일 경로·예외 문구를
  찍지 않는다(이 앱의 오류 문구에는 식별값이 실린다). 값 이름은 계약 어휘(소요기준·Main/MI·`WF 구분` 선언
  목록)만 찍고 그 밖은 종류 수로 센다. 자동 판정(통과·실패·결론)은 넣지 않는다 — 넣으면 재검증이 갈래마다
  반례를 낸다. 사실만 찍고 결론은 사외가 사용자와 낸다. 사내 런북(`docs/internal_update_runbook.md`) 8장이 배포마다 부르고 —
  사용자가 Claude 밖의 별도 PowerShell 창에서 치고 사내 에이전트는 `--output` 파일만 옮긴다(2026-11-11 사용자 결정 — 사내 DB 를 Claude
  가 읽지 않는다, 런북 0장) — 결과는 리뷰 문서로 돌아온다. BigDataQuery 블록(8-5 `bdq`)은 스크립트에 남지만 **런북은 부르지 않는다** —
  꼭 필요하면 사외가 사용자에게 먼저 요청하고 사용자가 직접 돌린다. 사내 리뷰는 사람이 손으로 옮겨 적으므로(2026-10-22) 출력 끝에 `### 전송용 요약`(돈 블록마다 짧은 키와
  수만 실은 한 줄 · 합이 서는 수는 줄 안 `합 = 항 + 항` · 줄 끝에 그 줄의 수로 셈한 확인 코드 `#NN`, 8-10 은 0 이 아닌 키만 — 블록 출력은
  그대로)을 찍고, 사내는 그 줄을 코드째 리뷰 압축본에 옮긴다(런북 5장 · 8-6). 키의 뜻은 런북 8-6 범례 한 곳에 두고 요약에 안내문을 두지
  않는다. 사외는 받은 압축본에 `--check-summary <파일>`(DB 를 열지 않음)을 돌려 한 자리 오타 · 자리바꿈 · 빠진 8-10 · 8-12 줄을 잡는다 —
  수는 맞는 손 전사 꼴(띄어쓰기 빠진 `+` · 끝 괄호 덧말은 그대로 읽고, 빠진 ` + ` · `=+` · 글자 없는 키로 시작한 메모 줄은
  `(꼴)`)은 맞지 않는 것에 세지 않는다(`review_transcript` 의 `forms`, 런북 8-6). 8-2 · 8-3 은 같은 원천 데이터셋을 본다 —
  `--dataset-id` 가 없으면 원천에서 온 것 가운데 리비전 1 계산(대당 Capa → 소요대수)이 서는 가장 최근 것이고, 멈춘 더 최근 것은
  건너뛰어 차례 · 6-3 a 와 같은 `S<n> r1`(`_numbered_revisions` — 8-12 도 같은 번호) · 원천 종류 · 적재일 · 단계와 예외 종류 ·
  꼴 이름만 찍는다(최근 `SOURCE_CANDIDATES` 개, 다 멈추면 가장 최근 것 — 요약 `8-2D`, 돌아온 것의 자리 · 꼴은 `8-2R`).
  그 데이터셋에 부대공정(BDQ 밖)을 합쳤으면 리비전 1 표에서 그 행을 걷고 본다 — 원천과 기존 결과를 맞대는 블록이라 원천에 없는
  공정이 소요대수 대조에 「신규만」 으로 섞이지 않게(설계 A12, `_extra_processes` — 0037 전 DB 사본은 없음으로 본다). 데이터셋 줄은
  「(원천 + 부대공정 n — 부대공정 행은 대조 · 계산에서 뺌)」 이고 요약 키는 그대로다.
  꼴 이름은 6-3 a 갈래 표 `꼴` 칸의 글자(`ReferenceJoinProblem.label`)다. 8-5 사본 확인의 조회는 실패하면
  한 번 더 묻는다(시간 초과 · 어댑터 안내는 빼고, `ask_twice`). 8-5 는 넓은 목록이 실패하면
  다시 묻지 않고 좁은 창으로 이어 가며 그 뒤 요약 줄마다 `기준 n일` 을 단다(창을 줄이는 `--bdq-wide-days`). 블록이
  요약 줄을 `Session.notes` 에 쌓고 끝에 한 번 찍는다 — `Ctrl+C` 로 멈춘 실행도 「(중단 — 여기까지)」 와 함께 찍고(센서스는 센 줄까지),
  요약 줄 조립은 `_noted` 로 감싸 실패해도 블록 출력을 잃지 않는다. 블록을 더하면 그 요약 줄과 범례 한 줄도 더한다. 블록을 더할 때는
  `tests/test_inspect_real_data_checks.py` 의 표지값(`ZZSENTINEL…`) 검사를 함께 늘리고, 출력·요약이 런북 5장 자가 점검 그물(대소문자
  무시)에 걸리는 줄이 8-4 사용기준 한 줄뿐인지 보는 시험(그물은 런북에서 읽는다)이 그 블록도 덮게 한다. 앱은 rerun 동안만 DB 를 쥐어 쉬는 앱은 잠금에 안 잡히므로,
  운영 DB 를 열 때는 화면 확인 스크립트의 `running_app_count` 로 앱 프로세스를 먼저 보고 보이면 DB 를 열지
  않고 종료 1 로 멈춘다. 살피지 못하면 잠금만 보고 그 사실을 한 줄 찍는다. 사본만 열거나 BigDataQuery
  블록뿐이면 보지 않는다. 같은 8장 뒤에 도는 `inspect_wf_division.py` 와 7-8 의 개수 세기 `inspect_db_counts.py` 도 같은 판정으로
  멈추고, `--database <사본>` 을 주면(운영 DB 자리가 아니면) 앱 프로세스를 보지 않는다. `inspect_db_counts.py` 의 앞 세 줄(개수 ·
  Space 모듈 묶음 · 파일 크기)은 옛 7-8 `python -c` 세 줄과 글자가 같은 꼴이다 — 7장 기대 줄 · 지난 리뷰 값과 견주므로 꼴을 바꾸지 않는다.
  넷째 줄은 생산 계획 그리드 두 표의 크기이고 그 표 이름 · 값 꼴 · 0 을 빈칸으로 싣는 양식은 `components/plan_grid.py` 와 같은 값을 들고
  시험이 맞댄다(2026-11-12 사용자 답 ②-1 · ③-7). 다섯째 줄 `unit_mixed`(`--only mixed`)는 최신 설비 리비전의 모듈 묶음 수와 같이
  바뀌는 칸마다 갈린 묶음 수 `값 다름+빈 칸 섞임`이고 칸 갈래(`read` 여섯 · `save` 일곱 · `show`)와 짧은 키(`MIXED_KEYS`)는 계약 튜플을
  따른다 — `save` 가 0 이 아니면 그 묶음이 다음 설비 저장을 막으므로 이관 앞에서 읽는다(2026-11-12 Space 요청 3 · P2). 운영 DB 자리 판정은 `settings.is_operational_database_place` 한 벌이다 — 같은 파일
  (하드링크 · Windows 긴 경로 접두 · UNC 공유처럼 글자가 달라도 장치 · 파일 번호로), 운영 `data/` 그 자체나 그 아래, git 저장소
  안(사본은 저장소 밖 — 사본 트리의 스크립트가 다른 저장소의 `data/` 를 못 가리는 것도 이것이 막는다). 경로 글자만 견주지 않는다.
  설비 DB 는 **공식 설비 시나리오**(공통 최신 + 최신 공식 발행)를 앱과 같은 읽기 길(`equipment_repository.read_official_pair`·
  `read_merged` — 3장)로 한 번 읽어 8-1·8-4 가 나눈다. 공통 칸 수는 공통 최신 SQL, 일정 칸 수(Q 자리표·개편 전 두 날짜·일정
  미정·정지+반출·비가동 행)는 공식 일정 리비전으로 센다 — Q 자리표는 레거시 원천 행만 센다(새 일정 표에는 자리표가 없다).
  8-4 요약 키의 `r` 은 공식 일정 리비전 번호라 일정은 그대로 두고 공통만 v4 로 저장해도 8-1·8-4 키가 그대로다(시험). 이관 확인
  줄(설비 `0027` — 시나리오 수·이관 리비전/이관 전 리비전·공식·옛 배포 흔적·일정 없음·고아 일정 행, 설비 `0031` 뒤 끝에 가정
  배치 차이 호기 행 `Y` — S4)은 요약 키 `8-4s` 로 따로 지어 8-4 줄이 멈춰도 남는다. 시나리오 이름은 값이라 찍지 않는다. 같은 표의
  「가정 배치 차이」(ACTIVE 시나리오 최신의 저장된 행: 시나리오 / 호기 / 요소 / 이름표)·「배치 옛 코드 흔적」(0 이어야 함) 두 줄은
  앱 목록 투영(`equipment_scenario_store.scenario_rows`)을 그대로 읽는다. `--check-summary` 는 수만 셈하므로 `Y` 없는 옛 8-4s 도
  받는다.
