# AGENTS 1장 — 프로젝트 목표와 현재 경계

## 1. 프로젝트 목표와 현재 경계

이 프로젝트는 월별 PKG 생산계획과 제품·공정 기준정보를 이용해 다음 순서로 Capa를
시뮬레이션하는 Streamlit 앱이다.

```text
PKG PLAN
→ PKG·Chip·Wafer·Density 부하량
→ 공정·제품·속성별 대당 Capa
→ RQ_REQB 경로별 소요대수
→ 공정별 가용대수 대비 확보율
→ 월별 Bottleneck 및 대시보드
```

기본 런타임 원본은 `data/capa_simulation.duckdb`의 최신 공식 리비전이며, 계산 페이지는
XLSB를 읽지 않는다. `templates/structure_template.xlsb`는 초기 표시순서 이관과 병행
검증에만 사용한다. SQLite 파일은 병행 검증용으로 앱에서 읽지 않는다. 가용설비 현황의
운영 데이터는 시뮬레이션과 물리적으로 분리된
`data/equipment_availability.duckdb`에 저장한다. `Core_Data` 78컬럼 계약·typed raw
적재와 pandas 기반 16개 RQ 변환은 구현되었고, BigDataQuery 어댑터의 실제 SQL·컬럼
매핑도 커밋을 마쳤고 사내에서 약 3만 행 조회와 시나리오 저장까지 확인했다. 남은 것은 상세 조회 창의 결정과
사내 런북 8장의 실데이터 대조 결과다.

GitHub 소스만 있는 빈 환경에서는 `config/bootstrap_display_order.json`과 코드로 생성한
비민감 `DEMO_*` Core Data를 공통 변환 파이프라인에 넣어 초기 시나리오·리비전·공식버전을
자동 생성한다. 운영 서버(`SsoConfig.operational` — Admin Area 잠금과 같은 판정)에서는 빈 저장소에도
만들지 않아 「공식버전 없음」 으로 서고, 개발자가 데이터를 올리면 공식이 선다(2026-11-14 물음 보드
seed (nopub)). 기존 시나리오나 공식버전은 자동 시드가 변경하지 않으며 내장 시드는 운영
기준정보가 아니다. 실제 표시순서는 시나리오와 분리된 공용 DB 프로필이며, 선택적 로컬
`data/input/RQ_DISPLAY_ORDER.csv` 또는 웹 Excel 표 붙여넣기로 초기화할 수 있다.

### 세 영역 — Static · 실행 관리 · Dynamic (2026-10-17 사용자 결정)

사이드바 계산 그룹은 셋이고 차례도 이렇다(`navigation.SIDEBAR_GROUPS`). 2026-11-02 실행 관리와 Dynamic 사이에 「생산 진도」 상자가 섰다(2026-11-03 — 내용은 모듈이 맡는다, 2026-11-04 — 하위 샘플 페이지 셋으로 펼침 상자).

| 그룹(상자 이름) | 뜻 | 화면 |
|---|---|---|
| **Static Capa** | **약속.** 기술팀이 공정별 설비 셋업 시점·성능(UPEH·효율·수율)을 기준정보에 정하고, 그 기준정보와 생산계획으로 미래 Capa 를 낸다. 자원운영팀(옛 Guide 의 「GO팀」과 같은 팀)이 그 부족대수로 투자한다. | 현황 요약 · 생산 계획 · 기준 정보 · 산출 결과 · 표준 목표 |
| **실행 관리** | **이행.** 제조팀이 약속된 Capa 가 실제로 확보되는지 공정·기간·호기로 재고, 어긋난 곳을 유관부서에 이행 요청하고, 지킬 수 없으면 Static 반영까지 추적한다. | 현황 요약(머리, `execution_management.py`) · 공정 Capa 상세 · 필요 단축 일정(2026-10-18 가용설비 현황 탭에서 뗀 별도 화면) · 제약 시뮬레이션(2026-10-24, 저장하지 않는 미래 가정) · 가용설비 현황 · Space 현황 · 효율·UPEH·수율 실적 |
| **생산 진도** | 2026-11-02 사용자 요청으로 실행 관리와 Dynamic Capa 사이에 세운 상자다. 보일 내용은 모듈이 맡는다(2026-11-03 사용자 「모듈에 스크립트를 넣으면 반영될 페이지 영역만 표시」) — 머리 화면(`production_progress.py`)과 하위 샘플 페이지 셋(2026-11-04 검수 의견 prog-01 · prog-02 — 임시)은 모두 모듈 화면이 들어올 점선 자리 하나이고(`components/module_slot.py` 한 벌 — 이름만 다르다) 데이터를 읽지 않으며 공통 조건 줄·조건 카드가 없다. 모듈이 그 자리에 그리는 길은 아직 없다(`docs/TODO.md` 2장 「생산 진도 화면 내용」). | 현황 요약(머리, `production_progress.py`) · 샘플 페이지 1 · 2 · 3(`production_sample_1.py` ~ `production_sample_3.py`, `PRODUCTION_PROGRESS_SUBPAGES`) — 모두 「모듈 화면 자리」 |
| **Dynamic Capa** | **실적.** 실행 관리가 모은 실적으로 Capa 를 다시 내고 그 Capa 로 단기 운영(재공·Rundown·병목)을 한다. | 현황 요약(머리, `reference_integrity.py`, 주소 `dynamic_capa`) · 표준 대비 재공 현황 |

- **경계 규칙**: 약속 이행을 **재고·비교·요청·추적**하는 일은 실행 관리, 그 실적으로 **Capa 를 다시
  내거나 단기 운영에 쓰는** 일은 Dynamic 이다. 표준 목표는 약속(대당 Capa)을 일·주로 푼 표준이라
  Static 이고, 재공 현황이 그것을 기준선으로 링크해 쓴다.
- **「Dynamic」 은 실적 Capa 에만 쓴다.** 화면 글자·Guide·문서에서 설비 마스터 일정으로 낸 가용대수는
  **설비 일정 기준 가용대수**(짧게 「일정 기준 가용」, B/N 은 「일정 기준 B/N」)이고, 가용설비 현황의 그
  탭 이름은 `Static 대비 일정` 이다. 기준정보 `RQ_EQP_AVBL` 의 값은 「기준정보 가용대수」(Static)다.
  **코드 식별자·내부 파생 컬럼·세션/위젯 키·DB 이름은 그대로다** — `dynamic_*`·`DYNAMIC_*`·
  `Dynamic가용대수`·`Dynamic확보율`·`process_detail_dynamic_absent` 같은 이름과 그것을 설명하는 주석의
  「Dynamic」은 설비 일정 기준 가용을 뜻한다. 내부 컬럼이 화면 표 머리로 나갈 때만 표시용 이름으로 바꾼다.
- **「확보율 보정」**: HOME 의 토글·Preference 편집기·풍선 글자다(옛 화면 이름 「실행 Loss」·「실행 Capa
  반영」·「실행 반영 ±n[퍼센트 포인트 기호]」 — 기호 자리만 [ ] 로 바꿔 적음). 뜻은 「기준정보 밖 변수
  (비가동·UPEH·재공)를 확보율에 % 로 더하고 빼는 손입력 보정」이고 실행 관리 그룹과 상관없다. 코드·저장 이름은 `execution` 그대로다(공용 프로필
  `app_meta.global_execution_capacity`, 마이그레이션 0021, 토글 키 `EXECUTION_TOGGLE_KEY`, 내부 컬럼
  `실행 비고`).
- **「UPEH 가정」**(2026-10-22 사용자 요청): 공정 Capa 상세·필요 단축 일정 조건 카드 끝 「이 세션만」 % 칸이다. 뜻은 「적용
  구간의 달에 기준정보 계획 UPEH 전체(Main UPEH·MI ST)가 p% 라면」 이고 소요대수에 ÷f 를 사후로 건다(6장 「소요대수와
  확보율」). 효과는 공정 Capa 상세에서만 보인다 — 필요 단축 일정은 같은 세션 칸을 그릴 뿐 계획에 걸지 않고 공식 대 가정
  비교 보기를 두지 않는다(2026-10-26 사용자 결정 — 사내 리뷰 202610231430 사외 요청 1). 세션 값이라 기준정보·리비전·
  HOME·공식버전·공용 프로필은 바뀌지 않는다. 「확보율 보정」(공용 손입력 — 확보율에 % 를 더한다)과 다른 것이라 화면 글자·Guide 에
  「보정」이라는 말을 쓰지 않는다. 코드·키 이름은 `upeh_assumption*` 이다.
- 파일 이름·페이지 제목·주소는 그룹을 옮겨도 바꾸지 않는다 — 주소는 파일 이름에서 나오고, Static 하위
  네 제목은 표시순서 DB 의 페이지 키다(`services/display_order_scopes.py`). 그룹을 옮긴 화면의 북마크는
  그대로 산다.

### 모듈 영역 — 모델 2 (2026-11-01 사용자 결정)

동료가 따로 만든 Streamlit 기능을 이 앱 웹 안의 별도 화면으로 띄운다. 코어와의 데이터 연계는 다음 단계다. 정본을 **폴더로**
가른다(보드 C3 는 이 결정으로 닫혔다).

| 무엇 | 정본 | 자리 |
|---|---|---|
| 코어 | 사외 `origin/main` | 배포 ZIP 이 싣는 것 전부 |
| 모듈 | 사내 저장소 | `modules/<id>/` — ZIP 이 싣지도 덮지도 지우지도 않는다. 사외에는 그 폴더가 없다 |
| 모듈 데이터 | 그 PC · 서버 | `data/modules/<id>/` — git · 이미지 밖 |

- **같은 사내 저장소다**(별도 저장소가 아니다). C-DEP CD 서버는 사내 저장소 하나로 이미지를 만든다(`docker/Dockerfile-prod` 의
  `COPY . /project/`, 셸 없음, 시작 명령 고정) — 둘째 저장소는 서버에 닿지 않는다. iframe · 별도 프로세스는 쓰지 않는다.
- **경계 다섯**(10-15 규칙 그대로):
  1. 의존 방향 — 모듈은 코어 공개 창구 `module_api` 만 쓰고, 코어는 모듈을 import 하지 않는다.
  2. 자기 데이터 자리 — `data/modules/<id>/` 만 쓰고 코어 두 DB · `data/input|output|temp` 를 열지 않는다.
  3. 키 접두 `mod_<id>__` 필수 — 코어는 `mod_` 로 시작하는 키를 만들지 않는다.
  4. 전역 CSS · `st.sidebar` · `st.set_page_config` · 프로세스 전역 상태 금지.
  5. 들어갈 때만 불러오기 — 찾기는 `module.json` 만 읽고 `.py` 를 import 하지 않는다.
- **자격은 코어가 쥐고 모듈은 창구 도우미만 부른다**(2026-11-12 사용자 결정 「도우미 함수로」 — 리뷰 202611111500 사외요청 2,
  보드 N9 · N10 · N11). BigDataQuery 조회는 `module_api.query_bigdataquery`(앱의 DB 등록과 같은 길 · 같은 실패 갈래 — 요청자
  계정 · 토큰은 코어가 채운다), S3 는 `s3_upload` · `s3_download`(모듈 데이터 자리 파일 하나를 버킷의 `modules/<id>/` 아래로 —
  접속 명단과 같은 키 · 주소 · 버킷, 동기화 모드 `managed` 서버에서만, 파일 하나 8 MiB, 예외 없이 `S3Result`)다 — 창구 1.3, 속은
  `module_helpers`. 언제 올리고 받을지는 모듈이 정한다. 자격 환경변수 이름(`CAPA_BDQ_` · `CAPA_S3_` · `AWS_` · `JWT_SECRET` ·
  `ADFS_`)과 토큰 파일 자리(`.credential` · `bigdataquery.token`) · BigDataQuery 자동 로그인 계정의 버킷 자리(`secrets/` ·
  `bdq_login` 마디)를 코드에 적으면 점검 오류 M21(시험 막음)이다 — S3 도우미는 이름이 무엇이든 `modules/<id>/` 밖에 닿지 않는다
  (`tests/test_module_helpers.py`). `bigdataquery`
  직접 import 는 2026-11-01 결정대로 경고(M09)로 둔다. 모듈 시험(`check_module.py`)은 자격 이름의 변수를 빼고
  `CAPA_MODULES_TEST_RUN` 을 켜 도우미가 밖에 닿지 않는다(조회 · S3 모두 「쓸 수 없음」).
- 깨진 모듈은 그 화면만 오류 카드다 — 화면 본문은 `module_runtime.run_module_page`, 위젯 콜백은 `ctx.callback`, 프래그먼트 · 팝업
  본문은 `ctx.guard` 가 감싼다. 끄는 스위치는 둘이다 — `module.json` 의 `"enabled": false` 와 실행 환경변수 `CAPA_MODULES_DISABLED`
  (`*` 또는 id 들). 사이드바 상자 「모듈」 은 켜진 모듈이 있을 때만 서고 자리는 Dynamic 다음 · Support 앞이다.
  `CAPA_MODULES_ROOT=off` 는 사외와 같은 화면이다(상자 · Admin 펼침 · 색인 캡션이 모두 없다) — 화면 확인 · 가이드 자식 앱이 쓴다.
- **역할 이름 둘** — **담당자**(모듈을 맡아 그 에이전트와 대화하는 동료)와 **앱 관리자(개발자)**(배포를 적용하고 승인하는 한 사람 — 이
  저장소의 사용자). 동료 세션에서 「사용자」 는 담당자 자신이라 지침서는 「앱 관리자(개발자)의 승인」 이라고만 쓴다. 그 승인은 동료 에이전트의
  대화 안에서 받을 수 없고, 담당자가 받아 와 커밋 본문과 PR 본문에 `승인: 앱 관리자(개발자) <YYYY-MM-DD>` 를 적는다 — 앱 관리자(개발자)가 그 PR 을
  합치는 것으로 승인이 끝난다.
  두 이름은 역할이지 접속 등급이 아니다 — 앱 안에서는 둘 다 명단 등급을 따르고, 앱 관리자(개발자)는 등급으로 개발자다(새 등급 「관리자」 와
  다른 사람). 모듈 화면은 **모두 열람부터** 열고 모듈 안의 저장 · 올리기 · 공용 BigDataQuery 조회도 등급으로 막지 않는다 — `module.json` 에
  등급 칸을 두지 않는다(앞 ZIP 으로 되돌릴 때 「모르는 칸」 으로 실패하지 않게). 그 대신 올리기 · 조회는 `module_helpers` 가 작업 기록 한
  줄(`data_module_upload` · `data_module_query` — 대상 모듈 id · 결과 낱말 · 크기 · 행 수만)을 남긴다(2026-11-17 두 차례 답 — 5장 41).
  `module_api` 는 등급을 내지 않는다(다음 판 후보 `can_write()`). 모듈 오류 카드의 「담당자용 진단」 은 누구나 펼친다.
- **담당자의 모듈 변경은 PR 로만 사내 main 에 들어간다**(2026-11-02 사용자 — 사내 GitHub 에서 PR · 가지 보호를 쓸 수 있다, 사양 10장 3).
  담당자 에이전트가 자기 가지 `module/<id>/<주제>` 에서 커밋하고 담당자가 푸시해 PR 을 열면, 앱 관리자(개발자)가 PR 머리를 사본 트리에서 점검한 뒤
  (런북 4-6) 「Squash and merge」 로 합친다. 사내 main 보호 규칙은 강제 푸시 · 지우기 막기와 PR 필수(배포 `deploy:` · `review:` 푸시를
  위해 앱 관리자(개발자) 계정은 우회 — 우회를 둘 수 없으면 PR 필수는 걸지 않는다)다(`docs/dual_env_workflow.md` 1-2). 직접 커밋 길은 닫았다.
- **CI/CD 단추는 앱 관리자(개발자)만, 런북 4-5 모듈 점검을 본 뒤에 누른다**(2026-11-01 사용자 「권장대로」 — 사양 10장 4). C-DEP CD 는 단추를
  누른 때의 사내 main 을 그대로 빌드하고 프로젝트 사람이면 누구나 누를 수 있다. 모듈은 PR 로만 들어와 4-6 점검을 한 번 거쳤고, 4-5 는
