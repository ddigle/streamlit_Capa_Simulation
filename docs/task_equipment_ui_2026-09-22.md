## 0. 이 과제는 경쟁이다

1주기(리팩토링)는 둘이 다른 파일을 집어 분업으로 끝났다. **이번은 같은 화면을 두
방향으로 만드는 일이라 진짜 경쟁이다.** 하나만 채택하고 하나는 버린다. 그래서
**평가 기준을 결과물보다 먼저 못박는다**(5장).

두 후보는 서로의 결과를 보지 않는다. 같은 정의서만 받는다.

## 1. 무엇이 문제인가

`app_pages/available_equipment_status.py` 의 **Main 탭 한 화면(307줄)에 서로 다른
질문 여섯 개의 답이 동시에 펼쳐져 있다.**

| 구획 | 시각화 |
|---|---|
| metric 4장 | 총대수·가용대수·비가동대수·가용률 |
| 주차별 설비 현황 | Altair 막대 |
| 호기 생애주기 상태 모니터링 | Altair 막대 + 표 |
| 호기별 생애주기 일정 | Plotly Gantt |
| Qual 확정상태 실행관리 | metric 4장 + Altair 막대 + 표 |
| 공정소분류별 현황 | 표 |
| 비가동 설비호기 | 표 |

사용자 말: **「가시화된 양식이 너무 많아서 어떤 게 내가 필요한 양식인지 찾는 것부터가
어렵다」**

탭도 다섯으로 늘었다 — `Main`·`Cut-off`·`Static/Dynamic`·`Preference`·`RawData`.

## 2. 무엇을 만들 것인가

### 2-1. Main 탭 — 「고르면 그 방식대로 보인다」

사용자 말: **「하나의 틀 안에서 내가 옵션들을 골라서 선택하면 그 필요한 데이터가
셋팅한 옵션의 방식대로 표현되게끔」**

- Main 탭의 목적은 **가용설비 현황의 전체 데이터를 정리해서 보는 것**이다.
- 여섯 구획을 동시에 펼치지 않는다. **무엇을 볼지 고르고, 고른 것이 고른 방식으로
  그려지는 하나의 틀**을 만든다.
- 「옵션」이 무엇이고 「방식」이 무엇인지는 **후보가 설계한다.** 축(무엇을 세로로
  볼 것인가)·기간 단위·보기 형태(표/막대/타임라인) 같은 것이 후보가 될 수 있으나
  그 목록을 여기서 못박지 않는다 — 그 설계가 곧 경쟁의 내용이다.
- **기존 여섯 구획이 답하던 질문을 잃지 않는다.** 하나의 틀로 접되, 그 틀에서 같은
  질문에 답할 수 있어야 한다. 무엇을 덜어냈다면 왜 덜어도 되는지 적는다.

### 2-2. Cut-off 탭 → Preference 로 합친다

지금 별도 탭인 공정별 Cut-off 입력을 `Preference` 안으로 옮긴다. 탭이 하나 준다.
저장 경로·계약은 그대로 둔다(`equipment_ops.process_cutoff`, 전체 교체).

### 2-3. Static/Dynamic 탭 — Main 과 같은 방향으로

지금 한 탭에 그림 + 10분류 분해표 + 확보율 교차검증이 세로로 쌓여 있다. Main 과
같은 원칙(**고른 것이 고른 방식으로**)을 적용해 개선안을 찾는다. 탭을 유지할지
Main 의 한 옵션으로 흡수할지도 후보가 정한다.

### 2-4. RawData 탭 — 데이터 적용 방식 자체를 다시 본다

사용자 말: **「지금 공통적으로 활용하는 데이터 적용 방식과 기본 라이브러리 시트로
표시하고 있는데, 데이터 적용 방식을 좀 더 시각적으로나 접근성 측면으로나 개선된
방법이 있을지 탐구해보고 적용 가능한 방안 수립해서 구현」**

지금은 이렇다.

- Excel 붙여넣기 Import → 미리보기 → 편집본(draft) → `st.form` 하나로 세 표를
  한꺼번에 불변 리비전으로 저장
- 표는 전부 `st.data_editor`(기본 라이브러리 시트)

**탐구 범위는 넓게 연다.** 붙여넣기·검증·미리보기·편집·저장의 흐름 전체이고,
파일 업로드·드래그앤드롭·외부 그리드 라이브러리까지 본다. 어디가 막히는지 직접 써 보고
정한다. 무엇을 바꾸든 **저장되는 계약(31컬럼 호기 마스터·비가동·기존 보유대수의 불변
리비전)은 지키고**, 바꾸는 것은 그 앞의 경험이다.

**새 라이브러리를 써도 된다.** 다만 사내 WebIDE 는 인터넷이 없어 반입이 별도 문제다.
사용자 결정: **우선 탐구·구현하고, 의존성 문제는 사내에서 테스트해 최종 적용 여부를
정한다.** 그래서 후보는 아래 넷을 반드시 지킨다.

1. **의존성 추가 커밋을 따로 뗀다.** `pyproject.toml`·`uv.lock` 변경만 담은 커밋 하나로
   분리해 채택 후에도 그 한 커밋만 되돌릴 수 있게 한다.
2. **그 라이브러리 없이도 화면이 열리는 길을 남긴다.** 사내에서 못 깔 수도 있다 —
   import 실패가 페이지를 죽이면 그 화면은 사내에서 영영 못 쓴다.
3. **사내 반입 난이도를 미리 재서 적는다.** 순수 파이썬 휠인가 네이티브 빌드가 필요한가,
   설치 크기가 얼마인가, 전이 의존성이 몇 개 늘어나는가. 순수 파이썬 휠 하나와 컴파일이
   필요한 것은 사내에서 난이도가 전혀 다르다.
4. **왜 그것을 골랐고 대안은 무엇이었는지 적는다.** 사내 테스트에서 떨어지면 대안으로
   갈아타야 하는데, 그때 후보가 이미 본 것을 다시 보지 않게 한다.

## 3. 건드리지 말 것

- **계산 결과가 달라지면 안 된다.** 이 과제는 화면과 입력 경험이다.
  `services/` 의 산식을 바꾸지 않는다.
- `equipment_ops` 스키마를 바꾸지 않는다. **새 마이그레이션이 필요하다고 판단되면
  만들기 전에 사용자에게 묻는다**(홀짝 규칙: claude 홀수 · codex 짝수).
- HOME·B/N·확보율의 정본은 여전히 Static 이다. 전역 전환은 이 과제가 아니다.
- `AGENTS.md`·`docs/TODO.md` 는 **자기 후보의 절만** 고친다. 새 절 번호를 만들지
  않는다(합칠 때 충돌한다).
- `HANDOFF.md`·`README.md` 는 건드리지 않는다 — 통합하는 쪽 몫이다.

- **결과를 한 장으로 설명하는 글을 커밋에 남긴다** — 무엇을 어떤 틀로 접었고, 어떤
  질문을 어디서 답하게 했고, 무엇을 덜어냈고 왜 덜어도 되는지.

## 5. 평가 기준 — **결과물을 보기 전에 정한다**

채택은 아래 순서로 본다. 위가 우선이다.

| # | 기준 | 어떻게 재나 |
|---|---|---|
| 1 | **처음 여는 사람이 무엇부터 해야 하는지 아는가** | 빈 DB 로 열어 첫 화면만 보고 다음 행동이 보이는가 |
| 2 | **한 화면이 한 가지 일만 하는가** | 한 화면에서 답하는 질문의 수 |
| 3 | **찾던 것을 몇 번 만에 찾는가** | 「10월 Die Attach 의 비가동 호기」를 찾는 데 드는 조작 수 |
| 4 | **기존 질문 여섯을 여전히 답할 수 있는가** | 1장 표의 여섯 구획을 하나씩 대조 |
| 5 | **RawData 입력이 실제로 쉬워졌는가** | 30행 붙여넣기 → 저장까지의 조작 수와 막히는 자리 |
| 5-1 | 새 의존성을 썼다면 사내 반입이 현실적인가 | 순수 파이썬 휠 여부·설치 크기·전이 의존성 수, 없을 때의 폴백 |
| 6 | **계산이 그대로인가** | 검증 5종 + 같은 입력에서 같은 숫자 |
| 7 | 되돌리기 쉬운가 | 커밋이 단계로 나뉘어 있는가 |

**1~3이 이 과제의 본질이다.** 6은 통과/탈락 조건이지 점수가 아니다.

## 6. 데모 데이터

두 폴더의 `data/` 는 서로 다르다(워크트리마다 따로). **통합 폴더의 DuckDB 둘을
복사해 같은 화면에서 출발한다** — 빈 화면을 보고 디자인하면 안 된다.

공정별 Cut-off 30건이 합성값으로 채워져 있고 호기 마스터는 비어 데모 fleet 796대가
표시된다. **이 값들은 실적이 아니다**(`CLAUDE.md` 의 합성 표본 규칙).
