# 통합인증(SSO) 연동 — 운영 · 개발 안내

C-DEP 운영 서버에서 통합인증(ADFS, 포털 시스템 형식 「Legacy (OpenID)」)으로 로그인하고 접속 명단에 있는 사람만 앱에 들어오게 한다.
**이 문서에는 사내 주소 · 인증서 · client id · 실제 loginid 를 적지 않는다** — 이 저장소는 공개다. 예시는 모두 `*.example.invalid` · `demo.*` 이고, 실제 값은
C-DEP 배포 설정의 **환경변수 표**에만 넣는다(리뷰 압축본 · 전문에도 값을 옮기지 않는다).

코드: 진입 파일 `capa_server.py`, 꾸러미 `src/capa_simulation/auth/`(S3 명단 `auth/access_store.py`), 작은 객체 경계 `io/s3_small.py`, 화면 조각 `components/sso_identity.py` · `components/sso_status.py` · `components/access_list_admin.py`,
툴바 스크립트 `components/sso_reconnect.py`(「다시 로그인」 띠) · `components/sso_refresh.py`(쓰는 동안 로그인 늘리기), 가짜 IdP
`scripts/sso_mock_idp.py`, 가짜 S3 `scripts/s3_mock_store.py`. 규칙은 `AGENTS.md` 3장(파일 책임) · 5장 36 · 37 · 9장(문지기) · 10장(공개 저장소).

## 1. 흐름

```text
브라우저 ──GET /──▶ 문지기(SsoGate) ── 세션 쿠키 없음 ──302──▶ ADFS authorize
                                                              (response_type=id_token, response_mode=form_post,
                                                               redirect_uri=<CAPA_PUBLIC_URL>/auth/callback, nonce, state)
ADFS ──POST /auth/callback (id_token, state)──▶ 앱
        ① state 쿠키(서명 · 10분) 대조  ② id_token 검증(RS256 · 서명 인증서 핀 · aud=ADFS_CLIENT_ID · iss=ADFS_ISSUER ·
        exp/iat · nonce)  ③ loginid · username · deptname 꺼냄  ④ 접속 명단 확인(없으면 세션 없이 ──303──▶ 거절 화면)
        ⑤ 우리 세션 토큰(HS256, JWT_SECRET_KEY) 발급  ⑥ HttpOnly 세션 쿠키 설정 ──303──▶ 처음 가려던 화면
브라우저 ──websocket /_stcore/stream (쿠키)──▶ 문지기가 쿠키 · Origin 확인 ──▶ Streamlit
app.py ── 매 회차 st.context.cookies 의 세션 쿠키를 다시 검증(만료 · 로그아웃 · 접속 명단 · 계정 바뀜) ──▶ 화면
브라우저 ──POST /auth/sso/refresh (쿠키 · X-Capa-Sso-Refresh: 1)──▶ 앱
        사람이 앱 화면에서 누르거나 · 치거나 · 굴렸고 직전 답 뒤 5분이 지났을 때만 ──▶ 204 + 새 세션 쿠키
```

- **한 프로세스다.** `capa_server.py` 가 `app.py` 를 `st.App(routes=…, middleware=…)` 으로 감싸 콜백 경로와 문지기를 같은
  프로세스에 붙인다. nginx · 사이드카는 없다. C-DEP 시작 스크립트(`scripts/container_start.py`)가
  `streamlit run capa_server.py --server.port 8080` 으로 띄운다. 개발 PC · 사내 WebIDE · 시험은 지금처럼 `app.py` 다.
- **경로 여섯** — `POST /auth/callback`(포털 Endpoint URL), `GET /auth/sso/login?next=`, `GET /auth/sso/logout`,
  `GET /auth/sso/error?id=`, `POST /auth/sso/refresh`(로그인 갱신 — 아래), `POST /auth/sso/register`(거절 화면의 「접속 권한 신청」 — 6장).
  Streamlit 자체 `st.login`(`/auth/login` 등)은 GET 콜백이라 쓰지 않는다.
- **로그인 유지 — 마지막 사용 뒤 6시간, 최대 24시간(기본값 — 2장).** 세션의 끝은 `min(마지막 발급 + 세션 시간, 처음 로그인 + 최대 시간)` 하나이고
  (`auth/tokens.session_end` — 모든 판정이 끝 + 30초까지 받는다), 쿠키 `Max-Age` 도 그 끝 + 30초로 맞춘다. 앱 화면의 사람 입력(누름 ·
  키 · 휠 · 터치 — 스크립트가 만든 사건과 로그아웃 링크 위 입력은 세지 않는다)이 있으면 툴바 스크립트(`components/sso_refresh.py`)가
  갱신 경로로 POST 하고, 서버는 같은 묶음(`sid` · 처음 로그인 시각은 그대로)의 쿠키를 새로 발급한다. 타이머는 없다 — 화면을 열어
  두기만 하면 늘지 않는다. 서버는 그 묶음의 직전 발급(보낸 쿠키의 발급 시각과 프로세스 메모리에 적은 마지막 발급 가운데 늦은 것)에서
  60초 안이거나 최대에 닿아 늘 것이 없으면 다시 발급하지 않고 204 만 답한다 — 같은 옛 쿠키를 되풀이해 보내도 다시 서명하지 않는다.
- **갱신 경로의 문** — POST 만(켜짐에서 다른 메서드는 문지기가 405), 사용자 정의 머리 `X-Capa-Sso-Refresh: 1` 이 없으면 403, `Origin` 이
  `CAPA_PUBLIC_URL` 의 출처와 다르거나 `Sec-Fetch-Site` 가 있는데 `same-origin` 이 아니면 403, 본문이 있으면 400, 쿠키가 없거나 끝났거나
  로그아웃한 묶음이면 401(쿠키를 건드리지 않는다). 모든 답에 `Cache-Control: no-store`. 꺼짐이면 404, 막힘이면 503.
- **열린 탭** — websocket 은 핸드셰이크 때의 쿠키만 안다. 갱신 경로가 다시 발급하면 프로세스 메모리의 갱신 표(`sid` → 최신 끝)에
  적고, 문지기의 열린 연결과 `app.py` 의 신원 확인만 그 표와 견준다(쓰는 동안 열린 탭이 첫 쿠키 끝에서 끊기지 않게). 새 요청 · 새
  핸드셰이크 · 갱신 경로는 브라우저가 지금 실은 쿠키 자신의 끝만 본다 — 갱신 전에 복사된 옛 토큰이 다른 사람의 사용 덕에 살아나지
  않게.
- **로그인은 쿠키로만 든다.** `?token=` 질의 인자나 세션 상태 보관은 쓰지 않는다 — 테마 단추의 새로고침이 새 세션을 만들어도
  쿠키는 남는다.
- **모드 셋** — `ADFS_CLIENT_ID` 가 비면 **꺼짐**(지금처럼 열림, 운영이면 경고), 다 맞으면 **켜짐**, client id 는 있는데 나머지가
  없거나 틀리면 **막힘**(상태 검사 `/_stcore/health` 만 살리고 `/` 는 설정 화면 — 누구나 「지금은 앱을 열 수 없습니다」, 접힌 「관리자용 진단」 에 값 없이 환경변수 이름 · 상태 · 까닭).
  `CAPA_SSO=required` 면 client id 가 지워져도 막힘이다(잠금).
- **접속 명단** — 운영(`APP_ENV=prod`)이거나 · 잠금(`CAPA_SSO=required`)이거나 · `CAPA_PUBLIC_URL` 이 루프백이 아니거나 · 두 목록 변수(`CAPA_ACCESS_ADMINS` · `CAPA_ACCESS_USERS`) 가운데 하나라도 값이 있으면
  켜진다 — `APP_ENV` 를 빠뜨린 실제 서버가 조용히 전부를 받지 않게 주소도 본다. 켜졌는데 읽은 관리자가 없으면 막힘이다(고칠 사람이 없는 앱을 열지 않는다 — 꺼짐이면 「켜면 막힐 문제」). 인증된 사람
  전부를 받는 것은 그 어느 쪽도 아닌 루프백 개발뿐이다(가짜 IdP · 시험). 판정은 쿠키 → 신원의 한 곳(`auth/identity.session_check` — 폐기 → 명단 → 끝)
  이라 문지기 http · 새 핸드셰이크 · 열린 연결의 메시지 · `app.py` 가 모두 지나고, 콜백(세션 발급 앞) · 갱신 경로가 같은
  `AccessList.allows` 를 묻는다. 거절 화면과 기록(`login_denied`)은 콜백 한 곳에서만 낸다. 등급 맵(loginid → `admin` · `user`)은 들어올 수 있나와 관리자인가를
  가른다 — 관리자 판정은 `sso_identity.viewer_is_admin` 하나(환경변수 관리자 ∪ 명단의 관리자 등급)이고, **운영 서버의 Admin Area 는
  관리자에게만 열린다**(`sso_identity.admin_area_locked` — 운영 서버 = `APP_ENV` 운영, 켜짐이면 잠금 · 루프백 밖 공개 주소도. 관리자가
  아니면 사이드바 메뉴가 없고 주소로 열면 「관리자만 여는 화면입니다」 + 「HOME 으로」. 개발 · WebIDE · 사내 PC 는 지금처럼 연다).
  그 밖의 화면별 권한은 다음 단계다(`docs/TODO.md`).
- **S3 명단** — 사람을 넣고 뺄 때마다 재시작하지 않으려고 사용자 명단을 S3 의 작은 JSON 파일 하나에 둔다(키 `CAPA_S3_ACCESS_KEY` · `CAPA_S3_SECRET_KEY` 가 있으면 켜진다). **앱 시작** 때 받아 메모리에 올리고, **판정**은 메모리로만 하고(요청마다 S3 에 가지 않는다),
  **고침**은 Admin 「접속 명단」 → S3 저장 성공 → 메모리 교체다(재시작 없음). 관리자는 환경변수 `CAPA_ACCESS_ADMINS` 의 사람(늘 관리자 — 화면에서 빼지 못한다, S3 장애 때의 비상구)과 명단 파일에서 관리자 등급(`grade: admin`)을 받은 사람이다(2026-11-14 결정) — 관리자 누구나 Admin 「접속 명단」 에서 명단 구성원에게 관리자 등급을 주고 뺀다(자기 등급은 자기가 빼지 못한다). **그래서 명단 파일을 쓸 수 있는 S3 키는 관리자를 만들 수 있는 키다.** 명단 밖 사람은 거절 화면의 「접속 권한 신청」 으로 스스로 들어온다(6장 — 늘 일반 등급).
  못 읽으면 앱은 뜨고 **관리자만** 들어온다(열림으로 떨어지지 않는다). 못 읽은 동안은 콜백이 거절하기 직전에 다시 읽어 보고(60초에 한 번까지 · 스레드 풀) Admin 「다시 읽기」 도 있다. 잘 읽어 둔 뒤에는 S3 가 막혀도 메모리 명단으로 판정이 이어진다.
  **파일이 404 로 보여도 같다** — 첫 버전으로 읽는 것은 받은 파일도 표지 객체도 없을 때 저장소가 `NoSuchKey` 라고 답한 경우뿐이다. 그때는 `CAPA_ACCESS_USERS` 를 그대로 쓴다(비었으면 빈 명단). 받아 둔 파일이 있었으면 `실패 · 파일 없음` 으로 적고 메모리 명단을 그대로 둔다(저장소 앞단의 일시 오류로 전원을 거절하지 않게 · 메모리가 마지막 사본일 수 있어서). 코드 없는 404(앞단 HTML · 빈 본문)는 언제나 `실패 · 그 밖의 응답(HTTP 404)` 이다.
  **첫 버전은 처음 한 번뿐이다** — 첫 저장이 그 목록 + 고침을 버전 1 로 쓴다. **파일이 있으면 표지 객체 `access/seeded.json` 도 있게 맞춘다** — 파일을 처음 만든 저장이 쓰고, 파일을 받은 읽기가 표지가 없으면 쓴다(첫 저장의 답이 끊긴 경우 · 표지만 실패한 경우 · 표지가 없던 때의 파일 · 버킷을 옮긴 경우). 표지를 못 써도 저장 · 읽기의 실패가 아니고 사건 `access_seed_mark_failed` 만 남는다. 그 뒤로는 환경변수를 듣지 않고, 파일이 사라지면 재시작해도, 환경변수를 지운 서버에서도 첫 버전으로 돌아가지 않는다(`실패 · 파일 없음`, 관리자만 — 지워진 뒤 옛 환경변수 명단이 되살아나 닫힘이 열림으로 바뀌지 않게).

## 2. 환경변수

C-DEP 배포 설정의 환경변수 표(key · value, 값은 한 줄)에 넣는다. `.env` 파일 로더는 없다 — 그 표가 그 자리다.
환경변수를 바꾸면 CI/CD 를 다시 돌려 재시작해야 반영된다.

| 이름 | 필요할 때 | 뜻 | 예시(가짜) |
|---|---|---|---|
| `ADFS_CLIENT_ID` | 켜는 스위치(비면 꺼짐) | 포털 승인 메일의 Client ID. id_token 의 `aud` 와 정확히 같아야 한다 | `00000000-0000-0000-0000-000000000000` |
| `JWT_SECRET_KEY` | 켜짐 필수 · **비밀** | 우리 세션 토큰 비밀. 32바이트 이상 · 고정값(바꾸면 모두 다시 로그인). 아래 4장 | (만든 값) |
| `APP_ENV` | 운영 서버에 넣는다 | `prod` 면 운영 규칙(https 만 · `__Host-` 쿠키 · 꺼짐 경고 · 접속 명단 필수). 빠져도 `CAPA_PUBLIC_URL` 이 루프백이 아니거나 잠금이면 접속 명단은 켜진다 | `prod` |
| `ADFS_AUTHORIZE_URL` | 켜짐 필수 | ADFS authorize 엔드포인트 | `https://idp.example.invalid/adfs/oauth2/authorize/` |
| `ADFS_ISSUER` | 켜짐 필수 | id_token 의 `iss` 와 **글자 하나까지** 같은 값. 짐작하지 않는다 — 비면 막힘(설정 화면에 관례 후보만) | `https://idp.example.invalid/adfs` |
| `ADFS_SIGNING_CERT` | 켜짐 필수 | 토큰 **서명** 인증서 한 줄(base64 DER · base64 PEM · PEM). 여럿은 쉼표(교체 때). 아래 3장 | `MIIC…`(한 줄) |
| `CAPA_PUBLIC_URL` | 켜짐 필수 | 브라우저가 여는 앱 주소. redirect_uri 와 모든 이동 주소의 바탕(요청 Host 는 보지 않는다) | `https://capa.example.invalid` |
| `CAPA_SSO_SESSION_HOURS` | 선택 | 로그인 유지 시간 — **마지막 사용 뒤** 이만큼 지나면 끝(1~24, 기본 6). 앱 화면에서 누르거나 · 치거나 · 굴리면 늘어난다 | `6` |
| `CAPA_SSO_SESSION_MAX_HOURS` | 선택 | 써도 넘지 못하는 최대 시간 — 처음 로그인에서 이만큼 지나면 다시 로그인(통합인증으로 계정을 다시 확인). 세션 시간 이상 72 이하, 기본 24. 틀리면 사유 `max_out_of_range` | `24` |
| `CAPA_SSO` | 선택 | `required` 면 잠금 | `required` |
| `ADFS_SCOPE` · `ADFS_RESOURCE` | 선택 | 클레임을 id_token 에 싣는 데 필요하면(기본 scope `openid`) | `openid allatclaims` |
| `ADFS_CLAIM_LOGINID` · `ADFS_CLAIM_USERNAME` · `ADFS_CLAIM_DEPTNAME` | 선택 | 클레임 이름(기본 `loginid` · `username` · `deptname`) | `loginid` |
| `ADFS_LOGOUT_URL` | 선택 | 로그아웃 · 거절 · 포털 거절 화면의 「다른 계정으로 로그인」 링크(이 주소로 간다 — 전의 「통합인증에서도 로그아웃」) | `https://idp.example.invalid/adfs/oauth2/logout` |
| `CAPA_ACCESS_ADMINS` | **운영 · 잠금 · 루프백이 아닌 주소에서 필수** — 없거나 읽은 것이 없으면 막힘 | 관리자 loginid 목록(잠김 방지 — 들어올 수 있는 사람이고 다음 단계의 관리자) | `demo.admin` |
| `CAPA_ACCESS_USERS` | 선택 — **S3 명단이 켜지면 파일이 없을 때의 첫 버전으로만 쓴다**(파일이 있으면 쓰지 않고 점검 표에 알림) | 사용자 loginid 목록. 두 목록에 다 있으면 관리자 | `demo.user,demo.user2` |
| `CAPA_ACCESS_CONTACT` | 선택 | 문의 줄(「문의 · <메일> · <창구 글>」 — 메일은 `CAPA_APP_CONTACT_EMAIL`)의 창구 글(500자까지, 값은 이스케이프해 싣는다). 싣는 곳은 셋이다 — 거절 · 포털 거절 화면(`auth/page_frame.py`), 열린 탭의 앱 안 로그인 · 접속 멈춤 판의 문의 캡션(`components/stop_panel.py` — 앱 시작 실패 판은 메일만), 앱이 뜨기 전 시작 임시 화면(`scripts/container_stage.py` 의 `contact_of` — 시작 스크립트가 환경변수에서 바로 읽는다). 두 칸이 모두 비면 문의 줄이 없고 거절 화면의 「문의처」 글은 「앱 관리자」 를 가리킨다. **로그인 없이 누구나 보는 글이다** — 사람 loginid 를 쓰지 말고 창구 이름을 쓴다 | `CAPA 담당 창구` |
| `CAPA_S3_ACCESS_KEY` · `CAPA_S3_SECRET_KEY` | S3 명단을 쓸 때 — 둘 다 비면 꺼짐 · **비밀** | S3 명단용 앱 키 한 쌍. 하나라도 있으면 S3 명단이 켜진다. 앱이 기동 때 읽고 `os.environ` 에서 뺀다. 키를 넣으면 C-DEP 시작 스크립트의 동기화 점검도 돌므로 `CAPA_S3_PROFILE`(aws 프로필 이름 — 기본값 없음)도 넣는다 — 없으면 「서버 시작 점검」 프로필 · 버킷 목록 줄이 실패이고 Alarm `SY-06` 이 이름을 댄다([`objectstore_setup.md`](objectstore_setup.md) 2장) | (받은 값) |
| `CAPA_S3_ENDPOINT_URL` | S3 명단을 켜면 필수 | S3 주소(`http` · `https`, 경로 없음). `io/object_storage.py` 와 같은 이름이고 어느 쪽에도 기본값이 없다(사내 값 — 저장소에 적지 않는다) — 표에 적는다 | `https://store.example.invalid:9021` |
| `CAPA_S3_BUCKET` | S3 명단을 켜면 필수 | 버킷 이름(경로 스타일이라 대문자 · 밑줄 가능) | `Demo_bucket` |
| `CAPA_S3_REGION` | 선택 | 서명 영역(기본 `us-east-1`) | `us-east-1` |
| `CAPA_ACCESS_S3_OBJECT` | 선택 | 명단 파일의 객체 키(기본 `access/access_list.json`) — 같은 버킷을 다른 서버와 나눠 쓸 때 | `access/demo_list.json` |

- **목록 꼴** — 항목은 쉼표 · 세미콜론 · 공백으로 나눈다(표가 한 줄 값만 받는다). 견주는 값은 로그인 클레임(`ADFS_CLAIM_LOGINID`, 기본 `loginid`)의 값이고, 앞뒤 공백을 떼고 대소문자를 가리지 않는다. loginid 꼴
  (`A-Z a-z 0-9 . _ @ -` · 64자까지)이 아닌 항목(`DOMAIN\이름` 포함)과 글자 · 숫자가 하나도 없는 항목(`-` 같은 자리표)은 버리고 개수만 센다 — 막지 않으므로 그 사람만 거절 화면을 본다. Admin 「통합인증 점검」 의
  「읽지 못함」 이 0 인지 본다. 값 길이는 대략 1 KiB 에 100개 안팎이다(9장 7 — 표의 값 길이 제한). 앱은 기동 때 두 목록을 읽은 뒤 `os.environ` 에서 뺀다 — 앱이 띄우는 하위 프로세스는 물려받지 않는다(그 이상의 한계는 4장 비밀값과 같다).
- **환경변수 명단을 고치면 CI/CD 를 다시 돌려 재시작해야 반영된다.** 재시작하면 모든 연결이 끊겨 열어 둔 탭의 저장하지 않은 편집이 사라지고, 재배포 때 디스크가
  사라지는 환경(지금 C-DEP — `/project/data` 영속 볼륨 없음)에서는 영속 저장이 붙기 전까지 저장한 시나리오도 사라진다. 사람을 넣고 뺄 때는 쓰는 사람이 적을 때 고르고 남길 자료를
  먼저 챙긴다. 쿠키는 재시작 뒤에도 유효하지만 명단에서 빠졌으면 그 쿠키로는 들어오지 못한다. **S3 명단을 켜면 사용자는 재시작 없이 Admin 에서 넣고 뺀다**(아래 5장) — 재시작이 필요한 것은 관리자 목록뿐이다.
- **S3 명단 값의 한계** — 없는 키에 저장소가 `NoSuchKey` 를 주지 않으면 첫 읽기가 `실패 · 그 밖의 응답(HTTP 404 · …)` 으로 남아 첫 버전을 쓰지 못하고 사람을 넣을 수 없다 — 첫 파일을 저장소에 손으로 올린다(내용 `{"format": 1, "revision": 1, "users": []}`). 키 둘이 있으면 켜지므로 주소 · 버킷이 빠지거나 꼴이 틀려도 막힘이 아니라 「못 읽음」 이다(앱은 뜨고 관리자만 들어온다 · 점검 표와 「S3 명단」 줄이 까닭을 말한다). 키가 하나만 있어도 같다(한쪽만 지워도 환경변수 명단으로 돌아가지 않는다 — 둘 다 지워야 꺼진다). 평문 `http` 주소는 받지만 점검 표에 알림이 붙는다 — **명단(실제 loginid)이 사내망에 평문으로 흐른다.** 재시작으로 프로세스 메모리가 비면 시작 때 다시 받는다.
- 포털에 등록하는 값: 서비스 URL = `CAPA_PUBLIC_URL`, Endpoint URL = `CAPA_PUBLIC_URL` + `/auth/callback`. 둘은 한 글자도
  달라선 안 된다 — Admin Area 「통합인증 점검」 · 설정 화면이 계산한 redirect_uri 를 보인다.
- 사용자 샘플은 `APP_ENV=prod` 가 ADFS 주소와 인증서 파일을 자동으로 넣었다. 이 저장소는 공개라 그 값을 둘 수 없어
  `ADFS_AUTHORIZE_URL` · `ADFS_ISSUER` · `ADFS_SIGNING_CERT` · `CAPA_PUBLIC_URL` 을 환경변수 표로 받는다. `APP_ENV=prod` 는
  「엄격하게 보라」 는 뜻만 갖는다.
- C-DEP 이 HTTPS 를 주므로 도메인 · 인증서 신청은 필요 없다. TLS 는 인그레스에서 끝나고 pod 안은 http 다 — 쿠키의 Secure 는
  요청이 아니라 `CAPA_PUBLIC_URL` 의 https 로 정한다.

## 3. 서명 인증서 넣는 법 · 교체

- 넣는 것은 ADFS 의 **토큰 서명 인증서**다(TLS 인증서가 아니다). 사내 WebIDE 터미널에서 `base64 -w0 <토큰 서명 인증서 파일>`
  출력 한 줄을 `ADFS_SIGNING_CERT` 값으로 넣는다(PEM 이면 그 파일도 같은 줄로 넣으면 된다). 인증서 파일을 저장소 · `cert/` 에
  두지 않는다 — `.gitignore` · 배포 ZIP 금지 · 감시 시험이 막는다.
- 체인 검증은 하지 않는다(핀 고정). 만료는 막지 않고 경고만 한다 — 30일 안이면 Admin Area 와 기동 로그에 알린다.
- **교체**: 새 인증서를 쉼표로 **더해** 두 값으로 두고(최대 3개), 옛 인증서가 만료된 뒤 뺀다. id_token 헤더의 지문(x5t)이 맞는
  것부터 시도한다.

## 4. 비밀값 만들기

```bash
python -c "import secrets; print(secrets.token_urlsafe(48))"
```

- 출력을 `JWT_SECRET_KEY` 로 넣는다. 고정값이다 — 재시작해도 로그인이 유지되고, 바꾸면 모두 다시 로그인한다.
- 32바이트 미만 · 서로 다른 글자 10개 미만 · 자리표(`changeme` · `secret` 등) · 짧은 글 되풀이(`0123456789` 를 네 번 등) ·
  키보드 줄 · 알파벳 · 숫자 차례가 절반 이상 · client id 와 같은 값은 막힘이다. 사람이 고른 낱말 문장(앱 이름 · 연도를 이은 것
  등)은 가려내지 못하므로 위 명령의 무작위 값을 쓴다. 이미 넣은 값이 막히면 위 명령으로 새로 만든다(바꾸면 모두 다시 로그인).
- **환경변수 표를 본 사람은 이 값으로 로그인 토큰을 만들 수 있다.** 표를 볼 수 있는 사람을 좁힌다.
- 앱은 기동 때 이 값을 읽은 뒤 `os.environ` 에서 지운다 — 앱이 띄우는 하위 프로세스는 물려받지 않는다. 그 이상은 막지 못한다:
  커널은 기동 때의 환경 사본을 `/proc/<pid>/environ` 에 남겨 같은 사용자의 프로세스가 읽을 수 있고, 같은 프로세스의 코드(모듈
  포함)는 메모리에 닿는다. 이 값을 지키는 것은 환경변수 표의 열람 권한이다.
- **모듈 코드는 비밀값뿐 아니라 S3 키와 명단 쓰기에도 닿는다** — 코어와 한 프로세스라서다. 의도를 가진 모듈은 관리자가 아닌 사람의 회차에서도 S3 키를 읽고 명단 파일을 고칠 수 있고, 그 고침은 파일에 영속으로 남으며 고친 기록과 사건에는 관리자 계정이 찍힌다(쓰기 함수의 관리자 확인은 화면의 실수를 막는 벽이지 같은 프로세스의 코드를 막는 벽이 아니다).
  `scripts/check_module.py` M06 이 창구를 돌아가는 쉬운 꼴을 오류로 잡지만 **점검 통과가 보증이 아니다** — 방어선은 앱 관리자의 PR 점검(런북 4-6)이다. 같은 까닭으로 쓰기 함수가 신원 대신 세션 토큰을 받게 해도 나아지지 않는다(그 코드는 서명 비밀에도 닿는다).

## 5. 첫 배포 순서

1. 이 변경이 실린 배포를 적용한다. C-DEP 환경변수 표에 `JWT_SECRET_KEY` · `CAPA_PUBLIC_URL` ·
   `ADFS_AUTHORIZE_URL` · `ADFS_ISSUER` · `ADFS_SIGNING_CERT` · `CAPA_ACCESS_ADMINS` 를 넣고 **client id 와 `APP_ENV` 는 비운 채** CI/CD 를 돌린다.
   앱은 지금처럼 열린다. **켜기 전에 나머지 값을 미리 보는 화면은 없다** — `APP_ENV` 를 비운 꺼진 서버는 「통합인증 점검」 을 그리지 않고, `APP_ENV=prod`
   를 먼저 넣으면 운영 서버라 Admin Area 가 관리자에게만 열리는데 통합인증이 꺼진 동안은 관리자 신원이 없어 아무도 열지 못한다(그 잠긴 화면에
   Alarm `AD-02` 「운영 서버인데 통합인증이 꺼져 있습니다」 가 뜬다). 나머지 값은 2 에서 켤 때 설정 화면이 본다.
2. 포털 승인 메일의 Client ID 를 `ADFS_CLIENT_ID` 에, `APP_ENV=prod` 를 함께 넣고 CI/CD 를 돌린다 → 로그인해 본다. 실패면 오류 화면 바닥의 사유 코드와
   접힌 「관리자용 진단」 의 받은 iss/aud(서명이 맞을 때만 보인다) · 받은 클레임 이름으로 값을 고친다. 설정 화면(막힘)이 뜨면 접힌 진단의 「고칠 것」 과
   그 아래 「환경변수 전체(n)」 표(환경변수 이름 · 까닭 — 꺼짐 때의 「켜면 막힐 문제」 와 같은 판정)대로 고친다. 로그인 화면이 ADFS 에서 멈춰 앱으로
   돌아오지 않으면 7장 대응표 「ADFS 화면에서 멈춤」.
3. 로그인한 채 10분 넘게 앱을 써 보고 Admin Area 「통합인증 점검」 의 「로그인 갱신」 누계에서 「다시 발급」 이 1 이상 · 「출처·머리
   거절」 이 0 인지 본다. 「다시 발급」 이 0 이고 「출처·머리 거절」 만 늘면 접속 주소가 `CAPA_PUBLIC_URL` 과 다르거나 앞단이 머리를 바꾼
   것이다(9장 11) — 그대로 두면 쓰는 중에도 처음 로그인 6시간 뒤 끊긴다. 그 동안은 관리자의 Alarm 에 `AD-21` 이 서 있다.
4. 되면 `CAPA_SSO=required` 를 넣어 잠근다 — 실수로 client id 를 지워도 열리지 않는다.

**이미 통합인증이 켜진 서버에 접속 명단이 실린 배포를 적용할 때** — `CAPA_PUBLIC_URL` 이 루프백이 아닌 서버는 `APP_ENV` 와 관계없이 `CAPA_ACCESS_ADMINS` 가 없으면 **막힘**이다(앱 관리자까지 모두 설정 화면만 본다).

1. **새 코드를 싣는 배포 전에** 환경변수 표에 `CAPA_ACCESS_ADMINS`(앱 관리자 본인 loginid 를 꼭 넣는다)와 `CAPA_ACCESS_USERS` 를 먼저 넣는다. 예전 코드는 모르는 변수를
   무시하므로 먼저 넣어도 해가 없다. **넣을 값은 ADFS 담당 · 포털에서 글자까지 확인한다** — 아래 「전원이 거절되면」.
2. CI/CD 로 새 코드를 적용하고 로그인해 본다. 안 넣고 적용했으면 설정 화면(「지금은 앱을 열 수 없습니다」)의 접힌 「관리자용 진단」 맨 위 「고칠 것 n개」 첫 줄이 「관리자 목록(`CAPA_ACCESS_ADMINS`)이 비었거나 …」 다 — 표에 넣고 다시 돌리면 풀린다.
3. Admin 「통합인증 점검」 의 「접속 명단 · 켜짐 · 관리자 n · 일반 n · 읽지 못함 0」 을 본다. 수가 생각과 다르면 표의 값을 고친다.
4. 명단 밖 계정으로 들어가 거절 화면이 서는지, 「명단 밖 로그인」 표에 앞 두 글자와 횟수로 남는지 본다.
5. 재시작 없이 사람을 넣고 빼려면 아래 「S3 명단을 켤 때」 로 간다(2026-11-05 사용자 결정 — 그룹 클레임은 쓰지 않고 `loginid` + S3 명단). 「마지막 로그인의 클레임 이름」 은 클레임 문제를 볼 때 쓴다(값은 보이지 않는다).

**전원이 거절되면(앱 관리자 포함)** — `CAPA_ACCESS_ADMINS` 에 오타가 있거나 실제 `loginid` 클레임 값과 다른 값이다. 꼴은 맞으므로 모드는 켜짐이고 설정 화면이 서지 않는다. 거절 화면은 그 브라우저에서 15분 동안 **본인 계정**을 보인다(거절 표 — 6장) — 그 글자를 환경변수 값과 대 본다. 「접속 권한 신청」 으로 들어와도 일반 등급이라 Admin 에는 들어갈 수 없다.
푸는 길은 표의 값을 고치고 CI/CD 를 돌리는 것뿐이다. 돌릴 때마다 연결이 끊기고, 영속 볼륨이 없는 동안은 저장한 것도 사라지므로 값을 짐작해 되풀이하지 않는다 — ADFS 담당 · 포털에서 본인 `loginid` 클레임 값을 글자까지 확인해 넣는다. 앱 안에서는 전체 값을 볼 수 없다(사건 표는 앞 두 글자까지, 앱 정보 카드는 이름이 있으면 이름만). 서버 로그를 볼 수 있으면 `sso event=login_denied` 줄에 전체 값이 있다.

**앞 배포 ZIP 으로 되돌리면** — 앞 코드에는 명단 판정이 없다. 되돌린 동안은 환경변수가 무시되어 통합인증을 지난 사람 전부가 들어온다. 포털 범위로 막거나, 그 사실을 알고 되돌린다.

**S3 명단을 켤 때** — `CAPA_S3_*` 키를 넣은 배포를 적용해도 파일이 아직 없으면(`NoSuchKey`) `CAPA_ACCESS_USERS` 를 첫 버전으로 쓰므로 **사용자가 막히지 않는다.** 그 동안 「S3 명단」 줄 끝에 `환경변수 첫 버전 · 파일 없음` 이 서고 `AD-09` 가 알린다. 명단 파일은 같은 버킷이다.

1. 키 한 쌍(그 버킷에 읽기 · 쓰기)과 주소 · 버킷을 받아 환경변수 표에 `CAPA_S3_ACCESS_KEY` · `CAPA_S3_SECRET_KEY` · `CAPA_S3_ENDPOINT_URL` · `CAPA_S3_BUCKET` 을 넣고 CI/CD 를 돌린다(관리자 목록은 그대로 둔다).
2. 관리자로 들어가 Admin 「통합인증 점검」 의 「S3 명단」 줄을 본다 — `정상 · 마지막 읽기 … · 명단 n · 버전 0 · 환경변수 첫 버전 · 파일 없음` 이면 그 서버에서 S3 에 닿은 것이다(첫 파일이 없어 버전 0). `실패 · …` 면 까닭대로 고친다(7장). **쓰기 권한은 저장해 봐야 안다.**
3. Admin 「접속 명단」 의 「추가」 로 한 사람을 넣고 적용한다 — 첫 버전 + 그 사람이 버전 1 로 파일이 된다. 줄 끝이 `쓰기 정상 · <시각>` 으로 바뀌면 쓰기 권한도 맞다. 실패면 알림창의 까닭(예: 인증 거절 · HTTP 403)을 보고, 메모리 명단은 그대로다.
4. **첫 저장 뒤 `CAPA_ACCESS_USERS` 를 지운다**(다음 CI/CD 때). 남겨 두면 점검 표에 「쓰지 않음」 알림만 남는다. 그 뒤 재시작이 있어도 시작 때 파일을 다시 받아 그대로 이어진다.
5. 끄려면 키 둘을 지우고 CI/CD 를 돌린다 — 사용자 명단은 다시 `CAPA_ACCESS_USERS` 에서 온다.

**같은 키가 두 DB 정본도 다룬다** — `managed` 서버에서는 시작 스크립트가 이 키로 `~/.aws` 프로필을 만들고(앱 프로세스의 환경변수는 이 문서대로 지운다) `aws` 가 두 DB 를 같은 버킷에서 받고 올린다(`docs/objectstore_setup.md`). 키를 바꾸면 다음 CI/CD 에 둘 다 바뀐다. 이 키는 운영 DB 삭제 권한이기도 하다.

**앞 배포 ZIP 으로 되돌리면** S3 명단 코드도 사라진다 — 환경변수 `CAPA_ACCESS_USERS` 만 듣는다. 파일은 저장소에 남아 있어 다시 올리면 이어진다.

**스스로 등록 · 명단 관리자 등급(2026-11-14)이 든 배포에서 그 앞 ZIP 으로 되돌리면** — 앞 코드는 명단 파일의 새 칸(이름 · 부서 · 등록 길)을 버리고
관리자 등급을 일반으로 읽는다(관리자는 다시 `CAPA_ACCESS_ADMINS` 뿐). Admin Area 는 다시 명단의 누구에게나 열리고 거절 화면의 「접속 권한 신청」 도
없다. 그동안 Admin 「접속 명단」 에서 한 번이라도 저장하면 파일이 앞 꼴로 다시 쓰여 이름 · 부서 · 등록 길 · 명단 관리자 등급이 사라진다(사람은 남는다).

## 6. 사용자가 보는 것

- 사이드바 앱 정보 카드 셋째 줄 「이름 · 부서 · 로그아웃」(켜짐에서만).
- **로그인은 마지막 사용 뒤 6시간 유지된다** — 앱을 쓰는 동안(누름 · 입력 · 굴림) 5분에 한 번 저절로 늘어난다. 화면을 열어 두기만
  하고 쓰지 않으면 5시간 55분 ~ 6시간 30초 뒤 끝난다(갱신 간격 5분 · 여유 30초). 계속 써도 처음 로그인에서 24시간이 지나면 한 번 다시
  로그인한다. 끝 30분 전부터 카드 셋째 줄에 남은 시간이 붙는다 — 쓰지 않아 끝나 가면 「로그인 n분 남음」, 최대 시간이
  다가오면 「로그인 최대 시간까지 n분」(끝나기 전에 저장해 두라는 말은 HOME Guide 「사이드바 · 조회 조건」 이 한다). 최대 시간이
  정한 끝 10분 안의 첫 회차에는 사건 알림 `AD-20` 「로그인 최대 시간까지 n분 — 저장해 두세요」 가 한 번 뜬다(그 로그인 묶음에
  한 번 — 새로고침해도 같은 탭은 다시 띄우지 않는다). 「지금 다시 로그인」 단추는 없다 — 로그인 경로는 이미 로그인한 사람의 처음
  로그인 시각을 새로 만들지 않는다. 쓰지 않아 끝나는 끝은 쓰는 동안 늘어 알리지 않는다. 오래 쉬다 돌아온 첫 누름의 회차에만 「n분 남음」 이 잠깐 보일 수 있다(갱신과
  그 회차가 겨룸 — 다음 회차에 사라진다).
- 만료 · 다른 탭에서 로그아웃 · 쿠키 없음은 화면 맨 위 경고 한 줄과 주 단추 「다시 로그인」(같은 탭 — 다시 로그인하면 그 탭의
  저장하지 않은 편집은 사라진다), 그 아래 「문의 <메일> · <창구 글>」(`CAPA_APP_CONTACT_EMAIL` · `CAPA_ACCESS_CONTACT` 가운데 있는 것 —
  사이드바 카드가 서지 않는 화면이라. 둘 다 비면 줄이 없다). 주 단추는 단추 꼴 링크라 Enter 로 연다.
  명단에서 빠진 열린 탭은 「이 앱을 쓸 수 있는 명단에 없습니다.」 와 「접속 권한 신청」(같은 로그인 경로 — 통합인증을 거쳐 거절
  화면으로 간다), S3 명단을 못 읽은 서버의 열린 탭은 끊긴 구름 아이콘 + 「다시 로그인」 이다. 끝난 쿠키로 새로 열면 경고 없이
  통합인증을 거쳐 다시 들어온다. 같은 탭이 다른 계정으로 이어지면 「「<새 계정 이름>」 계정으로 바뀌었습니다」 와 주 단추
  「새로고침」(같은 탭에서 지금 화면을 새로 연다 — 풍선 「이 탭에서 저장하지 않은 편집은 사라집니다」).
- **열어 둔 탭** — 만료됐거나 다른 탭에서 로그아웃한 뒤 그 탭에서 무엇이든 누르면(위젯 · 팝업 · 자동으로 도는 화면 조각
  포함) 서버가 그 요청을 받지 않고 연결을 닫는다. 탭은 다시 붙지 못하고, 3초쯤 뒤 화면 맨 위에 띠와 링크가 선다(띠가 선 동안
  Streamlit 의 영어 연결 오류 창 「Connection failed with status 401.」 은 감춘다). 띠는 까닭 셋으로 가른다 — 문지기가 띠가 묻는
  401 에 까닭 낱말 머리 `X-Capa-Sso-Reason`(`denied` · `unread` · `other`, 값 없음)을 단다.
  - 대부분(오래 쓰지 않음 · 로그인 최대 시간이 지남 · 로그아웃 — 로그아웃은 쿠키를 지우고 끝난 쿠키는 브라우저가 버려 서로 가를
    수 없다): 「로그인이 끝나 이 탭이 서버에 다시 붙지 못합니다(…). 다시 로그인하면 이 탭에서 저장하지 않은 편집은 사라집니다.」 +
    「다시 로그인」.
  - 명단에서 빠짐: 「이 계정은 접속 명단에서 빠져 이 탭을 이어 쓸 수 없습니다. …」 + 「접속 권한 신청」(→ 통합인증 → 거절 화면).
  - 서버가 명단을 못 읽음: 「서버가 접속 명단을 읽지 못해 다시 붙지 못합니다 — 1분 뒤 「다시 로그인」 을 누르세요.」.
  - 앞단이 그 머리를 떼면 넷을 한 문장에 적은 옛 글로 떨어진다. 끊긴 동안 다시 묻다 까닭이 바뀌면 띠 글을 바꾼다.

  누르면 그 화면 · 질의로 돌아온다. 저절로 다시 로그인하지는 않는다 — 로그아웃을 열린 탭이 조용히 되돌리지 않게.
- **로그아웃 화면**(공통 틀 — 표지 없음) — 「로그아웃했습니다」 · 「이 브라우저에서 이 앱의 로그인만 끝냈습니다. 열어 둔 다른 탭도 다음에 누를 때
  로그인 화면으로 갑니다.」 · 주 단추 「다시 들어가기」(로그아웃 전에 보던 화면 — 앱 정보 카드의 로그아웃 링크가 지금 화면 · 질의를 `?next=` 로
  싣고 로그아웃 경로가 정화한다) · 보조 「다른 계정으로 로그인」(`ADFS_LOGOUT_URL` 이 있을 때 — 전의 「통합인증에서도 로그아웃」 이 하던 일) · 문의 줄.
  저장하지 않은 고침이 있을 때 누르면 탭 줄이 걸어 둔 브라우저의 떠나기 확인 창이 뜰 것으로 보인다(코드로 읽음 — 사내 브라우저 확인 거리, 9장).
- **로그아웃의 한계** — 이 앱의 로그인만 끝낸다. 브라우저의 통합인증(AD) 로그인은 남아 「다시 들어가기」 를 누르면 묻지 않고
  다시 들어온다. 다른 사람으로 바꾸려면 「다른 계정으로 로그인」(통합인증 로그아웃 주소로 간다 — 자동으로 보내지 않는다). 로그아웃은 그 로그인
  묶음(`sid`)을 처음 로그인 + 최대 시간 + 30초까지 폐기한다 — 갱신 전에 받은 옛 쿠키도, 이미 끝난 쿠키로 누른 로그아웃도 같은 묶음을
  막는다. 다른 탭의 다음 갱신은 401, 그 탭의 다음 누름은 위 「열어 둔 탭」 띠다. 폐기 목록은 프로세스 메모리라 재시작하면 비워진다
  (지운 쿠키를 다시 넣은 탭이 그 끝까지 살아날 수 있다 — 쿠키 자체는 지웠으므로 받아들인다).
- **CONNECTING 에 머물면** — 위 띠가 서면 「다시 로그인」 을 누른다. 서버를 다시 띄우는 동안(시작 임시 응답)은 같은 스크립트가
  링크 없는 재시작 띠 「서버를 다시 시작하는 중입니다 — <데이터 받는 중 · 2번째 받기>. 끝나면 이 탭이 저절로 다시 붙습니다. …」 를
  세우고(답이 없거나 앞단이 5xx 를 내면 「서버 응답을 기다리는 중입니다」, 답 없음이 20초 넘게 이어지면 「서버에 닿지 않습니다 — 다시 붙는 중」) 영어 연결 창을
  감춘다 — Streamlit 이 스스로 다시 붙으면 띠를 걷고 `GL-07` 이 이어 알린다. 다시 선 앱이 **막힘**(설정이 비거나 틀림)이면 앱이 답하므로 띠를
  세우지 않는다 — 영어 창이 남고, 새로 읽으면 설정 화면이다. 로그인 띠가 서 있으면 재시작 띠는 서지 않는다. 띠 없이
  머물면 망 끊김이다 — 오래 머물면 새로고침한다(로그인이 끝났으면 로그인부터 다시 탄다). 재시작 띠는 통합인증이 꺼진 서버에도 선다.
- **로그인 실패 화면**(`/auth/sso/error?id=&code=&next=`, 공통 틀 · 400) — 위는 누구나 읽는 글, 아래 접힌 「관리자용 진단」 에 사유 한 줄 + 진단 표(받은
  iss/aud · 시각 · 클레임 이름 · 인증서 지문 — 값이 있는 칸만), 바닥에 「참고 <사유 코드> · <시각> UTC · 진단 <번호>」(한 번 눌러 통째로 고름 — 번호는
  보관한 진단의 것이고 10분 · 재시작이면 사라져 사유 코드 · 시각만 남는다). 갈래 셋(`web.failure_kind`):
  - **잠시 문제**(시작 정보 없음 · 시간 지남 · 다른 탭에서 새로 시작 · 뒤로 가기 재전송 · 짝이 다른 토큰 · IdP 일시 오류) — 표지 「다시 시도」 · 「로그인을 마치지
    못했습니다」 · 「로그인 도중 시간이 지났거나 다른 탭에서 로그인을 새로 시작했습니다.」 · 주 단추 「다시 시도」(처음 가려던 화면으로).
  - **설정 문제**(서명 · 앱 등록 번호(aud) · 이슈어 · 클레임 · 시각(서버 · IdP 시계) · 콜백 꼴 · 쿠키 크기 · 표준 IdP 설정 오류) — 표지 「점검 중」 · 「로그인 설정에 문제가
    있습니다」 · 「앱 설정 문제라 다시 시도해도 같습니다. 문의처에 아래 참고 번호를 알려 주세요.」 · 「다시 시도」 는 보조 링크. 시도 쿠키를 지운다.
  - **쿠키 없음**(`no_cookies` — 콜백에 이 앱의 쿠키가 하나도 오지 않음) — 「브라우저가 이 사이트 쿠키를 저장하지 않았거나 다른 주소로 열었습니다 — 주소창 주소와
    쿠키 설정을 보세요.」 + 「다시 시도」(공개 주소로 다시 시작해 다른 주소 문제는 풀린다). 통합인증 화면에 10분 넘게 머물러 상태 · 시도 쿠키가 둘 다 사라진
    때와는 가르지 못한다(관리자용 진단 줄이 말한다). 시도 쿠키를 지운다. 로그인을 마친 뒤 브라우저 「뒤로」 로 같은 state 가 쿠키 없이 다시
    오면(성공이 상태 · 시도 쿠키를 지우고 세션 쿠키는 교차 사이트 POST 에 실리지 않는다) 쿠키 없음이 아니라 재사용(`state_reused` — 잠시 문제)이다 — 쓴 state 를
    10분 기억하므로 그 뒤의 「뒤로」 는 쿠키 없음 꼴로 읽힌다.
  - 모르는 사유 코드(주소에 넣은 다른 글)는 제목 · 「다시 시도」 · 참고 줄만이다.
  「다시 시도」 의 처음 가려던 화면은 검증한 상태 토큰의 next 다(IdP 오류는 그 상태 쿠키에서 꺼냄). 주소의 `next` 는 읽을 때마다 다시 정화해 같은 출처의 앱
  경로만 쓴다(열린 리다이렉트 없음).
- **로그인 되풀이 화면**(200) — 「마지막 로그인 시작 뒤 2분 안에 또 시작」 이 이어져 넷째 시작이면 통합인증으로 보내지 않는다(시도 쿠키 — 시작마다 2분으로
  다시 심는다). 표지 「다시 시도」 · 「로그인이 되풀이됩니다」 · 「여러 탭에서 한꺼번에 로그인을 시작했거나, 같은 실패에서 「다시 시도」 를 되풀이했습니다.」 ·
  「<○시 ○분> 뒤에 「다시 시도」 를 누르세요.」(한국 시각 — 지금 + 2분을 분 올림, 늦어도 그때는 쿠키가 사라진다) · 주 단추 「다시 시도」(처음 가려던 화면).
  쿠키를 막은 브라우저는 시도 쿠키도 저장하지 못해 이 화면에 닿지 않고 위 「쿠키 없음」 이 된다.
- **설정 화면**(막힘 — 모든 방문자, `/` 200 · 그 밖 503) — 위는 누구나 읽는 표지 「점검 중」 · 「지금은 앱을 열 수 없습니다」 · 「서버 설정을 고치는 중입니다.
  잠시 뒤 다시 열어 보고, 계속되면 문의처에 알려 주세요.」 · 주 단추 「다시 열기」(지금 문서를 다시 연다 — 공개 주소가 틀린 변수일 수 있어서) · 문의 줄 ·
  「참고 config_broken · <시각> UTC」. 아래 접힌 「관리자용 진단」 맨 위가 「통합인증 설정을 마치지 못했습니다 — 고칠 것 n개」 이고 관리자 목록이 그 안이면
  첫 줄이 「관리자 목록(`CAPA_ACCESS_ADMINS`)이 비었거나 읽을 수 있는 계정이 없어 막았습니다 — 값을 넣고 CI/CD 를 다시 돌리세요.」 다. 그 아래 다시 접힌
  「환경변수 전체(n)」 에 표(이름 · 상태 · 까닭) · 알림 · 계산한 redirect_uri · 서명 인증서 지문 · 이슈어 후보 · 서버 시각. 접어도 누구나 펼친다 — 값 · 비밀값 ·
  client id 는 싣지 않고, 전부터 실려 온 계산한 주소 · 인증서 지문과 이름 · 수만 싣는다.
- **문지기 없이 뜬 앱**(`streamlit run app.py` 로 켜진 설정을 띄움 — 앱 안 멈춤) — 경고 「지금은 앱을 열 수 없습니다(서버 시작 설정)」 · 문의 캡션 · 「참고
  sso_no_gate · <시각> UTC」. 실행 명령 · 설정 문제 이름 · 안내 문서는 접힌 「관리자용 진단」(복사 단추)에 있다. 다시 열어도 같아 단추가 없다.
- **접속 명단 · 거절 화면** — 통합인증을 지났어도 명단에 없으면 앱에 들어오지 못한다. 세션 쿠키를 받지 못하고 거절 화면을 본다(HTTP 403). 거절 갈래 ·
  포털 거절 화면은 공통 틀(`auth/page_frame.py` — 머리 · 상태 표지 · 제목 · 까닭 · 다음에 할 일 · 주 단추 · 문의 줄 · 바닥 「참고 <사유 코드> · <시각> UTC」 ·
  접힌 「관리자용 진단」, 밝게 · 어둡게, 스크립트 없음)로 그린다. 문의 줄은 `CAPA_APP_CONTACT_EMAIL`(메일 링크)과 `CAPA_ACCESS_CONTACT`(창구 글)이고 둘 다 비면 없다.
  - **거절 표** — 콜백이 명단 밖이면 세션 대신 15분짜리 서명 쿠키 `capa_sso_denied`(https 면 `__Host-` 앞붙이 · HttpOnly · SameSite=Lax)를 심는다. 거절 화면은
    **그 브라우저에만** 본인 계정을 보이고(「계정 ○○ — 이 앱의 접속 명단에 없습니다.」), 주소만 연 사람 · 15분 지난 사람은 값 없이 「로그인하고 신청」 이다.
    로그인 성공 · 로그아웃이 지운다 — 콜백은 IdP 의 교차 사이트 POST 라 `SameSite=Lax` 인 표가 실려 오지 않으므로 로그인 성공은 있든 없든 늘 지운다(「다른
    계정으로 로그인」 으로 다른 사람이 들어온 뒤 앞 사람의 계정이 남지 않게). `JWT_SECRET_KEY` 에서 따로 파생한 키 · aud 라 세션 · 상태 토큰과 바꿔 끼울 수 없다.
  - **「접속 권한 신청」**(S3 명단을 쓰고 한 번 읽은 서버) — 누르면 결재 · 양식 · 메일 없이 거절 표의 본인 계정을 S3 명단에 **일반 등급**으로 바로 넣고(이름 · 부서 · 등록
    시각 · 등록 길 「스스로」 를 함께 — 이름 · 부서는 통합인증이 그 칸을 줄 때만) 「등록했습니다」(표지 「등록 완료」 · 「다시 접속」)로 간다. 「다시 접속」 은 통합인증을 거쳐
    처음 가려던 화면으로 바로 들어온다(재시작 없음). 신원은 거절 표에서만 꺼내고 폼 칸은 믿지 않는다(남의 계정 · 등급을 넣을 수 없다). 같은 출처 POST
    (`Sec-Fetch-Site` · `Origin`)와 그 표에 묶인 숨은 표지를 본다 — 거절 화면만 `Referrer-Policy: same-origin` 이다(`no-referrer` 면 폼의 Origin 이 `null`).
    새로고침 · 두 번 눌러도 한 번만 쓰고, 이미 명단에 있는 사람(관리자 포함)은 등급 · 칸을 건드리지 않는다. 뺀 사람도 다시 누르면 들어온다(차단 없음 — 일반 등급으로).
    쓰기 직전에 저장소의 지금 판을 다시 받아 그 위에 얹는다 — 같은 때 다른 등록 · 관리자의 등급 바꿈을 잃지 않는다. 받은 판이 메모리 판보다 오래되면(덮어쓴
    직후 옛 판을 돌려준 저장소) 얹지도 메모리에 올리지도 않고 저장 실패 화면이다 — 방금 뺀 사람 · 관리자 등급이 되살아나지 않게. 실패한 신청은 같은 거절 표로
    60초 동안 저장소에 다시 가지 않고(저장소가 막힌 동안의 되풀이가 입출력 잠금 · 감사 줄을 쌓지 않게) 그 사건은 최근 사건 고리에 적지 않고 「S3 명단」 줄의
    `스스로 등록 실패 n` 으로만 센다. 이 쓰기가 못 읽는 항목을 떨구거나 첫 판을 심으면 그 일은 자동 행위(`system:sso`)로 감사에 남는다(7-1).
  - **넣지 못하는 때** — S3 명단이 꺼진 서버 · 저장 실패(표지 「다시 시도」 · 「접속 명단에 넣지 못했습니다」)는 단추 대신 미리 채운 신청 글 상자(앱 이름 · 계정 ·
    이름 · 시각 · 참고 — 한 번 눌러 통째로 고른다)와 문의 줄이다. 문의 두 칸이 모두 비면 「문의처로 보내 주세요」 대신 「앱 관리자에게 보내 주세요」 다.
  - **S3 명단을 아직 한 번도 읽지 못한 동안**(관리자만 들어옴)은 명단에 든 사람도 막히므로 표지 「점검 중」 · 「접속 권한을 확인하지 못했습니다」 다(사유 코드
    `list_unread`, 신청 단추 없음). 잠시 뒤 풀리는 까닭(닿지 못함 · 시간 초과 · 5xx)이면 「권한 문제가 아닙니다」 + 「1분 뒤 「다시 확인」」, 관리자가 고칠 까닭(설정 ·
    파일 사라짐 · 깨짐 · 모르는 형식 · 인증 거절)이면 「관리자가 서버 설정을 고쳐야 열립니다」 다. 거절 표가 있으면 문의처로 보낼 글도 선다. 「다시 확인」 이 거절
    직전에 명단을 다시 읽어 본다(60초에 한 번까지). 재시작 뒤 못 읽은 서버에서 멈춘 열린 탭의 경고는 앱 안 글(`LIST_UNREAD_TEXT`) 그대로다.
  - 주소의 `code=` 는 갈래만 고른다 — 「등록했습니다」 는 거절 표가 있고 그 계정이 지금 명단에 들 때만 선다(코드만 넣어 연 사람에게는 거절 화면).
  - `ADFS_LOGOUT_URL` 이 있으면 「다른 계정으로 로그인」 이 붙는다(전의 「통합인증에서도 로그아웃」 — 하는 일 이름으로).
- **명단에서 빠진 사람** — 재시작으로 연결이 끊긴 탭은 다시 붙지 못하고 위 띠가 「접속 권한 신청」 으로 선다. 누르면 통합인증을 거쳐 거절 화면으로 간다. 그 쿠키로 새로 열어도 같다. **S3 명단에서 지우면 재시작 없이** 그 사람의 열린 탭이 다음 조작(메시지)에 닫혀 같은 길로 간다. 넣으면 거절 화면의 「다시 확인」 으로 바로 들어온다.
- **포털 거절**(`idp_error:access_denied` — 통합인증이 이 앱 사용을 막음)은 오류 화면이 아니라 같은 틀의 거절 꼴이다(표지 「권한 없음」 · 「통합인증이 이 앱 사용을
  막았습니다」 · 포털 권한 담당에게 신청, HTTP 403). 서명 전 실패라 누구인지 몰라 신청 칸이 없고, 고쳐지지 않는 실패라 시도 쿠키를 지운다(되풀이 화면으로 잘못 가지 않게).
- **Admin Area 는 운영 서버에서 관리자에게만** 열린다(위 1장). 관리자 = `CAPA_ACCESS_ADMINS`(늘 관리자 — 화면에서 빼지 못함) ∪ Admin 「접속 명단」 에서 관리자 등급을 받은
  사람. 그 밖의 화면별 권한은 아직 없다. 포털이 들어올 수 있는 범위를 따로 정하면 그 범위와 명단을 모두 지나야 한다.

## 7. 진단 창구

- **Admin Area 「통합인증 점검」** — 판정(켜짐 · 꺼짐(운영) · 막힘), 환경변수 이름 | 상태 | 까닭(값 없음), 계산한 redirect_uri ·
  issuer · 서명 인증서 지문(x5t · SHA-256 앞 16자) · 만료일, 「로그인 유지 · 마지막 사용 뒤 6시간 · 최대 24시간」 · 쿠키 이름 · 문지기 ·
  잠금, 「접속 명단 · 켜짐 · 관리자 n · 일반 n · 읽지 못함 n」(개수만 — 명단 값은 어디에도 보이지 않는다. 꺼짐이면 「꺼짐(인증된 사람 전부)」, 통합인증이 아직 안 켜졌으면 「통합인증이
  켜지면 적용 · …」), 켜짐이면 「로그인 시작 · 돌아옴(기동 뒤 누계) · 시작 n · 돌아옴 n」(시작 = 통합인증으로 보낸 수 — 되풀이로 막은 시작은 빼고, 돌아옴 = 앱 콜백에
  온 POST — 실패 · 거절 포함. 재시작하면 0. 돌아옴이 시작보다 훨씬 적으면 아래 대응표 「ADFS 화면에서 멈춤」 — 풍선이 말한다),
  「로그인 갱신(기동 뒤 누계) · 다시 발급 n · 건너뜀 n · 로그인 없음 n · 출처·머리 거절 n · 꼴 거절 n」
  (재시작하면 0. 「출처·머리 거절」 이 있는데 「다시 발급」 이 0 이면 접속 주소 · 앞단 머리를 본다 — 그 줄 풍선이 말하고, 그동안 관리자의
  어느 화면에서나 알림창 · Alarm 에 `AD-21` 「로그인 갱신이 거절됨 — 접속 주소 · 앞단 머리 확인」 이 선다 — 앱 정보 카드가 매 회차 내고
  「그 화면으로」 는 Admin Area, 한 번이라도 다시 발급하거나 건너뛰면(검사를 지난 요청) 걷힌다), 「마지막 로그인의 클레임 이름」(값 없음 · 거절된 로그인 포함 ·
  재시작하면 비워진다), 최근
  사건(재시작하면 비워진다 · 계정은 앞 두 글자 · 만료로 닫은 열린 탭은 사유 코드가 `expired · idle`(쓰지 않아 끝남) 또는
  `expired · max`(최대 시간)), 「명단 밖 로그인(기동 뒤 누계 n · 계정 n)」 표(마지막 시각 · 계정 앞 두 글자 · 횟수 — 계정마다 한 줄이라 한 사람이 되풀이해도 최근 사건이나 다른 사람의 줄을 밀어내지 못한다 · 50계정을 넘으면 가장 오래 전에 막힌 계정이 빠지고 누계에는 남는다), 「로그인 전 실패」(로그인하지 않은 누구나 보낼 수 있는 콜백 · 로그인 시작의 실패 —
  따로 둔 고리와 사유별 누계라 최근 사건을 밀어내지 못한다). 꺼짐이고 운영이 아니면 펼침이 없다. 꺼짐(운영)은 판정만 있고 화면에는 닿지 않는다 —
  운영 서버의 Admin Area 는 관리자에게만 열리는데 꺼진 동안은 관리자 신원이 없다 — 그 잠긴 화면에 `AD-02` 가 Alarm 으로 뜬다(5장 1). 갱신은 5분마다 사람마다 생겨
  사건 고리에 적지 않고 누계로만 센다.
- **Admin 「통합인증 점검」 의 「S3 명단」 줄** — 「C-DEP 에서 S3 로 닿는가」 의 답이고 키 · 서명 · 주소 · 명단 값이 없어 **리뷰 압축본에 그대로 옮겨도 된다.** 꼴은 다섯이다.
  `S3 명단 · 꺼짐`(키 없음 — 환경변수 명단) · `S3 명단 · 통합인증이 켜지면 적용`(키는 있는데 통합인증이 아직 안 켜짐) · `S3 명단 · 실패 · 아직 읽지 않음 · 관리자만 들어옴`(진입 파일을 지나지 않아 아직 읽으러 가지 않음) · `S3 명단 · 정상 · 마지막 읽기 <시각> · 명단 n · 버전 n · 쓰기 …` · `S3 명단 · 실패 · <까닭>(HTTP 상태 · 저장소 오류 코드) · 시도 <시각> · …`. 실패 뒤에는 거절이 되풀이되며 다시 읽어 본 횟수 `자가 회복 실패 n`(있을 때만)과 `마지막 읽기 없음 · 관리자만 들어옴`(한 번도 못 읽음) 또는 마지막으로 잘 읽은 시각 · 명단 · 버전(그 명단으로 판정 중)이 붙는다. 파일의 등급 칸이 `user` · `admin` 밖이면 `등급을 일반으로 읽음 n`, 거절 화면 「접속 권한 신청」 이 실패한 적이 있으면 끝에 `스스로 등록 실패 n`(기동 뒤 누계)이 붙는다. 저장에 성공하면 앞선 읽기 실패 표시는 걷힌다(저장소에 닿았고 방금 쓴 것이 지금 명단이다). 까닭은
  `주소에 닿지 못함` · `시간 초과`(연결 3초 · 읽기 5초 · 요청 전체 8초 — 조금씩 흘리는 답 · 주소 여럿도 이 안이고, 이름 풀기(DNS)만 이 제한 밖이다) · `파일 없음`(받아 둔 파일이 저장소에서 사라짐 — 메모리 명단으로 판정 중. 파일을 저장소에서 되돌린 뒤 「다시 읽기」. 정말 지워졌으면 그 명단을 되살리는 단추는 없고 저장도 「그 사이 바뀜」 으로 막힌다 — Admin 표를 옮겨 적고 저장소에서 표지 `access/seeded.json` 을 지운 뒤 재시작하면 첫 버전으로 돌아오니 다시 넣는다. 그때 `CAPA_ACCESS_USERS` 에 남은 사람이 첫 버전이 되므로 환경변수 표를 먼저 본다) · `인증서 확인 실패` · `인증 거절`(401 · 403 — 코드가 `SignatureDoesNotMatch` 면 비밀키 · 시계, `InvalidAccessKeyId` 면 키, `AccessDenied` 면 권한) · `버킷 없음` · `파일 깨짐` · `모르는 파일 형식` · `파일이 너무 큼` · `그 밖의 응답` · `설정 값 빠짐 · 틀림`(환경변수 표의 그 줄 까닭을 본다).
  **쓰기 권한은 저장할 때 알게 된다** — 끝의 `쓰기` 칸이 `쓰기 저장할 때 알게 됨` · `쓰기 정상 · <시각>` · `쓰기 실패 · <까닭>`(답을 받은 거절 · 저장 전 대조 실패 — 저장소 그대로) · `쓰기 결과 모름 · <까닭>`(PUT 을 보내고 답을 받지 못함 — 저장소에 들어갔을 수 있다. 메모리는 그대로이고 「다시 읽기」 로 확인하면 걷힌다. 다시 읽지 않으면 그 고침은 다음 재시작 때 조용히 반영된다. 그대로 다시 저장해도 덮어쓰지 않고 「그 사이 바뀜」 으로 막힌다) 이다. 읽기 실패는 **관리자의** 알림창 · Alarm(`AD-08`)에도 뜬다 — Admin 을 열기 전 **어느 화면에서나**(앱 정보 카드가 매 회차 낸다 · 「그 화면으로」 는 Admin Area) 뜨고, 「다시 읽기」 자리가 관리자에게만 있어 다른 사람에게는 이 줄만 보인다. 환경변수 첫 버전 알림(`AD-09`)도 같다.
  최근 사건 표의 `access_read` · `access_saved` · `access_save_failed` · `access_seed_mark_failed`(표지를 못 씀 — 저장은 된 것이고 다음 저장 · 다음 읽기가 다시 쓴다) 는 시각 · 사유 코드 · 저지른 관리자 계정 앞 두 글자만 보인다(서버 로그에는 저지른 관리자의 전체 loginid 와 개수 — `login_ok` 와 같다, **서버 로그를 리뷰에 옮기지 않는다**). 넣고 뺀 사람의 값은 어느 쪽에도 없다 — 고친 기록의 누가 · 무엇은 S3 파일의 `changes` 마지막 200건에 있다. 못 읽은 서버의 자가 회복 실패(`access_retry_failed`)와 「접속 권한 신청」 의 실패(`access_self_register_failed`)는 표에 쌓지 않는다 — 들어오지 못하는 사람이 되풀이해 남길 수 있어 위 줄의 횟수로만 센다. **명단 값은 실제 loginid 라 리뷰에 옮기지 않는다.**
- **Admin Area 「서버 시작 점검」** 표 넷째 줄 「통합인증」 — 정상 · 건너뜀(`ADFS_CLIENT_ID` 없음) · 실패(문제 이름). 시작 스크립트가
  남긴 「시작 때 있던 통합인증 환경변수」 이름도 한 줄 붙는다. 그 아래 줄은 S3 키가 있을 때의 동기화 줄이다(`docs/objectstore_setup.md` 3장).
- **임시 화면** — 앱이 뜨기 전 시작 스크립트가 같은 포트로 답하는 동안은 로그인 전 화면 하나다(`scripts/container_stage.py` — 단계 · 지난 시간 · 머무는 까닭). 앱이 뜨면 쪽이 **처음 연 주소를 다시 읽는다** — 그 사이 누른 로그아웃 · 「다시 로그인」 · 로그인 시작 경로는 앱이 받아 그대로 이어진다. IdP 가 그때 콜백으로 돌아오면(form_post — POST) 그 화면이 받고, 앱이 뜨면 쪽이 바탕 주소로 가서 다시 로그인한다(코드를 되풀이하지 않는다). 값을 싣지 않고 요청 경로 · 질의를 화면에 싣거나 기록하지 않는다.
- **설정 화면**(막힘) · **오류 화면**(로그인 실패, 새로고침해도 폼이 다시 가지 않는다) — 위는 누구나 읽는 글, 바닥 참고 줄에 사유 코드(오류 화면은 진단 번호까지),
  접힌 「관리자용 진단」 에 한 줄 설명 · 진단 표 · 고칠 것(6장). 토큰 · state · nonce · 쿠키 값 · 비밀값 · 이름 · 부서는 어디에도 보이지 않는다.
- **대응표** — 사람이 본 화면 → 관리자가 볼 곳.

  | 본 화면 · 증상 | 볼 곳 · 할 일 |
  |---|---|
  | 「로그인 설정에 문제가 있습니다」(점검 중) | 참고 줄의 사유 코드 · 접힌 진단 표 — aud 면 `ADFS_CLIENT_ID`, iss 면 `ADFS_ISSUER`(받은 iss 로), 서명이면 인증서 지문, 시각이면 서버 시계, 클레임이면 받은 클레임 이름 |
  | 「로그인을 마치지 못했습니다」(다시 시도) | 사람이 「다시 시도」 하면 된다. 같은 사람이 되풀이하면 그 사람의 탭 · 북마크(로그인 도중 주소)를 본다 |
  | 「브라우저가 이 사이트 쿠키를 저장하지 않았거나 …」 | 그 사람이 연 주소가 `CAPA_PUBLIC_URL` 과 같은지(다른 이름 · IP · 포트) · 쿠키 차단 · 통합인증 화면에 10분 넘게 머물렀는지 |
  | 「로그인이 되풀이됩니다」 | 시각까지 기다려 「다시 시도」. 여러 사람이면 바로 앞 실패의 사유 코드(Admin 「로그인 전 실패」 누계)를 본다 |
  | **ADFS 화면에서 멈춤**(우리 화면이 안 뜸) | 포털 등록 주소(redirect_uri) · 앱 등록 번호 · ADFS 장애 · 계정 잠김은 앱으로 돌아오지 않아 사건이 없다. Admin 「로그인 시작 · 돌아옴」 에서 돌아옴이 시작보다 훨씬 적은지 보고, 멈춘 ADFS 화면을 찍어 받아 그 글로 포털 · ADFS 담당과 고친다 |
  | 「지금은 앱을 열 수 없습니다」(설정 화면) | 접힌 진단의 「고칠 것 n개」 대로 C-DEP 환경변수 표를 고치고 CI/CD |
  | 「지금은 앱을 열 수 없습니다(서버 시작 설정)」(앱 안) | 접힌 진단 — `capa_server.py` 로 띄운다(C-DEP 시작 스크립트는 그렇게 띄운다) |
- 서버 로그(볼 수 있다면) — `sso event=config|login_ok|login_denied|login_fail|idp_error|logout|session_closed|cert_expiring|access_read|access_retry_failed|access_saved|access_self_registered|access_self_register_failed|access_save_failed|access_seed_mark_failed …` 한 줄씩
  (`session_closed` 는 만료 · 로그아웃한 열린 탭의 연결을 문지기가 닫은 것 — 만료면 `end=idle`(쓰지 않아 끝남) · `end=max`(최대 시간)).
- **거절 화면**(`/auth/sso/error?code=not_on_list`, 403) — 접속 명단 밖. 사유 코드 `not_on_list` 는 IdP 의 `access_denied`(포털이 거절 — 같은 틀의 포털 거절 꼴 `idp_error:access_denied`)와 다르다. 바닥 참고 줄의 사유 코드 · 시각으로 Admin 최근 사건과 짝을 맞춘다. 명단
  밖인 사람과 까닭을 맞출 때는 Admin 「명단 밖 로그인」 표를 본다. loginid 는 실데이터라 리뷰 압축본 · 전문에 옮기지 않는다. S3 명단을 아직 못 읽은 동안의
  거절은 `code=list_unread` 의 같은 꼴 화면(「접속 권한을 확인하지 못했습니다」)이고, 그 거절도 「명단 밖 로그인」 표에 센다(사건 사유 코드 `list_unread`).
- 오류 화면의 사유 코드는 이 서버가 내는 이름뿐이다 — 주소의 `code=` 에 다른 글을 넣어도 `unknown` 으로 보인다(로그인 없이 여는
  화면에 남이 고른 문장이 서지 않게). IdP 의 표준이 아닌 오류 이름은 `idp_error:other` 로 보이고 원문은 사건 기록에만 남는다.
  같은 까닭으로 거절한 토큰 머리의 alg 는 알려진 JWS 이름(`none` · `HS256` 등)만 그대로, 그 밖은 `other` 로 보인다.

## 7-1. 접속 · 작업 감사 기록

통합인증이 켜진 기동(`capa_server.py` — 모드 켜짐)에서만 감사 기록기가 켜진다(`audit/boot.py`). 꺼짐 · 막힘 · `app.py` 개발
실행 · 사내 PC · WebIDE 는 기록도 탭도 없다. 끄는 환경변수는 없다. 위 사건 고리 · 서버 로그는 그대로이고, 같은 사건이 아래
대응표로 감사 줄이 되어 메모리 큐 → 스풀 → 버킷 `audit/` 에 남는다(`docs/objectstore_setup.md` 「감사 기록 접두사」, 운영은
`docs/audit_log_operations.md`). 화면은 Admin Area 넷째 탭 「접속 · 작업 기록」(관리자만)이고, 그 탭이
서는 서버의 「통합인증 점검」 은 최근 사건 · 명단 밖 표를 그리지 않고 누계 줄과 리뷰용 「복사」 만 남긴다.

| 통합인증 사건(`sso event=`) | 감사 줄 | 남기는 것 |
|---|---|---|
| `login_ok` | `authn_login_success` | 계정 · 세션 꼬리표(sid 앞 8자) · 유지 시간 · **이름(이 줄에만)** — 부서 · `jti` 는 없다 |
| `login_fail`(서명이 통과한 뒤 — 계정 있음) | `authn_login_fail` | 계정 · 사유 코드 |
| `login_fail` · `idp_error`(무인증) · `session_closed reason=missing` | `authn_login_fail_summary` | 한 시간에 한 줄 — 사유 코드별 건수 |
| `login_denied` | `authz_fail_access_list` · `…_summary` | 계정마다 그 시간의 첫 건 한 줄, 되풀이는 시간 묶음 건수 |
| `username_missing` | `authn_username_missing` | 계정 |
| `logout` | `session_logout` | 계정 · sid 앞 8자 |
| `session_closed reason=expired` · `revoked` · `denied` · `invalid` | `session_expired`(끝 `idle` · `max`) · `session_revoked` · `authz_fail_session` · `session_invalid` | 계정 · 사유 |
| 갱신 경로 누계(`refresh_counts`) | `session_renew_summary` | 한 시간에 한 줄 — 결과별 건수 |
| `cert_expiring` · `access_read`(실패) · `access_save_failed` · `access_seed_mark_failed` | `sys_cert_expiring` · `sys_access_read_fail` · `sys_access_save_fail` | 남은 날 · 사유 · 상태 |
| (Streamlit 세션 첫 회차) | `session_created` | 계정 · sid 앞 8자 · 탭 꼬리표(Streamlit 세션 id 의 SHA-256 앞 8자) |
| (명단 저장 `save_changes`) | `user_created` · `user_deleted` · `user_grade_changed` | 관리자 · **대상 loginid** · 명단 판 전 → 후(등급 바꿈은 등급 전 → 후도), 답을 못 받으면 결과 `unknown` |
| (스스로 등록 `register_self`) | `user_self_registered` | 행위자 = 그 사람(거절 표의 인증 신원) · **대상 loginid** · 판 전 → 후(실패면 결과 `fail` · `unknown`). 서버 로그 · 사건 고리의 `access_self_registered` 에는 계정이 없고, 실패(`access_self_register_failed`)는 감사 대응표 밖이다 — 그 사람의 실패 줄 하나만 남는다 |
| (다시 쓰기에 딸린 일) | `user_bulk_dropped` · `user_seeded` | 못 읽은 항목이 빠진 수 · 첫 판 심기 수 · 판 전 → 후. 관리자 저장이면 행위자가 그 관리자, 스스로 등록이면 자동 행위 `system:sso`(미검증) — 일반 사용자의 누름이 관리 행위로 읽히지 않게 |

- 기동 때 `sys_startup`(환경 · 통합인증 · 동기화 모드)과 `authz_admin_config`(관리자 수 · 목록 지문 8자 — 사람 값은
  없다)를 남긴다.
- **남기지 않는 것** — 토큰 · 쿠키 · state · nonce · `jti` 전체 · 서명 키 · S3 키 · 비밀값 · 부서. 이름은 로그인 성공 줄에만.
  모든 글은 줄바꿈 · 제어 문자를 지우고 토큰 꼴(JWT 세 토막 · 긴 키 덩이)은 가린다.
- 접속지(IP) 칸은 비워 둔다 — 사내에서 실제 사용자 IP 가 실리는 머리를 확인한 뒤 로그인 · 세션 시작 줄에만 켠다.
- 감사 화면(관리자)에는 loginid 가 그대로 보인다. **리뷰 압축본 · 전문에는 옮기지 않는다**(수와 날짜만).

## 8. 개발 — 가짜 IdP 로 끝까지 돌리기

실제 ADFS 없이 로그인 흐름을 돌린다. 가짜 IdP 는 실행 때 RSA 키를 메모리에만 만들고, `APP_ENV` 가 운영이면 · 루프백이 아닌
`--host` 면 · env 파일이 작업 트리 안이면 거절한다. 명령은 창 둘로 나눠 친다(포트는 늘 적는다).

창 1 — 가짜 IdP(그 자리에 개발용 환경변수 파일을 쓴다):

```bash
python scripts/sso_mock_idp.py --port 8591 --app-url http://localhost:8510 --env-out ~/sso-dev.env
```

창 2 — 그 파일을 읽어 진입 파일로 앱을 띄운다:

```bash
set -a; . ~/sso-dev.env; set +a
python -m streamlit run capa_server.py --server.port 8510
```

- 브라우저로 `http://localhost:8510` 을 열면 가짜 IdP 화면(클레임 표 + 「로그인」)을 거쳐 앱으로 돌아온다. `--aud` · `--omit-claim` ·
  `--error` 로 실패 화면을 볼 수 있다.
- http 루프백에서는 브라우저가 상태 쿠키(`SameSite=None; Secure`)를 받지 않을 수 있다. 확인된 길은 HTTPS(자체서명)다 — 앱은
  `--server.sslCertFile/--server.sslKeyFile`, 가짜 IdP 는 `--tls-cert/--tls-key` 로 띄우고 `--app-url` 을 https 로 준다.
- **사내 WebIDE 에서 시험할 때** — 앱 · 가짜 IdP 를 WebIDE 프록시 주소로 연다. `--app-url` 에 앱의 프록시 주소(경로 접두
  `/proxy/<포트>` 포함)를, `--public-url` 에 가짜 IdP 의 프록시 주소를 준다. 쿠키 이름에 경로 접두의 지문이 붙어 같은 호스트의
  여러 앱이 서로 덮지 않는다. 이 주소는 루프백이 아니라 접속 명단이 켜진다 — 가짜 IdP 가 env 파일에 `--loginid` 를 `CAPA_ACCESS_ADMINS` 로 적어 그 계정으로 그대로 들어온다(값은 합성만).
- **접속 명단 세 갈래** — 루프백 주소에서는 두 목록이 없으면 명단이 꺼져 있다. 창 1 을 `--loginid demo.user` 를 더해 띄우고, 창 2 에서 `streamlit run` 앞에 아래 줄을 친다(값은 합성만).

  ```bash
  export CAPA_ACCESS_ADMINS=demo.admin
  export CAPA_ACCESS_USERS=demo.user
  ```

  ① **허용** — 브라우저로 들어와 HOME 이 선다. ② **명단에서 빠진 쿠키** — 창 2 를 끄고 `unset CAPA_ACCESS_USERS` 뒤 같은 줄로 다시 띄운다(같은 `JWT_SECRET_KEY` 라 쿠키는 그대로 유효하다). 열어 둔
  탭은 다시 붙지 못해 「다시 로그인」 띠가 서고, 누르면 거절 화면이다. ③ **거절** — 거절 화면의 「다시 확인」 을 눌러도, 새 탭으로 열어도 거절 화면이고 세션 쿠키가 남지 않는다(Streamlit 자체 `_streamlit_xsrf` 는 남을 수 있다). Admin 「통합인증 점검」 은
  명단에 든 누구로든 볼 수 있다(화면별 권한은 다음 단계) — ② 뒤에는 `demo.user` 가 명단에 없으니 `--loginid demo.admin` 으로 창 1 을 다시 띄우고 그 env 파일을 다시 읽는다(가짜 IdP 키가 새로 생긴다).
- **S3 명단을 끝까지 돌리려면** — 창 하나를 더 열어 가짜 S3 를 띄우고(서명을 검증하는 메모리 저장소 — 끄면 사라진다, 루프백만 · env 파일이 작업 트리 안이면 거절), 창 2 에서 그 env 파일도 읽는다. 값은 합성만이다.

  ```bash
  python scripts/s3_mock_store.py --port 8607 --env-out ~/s3-dev.env
  ```

  ```bash
  set -a; . ~/sso-dev.env; . ~/s3-dev.env; set +a
  export CAPA_ACCESS_ADMINS=demo.admin
  python -m streamlit run capa_server.py --server.port 8510
  ```

  창 1 은 `--loginid demo.admin` 으로 띄운다. 들어오면 Admin 「접속 명단」 이 서고, 「추가」 로 `demo.user` 를 넣으면 재시작 없이 저장되고 「S3 명단」 줄이 `버전 1 · 쓰기 정상 · <시각>` 으로 바뀐다. 그 사람으로 들어가 보려면 창 1 을 `--loginid demo.user` 로, 창 2 를 그 env 파일로 다시 띄운다(가짜 IdP 키가 새로 생겨서다 — 가짜 S3 창을 그대로 두면 명단은 이어진다). 편집 자리가 없고 지우면 다음 조작에 탭이 닫힌다.
  장애를 보려면 가짜 S3 창을 끄고 「다시 읽기」(지난 명단으로 판정 · 줄이 `실패 · 주소에 닿지 못함`), 끈 채로 앱을 다시 띄우면 관리자만 들어온다. 자가 회복을 보려면 가짜 S3 를 `--seed-loginid demo.user` 를 더해 다시 띄운다(메모리뿐이라 그냥 다시 띄우면 비어 있고, 없는 키는 빈 명단이라 그 사람은 계속 거절된다). 창 1 을 `--loginid demo.user` 로 띄운 상태에서 60초 뒤 거절 화면의 「다시 확인」 을 누르면 재시작 없이 들어온다. `--seed-loginid` 는 `demo.` 로 시작하는 합성 값만 받는다.
- **갱신을 눈으로 보려면** — 서버는 직전 발급에서 60초 안이면 다시 발급하지 않고 브라우저는 답 뒤 5분 동안 보내지 않는다. 로그인
  뒤 61초를 실제로 기다린 다음 브라우저 시계만 5분 넘겨(Playwright `clock.set_system_time` — 타이머를 쏘는 `fast_forward` · `run_for`
  는 Streamlit 타이머를 건드린다) 휠 한 번 → `204` + `Set-Cookie`(새 `jti`, `sid` · `auth_time` 그대로), Admin 「다시 발급」 이 는다.
- 개발 · 시험 · 화면 확인(`scripts/check_deploy_screens.py`)은 지금처럼 `app.py` 로 띄운다 — 통합인증 환경변수가 없으면 꺼짐이고,
  켜진 설정을 `app.py` 로 띄우면 「지금은 앱을 열 수 없습니다(서버 시작 설정)」 로 멈춘다(진입 파일 없이 열리지 않게 — 까닭은 접힌 진단의 「문지기 없이 앱이
  시작됐습니다」).
- **로그인 실패 화면 갈래를 가짜 IdP 로 보려면** — `--aud other-app`(설정 문제 · aud), 앱 쪽 `ADFS_SIGNING_CERT` 를 다른 인증서로(서명), 브라우저 쿠키를 지운 뒤
  가짜 IdP 화면에서 보냄(쿠키 없음 — `--submit-delay-ms` 로 시간을 번다), 오류 주소에 `?code=state_missing`(잠시 문제)을 직접 연다.

## 9. 사내에서 확인할 것(포털 · ADFS · C-DEP 담당)

1. issuer 의 정확한 문자열과 id_token `aud` 가 client id 문자열 하나인지(목록이면 `azp` 처리가 더 필요하다).
2. 포털 「Legacy (OpenID)」 가 `response_type=id_token` + `response_mode=form_post` 를 허용하는지.
3. loginid · username · deptname 이 **id_token** 에 실리려면 `scope`(예: `allatclaims`)나 `resource` 가 필요한지 — `ADFS_SCOPE` ·
   `ADFS_RESOURCE` 로 넣는다.
4. 클레임 이름이 그 셋 그대로인지. loginid 의 도메인 접두(`DOMAIN\`)는 2026-11-05 로그인 성공으로 닫았다 — 백슬래시는 loginid 글자 집합 밖이라 붙었다면 로그인이
   `claim_invalid` 로 거절됐을 것이다. 그래서 접속 명단에도 접두 없이 적는다(적으면 읽지 못한 항목으로 빠진다).
5. 넣을 인증서가 **토큰 서명** 인증서인지, 꼴(DER/Base-64), 교체 방식 · 주기 · 공지 채널.
6. ADFS 로그아웃 주소와 로그아웃 뒤 돌아올 주소 등록이 되는지.
7. C-DEP 상태 검사 경로 · 방식(TCP · `/` · `/_stcore/health`), 환경변수 값 길이 제한(인증서 한 줄 1~2 KiB), 인그레스가 Host 를
   그대로 넘기는지, replica 수(1 전제 — 로그아웃 폐기 목록 · 로그인 갱신 표가 프로세스 메모리다).
8. 사내 이미지 빌드(pip)와 WebIDE `uv sync --inexact` 가 새 의존성 넷(pyjwt · cryptography · cffi · pycparser) 휠을 받는지.
9. 앱에 들어올 수 있는 사람의 범위를 포털도 정하는지(그렇다면 포털 범위와 접속 명단을 모두 지나야 한다). AD 그룹 클레임은 쓰지 않기로 했다(2026-11-05 사용자 결정 — `loginid` + S3 명단).
   통합인증이 포털 거절(`access_denied`)을 앱 콜백으로 돌려보내는지(아니면 포털 거절 화면은 뜨지 않는다), id_token 에 이름 · 부서 칸(`username` · `deptname`)이 실리는지(칸 이름만 —
   스스로 등록이 그 칸을 명단에 적는다).
10. C-DEP 환경변수 표를 볼 수 있는 사람 — `JWT_SECRET_KEY` 를 본 사람은 로그인 토큰을 만들 수 있다.
11. C-DEP 운영 pod 에서 S3 주소(`CAPA_S3_ENDPOINT_URL`)에 닿는지 · 앱용 키를 받을 수 있는지(그 버킷 읽기 · 쓰기) · HTTPS 포트가 열렸는지 — 닿는지는 Admin 「S3 명단」 줄이 답한다. 평문 `http` 면 명단이 사내망에 그대로 흐른다. 프록시를 거쳐야 닿는 망이면 지금 경계는 프록시를 따르지 않아 `주소에 닿지 못함` 이 된다.
12. 앞단(인그레스 · WebIDE 프록시)이 `X-Capa-Sso-Refresh` 머리와 `Origin` 을 그대로 넘기는지 — 아니면 로그인이 쓰는 중에도 처음
    로그인 6시간 뒤 끊긴다(Admin 「출처·머리 거절」 이 늘고 「다시 발급」 은 0). 응답 머리 `X-Capa-Sso-Reason` 을 그대로 돌려주는지도 —
    떼면 열어 둔 탭의 띠가 까닭을 가르지 못하고 옛 글로 선다.
13. ADFS 쪽 오류 · 장애 화면 — 포털 등록 주소(redirect_uri) · 앱 등록 번호가 안 맞을 때, ADFS 장애 · 계정 잠김일 때 ADFS 가 무엇을 보이는지(앱으로 돌아오지 않아
    우리 화면도 사건도 없다). 그 화면을 찍어 오고, 그때 Admin 「로그인 시작 · 돌아옴」 에서 돌아옴이 시작보다 적게 느는지 본다.
14. 저장하지 않은 고침이 있는 탭에서 앱 정보 카드의 「로그아웃」 을 누르면 사내 브라우저가 「사이트에서 나가시겠습니까?」 확인 창을 띄우는지(탭 줄의 떠나기 확인 —
    코드로 읽은 것). 뜨지 않으면 로그아웃 단추 + 우리 확인 창을 다시 본다.
15. 로그인 실패 화면의 「쿠키 없음」 이 실제로 뜨는 경우 — 사람들이 북마크 · 다른 이름(IP · 짧은 호스트 이름)으로 여는지, 사내 브라우저 정책이 이 사이트의
    쿠키(`SameSite=None` 상태 · 시도 쿠키)를 막는지.
