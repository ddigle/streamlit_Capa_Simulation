# 운영 DB 정본 — C-DEP 운영 절차

C-DEP 운영 서버는 영속 볼륨을 쓸 수 없고 CI/CD 때 디스크(`/project/data`)가 사라진다. 그래서 두 DuckDB(`data/capa_simulation.duckdb` · `data/equipment_availability.duckdb`)의
**정본을 운영 버킷에 둔다.** 앱이 시작할 때 받고 저장하면 올린다. 이 문서는 **사람이 넣고 · 보고 · 하는 것**을 적는다. 차례의 정본은 코드(`scripts/container_start.py` · `object_sync_engine.py` ·
`object_sync_worker.py`), 파일별 책임은 `AGENTS.md` 3장, 결정은 `docs/TODO.md` 3장 「데이터·DB」 2026-11-07 이다.

**쓰는 쪽은 운영 앱 하나다.** 이관이 끝나면 사내 PC 앱은 쓰지 않고, 읽을 때는 사본을 받는다(5장).

**접속 명단 파일은 이 절차 밖이다.** 앱이 환경변수 키로 작은 JSON 하나를 직접 받고 올린다(표준 라이브러리 SigV4 — `io/s3_small.py` · `auth/access_store.py`, `aws` CLI · 프로필을 쓰지 않는다).
켜는 법과 진단은 `docs/sso_setup.md` 2 · 5 · 7장이고 같은 버킷 · 같은 키다.

**모듈 데이터 파일도 이 절차 밖이다.** 코어가 대신 올리고 받지 않는다 — 모듈이 창구 도우미(`module_api.s3_upload` · `s3_download`)로 접속 명단과
같은 길 · 같은 키 · 같은 버킷의 `modules/<id>/` 아래에 스스로 올리고 받는다. 동기화 모드가 `managed` 인 서버에서만 되고 파일 하나는 8 MiB 까지다
(2026-11-12 사용자 결정 「도우미 함수로」 — 「하지 않은 것」 첫 줄).

**두 DB 는 한 쌍이다.** 세대 포인터 하나(`generations/heads/`)가 두 스냅샷을 함께 가리키고 그 PUT 이 게시다. 포인터는 맨 마지막에 쓴다 — 올리는 중 죽으면 앞 세대로 온전히 복구된다. 바뀌지 않은 DB 는
앞 세대의 스냅샷을 그대로 이어 적는다.

## 1. 확인된 환경

| 항목 | 값 |
|---|---|
| CLI | 운영 이미지 `aws-cli/1.46.3`(`docker/Dockerfile-prod` 의 따로 된 한 줄 — 판 값은 `AWS_CLI_VERSION` 과 시험이 맞댄다) · 사내 PC `aws-cli/2.36.8` (Windows exe 번들, 자체 Python 3.14) |
| 엔드포인트 | 사내 값 — C-DEP 환경변수 표 · 사내 PC 사용자 환경변수(`CAPA_S3_ENDPOINT_URL`)에만 둔다(저장소에 적지 않음 — 공개 저장소) |
| 프로필 | 사내 값 — 같은 자리(`CAPA_S3_PROFILE`, 저장소에 적지 않음). 사내 PC 는 `~/.aws` 에 이미 만든 이름 그대로, C-DEP 는 시작 스크립트가 그 이름으로 `~/.aws` 를 쓴다 |
| 네임스페이스 | 사내 값 — 저장소에 적지 않음. **프로필에 매여 있고 명령 인자가 아니다** |
| 버킷 | 운영 · 개발 둘 · 각 1000GiB. 이름은 사내 값 — 운영은 C-DEP 환경변수 표 `CAPA_S3_BUCKET` 에만, 사내 PC 는 명령마다 `--bucket` — 그 창의 변수(`$b`)로만 넣고 PC 환경변수에 남기지 않는다(저장소에 적지 않음 · 코드에 기본 버킷이 없다 — 6장 1단계) |
| 전송 | http 9020(폐쇄망). https 는 서버 TLS 문제로 쓰지 않는다 |
| 닿음 | 운영 pod 에서 http 403(인증 없는 요청의 정상 답) 확인 · WebIDE 에서 개발 버킷 읽기 쓰기 · probe 셋 true(2026-11-06) |
| 서버 | 쓰는 쪽 운영 앱 하나 · pod 는 겹치지 않음(새로 띄우면 기존은 죽음) · 끄면 바로 꺼짐(끌 때 올릴 기회가 없다) · 상태 검사 시작 제한 1분 · 메모리 한도 1GiB · 노드 디스크 여유 40GiB · overlay 하나 |
| 명령 접두 | 사내는 `uv` 구성이라 **`uv run --no-sync python`** (재잠금·재설치를 막는 안전장치다. `bigdataquery` 를 지우는 것은 맨 `uv sync` 쪽이다) — 아래 본문의 `.\.venv\Scripts\python.exe` 는 개발 PC 표기다 |

## 2. C-DEP 환경변수 표

값은 배포 설정의 표에만 넣는다 — 그 표는 가림이 없고 그룹원 전권이다. 키는 개인 키로 시작해 공용 계정으로 옮긴다. **이 키는 운영 DB 삭제 권한이다.** 앱이 이 키를 받는 구조는 그대로 두고 PR 점검(런북 4-6)으로 보며, 공용 계정으로 옮길 때 버킷 권한을 좁힌다(2026-11-07 통합 검수 D6 (가), 4장 끝).

| 이름 | 필수 | 뜻 |
|---|---|---|
| `CAPA_S3_SYNC_MODE` | 운영 `managed` | 비면 `local` — 표가 빈 값을 받지 않으면 소문자 `local` 을 적는다(같은 길이다). 다른 철자 · 공백 한 칸 같은 틀린 값은 동기화 꺼짐 + `SY-01`. 키가 있고 버킷에 세대가 있는데 `managed` 가 아니면(비었거나 `local`) `SY-05` |
| `CAPA_S3_BUCKET` | `managed` 필수 | 운영 버킷(사내 값). 없으면 받지 않고 머문다 — 코드에 기본 버킷이 없다. 접속 명단도 같은 버킷. 운영 버킷과 `managed` 는 운영 C-DEP 표에만 둔다 — 개발 서버 · WebIDE · 사내 PC 앱에 넣으면 쓰는 쪽이 둘이 되어 세대가 갈라진다(`원격이 갈라짐`) |
| `CAPA_S3_ACCESS_KEY` | `managed` 필수 · 비밀 | `~/.aws` 프로필 · 접속 명단 |
| `CAPA_S3_SECRET_KEY` | `managed` 필수 · 비밀 | `~/.aws` 프로필 · 접속 명단 |
| `CAPA_S3_ENDPOINT_URL` | `managed` 필수 · 키를 넣으면 필요 | S3 주소(사내 값 — 코드에 기본값이 없다). 없으면 「서버 시작 점검」 의 프로필 · ECS 줄이 `CD 환경변수 CAPA_S3_ENDPOINT_URL 없음` 이고 받지 않고 머문다. 접속 명단 · 모듈 S3 도우미도 이 값을 쓴다 |
| `CAPA_S3_REGION` | 선택 | 기본 `us-east-1` |
| `CAPA_S3_PROFILE` | `managed` 필수 · 키를 넣으면 필요 | aws 프로필 이름 — 시작 스크립트가 이 이름으로 `~/.aws` 를 쓰고 앱 · 받기가 그 이름으로 부른다. 코드에 기본 이름이 없다 — 없으면 프로필 · 버킷 목록 줄이 `CD 환경변수 CAPA_S3_PROFILE 없음` 이고, `managed` 면 받지 않고 머물며 `local` 이면 Alarm `SY-06` 이 이름을 댄다 |
| `CAPA_ACCESS_S3_OBJECT` | 선택 | 기본 `access/access_list.json` |
| `CAPA_ACCESS_USERS` | 선택 | 명단 **파일이 처음 없을 때** 첫 판(`docs/sso_setup.md` 5장) |
| `CAPA_ACCESS_ADMINS` | 운영 필수 | 관리자 — 「지금 올리기」 |

`HOME`(`~/.aws` 자리) · `HOSTNAME`(pod 이름)은 런타임이 준다. 시간 상수는 코드에 두고 환경변수로 늘리지 않는다.
처리하지 못한 오류의 화면 꼴(`STREAMLIT_CLIENT_SHOW_ERROR_DETAILS=type` — 오류 종류 이름만, 2026-11-14 「앱 대신 뜨는 화면」 보드 d12 (가))은
운영 이미지(`docker/Dockerfile-prod`)에 들어 있어 표에 넣지 않는다 — 화면 본문의 오류는 앱이 「이 화면에 오류가 났습니다」 카드와 참고 번호로 감싸고, 관리자는
Alarm 「화면 오류」(`AD-22`)와 그 카드의 「관리자용 진단」 으로 원문을 본다.

**S3 키를 다시 발급하면 사내 PC 프로필(`~/.aws`)과 C-DEP 표(`CAPA_S3_ACCESS_KEY` · `CAPA_S3_SECRET_KEY`)를 함께 바꾼다** — 한쪽만 바꾸면
C-DEP 는 S3 명단을 못 읽어 관리자만 들어오고, 이관 뒤에는 시작 때 DB 받기에서 멈춘다(2026-11-11 사내 리뷰 `202611111500` 보드 답).

**pod 에 `HTTP_PROXY` · `HTTPS_PROXY` 가 있으면 S3 주소(`CAPA_S3_ENDPOINT_URL` 의 호스트)를 `NO_PROXY` 에 넣는다** — 운영 `aws` CLI(두 DB 받기 ·
올리기)는 pod 의 프록시 변수를 따른다. 지금 C-DEP 는 프록시 없이 닿는다(「서버 시작 점검」 ECS `HTTP 403 닿음` — 2026-11-12 사내 리뷰 `202611111500` 보드 답).

## 3. 운영 서버가 스스로 하는 것

**시작 차례**(`scripts/container_start.py`). 시작 스크립트가 맨 앞에서 8080 을 잡고, 끝나면 소켓을 닫고 앱이 같은 포트를 잡는다.

| 차례 | 하는 일 | 실패하면 |
|---|---|---|
| ① 임시 응답 | 모든 경로 200 · `/_stcore/health` 200 — 상태 검사(TCP · `/` · health 어느 것이든)를 통과시키고 접속자에게 앱 밖 화면 꼴로 단계 줄(준비 · 점검 → 설치 → 데이터 받기 → 앱) · 지난 시간 · 머무는 까닭을 보인다 — 표지 「시작 중」 · 「다시 시도」 · 「점검 중」. 로그인 전 화면이라 데이터 · 주소 · 키 · 버킷을 싣지 않는다 | 이어 간다 |
| ② 프로필 | 키 둘로 `~/.aws/credentials` · `config` (0600) — `sync_object_storage.py profile` 이 찍는 설정과 같은 한 벌 | 줄에 적고 이어 간다 |
| ③ 점검 | aws 판 · ECS 연결 · 버킷 목록 · `/project` 디스크 · pod · cgroup · DuckDB 기본값 | 줄에 적고 이어 간다 |
| ④ 설치 · 토큰 | `bigdataquery` 설치(240초까지) · 로그인 토큰 · 요청자 계정 | 줄에 적고 이어 간다 |
| ⑤ 받기 | `managed` 면 `sync_object_storage.py boot-pull`(하위 프로세스) | **앱을 띄우지 않는다** — 그 화면에 머물며 물러나서 다시 시도(5 · 10 · 20 · 40 · 60초, 이후 60초). 사람이 손대야 풀리는 갈래(8장 표 「다시 봄」 300초 — 설정 오류 · aws 명령 없음 · 저장소가 거절 · 버킷 없음 · 디스크 부족 · 스냅샷이 깨짐 · 원격이 갈라짐 · 원격과 어긋남 · DB 판이 코드보다 새로움)는 300초마다 다시 보고 표지가 「점검 중」 이다 |
| ⑥ 넘김 | 결과 파일 → 소켓 닫기 → 앱. 틈은 0.7초 안팎, 캐시 없는 첫 실행 1.2초(샘플 관측)이고 쪽의 JS 가 기다렸다 처음 연 주소를 다시 읽는다(재시작 중에 누른 로그아웃 · 로그인도 이어진다 — POST 로 받은 쪽 · 콜백만 바탕 주소. 거절 화면의 「접속 권한 신청」 을 그 틈에 눌렀으면 「「접속 권한 신청」 이 닿지 않았습니다 — 앱이 열리면 다시 눌러 주세요.」 한 줄이 서고, 같은 주소를 다시 보내지 않고 열어 거절 화면이 다시 선다) | — |

**모드**: 키도 모드도 없으면 지금처럼 ② ③ ⑤ 를 건너뛴다. 키만 있으면 ② ③ 까지 돌고 앱은 빈 디스크로 뜬다(첫 CI/CD 로 aws 판 · 연결을 보는 판). `managed` 면 ⑤ 까지 간다. 그 밖의 값은 동기화 꺼짐으로 앱이 뜨고 `SY-01` 이 알린다
(올리지도 않으니 정본을 덮지 않는다). **이관 뒤 환경변수 표에서 모드 칸이 빠지거나 `local` 로 남으면** 앱은 같은 길로 빈 디스크로 뜬다 — 두 값은 유효한 `local` 이라 CI/CD 가 초록이다. 그때는 ③ 의 버킷 목록에 세대가 보여 `SY-05` 가 알린다(이 앱의 저장은 다음 CI/CD 에 사라진다). 주소 · 버킷 · 프로필 칸이 비어 ③ 이 버킷 목록을 못 보면 `SY-05` 를 가릴 수 없다 — 그때는 `SY-06` 이 빈 이름을 댄다.

**받기 판정** — 받기 성공의 끝에 같은 멤버로 포인터 G+1(`origin: boot`, 펜스)을 낸다. 끝나는 옛 pod 가 그 뒤로 내는 게시는 「HEAD 그대로인가」 에서 멈춘다. **그래서 시작마다 세대가 하나 는다.**
그 세대는 저장이 아니라 Admin 「DB 동기화」 의 세대 줄과 사내 PC `status` 의 원격 줄(전송용 요약의 `원격 seq n` 칸도)이 번호 뒤에 `(시작 펜스)` 를 단다 — 받은 뒤 저장이
없었다는 뜻이고, 그때 「마지막 올림」 시각은 펜스를 낸 시각이다.

| 로컬 | 표시 | 원격 | 행동 |
|---|---|---|---|
| 없음 | — | 있음 | 받기 |
| 있음 | 변경 없음 · 세대 같음 | 있음 | 그대로 |
| 있음 | 변경 없음 · 세대 다름 | 있음 | 받기(옛 파일은 superseded) |
| 있음 | 변경 있음 · 세대 같음 | 있음 | 그대로 — 일꾼이 올린다 |
| 있음 | 변경 있음 · 세대 다름 | 있음 | 머문다(`diverged`) |
| 있음 | 세대 모름 | 있음 | 받기 — 컨테이너에서 세대 없는 DB 는 빈 저장소뿐이다(운영 서버는 내장 시드도 올리지 않는다) |
| — | — | 없음 | 머문다(`remote_empty`) — 이관 전. 이관이 끝나면 다음 시도가 받는다 |
| — | — | 갈라짐 | 머문다(`forked`) |

**저장 뒤**(일꾼 `capa-object-sync`): 첫 저장 뒤 쉬면 20초, 늦어도 60초에 올리기를 **시작**한다. 공식 발행 · 「지금 올리기」 는 바로다. 실패는 30 · 60 · 120 · 300초로 물러나고, 쉬는 동안 10분마다 HEAD 를 본다. 끝나는 시각은 전송 속도에
달렸다 — C-DEP 사내 관측 1회(사내 리뷰 202611131000)는 시뮬레이션 252.7MiB 올림 7.4초(약 34 MiB/s)라 두 DB 를 다 올려도 10초 안팎이다(9장).

**CI/CD 뒤 열어 둔 탭** — 다시 띄우는 동안은 맨 위 한국어 재시작 띠(임시 응답의 상태 — 「데이터 받는 중 · n번째 받기」 등)가 서고, 다시 붙으면 `GL-07` 의 전문 끝에 「마지막으로 정본에 올라간 저장 ○시 ○분」(받은 세대 멤버 스냅샷을 만든 시각 가운데 늦은 것, KST · 분 아래는 버림)이 선다 — 그보다 늦은 저장은 이 서버가 받은 정본에 없다. CI/CD 로 새 디스크에 선 서버면 사라졌고, 같은 디스크로 컨테이너만 다시 선 서버(위 표 「변경 있음 · 세대 같음」)면 로컬 DB 에 남아 일꾼이 곧 올린다. 같은 분 안의 저장은 이 줄로 가르지 못한다.

**CI/CD 앞 규칙** — 끌 때는 올릴 기회가 없다. Admin 「DB 동기화」 에 올릴 것이 남았으면 「지금 올리기」 를 누르고 끝날 때까지 기다린 뒤 CI/CD 를 누른다. 올리는 중에 들어온 저장은 다음 차례라 그 올리기가 끝나도 `올릴 것 있음` 이 남을 수 있다 — `올릴 것 없음` 을 보고 누른다.
「지금 올리기」 는 **접속 · 작업 감사 기록부터** 올린다 — 같은 칸의 「감사 미전송 n줄」 이 0 이 된 것도 함께 보고 누른다(아래 「감사 기록 접두사」).

**감사 기록 접두사 `audit/`**(통합인증이 켜진 서버만 — `docs/sso_setup.md` 7-1, 운영은 `docs/audit_log_operations.md`). 같은 일꾼이
같은 고리에서 한다(새 스레드 없음).

| 키 | 쓰는 쪽 | 때 |
|---|---|---|
| `audit/v1/seg/YYYY/MM/DD/<inst>__<첫 seq>-<끝 seq>.jsonl.gz` | 일꾼 — 로컬 스풀(`data/temp/audit/spool/`)의 아직 올리지 않은 줄 | 5분마다 또는 200줄, 「지금 올리기」 는 곧바로 |
| `audit/v1/daily/YYYY/MM/DD.p<n>.jsonl.gz` · `.p<n>.manifest.json` | 일꾼 — 최근 14일의 지난 UTC 날짜를 묶음(늦게 온 조각은 보충 판 p1, p2 …) | 시작 10분 뒤 · 이후 하루 한 번 |
| `audit/v1/tool/YYYY/MM/DD/<inst>__…` | 사내 PC 의 `sync_object_storage.py` `rollback` · `init` · `fetch-copy` · `prune`(명령마다 한 줄) | 명령 끝 |

- **새 객체로만 쓴다**(조건부 쓰기 `If-None-Match: *` — 지원이 확인되지 않은 버킷은 HEAD 로 없음을 본 뒤). 고치거나 지우지 않는다.
  줄마다 앞 줄의 해시를 잇고 manifest 는 앞 manifest 의 sha256 을 잇는다 — 고친 곳 · 빠진 날을 알아챌 수 있다(막지는 못한다).
- **세대 · 정리 · 되돌리기 밖이다** — `generations/` · `snapshots/` 와 따로 있고 하루 한 번 정리(위)와 `rollback` 은 `audit/` 를
  건드리지 않는다(접속 명단 `access/` · 모듈 `modules/` 와 같은 줄). 마이그레이션도 없어 앞 ZIP 으로 되돌려도 앱은 뜬다 — 그동안
  감사 기록만 빈다.
- 감사 올리기는 DB 올리기 판정 · `SY-03` 멈춤과 상관없이 돈다. 실패는 감사 쪽이 물러나 다시 하고(60 · 120 · 300초) DB 의
  `SY-02` 를 건드리지 않는다. 버킷에 보관되지 않는 동안(동기화 아님 · 30분 넘게 밀림 · 기록 못 한 줄 · 첫 조각의 시계 차이 60초)은
  관리자에게 `AD-12` 가 뜬다.
- 화면은 로컬 미러(`data/temp/audit/mirror/` — 400일까지)와 스풀만 읽는다. 스풀은 그 날짜의 일별 파일이 미러에 든 뒤에야 지운다.
- **권한 · 수명 규칙(저장소 관리자에게 요청할 것)** — `audit/` 에 만료 3년 + 30일의 수명 규칙을 건다. 앱 키에서 `audit/` 의
  지우기 권한을 빼면 가장 좋다(앱은 지우지 않는다). 버전 관리 · Object Lock(보존 모드)을 지원하면 꼬리 지우기 · 통째 갈아 끼우기까지
  막는다(10장 14).
- 사내 PC 에서 날짜 · 달의 조각 수만 볼 때는 `sync_object_storage.py --bucket $b audit-list --date today`(또는 `--month YYYY-MM`)
  — 사람 값 · 키는 찍지 않는다.

**정리**: 앱이 시작 10분 뒤 · 이후 하루 한 번 스스로 돈다(C-DEP 에는 셸이 없다). 남기는 것은 HEAD · 멤버 쌍이 다른 최신 5세대 · HEAD 시각 기준 7일 안 세대이고 그 세대가 가리키는 스냅샷이다. 나이는 저장소가 준 시각으로 잰다. 고아는 지키고, 저장을 막지 않는다. 지우는 동안 HEAD 가 움직이면(저장 · `rollback`) 그 자리에서 멈추고 다음 정리가 새 HEAD 로 다시 판정한다.

**볼 자리** — Admin 「서버 시작 점검」(aws 판 · ECS 연결 · 버킷 목록 · DB 받기 · 디스크 · pod · 메모리와 CPU 한도 · DuckDB 기본값 · `받기 n초 · 앱 응답까지 n초` · 앞 pod 마지막 올림과 이번 앱 준비 사이)과 「DB 동기화」(올릴 것 · 마지막 올림 · 세대 · 크기 · 실패 · 갈래).
알림은 `SY-01`(설정 오류) · `SY-02`(올라가지 못함) · `SY-03`(멈춤) · `SY-04`(정본을 넘긴 사본) · `SY-05`(버킷의 정본을 받지 않은 서버) · `SY-06`(빈 CD 환경변수로 정본을 점검하지 못한 서버 — 이름만)이다. 값에 주소 · 버킷 · 키가 없어 리뷰에 옮겨도 된다(pod 은 이름 끝 다섯 글자만 보인다).
짧은 글은 누구나 읽는 꼴이다 — `SY-05` 「정본이 아닌 데이터 — 여기 저장은 다음 배포에 사라집니다」, `SY-01` 「저장이 정본에 올라가지 않습니다」, 일반 사용자의 `SY-02` 「저장이 정본에 올라가지 못함 — 관리자에게 알려 주세요」 · `SY-03` 「올리기가 멈춤 — 관리자에게 알려 주세요」. 환경변수 칸 · CI/CD · 설정 파일 · 런북 지시와 갈래 낱말은 관리자 회차의 전문에만 있고(운영 서버가 아니고 통합인증이 꺼진 곳은 누구에게나, 통합인증이 꺼진 운영 서버는 아무에게도 — `SY-02` · `SY-03` 관리자 줄의 「그 화면으로」 는 Admin 「DB 동기화」, 일꾼이 없으면 「일꾼이 돌지 않음 — CI/CD 를 누르면 이 서버의 저장은 사라짐」 한 줄이 붙는다), `SY-06` 은 관리자 회차에만 선다. `SY-04` 전문 끝은 「최신 데이터를 보려면 사본을 다시 받습니다(런북)」 다(런북의 사본 받기 — 아래 `fetch-copy`). `SY-05` · `SY-01` 인 서버는 앱 머리 띠에 「정본 아님」 표지가 늘 서고 누르면 Alarm 의 그 줄이 열린다(저장은 막지 않는다).
「DB 동기화」 펼침 제목 끝에는 지금 CI/CD 를 눌러도 되는지 판정 배지 하나가 선다 — `CI/CD 눌러도 됨`(올릴 것 없음 · 초록) · `기다리세요`(올릴 것 있음 · 올리는 중 · 주황) · `누르면 저장 잃음`(실패 · 멈춤 · 일꾼 없음 · 빨강). 멈춤을 푸는 단추는 두지 않는다(명령으로만 — 7장). 「서버 시작 점검」 에 실패한 단계가 있으면(토큰 줄은 `AD-10` 몫) 관리자 회차의 모든 화면에 상태 알림 `AD-01` 「서버 시작 점검 실패 — <단계>」 가 서고 「그 화면으로」 가 Admin Area 를 연다 — 키만 넣은 서버 · `local` 서버의 버킷 연결 실패도 여기로 드러난다.

## 4. 이관 차례 (한 번)

사내 PC 앱이 정본이던 것을 운영 버킷으로 옮긴다. 지금 C-DEP 에 있는 저장은 버린다. 그 뒤 사내 PC 앱은 쓰지 않는다.

| 차례 | 누가 | 할 일 | 볼 것 |

| 1 | 사용자 | 환경변수 표에 키 둘 · `CAPA_S3_BUCKET` · 주소(`CAPA_S3_ENDPOINT_URL`) · 프로필 이름(`CAPA_S3_PROFILE`)을 넣고 CI/CD(`CAPA_S3_SYNC_MODE` 는 아직 비움 — 표가 빈 값을 받지 않으면 소문자 `local`) | Admin 「서버 시작 점검」 — aws 판 `1.46.3` · ECS `HTTP 403 닿음` · 버킷 목록 정상. 이미지의 pip 한 줄이 공개 미러로 받히는지가 여기서 답이 난다 |
| 2 | 사용자 | 사내 PC 앱을 끄고 별도 PowerShell 창에서 운영 버킷 이름을 그 창의 변수(`$b`)로 넣고 `doctor`(6장 1단계) — 원격 세대가 `비어 있음` 이 아니면 3 을 하지 않고 멈춘다(받기 모드를 켜면 C-DEP 가 그 옛 세대를 받는다). `doctor` 의 `버킷` 줄(가린 꼴 `앞 두 글자 … 뒤 두 글자 · n자`)을 1 의 `CAPA_S3_BUCKET` 값의 앞 두 글자 · 뒤 두 글자 · 글자 수와 대 본다. 그 창은 4 까지 닫지 않는다 | `doctor` 원격 세대 `비어 있음` · `버킷` 줄이 표 값과 맞음 |

**받기 모드를 먼저 켜고 정본을 올린다**(2026-11-12 사용자 답 — 런북 6-4 · 그 배포 7장과 같은 차례). `doctor` 는 받기 모드 앞이다 — 원격이
비어 있지 않은데 받기 모드를 켜면 C-DEP 가 그 옛 세대를 받는다. 3 과 4 사이 C-DEP 는 임시 화면에 머물러 쓸 수 없다(그동안 C-DEP 에서도 사내 PC
에서도 저장하지 않는다). `init` 을 받기 모드보다 먼저 하면 그 사이에 CI/CD 가 돌 때 빈 앱(「공식버전 없음」 — 운영 서버는 내장 시드를 올리지 않는다)이 뜨고 `SY-05` 가 알리며, 그 사이 C-DEP 저장은
다음 CI/CD 에 사라진다 — 그래서 이 차례로 한다. 4 뒤에도 임시 화면이 「데이터를 처음 올리는 중입니다」(「원격이 비어 있음」)에 머물면 다시 `init` 하기 전에 2 의 `버킷` 줄이 표 값과
앞뒤 글자 · 글자 수까지 맞았는지 먼저 본다(8장).

**공용 계정으로 옮길 때 버킷 권한을 좁힌다**(사내 할 일 — 2026-11-07 통합 검수 D6 (가)). 이 키가 닿는 곳을 운영 버킷 하나로 줄인다. 버킷 안의 지우기 권한은 뺄 수 없다 — 앱의 하루 한 번 정리(3장)가 지우고, 없으면 세대가 쌓인다. 좁힌 뒤 Admin 「서버 시작 점검」 의 버킷 목록 · 「DB 동기화」 · 「S3 명단」 줄이 그대로인지 보고 결과를 10장 13번에 적는다.

## 5. 사내 PC — 읽기는 사본으로

`init` 뒤 그 PC 는 쓰는 쪽이 아니다. 사이드카에 넘긴 표지(`handed_over_utc`)가 남아 `push` · `resolve --keep mine` · `adopt --source local` 이 거절되고 앱에는 `SY-04` 가 뜬다(그 PC 의 저장은 막지 않는다 — 정본에 닿지 않을 뿐이다). 운영 앱이 포인터를 낸 뒤(`origin` 이
`app` · `boot` · `rollback`)에는 표지가 없는 PC 도 같다. `--override-writer` 는 운영 앱의 저장을 덮을 수 있다.

```powershell
$b = Read-Host "C-DEP 표의 CAPA_S3_BUCKET 값"
```

```powershell
.\.venv\Scripts\python.exe scripts\sync_object_storage.py --bucket $b fetch-copy --to C:\capa-copy
.\.venv\Scripts\python.exe scripts\sync_object_storage.py --bucket $b fetch-copy --to C:\capa-copy --seq 12
```

`$b` 줄은 그 줄만 붙여 넣고 묻는 자리에 C-DEP 표의 값을 붙여 넣는다(6장 1단계). 둘째 줄의 `12` 는 보기다 — 받을 세대 번호로 바꾼다.

HEAD(또는 그 세대) 두 멤버를 받아 검증한 뒤에만 그 폴더에 두 DB 와 `generation.json` 을 둔다. `data/` 를 건드리지 않고 운영 DB 자리는 거절한다. 앱이 떠 있어도 된다. 런북의 점검 스크립트는 이 사본을 `--database` · `--equipment-database` 로 받는다(런북 6-4).

## 6. 사내 PC 준비 · 이관 명령

**0단계 — 사내 값 환경변수와 프로필(한 번만).** 주소 · 프로필 이름은 사내 값이라 저장소에 없다 — 스크립트는 사용자 환경변수에서만 읽고, 비었으면
aws 를 부르기 전에 `[중단] … 넣을 환경변수: …` 한 줄로 멈춘다. 별도 PowerShell 창에서 한 줄씩 넣고 **새 창을 연다**(넣은 창에는 아직 안 보인다).
값은 지금 쓰는 주소 · 프로필 이름 그대로다 — 손으로 치지 않고 출력을 붙여 넣는다. 프로필을 이미 만든 PC 는 이름이 `aws configure list-profiles` 에 보이는 그 이름,
주소가 `aws configure get endpoint_url --profile (Read-Host "프로필 이름")` 의 출력이다(아래 `profile` 블록이 그 프로필에 넣는다). 그 줄이 비면(프로필을 손으로 만든 PC) 주소는
2026-11-12 전 판의 `config/object_storage.json` `endpoint_url` 칸에만 있다 — 그 판을 덮기 전에 옮긴다. 버킷은 넣지 않는다 — 명령마다 `--bucket` 이다(아래 3단계 끝).
아래 두 줄은 **한 줄씩** 붙여 넣는다 — 줄마다 값을 묻고, 묻는 자리에 그 값을 붙여 넣는다(두 줄을 함께 붙이면 둘째 줄이 첫 값으로 들어간다).

```powershell
[Environment]::SetEnvironmentVariable("CAPA_S3_ENDPOINT_URL", (Read-Host "사내 S3 주소"), "User")
```

```powershell
[Environment]::SetEnvironmentVariable("CAPA_S3_PROFILE", (Read-Host "사내 aws 프로필 이름"), "User")
```

프로필을 아직 만들지 않은 PC 는 출력되는 블록을 그대로 붙여 넣는다. 손으로 옮겨 적지 않는다. 블록의 마지막 줄이 키 둘을 차례로 묻는다 — 묻는 자리에 실제 키를 붙여 넣는다.

```powershell
.\.venv\Scripts\python.exe scripts\sync_object_storage.py profile
```

- `s3.addressing_style path` — 버킷명에 대문자와 언더바가 있어 가상 호스트 스타일로는 표현할 수 없다. 없으면 서명 불일치나 DNS 오류가 난다.
- `request_checksum_calculation` / `response_checksum_validation` = `when_required` — AWS CLI 2.23.0 이상은 ECS 에서 `Missing required header for this request: Content-MD5` 로 실패한다(Dell KB 000299507). **이 오류를 방화벽 · 권한 문제로 오진하면 며칠을 태운다.**

**1단계 — 접속 확인.** `$env:` 는 이 창의 스크립트용이다. 이관 뒤 사내 PC 앱은 `managed` 로 띄우지 않는다. **운영 버킷 이름은 그 창의 변수(`$b`)로만 넣는다** —
PC 환경변수(`[Environment]::SetEnvironmentVariable` · `setx` · 시스템 환경 변수 편집)에 남기지 않는다(2026-11-12 사용자 답 — 사내 PC 에 운영 버킷이 남으면 쓰는 쪽이 둘이 될 수 있다).
`$b` 는 창을 닫으면 사라지고 그 창에서 띄우는 다른 프로그램에도 넘어가지 않는다 — 3단계까지 같은 창에서 친다(4장 2 ~ 4). `$b` 가 비었으면 PowerShell(사내 PC 의 5.1)이
그 자리를 빼 바로 뒤 낱말이 버킷 값으로 들어가고 `the following arguments are required: command`(`doctor` · `status` · `generations`) 또는
`argument command: invalid choice: …`(`init --note …` · `fetch-copy --to …` · `rollback --to …`) 꼴 오류(종료 2)로 멈춘다 — 아무것도 쓰지 않았다.
빈 글자를 그대로 넘기는 셸이면 `--bucket ""` 이 되어 `CAPA_S3_BUCKET` 환경변수로 넘어간다 — 사내 PC 에는 그 변수가 없으니 `[중단]` 으로 그 이름을 대며
멈춘다(넣어 두었으면 그 버킷으로 간다 — 넣지 않는 까닭이다). 어느 꼴이든 `$b` 줄부터 다시 친다.
값에 꺾쇠 · 공백 · 따옴표가 들면(자리표째 넣었거나 묻는 자리가 뒤에 붙은 줄을 먹은 값) 스크립트가 `aws` 를 부르기 전에
`[중단] 꺾쇠 · 공백 · 따옴표가 든 값이 있습니다 — --bucket. …` 꼴 한 줄로 멈춘다 — 대는 것은 값이 온 자리(인자 또는 환경변수 이름)이고 값은 찍지 않는다.
아무것도 쓰지 않았으니 그 값을 넣는 줄부터 다시 친다(주소 · 프로필이면 0단계).

```powershell
$env:CAPA_S3_SYNC_MODE = "managed"
$b = Read-Host "C-DEP 표의 CAPA_S3_BUCKET 값"
```

묻는 자리에 C-DEP 표의 값을 붙여 넣는다 — `$b` 줄을 펜스의 마지막 줄로 둔 까닭이다(뒤 줄을 함께 붙이면 그 줄이 값으로 들어간다). 같은 창에서 —

```powershell
.\.venv\Scripts\python.exe scripts\sync_object_storage.py --bucket $b doctor
```

모드 · 엔드포인트 · 버킷 · 프로필과 CLI 버전, 두 DB 의 원격 · 로컬 세대를 찍는다. **사내 값은 가려 찍는다** — 버킷은 `앞 두 글자 … 뒤 두 글자 · n자`(네 글자 이하면 `n자` 만),
엔드포인트 · 프로필은 `있음` · `없음` 뿐이고, `[중단]` 줄의 오류 첫 줄 · 「실행한 명령」 안의 값은 이름표 「주소」 · 「버킷」 · 「프로필」(꺾쇠로 감싼 꼴)로, 세대 줄 끝의 작성자는 이름표 「작성자」 로 바뀐다. 표준 오류도 같은 가림을 지난다 — 감사 조각을 못 올린 경고는 `감사 조각을 올리지 못했습니다 — <갈래 낱말>` 한 줄이고, 그 밖의 로거 글 · 잡지 못한 예외의 트레이스백 안 값도 이름표다. 원값을 보는 옵션은 없다 —
값은 C-DEP 표와 그 창의 변수에만 있다(`profile` 블록만 셸에 붙여 넣는 줄이라 주소 · 프로필 이름이 그대로 든다). 하위 명령마다(`profile` 밖) 출력 끝에 `전송용 요약: doctor 통과; 종료 0; CLI aws-cli/…; 원격 비어 있음; …` 꼴 한 줄이 붙는다 — 갈래 낱말 · 세대 번호 · 크기 · 초 · 종료 코드뿐이라 리뷰에는 이 줄만 옮긴다. 빈 값은 `없음` 으로 찍고 넣을 환경변수 이름을 대며 멈춘다(0단계). 통과는 종료 코드 0 · `[중단]` 줄 없음 · `CLI` 와 `원격 세대` 줄이 찍힘이다 — 주소 오타 · 없는 프로필 이름은 값 줄이 `있음` 이어도 `[중단] <까닭>` 으로 멈춘다. 원격이 비어 있는 것이 최초 상태의 정상이다. `mode` 는 이 스크립트에서 출력에만 쓰이고 어떤 하위 명령도 막지 않는다. `Content-MD5` 오류가 나면 0단계의 체크섬 설정이 안 먹은 것이다 — 그래도 나면 CLI 를 2.22.x 로 내린다.

**2단계 — 능력 측정.** 확인하지 못한 능력은 없는 것으로 본다. `_probe/` 아래에 임시 객체를 만들었다 지운다. 사내 값은 이미 파일에 있다(2026-11-06) — 저장소가 바뀌었을 때만 돌린다.

```powershell
$dev = Read-Host "개발 버킷 이름"
```

```powershell
.\.venv\Scripts\python.exe scripts\sync_object_storage.py --bucket $dev probe --write config\object_storage_capabilities.json
```

**3단계 — 최초 이관(앱을 끈 채로 · 1단계의 같은 창 — 4장 차례로는 받기 모드(4장 3)를 켠 뒤다).** `aws s3 cp` 가 아니라 `init` 이다. 치기 전에 1단계 `doctor` 를 다시 본다 — 원격 세대가 `비어 있음` 이 아니면 치지 않고 멈추고, `버킷` 줄을 C-DEP 표의 `CAPA_S3_BUCKET` 값의 앞 두 글자 · 뒤 두 글자 · 글자 수와 대 본다(다르면 `--bucket` 을 고쳐 1단계부터).

```powershell
.\.venv\Scripts\python.exe scripts\sync_object_storage.py --bucket $b init --note "최초 이관"
.\.venv\Scripts\python.exe scripts\sync_object_storage.py --bucket $b status
```

`init` 은 원격이 비어 있을 때만 동작하고 두 DB 를 함께 올린다. 이미 세대가 있으면 건너뛴다. 스냅샷을 만드는 과정이 곧 재구축이라 파일이 줄어든다. 넘기지 않고 시험할 때(개발 버킷)는 `init --keep-writer` 다.

`--bucket` · `--dry-run` 은 **하위 명령 앞에** 놓는다. 뒤에 붙이면 `unrecognized arguments` 로 죽는다. `--dry-run` 은 앞 회차가 남긴 포인터도 내지 않는다 — `앞 회차가 남긴 포인터` 줄이 뜨면 실제 실행이 마무리한다. 코드에 기본 버킷이 없다 — 운영이든 개발이든 `--bucket` 을 늘 적는다(빠지면 `CAPA_S3_BUCKET` 을 대며 멈춘다). 사내 PC 에 `CAPA_S3_BUCKET` 을 넣지 않는다 — 운영 버킷이 남으면 쓰는 쪽이 둘이 된다. 운영 버킷 이름은 명령을 치는 그 창의 `$b` 로만 둔다(1단계).

## 7. 세대 되돌리기

앱 결함으로 망가진 세대가 게시됐거나 원격이 갈라졌으면 앞 세대의 멤버로 새 HEAD 를 낸다. 지우지 않고 앞으로만 간다.

```powershell
$b = Read-Host "C-DEP 표의 CAPA_S3_BUCKET 값"
```

```powershell
.\.venv\Scripts\python.exe scripts\sync_object_storage.py --bucket $b generations
$g = Read-Host "이어 갈 세대 번호(seq)"
```

```powershell
.\.venv\Scripts\python.exe scripts\sync_object_storage.py --bucket $b rollback --to $g --yes
```

묻는 줄은 펜스의 마지막 줄이다 — 펜스 하나씩 붙여 넣고 묻는 자리에 값을 넣는다.

`generations` 는 세대 번호 · 두 멤버의 세대 · 키 꼬리 · 시각을 최신부터 찍는다(포인터 키에 실린 값이라 받지 않는다). **시작마다 같은 멤버의 펜스 세대가 쌓이므로 바로 앞 세대는 깨진 멤버를 그대로 가리킬 수 있다 — 멤버 세대가 HEAD 와 다른 앞 세대를 고른다.** `rollback` 은 멤버가 저장소에 있는지와 크기만 대조하고, 포인터를 낸 뒤 한 번 더 본다 — `새 HEAD 는 나갔지만` 으로 멈추면 그 HEAD 의 멤버가 사라진 것이라(보존 밖 세대를 정리가 지우는 틈) 다른 세대로 다시 `rollback` 한다. 같은 세대에 포인터가 둘이면 그 세대 줄의 키 꼬리 8자리를 `--token` 뒤에 붙여 고른다. 그 뒤 운영 앱의 일꾼은 HEAD 가 움직인 것을 보고 멈춘다(`SY-03`) — CI/CD 로 새 pod 가 그 세대를 받게 한다. **멈춘 pod 의 미반영 변경은 그 CI/CD 로 사라진다.**

## 8. 막혔을 때

임시 화면 접힌 「관리자용 진단」 첫 줄의 낱말과 Admin 의 갈래는 같은 말이다. 진단에는 그다음 줄에 경우별 할 일과 이름 · 수(비어 있는 환경변수 이름 · 필요 · 남은 MB · 멈춘 세대 · 바뀐 DB · DB 판 · 코드 판 — 값 · 주소 · 키 · 버킷 이름은 없다, 2026-11-14 결정 D9)가 서고 모르는 수는 줄을 뺀다 — 화면 바닥 참고 줄에는 그 갈래 키(`unreachable` 등)와 그 시각(UTC)이 선다. 「저장소에 닿지 못함 · 시간 초과 · 그 밖의 실패」 는 표지 「다시 시도」(이 셋이 끊김 없이 10분 넘게 이어지면 「계속되면 문의처에 알려 주세요」 — 앞서 「원격이 비어 있음」 · 사람이 고칠 갈래에 머문 시간은 세지 않는다)이고, 다시 받는 동안은 값 줄이 「n번째 받는 중 · 지난 시간」 으로 흐르며 첫 받기의 두 노트(몇 분 · CI/CD 를 다시 누르지 않기)가 선다. 「원격이 비어 있음」 은 「점검 중」 이다 — 관리자가 `init` 한 뒤의 다음 시도처럼 실제로 받는 동안은 그 화면도 같은 값 줄 · 두 노트다. 「스냅샷이 깨짐」 · 「원격이 갈라짐」 의 `rollback` 뒤도 같다(그 밖의 사람 갈래는 CI/CD 로 고치므로 「다시 확인하는 중」). 그 값 줄은 그 시도가 실제 내려받기로 넘어간 뒤부터이고, 그동안 열어 둔 탭의 재시작 띠도 「점검 중 · …」 대신 「데이터 받는 중 · n번째 받기」 다 — 받기로 넘어가기 전에 머무는 확인(`init` 전 늦어도 60초마다 · 원격이 갈라졌거나 포인터가 깨진 `rollback` 전 300초마다)은 받기가 아니라 「확인하는 중」 · 「다시 확인하는 중」 이다. 깨진 멤버(스냅샷이 없거나 크기 · 해시가 다름)는 받는 도중에 드러나므로 `rollback` 전에도 300초마다 실제로 받다가 다시 머문다 — 그동안은 받는 값 줄 · 띠다.

| 낱말 | 뜻 | 다시 봄 · 화면 | 할 일 |
|---|---|---|---|
| 원격이 비어 있음 | 이관 전 | 5 ~ 60초 · 「점검 중」 데이터를 처음 올리는 중 | 먼저 4장 2 의 `doctor` 버킷 줄이 C-DEP 표 값과 앞뒤 글자 · 글자 수까지 맞았는지 본다 — 다른 버킷에 `init` 했으면 그 버킷에 다시 해도 풀리지 않는다. 같으면 4장 4 의 `init` — 다음 시도가 스스로 받는다 |
| 설정 오류 | `CAPA_S3_BUCKET` · `CAPA_S3_ENDPOINT_URL` · `CAPA_S3_PROFILE` · 키 없음(컨테이너 출력 줄 · Admin 줄 · 임시 화면 진단 「비어 있는 환경변수」 가 이름을 댄다), 설정 파일 깨짐, `~/.aws` 를 못 써 프로필 없음(`HOME`) | 300초 · 「점검 중」 서버 설정 | 환경변수 표를 고치고 CI/CD. 표가 맞는데 그대로면 `HOME` 자리에 쓸 수 있는지 담당에 묻는다(임시 화면에 머무는 동안은 Admin 이 없다) |
| aws 명령 없음 | 이미지에 `aws` 가 없다 | 300초 · 「점검 중」 서버 설정 | `docker/Dockerfile-prod` 한 줄 · PATH — 사외 요청 |
| 저장소가 거절 | 키 · 권한 | 300초 · 「점검 중」 서버 설정 | 키를 고치고 CI/CD |
| 버킷 없음 | 버킷 이름 | 300초 · 「점검 중」 서버 설정 | 이름을 고치고 CI/CD |
| 저장소에 닿지 못함 · 시간 초과 | 망 · 저장소. 받는 도중 연결이 끊긴 것도 여기다 | 5 ~ 60초 · 「다시 시도」 | 저절로 다시 시도한다 |
| 디스크 부족 | `/project` 자리. 받는 도중 찬 것도 여기다 | 300초 · 「점검 중」 디스크(진단 「필요 n MB · 남음 m MB」 — 받기 전 점검일 때만) | 앞 배포의 「서버 시작 점검」 디스크 값을 보고 담당에 묻는다 |
| 스냅샷이 깨짐 | 받은 파일이 검증에 실패했거나 HEAD 의 스냅샷이 저장소에 없다 | 300초 · 「점검 중」 되돌리기(진단 「멈춘 세대 n」) — 되돌리면 다음 시도가 저절로 받는다 | 사내 PC `generations` 로 멤버 세대가 다른 앞 세대를 골라 `rollback`(7장) |
| 원격이 갈라짐 | 같은 세대에 포인터가 둘 | 300초 · 「점검 중」 되돌리기(진단 「멈춘 세대 n」) | `rollback` 으로 이어 갈 세대를 고른다 |
| 원격과 어긋남 | pod 의 미반영 변경이 있는데 세대가 다르다 | 300초 · 「점검 중」 정본과 다름(진단 「바뀐 DB」) | CI/CD — 디스크가 비어 풀린다. 그 변경은 사라진다 |
| DB 판이 코드보다 새로움 | 마이그레이션이 든 배포를 앞으로 되돌렸다 | 300초 · 「점검 중」 앱 판이 오래됨(남은 초 없음 · 진단 「<DB> 판 n · 코드 판 m」) | 최신을 다시 CI/CD |
| 그 밖의 실패 | 위에 없는 실패(저장소의 5xx 등) | 5 ~ 60초 · 「다시 시도」 | 저절로 다시 시도한다. 오래 가면 사내 PC 에서 `doctor` 를 돌려 원문(사내 값은 이름표로 바뀐 꼴)을 본다 |
| 동기화 일꾼이 돌지 않음 | 앱은 떴는데 올리는 일꾼이 없다(부트 기록 없음 · 일꾼 시작 실패 · 고리가 180초 넘게 멈춤 · 회차가 제한 시간을 넘김) — `SY-02`, 「DB 동기화」 판정 `누르면 저장 잃음` | 임시 화면이 아니라 앱 화면 — 알림 `SY-02` · 「DB 동기화」 판정 | 그대로 CI/CD 를 누르면 이 서버의 저장은 사라진다. 「서버 시작 점검」 의 DB 받기 줄과 부트 기록을 보고, 남길 저장이 없으면 CI/CD 로 다시 띄운다 |

**임시 화면은 HTTP 200 이라 CI/CD 는 성공으로 보인다.** CI/CD 뒤에는 앱을 열어 본다.

| 스크립트 출력 | 뜻 | 할 일 |
|---|---|---|
| `Missing required header ... Content-MD5` | CLI 2.23+ × ECS 비호환 | 6장 0단계 체크섬 설정 확인 → 안 되면 CLI 2.22.x |
| `[건너뜀] … 어느 세대에서 왔는지 모릅니다` | 로컬 DB 가 어느 세대에서 왔는지 모름 | `adopt --source local` 또는 `pull --force` |
| `[중단] … 원격이 먼저 앞섰습니다` | 남이 먼저 저장 | `resolve --keep mine` 또는 `--keep remote`. `--keep remote` 는 앱을 끄고 돌리고 변경 표시도 내린다 — 이어 `pull` 로 받으면 옛 파일은 백업으로 물러난다. 승격은 멤버가 저장소에 있는지 먼저 보고, 내 세대가 만들지 않은 멤버는 HEAD 값으로 적는다 — 그러면 `[주의]` 가 뜨고 `pull` 로 받는다 |
| `판정 : 정본은 운영 앱에 있습니다` | 정본을 넘긴 PC 의 평상 상태(시작마다 세대가 는다) | 할 일 없음. 읽을 때는 `fetch-copy` |
| `[중단] … 갈라졌습니다` | 같은 세대에 포인터가 둘 | 양쪽 파일 모두 남아 있다. `rollback` 으로 이어 갈 세대를 고른다 |
| `[중단] 판정 뒤 HEAD 가 움직였습니다` | 손으로 돌린 `prune` 이 지우는 사이 저장 · `rollback` 이 들어옴 | 다시 돌린다 — 새 HEAD 로 다시 판정한다 |
| `[중단] 이 PC 는 … 정본을 넘겼습니다` | `init` 뒤의 쓰기 | 정본은 운영 앱이 쓴다. 읽을 때는 `fetch-copy` |
| `IOException` 류 | 앱이 DB 파일을 잡고 있음 | 앱을 끄고 다시 실행 |
| `[중단] 꺾쇠 · 공백 · 따옴표가 든 값이 있습니다 — …` | 그 자리의 값을 자리표째 넣었거나 다음 줄까지 붙여 넣었다(`aws` 를 부르지 않았다) | 댄 자리의 값을 넣는 줄부터 다시(6장 0 · 1단계) |

**올라간 스냅샷은 정리(3장) 밖에서는 지워지지 않는다.** 경합에서 지면 고아 스냅샷으로 남고 `--dry-run prune` 의 「지킨 고아 n」 이 수를 보여 준다. `prune` 은 고아를 기본으로 지키고, 같은 세대 번호의 스냅샷이 둘 이상이면 어느 쪽이 참조인지 목록으로 모르므로 둘 다 지킨다(재시도의 찌꺼기도 함께 남는다). 손으로 돌릴 때는 `prune --keep-last 5 --keep-days 7` 이다.

## 9. 잰 수

**사내 측정** — 2026-09-09 push 66초 · pull 50초. 시뮬레이션 62.6 → 42.8 MiB(스냅샷 생성 2.88초), 설비 0.4 → 0.4 MiB(0.06초). 전송은 양방향 모두 대략 1 MiB/s. 앱 최고 메모리 747MB(사내 PC 실데이터).

**2026-11-07 사용자 값** — 사내 두 DB 합 약 300MB. 위 1 MiB/s 로 계산하면 전체 받기 · 올리기가 각 약 5분이고, 올리기 중의 저장은 다음 차례라 잃을 수 있는 구간은 최대 약 10분이다(모두 계산값). 1 MiB/s 는 사내 PC 값이고, 압축 복사는 크기를 줄일 수 있다(앱 안 복사는 압축이 없다).

**C-DEP 사내 관측**(1회 — 사내 리뷰 202611131000, 이관 직후). 두 DB 받기(약 331MiB) 9.6 · 9.4초, 앱이 올린 시뮬레이션 252.7MiB 7.4초 — 양방향 약 34 MiB/s 로 사내 PC 값의 30배 남짓이다. CI/CD 뒤 앱 응답까지 42초(「서버 시작 점검」 의 `받기 n초 · 앱 응답까지 n초` — 같은 리뷰의 다른 값 320초 · 666초는 사람이 기다린 시간이 든 값이라 성능 값이 아니다). 이 속도로 다시 셈하면 전체 받기 · 올리기가 각 10초 안팎이라 끌 때 잃을 수 있는 구간은 모으기(늦어도 60초)에 그 몇 초를 더한 정도다(계산값). 그때 한도는 메모리 1.0GiB · CPU 2.4(코어 32), DuckDB 기본값 `memory_limit` 819.1MiB · `threads` 3 이다 — 메모리는 그대로라 아래 1GiB 예산 · 안전 인원 셈도 그대로다.

**샘플 관측**(합성 DB · 기계 32코어 WSL · 실제 `aws` 1.46.3 · 루프백 가짜 S3 — 실데이터 · 사내 망이 아니다).

**동시 접속 메모리 — 샘플 관측**(2026-11-07, 합성 표본 · 기계 32코어 WSL · 메모리 제한 없음 · `app.py` — 사내 실데이터가 아니고 실제 cgroup 도 아니다). 표는 프로세스 메모리 안정 / 최고 MiB, ×n 은 표본 규모 배수다(×1 리비전 하나 약 4.6만 행). 사내 규모는 ×2 ~ ×3 사이로 본다 — 지난 리뷰 값에서 고른 추측이다.

| 세션 | ×1 | ×2 | ×3 |
|---|---|---|---|
| 빈 서버 | 67 | 67 | 67 |
| 1 | 315 / 355 | 371 / 417 | 413 / 464 |
| 3 | 445 / 480 | 605 / 639 | 735 / 784 |
| 5 | 582 / 660 | 850 / 970 | 1,056 / 1,268 |

메모리는 DB 파일 크기가 아니라 **리비전 크기와 세션 수**로 정해진다 — 같은 ×1 표본 5세션에서 DB 46MiB 와 312MiB 가 579 / 654 · 582 / 660 으로 차이가 없다. 본체는 세션마다 든 리비전 표 문자열 칸이다. **열어 둔 탭 수가 접속자 수다** — 탭을 닫아도 바로 줄지 않는다(끊긴 세션을 2분 두고 다음 접근 때 지운다). 시나리오를 바꿔 가며 쓰면 캐시까지 차서 ×2 3세션 859 / 1,093 · ×3 3세션 1,157 / 1,472 까지 간다.

사내 규모 추정(계산값 — 앱에 쓸 수 있는 예산 942MiB = 1,024 − `aws` 57 − 바이트 복사 25): 1GiB 에서 **시나리오를 바꿔 가며 쓰면 안전 인원 2 ~ 3명, 공식만 보면 5명 이상**이다. 그 이상을 쓰려면 **2GiB 이상 증설을 권한다.** 못 잰 것은 사내 실데이터 · 실제 cgroup · OOM 순간 · `capa_server.py` · 동기화 일꾼 · BDQ 등록 · 자동 갱신 · 리비전 저장 · 공정 69 규모 표 · 장시간 운전이다.

**못 잰 것** — 실제 cgroup, 빈 컨테이너 첫 시작, overlay 복사 시간, 사내 망 전송, 운영 코어 수, C-DEP 검사 간격, 옛 pod 가 죽는 때. 앞의 다섯은 Admin 값이 알려 준다(한도 · 전송 · 코어 수는 위 C-DEP 사내 관측이 1회 답했다). 바이트 복사의 일관성은 DuckDB 내부 동작에 기대고 샘플 겹침 시험 694회는 증명이 아니다 — DuckDB 판을 올릴 때 겹침 시험을 다시 돈다.

## 하지 않은 것

- **코어의 모듈 데이터 동기화.** 코어는 `data/modules/<id>/` 를 대신 올리고 받지 않는다 — 코어가 모듈 파일 꼴을 몰라 일관된 한 벌을 뜰 수 없다
  (2026-11-07 통합 검수 C4 확정, 그 까닭 그대로). 그래서 그 자리는 CI/CD 마다 사라지는 것이 지금과 같고, 남겨야 하는 파일은 **모듈이 스스로**
  창구 도우미 `s3_upload` · `s3_download` 로 버킷의 `modules/<id>/` 아래에 올리고 받는다 — 언제 올리고 받을지도 모듈이 정한다(2026-11-12 사용자 결정
  「도우미 함수로」, `docs/module_guide.md` 3-10). 하루 한 번 정리(3장)는 `modules/` 를 건드리지 않는다.
- **올리기 멈춤을 푸는 Admin 단추.** 명령으로만 푼다(2026-11-07 통합 검수 C3 확정).
- **못 올라간 저장의 흔적.** 끌 때 잃은 저장을 새 서버는 모른다 — 간격 값만 보인다(2026-11-07 통합 검수 D5 (가)).
- **올리기를 앱에서 떼기.** 앱이 키를 받는 구조를 둔다(2026-11-07 통합 검수 D6 (가)).
- **개발 서버 읽기 전용 화면.** 다운 시간 값을 보고 정한다(`docs/TODO.md` 「S3 분리」).
