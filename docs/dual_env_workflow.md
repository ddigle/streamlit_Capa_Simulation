# 사내·사외 두 환경 운영 절차

이 저장소는 **두 곳에서 열린다**. 사외(개발 PC)와 사내(WebIDE). 양쪽 모두 Claude Code 를
쓰지만 **역할이 다르고, 코드를 고칠 수 있는 곳은 한 곳뿐이다.**
사외 개발 자리는 데스크탑 WSL(Ubuntu) 하나다(2026-10-13 사용자 결정) — 개발 명령은 bash 이고
`docs/wsl_dev_environment.md` 에 있다. 사내 명령은 그대로 PowerShell 이다.

지금 어느 쪽인지는 원격 주소로 가른다.

```powershell
git remote -v      # github.com 이면 사외, 사내 GitHub 주소면 사내
```

---

## 0. 원칙 — 정본이 둘로 갈리지 않게

| | 정본이 있는 곳 |
|---|---|
| **코드** | 사외 (`origin/main`) |
| **데이터** | 사내 (S3 스냅샷 · `data/` 실데이터) |

이 선을 흐리지 않는 것이 이 문서의 전부다. 사내 DuckDB 를 밖으로 가져오지 않듯,
**사내에서 만든 코드는 정본이 되지 않는다.**

작성자를 한쪽으로 몰아 둔 것은 취향이 아니라 설계다. 양쪽이 같은 파일을 고치기 시작하면
합칠 방법이 없다 — 두 저장소는 서로의 원격을 볼 수 없다.

## 1. 역할 분담

| | 사외 (개발 PC) | 사내 (WebIDE) |
|---|---|---|
| **하는 일** | 구현 · 리팩토링 · 테스트 작성 · 문서 | 진단 · 재현 · 검증 |
| **왜 거기서** | 사용량 여유, 합성 데이터로 충분 | **실데이터가 여기에만 있다** |
| **산출물** | 커밋 · 배포 ZIP | `review/` 아래 md |

사내 에이전트가 제일 잘할 수 있는 일은 **밖에서 못 하는 일**이다 — 실데이터로 돌려 보고,
오류 원문을 읽고, 실제 값의 분포를 확인하고, 재현 조건을 좁히는 것. 「고쳐라」가 아니라
**「무엇을 왜 고쳐야 하는지 밖이 재현할 수 있게 적어라」** 가 사내의 일이다.

### 사내 에이전트가 지킬 것 (하드 룰)

- **소스를 고치지 않는다.** `app.py`·`app_pages/`·`src/`·`tests/`·`scripts/`·`config/` ·
  루트 문서 — 어느 것도 편집하지 않는다. 예외는 **사용자가 직접 지시한 임시 수정** 하나다(2026-10-10 사용자 결정) —
  커밋하지 않고, 리뷰에 「임시 수정 있음 · 파일 N개 · 경로」 한 줄을 남기고, 다음 적용 전에 되돌린다(런북 0장 · 1-5).
  임시 수정은 정본이 아니다 — 계속 필요하면 리뷰의 「사외 요청」으로 낸다.
- **쓸 수 있는 곳은 `review/` 뿐이다.** 사내 커밋은 `deploy:`(적용기)와 `review:` 둘뿐이다(런북 1-6).
- **사용자 앱을 끄지 않는다** — 꺼 달라고 요청한다. 권한 판단이 막은 명령은 되풀이하지 않고 사용자에게 `!` 한 줄을
  준다(런북 1-1 · 6장).
- **사내 운영 규칙의 정본은 런북이다.** 에이전트 메모리에만 있는 규칙은 환경을 옮기면 사라진다 — 리뷰의
  「사외 요청」으로 내 런북에 들어가게 한다.
- 배포 적용은 **손으로 하지 않고 스크립트를 실행**한다(§3).
- 대조에서 나온 **정체불명 파일을 스스로 지우지 않는다.** 사용자에게 묻고 고른 대로 한다.
- 고쳐야 할 것은 **코드가 아니라 문서로** 낸다. 제안 코드는 md 안 코드블록에 적는다 —
  그것은 저장소 수정이 아니다.

## 2. 절차

| 단계 | 어디서 | 무엇을 | 사람이 하는 일 |
|---|---|---|---|
| 1 | 사외 | 개발 · 커밋 | — |
| 2 | 사외 | 배포 ZIP 생성 · 서피스로 전달(WSL Claude) | **메일 발송** — 서피스 Outlook 에서 |
| 3 | 사내 | ZIP 적용 → `deploy:` 커밋 | **ZIP 내려받기만** |
| 3-1 | 사내 | 목록 대조 → 정체불명 파일 처리 | **정체불명 파일의 방향 결정** |
| 4 | 사내 | 실데이터로 조사 | — |
| 5 | 사내 | `review/` md 작성 → 커밋 | **푸시** (에이전트는 막혀 있다) |
| 6 | 사외 | md 를 근거로 다음 개발 | md 를 사외로 옮겨 전달 |

사람이 개입하는 곳은 **2번의 메일 발송**, **3번의 ZIP 내려받기**, **5번의 푸시**, 그리고
**6번의 md 전달** 네 군데다. 5번이 사람 몫인 것은 `internal_claude_settings.json` 이
`Bash(git push*)` 를 막아 두었기 때문이다 — 사내 에이전트가 원격을 건드리지 못하게 한 것이
설계이므로 그대로 둔다. 에이전트가 직접 올리게 하려면 그 한 줄을 사외에서 빼는 결정이
따로 필요하다. 3-1 은 스크립트가 목록을 내밀고 사내 에이전트가 물어 오면 고르기만 하면 된다.
6번은 md 를 대화창에 그대로 붙여넣으면 된다 — 그래서 리뷰 md 는
**그 자체로 완결**돼야 한다(§4).

### 2-1. 배포 ZIP 만들기 (사외, 2단계)

사외 빌드 자리는 데스크탑 WSL 이다. ZIP 은 WSL Claude 가 만들어 서피스의 받는 자리로 넘기고, 메일은 사용자가 서피스에서
보낸다 — 흉내 저장소로 런북 수치를 재는 법, ZIP 자리(`~/projects/Deploy/`), 확인과 전달까지 `docs/wsl_dev_environment.md` 5장.

```bash
git push origin main                                   # 런북 7장을 채워 커밋한 뒤
.venv/bin/python scripts/build_deploy_package.py --out ~/projects/Deploy --stamp <STAMP>
git push origin deploy/<STAMP>                         # ZIP 을 확인한 뒤
```

`--out` 과 `--stamp` 를 준다 — `--stamp` 는 런북 7장 머리에 적은 stamp 와 같아야 하고, 다르거나 빠지면(빠지면 지금 분)
빌더가 멈춘다. 파일 이름은 `<stamp>.zip` 이고, 스크립트가 같은 이름의 태그 `deploy/<stamp>` 를 HEAD 에 남긴다. **그 태그를
올리지 않으면 다음 배포가 「직전 배포 이후 무엇이 바뀌었나」를 구하지 못한다** — 송장의 `changes` 가 빈 채로 나가고 사내는
변경 규모를 알 수 없다. 그래서 태그 푸시가 배포의 일부다. ZIP 을 확인한 뒤 서피스로 넘기기 전에 그 태그 하나만 올린다 —
`--tags` 는 남은 시험 태그까지 올린다.

다른 인자: `--list-only`(ZIP·태그 없이 목록만, `--out` 불필요), `--no-tag`(시험 삼아 만들 때만).

**빌드 전에 커밋하고 `main` 을 푸시한다 — 빌더가 확인한다.** 목록은 `git ls-files` 에서 오고 내용은 작업 트리에서 읽으므로
커밋하지 않은 수정은 실리되 송장의 커밋(HEAD)과 어긋나고, 푸시하지 않은 커밋은 사내 리뷰가 부를 때 원격에 없다. 그래서
빌더는 추적 파일에 커밋하지 않은 수정이 있거나 HEAD 가 `origin/main` 과 다르면 ZIP 도 태그도 만들지 않고 멈춘다(`--no-tag`
시험 빌드는 알리기만 한다). 추적하지 않는 새 파일은 ZIP 에서 빠지므로 막지 않고 `알림` 으로 찍는다 — 실을 파일이면 커밋한다.

## 3. 배포 적용 (3단계)

> 사내에서 실제로 치는 명령을 순서대로 적은 것은 **`docs/internal_update_runbook.md`** 다.
> 이 절은 적용기가 무엇을 왜 하는지를 적는다.

**덮어쓰기가 아니라 「지우고 풀기」다.** 덮어쓰기는 파일을 더하고 바꿀 뿐 **지우지 않는다.**
사외에서 지운 모듈이 사내에 남으면, 트리를 훑는 검사(`test_documentation_inventory` ·
`test_source_metadata`)가 **사내에서만** 깨진다. 그러면 사내가 그것을 진짜 결함으로 보고
리뷰에 적고, 사외에서는 재현되지 않는다.

```powershell
uv run --no-sync python scripts/apply_deploy_package.py <내려받은 ZIP 경로>
```

이 스크립트가 하는 일:

1. ZIP 과 송장을 검사한다 — 형식, 저장소 밖을 가리키는 경로, 대소문자만 다른 중복,
   사내 전용 자리를 덮으려는 항목.
2. `.deploy/applied.json` 의 적용 이력과 대조해 **순서를 본다.** 이미 적용한 ZIP 이거나
   과거 ZIP 이면 멈추고, 건너뛴 배포가 있으면 알리고 계속한다.

   > 커밋 조상 관계는 보지 않는다 — **두 저장소는 히스토리가 서로 달라** 사내에서 사외
   > 커밋의 조상 여부를 판정할 방법이 없다. 그래서 무엇을 어디까지 적용했는지 사내가
   > 스스로 적어 둔다.
3. 무엇을 지우고 무엇을 풀지 **먼저 보여 준다.** 목록 대조(3-1)도 여기서 함께 나온다.
4. 작업트리가 깨끗한지 확인한다 — **더러우면 멈춘다**(미저장 변경을 지우지 않기 위해).
   `--dry-run` · `--reconcile-only` 는 아무것도 바꾸지 않으므로 이 검사를 받지 않는다.
5. 추적 파일을 지우고 ZIP 을 푼다. `review/` · `.deploy/` · `.claude/` 는 남긴다.
6. 매니페스트의 해시로 **전 파일을 대조**한다.
7. `deploy: <stamp>` 로 커밋하고 `.deploy/applied.json` 을 갱신한다.

**처음에는 `--dry-run` 을 먼저 돌린다.** 「지움」 목록에 뜻밖의 것이 있으면 거기서 멈춘다.

`--no-commit` 도 있다. 파일은 적용하고 `.deploy/applied.json` 도 갱신하지만 커밋만 하지
않는다 — **적용 이력은 이미 갱신되므로 같은 ZIP 을 다시 돌릴 수 없다.** 커밋을 손으로 나누고
싶을 때만 쓰고, 그 경우 반드시 그 자리에서 `deploy:` 로 커밋한다.

> **`git clean` 에 `-x` 를 붙이지 않는다.** `-x` 는 gitignore 된 파일까지 지우고, 거기에는
> **사내 DuckDB 와 `data/input` 실데이터**가 들어 있다. 한 글자 차이로 사내 데이터가 날아간다.
> 스크립트는 `-x` 없이 돌며, 손으로 할 때도 마찬가지다.

> **운영 데이터는 추적 중이어도 지우지 않는다.** 지울 대상을 `git ls-files` 로 고르는 것은
> *운영 데이터가 무시 목록에 걸려 있다* 는 전제 위에 있다. 사내에서 그 규칙이 지워졌거나
> 파일이 먼저 커밋되면 전제가 깨지고 DuckDB 가 「사외에서 없어진 파일」로 판정된다.
> 그래서 `is_protected` 가 경로만 보고 한 번 더 막고, **추적되고 있다는 사실 자체를**
> 계획 출력이 `git rm --cached` 와 함께 알린다. 그 줄이 보이면 아래 8장으로 간다.

**사내에서는 `uv run` 에 반드시 `--no-sync` 를 붙인다.** 맨 `uv run` 은 돌기 전에 락을 다시
잡고 빠진 것을 설치한다. `--no-sync` 는 그 일이 아예 일어나지 않게 못박는 안전장치다.

> **지우는 것은 맨 `uv sync` 다. 맨 `uv run` 은 지우지 않는다.** 예전에 이 문서를 포함해 네
> 곳이 "맨 `uv run` 이 `bigdataquery` 를 지운다"고 적고 있었는데, 사내가 WebIDE 에서 반증했고
> 사외에서도 같은 uv(0.12.13)로 재현했다 — 락에 없는 패키지를 넣어 두고 맨 `uv run` 을 돌려도
> 남아 있고, `pyproject` 를 고쳐 락을 낡게 만든 뒤에도 넣기만 한다. 맨 `uv sync` 만
> `Uninstalled 1 package` 를 찍는다. `--no-sync` 를 계속 쓰는 결론은 그대로다.

**변경 목록에 `pyproject.toml` 이나 `uv.lock` 이 있으면 적용 뒤에 동기화한다.**

```powershell
uv sync --inexact
```

**맨 `uv sync` 를 쓰지 않는다.** 락에 없는 `bigdataquery` 를 지운다 — 사내 전용 패키지라
락에 들어갈 수 없다(README 4단계). 지워졌으면 `uv pip install -r requirements-company.txt`
로 되돌린다.

커밋은 **둘로 나눈다** — 3단계에서 `deploy:`(받은 것 그대로), 5단계에서 `review:`(판단한 것).
「무엇을 받았나」와 「무엇을 알아냈나」가 갈려야 나중에 되짚을 수 있다.

### 3-1. 목록 대조 — 사내에만 있는 파일 정리

적용 전후로 **송장의 파일 목록과 사내 폴더를 맞대어** 세 갈래로 가른다. 목록은 사외 기준의
정본이다.

| 갈래 | 무엇인가 | 스크립트가 하는 일 |
|---|---|---|
| 사외에서 지워짐 | 추적되는데 목록에 없다 | 적용이 함께 지운다 |
| **정체불명** | 추적도 무시도 되지 않는데 목록에 없다 | **손대지 않는다.** 보고만 한다 |
| 목록에만 있음 | 목록에 있는데 사내에 없다 | 적용 전이면 정상, 적용 뒤면 이상 |

가운데 칸이 이 대조의 이유다. 그동안 적용기는 `git ls-files` 만 보아 **사내에만 생긴 파일이
보이지 않았다.** 옛 배포의 잔해든 누가 받아 둔 산출물이든 조용히 쌓이고, 읽는 쪽은 그것이
살아 있는 코드인지 알 수 없어 일단 읽는다 — 사내는 쓸 수 있는 양이 적어 그 탐색이 먼저
비용이 된다.

**사내 에이전트는 이 목록을 보고 사용자에게 묻는다.** 스크립트는 판단하지 않는다 — 무엇인지
모르는 채 지우는 것이 가장 위험하기 때문이다. 파일마다 셋 중 하나를 고른다.

1. **사내에서만 쓰는 것** → 그대로 두고, `.gitignore` 에 넣을지 함께 정한다
2. **사외에도 있어야 하는 것** → 리뷰 문서에 적어 사외가 추가하게 한다
3. **옛 배포의 잔해** → 지운다

판단이 서지 않으면 (1)로 두고 리뷰 문서에 남긴다. 지우는 것은 되돌릴 수 없고, 남기는 것은
다음 배포에서 다시 물으면 된다.

적용하지 않고 대조만 보려면:

```powershell
uv run --no-sync python scripts/apply_deploy_package.py <ZIP> --reconcile-only
```

작업 중에도 돌릴 수 있다 — 아무것도 바꾸지 않으므로 깨끗한 작업트리를 요구하지 않는다.

## 4. 리뷰 문서 (5단계)

경로는 `review/<ZIP 파일명>.md` — 예: `review/202609161506.md`. 이름만으로 어느 배포를 본
리뷰인지 확정된다. **`review/` 는 사내에만 있는 폴더다.** 사외에 만들면 ZIP 에 실려
되돌아와 사내 기록을 덮는다.

### 실데이터를 적지 않는다

이 문서는 **사내에서 사외로 나가는 유일한 것**이다. 그런데 성격상 실데이터로 채워지기 쉽다 —
실제 Pack Code, 공정명, 호기 ID, 로그 원문. `CLAUDE.md` 가 코드에 금지한 바로 그 값들이
검사 없이 나가게 된다.

**값의 「꼴」은 남기고 식별자는 가명으로 쓴다.** 표기 형식 자체가 논점일 때만 그 형식을 남긴다.

- 좋음 — 「`Pack Code` 에 `4.00E+02` 꼴(지수 표기)인 값이 2종, 5행」
- 나쁨 — 실제 Pack Code 값을 그대로 적는 것

### 적는 꼴

사외는 리뷰를 표와 수로 읽는다(2026-10-10 사내 요청으로 정본화 — 사내 적용 다섯 번에서 굳은 꼴).

- **값으로 적는다** — 수 · 있음/없음 · 같음/다름 · 「미기록 — 까닭」. 서술·반복·런북 인용은 뺀다.
- **머리 둘째 줄에 「B 손 확인 n/N 기록」** — 런북 7장 B(손 확인)는 칸마다 값 또는 「미기록 — 까닭」이다(런북 5장). 칸은 B 의 번호
  항목 하나이고, 항목 안 값을 하나라도 적었으면 n 에 센다.
- **확인자를 가른다** — 에이전트가 본 것과 사용자가 눈으로 본 것.
- 7-8 값이 기대와 다르면 대개 사내 사용자의 저장이다 — 저장 시각과 확인 시각을 견줘 가리고 「사내 데이터 변화」 절에
  「결함 아님」과 수만 적는다.
- 8장 블록은 제목(`### 8-x.`)을 지키고, 직전 리뷰와 수가 하나도 다르지 않은 블록은 「<stamp> 리뷰와 같음」 한 줄로 줄인다.
  BigDataQuery 앞머리의 서비스 공지(사람 이름)는 옮기지 않는다.
- 커밋 전에 런북 5장의 자가 점검을 돌린다.

### 양식

```markdown
<ZIP stamp>

- B 손 확인 <n>/<N> 기록                     ← 머리 둘째 줄. 런북 5장 — 칸 = 7장 B 번호 항목, n 은 값을 하나라도 적은 항목 수
- 적용 전 stamp <…> · <사외 커밋 7자> · <N/N> 해시 일치 · 지움 <N> · 사내에 없는 파일 <N> · 마이그레이션 <걸린 번호>
- <적용 먼저, 확인은 YYYY-MM-DD>            ← 런북 0-1 의 그 꼴일 때만
- 관문: ruff format(<N>)·ruff check·mypy(<N>)·pytest — <통과 / 실패 — 까닭> (건너뜀 <N> — 까닭)
- 실데이터 식별값 포함 없음 : 확인함 ☐

## 7-<x> 화면 확인 (<에이전트 · 헤드리스 Chrome / 사용자>)

    <check_deploy_screens.py 의 --output 블록(머리 세 줄 + 표)을 고치지 않고 붙인다 — 런북 6-2>

| 손 확인 항목 | 결과 |
|---|---|
| 1) … | <값> |

## 7-8

    <출력 한 줄 그대로>

## 발견
### <제목>
- **증상** :
- **재현** : <사외에서 그대로 따라 할 수 있게>
- **관측** : <값의 꼴 · 건수. 식별자는 가명>
- **범위** : <몇 행 / 어느 화면 / 언제부터>
- **제안** : <수정 방향. 확신이 없으면 없다고 적는다 — 추측을 사실처럼 적지 않는다>

## 사내 데이터 변화 (결함 아님)
<리비전·호기 수 변화, 7-8 의 사용자 저장분, 사내 커밋(런북 1-6), 임시 수정(런북 1-5)>

## 사외 요청
<런북·스크립트·규칙에 대한 요청. 우선순위대로>

## 실데이터 확인 (8장, <YYYY-MM-DD HH:MM>)
<`scripts/inspect_real_data_checks.py` 의 출력 블록. 양식은 런북 8-6.>
```

발견이 없으면 「## 발견」 절은 「없음」 한 줄이다. 실패를 고정하는 테스트를 제안하려면 발견 안에 코드블록으로 적는다 —
그것은 저장소 수정이 아니다.

## 5. 응급 상황

사내에서 당장 고쳐야 하는 날은 온다. 규칙에 없으면 그날 규칙이 조용히 깨지므로 미리 정한다
(2026-10-10 사용자 결정 — 예전의 `hotfix/<날짜>` 브랜치 규칙을 대신한다).

- **사용자가 직접 지시했을 때만** 고친다. 커밋하지 않는다(브랜치도 만들지 않는다).
- 리뷰 md 에 「임시 수정 있음 · 파일 N개 · 경로」 한 줄을 남기고, 계속 필요하면 「사외 요청」에 **「밖에서 반드시
  재구현」** 으로 적는다.
- 다음 적용 전에 diff 를 저장소 밖에 남기고 `git checkout -- <경로>` 로 되돌린다 — 적용기는 미저장 변경이 있으면
  멈추므로 잊을 수 없다. 절차는 런북 1-5.

사내 수정은 어떤 경우에도 정본이 되지 않는다.

## 6. 파일 구조 위생

두 에이전트가 같은 저장소를 번갈아 읽는다. 한쪽이 지운 파일의 이름이 문서에 남거나 아무도
쓰지 않는 모듈이 굴러다니면 **읽는 쪽이 그것을 찾아 헤맨다.** 사내는 쓸 수 있는 양이 적어
그 탐색이 먼저 비용으로 나타난다.

그래서 **별도 감사 도구를 두지 않는다** — 강제되지 않는 감사는 돌지 않는다. 대신 두 층에
나눠 얹었다.

| 층 | 무엇이 | 어디서 |
|---|---|---|
| **막는다** | 없는 파일을 가리키는 문서 · 아무도 안 쓰는 모듈 · 선언 밖 최상위 항목 · 미링크 문서 | `tests/test_repository_hygiene.py` — 검증 4종에 실려 매번 돈다 |
| **알린다** | 파일 수 · 문서 수와 줄 수 · 가장 큰 문서 다섯 | 배포 송장의 `hygiene` — 배포를 막지 않는다 |

가르는 기준은 **판정이 명확한가**다. 「이 문서가 아직 유효한가」는 사람이 봐야 하므로 검사로
만들지 않고 추세 수치로 넘긴다. 정리 부채로 배포를 세우면 규칙이 무시당하기 시작한다.

최상위에 항목을 더해야 하면 `ALLOWED_TOP_LEVEL` 을 같은 변경에서 고친다. 목록을 손대지
않고 파일만 느는 것이 곧 떠도는 파일이다.

## 8. 사내 저장소 정리 (한 번)

사내 저장소에 **저장소에 있으면 안 되는 것이 커밋돼 있는** 상태가 확인됐다. 규칙은 사외에
있고 ZIP 으로 따라가지만, **이미 커밋된 파일은 규칙만으로 빠지지 않는다** — `git rm --cached`
가 한 번 필요하다.

`git rm --cached` 는 이력을 고치지 않는다. 새 커밋에 삭제가 기록될 뿐 과거 커밋의 blob 은
그대로고, 워킹 파일도 남는다. `git revert` 로 되돌아온다.

**순서가 중요하다.** 배포를 적용하기 **전에** 한다 — 추적 중인 파일은 ZIP 에 없으므로
「사외에서 없어진 파일」로 판정되고, 보호 대상이 아닌 것(`.omo/` 등)은 그대로 지워진다.

```powershell
# 0) 앱을 끈다. DuckDB 는 프로세스 배타 잠금이라 켜져 있으면 아무것도 못 한다.
# 0-1) 혼자 쓰는 저장소인지 확인한다. 다른 클론이 있으면 그쪽 사람이 pull 하는 순간
#      워킹 파일이 지워진다 — 먼저 알리고 백업하게 한다.

# 1) 운영 DB 를 저장소 밖에 복사한다. 이 단계를 건너뛰지 않는다.
New-Item -ItemType Directory -Force "$HOME/duckdb_backup"
Copy-Item data/capa_simulation.duckdb "$HOME/duckdb_backup/"
Copy-Item data/equipment_availability.duckdb "$HOME/duckdb_backup/"

# 2) 운영 데이터 추적 해제 (파일은 남는다)
git rm -r --cached "data/*.duckdb" "data/*.duckdb.*"

# 3) 에이전트 런타임 산출물 — 남길 것이 있으면 먼저 꺼낸다
git rm -r --cached .agents/ .omo/

# 4) 도구가 흘린 임시 산출물
git rm -r --cached idx_extract.tmp imgtmp/

git status          # 파일이 워킹 트리에 남아 있는지 눈으로 확인한다
git commit -m "저장소에 있으면 안 되는 파일의 추적을 푼다"

# 5) upstream (순수 로컬 설정. 이력에 영향 없음)
git branch -u origin/main
```

무시 규칙(`.agents/` · `.omo/` · `*.tmp` · `imgtmp/` · `data/*.duckdb`)은 사외 `.gitignore` 에
있으므로 **다음 배포에서 저절로 복원된다.** 사내에서 `.gitignore` 를 고치지 않는다.

### 미커밋 변경은 커밋하지 않는다

적용기는 더러운 트리에서 멈추므로 배포 전에 비워야 한다. 다만 **사내 수정은 정본이 될 수
없다** — 두 저장소는 서로의 원격을 볼 수 없어 합칠 방법이 없다.

| 무엇인가 | 어떻게 |
|---|---|
| 코드 수정 | 커밋하지 않는다. `review/` 에 리뷰 문서로 내고 `git checkout -- <경로>` 로 되돌린다 |
| 리뷰·기록물 | `review/` 로 옮겨 커밋한다. 보존 목록이라 배포가 건드리지 않는다 |
| 판단이 안 선다 | `git stash` 보다 `review/` 아래 사본. stash 는 잊힌다 |

> ZIP 에 사내 파일이 실릴 위험은 **없다.** ZIP 은 사외에서 사외 `git ls-files` 로 만든다.
> 사내에서 사외로 나가는 것은 `review/` 의 리뷰 문서 하나뿐이고, 거기에 실데이터를 적지
> 않는 규칙이 4장에 있다.
