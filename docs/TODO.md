## 3-3. [검토] 기존에 없던 제품 분류를 추가하는 방법

2026-09-04 사용자 제기. PKG PLAN 에 **기존에 없던 구분 컬럼 조합**(신규 제품 분류)을

차기 개발 대상으로 남긴다.

### 무엇이 필요한가 (신규 `제품정보 + Stack` 하나당)

| 테이블 | 연결 키 | 채워야 할 값 | 세션 편집 |
| --- | --- | --- | --- |
| `RQ_PKG_PLAN` | 월 + 양산구분·제품정보·Stack·Capa Code·Customer·CS·Pack Code | 생산수량 | 가능 |
| `RQ_CHIP_QTY` | 제품정보 + Stack + WF 구분 | 구분_Chip, Net Die | **불가** |
| `RQ_YLD` | 월 + 제품정보 + Stack + WF 구분 | EDS_수율, BE_수율 | 가능 |
| `RQ_CHIP_EQ` | 제품정보 + Stack + WF 구분 | 구분_Chip, 구분_EQ | **불가** |
| `RQ_REQB` | 월 + Area + 공정 + 제품 + Capa Code + Customer + CS + WF 구분 + 순서 + 소요기준 | 적용 경로 | 가능 |

| `RQ_MODULE` | 공정 | 모듈수 | **불가** |

### 구조적 제약 — 이것이 핵심이다

`RQ_CHIP_QTY`·`RQ_CHIP_EQ`·`RQ_MODULE` 은 `EDITABLE_SCENARIO_TABLES` 에 없다. 활성 리비전
(`reference_tables`)에서 읽기만 하므로 **세션에서 행을 추가할 방법이 아예 없다.**
리비전 저장도 `rev_data` 의 테이블별 물리 테이블에 하므로, 편집 대상에 넣으려면
`rev_data.rq_chip_qty`·`rq_chip_eq` 를 만드는 **새 번호 마이그레이션과 Repository
저장·복원 확장**이 필요하다. (기존 마이그레이션은 체크섬 때문에 수정 금지.)

즉 지금 구조에서 신규 제품은 **계획 편집 사건이 아니라 원천 데이터 사건**이다.
계획 편집기는 "이미 존재하는 제품 집합 안에서 수량을 조정하는" 도구로 설계돼 있다.

### [검토] 가상 제품과 실적 지표의 관계

실적 DB가 붙을 때 정해야 한다. 사용자 제기: 복제한 제품의 계획이 총 필요 생산량에 더해져
해야 할 양이 늘어나는데 실적은 그대로이므로, 늘어난 계획 대비 실적이 더 부족하게
표현되는 것이 맞지 않냐는 것이다. 방향은 맞지만 구분이 필요하다.

- **확보율(설비 관점)**: 가상 제품이 소요대수를 늘려 확보율이 떨어진다. 이것이 what-if 의
  목적 자체이고 지금도 자동으로 그렇게 동작한다. 그대로 두면 된다.
- **효율·UPEH 실적**: 공정 단위로 측정되므로 어떤 제품을 계획했는지와 무관하다. 가상 제품을
  넣어도 **실적 값 자체는 변하지 않는다.** 변하는 것은 "그 실적 수준으로 늘어난 계획을
  감당할 수 있는가" 다. "실적이 나빠졌다" 가 아니라 "계획이 늘어 갭이 벌어졌다" 이며,
  화면 문구가 이를 구분하지 않으면 설비가 실제로 나빠진 것으로 오해된다.
- **재공 현황**: 가상 제품은 실제 재공이 0이라 "재공 100% 부족" 으로 뜬다. 실제로 뒤처진
  것이 아니라 존재하지 않는 제품이다.

- [ ] 실적 대조 화면(재공 현황·효율/UPEH 실적)에서 가상 제품을 기본 제외하고 토글로
  포함하게 한다. 부하량·소요대수·확보율은 그대로 반영한다.
- [ ] 가상 제품 기여분을 분리 표시한다. 예: `확보율 92% · 가상 제품 제외 시 104%`.
  이래야 실제 갭과 가정된 갭이 섞이지 않는다.

### Stack 이후 Wafer 공정 — 사용자 설명 (배경 지식)

사용자 설명: Stack(Buffer 위 Core·Top·Dummy Bonding)이 끝난 Wafer 를 투입하는 공정이
Mold Wafer 이고, 그 이후 Wafer 단위 투입 공정도 대체로 같다. Stack 완료 Wafer 를 따로
네이밍하지 않으므로 그 공정의 부하량에는 Buffer 만 들어온다.

**코드는 그대로 둔다.** 사용자가 "특별히 분류하거나 매핑할 필요 없이 그대로 반영하되,
구조와 배경을 이해하고 있으라" 고 했다. 매핑은 산식이 아니라 `RQ_REQB` 기준정보 행이 정한다.

> **철회된 서술 (2026-09-05)** — 이 자리에는 원래 「현재 `RQ_REQB` 실측」이라며 WF 기준
> 공정 6개·CHIP 24개, `Mold` 의 소요기준은 `CHIP`, 따라서 「Stack 이후 Wafer 단위 투입
> 공정에 해당하는 행이 원천에 하나도 없다」는 표와 결론이 있었고, 확인이 필요한 3갈래
> 질문까지 달려 있었다. **전부 근거가 없어 지웠다.**
>
> 그 수치는 업무 데이터가 아니라 `scripts/generate_sample_core_data.py` 의
> `PROCESS_SPECS` 리터럴을 읽은 것이다. 공정 30개도, `basis="WF"` 가 6개인 것도,
> `Mold` 가 `"CHIP"` 인 것도 그 리터럴을 쓴 사람의 선택이다. 「WF 6개 공정이 5종을 모두
> 갖는다」도 관측이 아니라 `process_rows()` 가 계획 행을 30개 spec 전부에 `dict(plan)` 로
> 복제하기 때문에 생기는 구조적 강제다. 사용자 설명과 충돌한 상대는 실데이터가 아니라
> 표본 생성기였다.

- [ ] 실데이터 `RQ_REQB` 를 받은 뒤에 소요기준 분포를 다시 집계한다. 그전까지는 공정
  목록·소요기준에 대해 어떤 판단도 하지 않는다.

  반면 **`company` extra 는 목적과 반대로 동작한다** — uv 락파일은 universal 이라 모든
  extra·group 을 포함해 해석하므로 사내 인덱스에 `bigdataquery` 가 있으면 `uv.lock` 에 박히고
  없으면 `uv lock` 자체가 실패한다. "락에서 빼는" 방법이 아니다. **권장은** pyproject 에서
  빼고 `uv sync` 뒤에 `uv pip install bigdataquery` 로 따로 넣는 것이다(이후엔
  `uv sync --inexact`). 코드가 이미 부재를 전제로 짜여 있는 것이 근거다.
  **배포 ZIP 은 `pyproject.toml` 을 덮지 않는다** — `scripts/build_deploy_package.py` 의
  `EXCLUDED_FILES` 가 `uv.lock` 과 짝으로 뺀다. 그래도 양쪽 선언은 같게 유지한다.
  `io/company_bigdataquery_adapter.py` 의 안내 문구는 실제 명령
  (`uv pip install bigdataquery`)으로 고쳤다.
- [ ] **`mode` 가드 도입 여부 (사용자 판단 대기).** 원문은 `HANDOFF.md` §8-4 다.
  `config/object_storage.json` 주석은 `mode` 를 `local` 로 커밋해야 개발 PC 가 사내
  스토리지를 건드리지 않는다고 경고하지만, 코드에서 `mode` 는 `doctor`·`status` 출력에만
  쓰이고 실행을 막지 않는다. 개발 PC 에서 `local` 로 `status` 를 돌려도
  `aws s3api list-objects-v2` 를 그대로 시도하고 `aws` 부재로 멈출 뿐이다. 실제 방어는 개발
  PC 에 `aws` 가 없다는 것뿐이다. 가드를 넣을지는 결정 대기.

## 3-10. 2026-09-10 Admin Area 와 공정 표시명(Proc Rename)

사이드바 맨 아래 별도 박스에 `Admin Area` 페이지가 있고 그 안 `Proc Rename` 탭이
공용 공정 표시명 프로필을 관리한다. 저장은 시뮬레이션 DB 마이그레이션 `0015` 의
`app_meta.global_process_rename*` 두 테이블이며 표시순서 프로필과 같은 결이다 —
단일 행 프로필, 교체마다 version+1, 이전 규칙은 보존하지 않는다(되돌리기는 교체 전 CSV
다운로드뿐). 규칙 0건 저장이 전체 해제이고 프로필이 없는 상태(버전 0)가 정상이다.

규칙은 한 문장이다 — **화면은 표시명, 파일은 원본.** 화면에서 사람이 읽는 공정명은
빠짐없이 표시명이다: 월별 표의 분류 값(`value_labels=`), 공정 선택 위젯의 `format_func=`,
Figure 라벨(LOB annotation·hover, 상세 B/N 이름·hover, 재공 격자 제목, Dynamic Capa 공정
비교 막대의 y축), `st.dataframe` 조회 표와 화면용 안내 문구, `st.data_editor` 분류 컬럼의
`SelectboxColumn(format_func=)` 라벨.

CSV 출구가 있는 표는 화면 프레임과 CSV 프레임을 나눈다. `Static Capa` 의 `확보율 기준
설비 부족 현황`(`app_pages/static_capa.py`)과 제외 목록 세 개(`components/exclusion_table.py`)가
그 모양이다 — 화면 복사본에만 표시명을 입히고 같은 표의 CSV 는 원본 공정명을 내보낸다.
`st.data_editor` 의 분류 컬럼은 **값이 원본이고 라벨만 표시명**이다. 값을 갈면
`merge_edited_months` 되머지 키가 어긋나거나 필터 미적용 단축 경로에서 표시명이 `RQ_*`
저장값이 된다.

표시명이 닿지 않는 곳은 다섯 갈래다: 왕복 CSV·클립보드 양식, 보고용 CSV 전부,
원본 키를 편집·확인하는 화면(표시순서 `분류값`, Proc Rename 탭의 `보유 공정` 목록),
`services/` 예외 메시지와 프리셋·세션 저장값, 설비 DB 공정명. 그 경계는 `services/` 가
`components/process_labels.py` 를 import 하지 않는 것으로 강제한다.

예외가 하나 있다. `st.dataframe` 그리드 우상단의 내장 `Download as CSV`·복사는 화면
프레임을 그대로 내보내므로 표시명이 들어가고, 그 기능을 끄는 인자가 없다. 우리가 쓰는
표 위의 CSV 버튼은 원본이다.

표시명을 적어 붙여넣는 실수는 입력 경계에서 막는다. 주차별 가용대수 붙여넣기는
`services/weekly_availability_input.py` 의 준비 함수가 `known_processes` 목록 밖의 공정명을
거절한다. 목록은 화면이 소유하므로 표준 목표 Capa 페이지가 전체 공정 목록을 넘긴다.

1:1 검증은 규칙 안의 중복만 본다. 표시명이 **매핑 밖 보유 공정의 원본명**과 같은 경우는
저장을 막지 않고 경고로 건수만 알린다. 보유 공정 목록이 시나리오마다 달라 오류로
승격하면 다른 시나리오에서 저장 자체가 막히기 때문이다.

- [ ] 관리자 권한 게이트. 페이지 이름을 `Admin Area` 로 잡은 이유이며 아직 인증·권한
      계층이 없어 지금은 사내 배포본에 그대로 노출한다.
- [x] 정렬순서 관리를 이 페이지로 옮겼다. `Admin Area` 의 `표시순서 관리` 탭이고,
      `시나리오 관리` 페이지에는 `시나리오 관리`·`BigDataQuery 등록` 두 탭만 남았다.
- [x] `st.dataframe` 로만 그리는 조회 표에도 표시명을 적용했다. 제외 기준정보 표 세 개
      (`공정별 Capa`·`공정별 확보율`), STEP 구성 요약과 복제·삭제 대상 선택 라벨, 설비대수

    다르다. **채택본의 저장 검증은 그대로 두고** 안내와 버튼만 더한다.
    **옮긴 모양**: 저장 검증은 문구·차단 조건까지 한 글자도 바꾸지 않고 폼 위 경고와
    `예시 행 N건 지우기` 만 더했다. 지우기는 세션 플래그를 남겨 재검토가 원문에서 같은
    행을 다시 들이지 못하게 하고, 건수는 저장 가드와 같은 두 함수로 센다.
  - 보류: xlsx 업로드(`openpyxl`). 떨어진 쪽이 import 가드·캡션·커밋 분리까지 갖췄고
    `pd.read_excel` 을 쓰지 않은 이유(날짜가 `2026-10-01 00:00:00`, 정수가 `30.0` 이
    되어 검증에 걸린다)도 적어 두었다. **사내 반입 확인 뒤에 정한다.**
  - 건지지 않기로 한 것: 기준 월 pill(월 집계를 넣으면 축이 둘이 된다), Main 의 조회
    조건 popover(채택본의 `추가 조건` 이 같은 일을 한다).
- **보류: 라인 점검 등의 일정을 반영하기 위한 Workday 증감 적용 방안 마련.**
  일할 가용대수의 분모는 지금 **달력일**이다. 라인 공사·점검으로 라인 전체가 서는 날을
  빼려면 가동일 기준이어야 하는데, `RQ_RUN_DAY` 는 **월·공정별 개수**일 뿐 어느 날이
  쉬는 날인지를 모른다. 개수만으로 나누면 쉬는 날이 고루 퍼졌다고 보는 것이라
  `(기여일 x r) / (달력일 x r)` 로 약분되어 **지금과 결과가 같다** — 달력이 있어야
  실제로 달라진다.
  같이 정할 것: 라인 전체 다운을 `RQ_RUN_DAY` 축소로 적을지 호기 비가동으로 적을지.
  **둘 다 적으면 이중 계상**이다 — 대당 Capa 가 작아져 소요대수가 늘고 가용대수도 줄어
  확보율이 양쪽에서 깎인다. 2026-09-22 현재 어느 쪽에도 적고 있지 않다.
