## 3-3. [검토] 기존에 없던 제품 분류를 추가하는 방법

2026-09-04 사용자 제기. PKG PLAN 에 **기존에 없던 구분 컬럼 조합**(신규 제품 분류)을
추가하려면 계획 수량만으로는 부족하다. 환산과 Capa 산출이 참조할 기준정보가 없기 때문이다.
차기 개발 대상으로 남긴다.

### 무엇이 필요한가 (신규 `제품정보 + Stack` 하나당)

| 테이블 | 연결 키 | 채워야 할 값 | 세션 편집 |
| --- | --- | --- | --- |
| `RQ_PKG_PLAN` | 월 + 양산구분·제품정보·Stack·Capa Code·Customer·CS | 생산수량 | 가능 |
| `RQ_CHIP_QTY` | 제품정보 + Stack + WF 구분 | 구분_Chip, Net Die | **불가** |
| `RQ_YLD` | 월 + 제품정보 + Stack + WF 구분 | EDS_수율, BE_수율 | 가능 |
| `RQ_CHIP_EQ` | 제품정보 + Stack + WF 구분 | 구분_Chip, 구분_EQ | **불가** |
| `RQ_REQB` | 월 + Area + 공정 + 제품 + Capa Code + Customer + CS + WF 구분 + 순서 + 소요기준 | 적용 경로 | 가능 |
| `RQ_UPEH` | 공정 경로 + 소요기준 | UPEH, ST | 가능 |
| `RQ_LOT_RATIO`·`RQ_WF_RATIO` | 월 + 공정 + 양산구분 + 제품정보 + Stack + WF 구분 | 측정률 | 가능 |
| `RQ_MODULE` | 공정 | 모듈수 | **불가** |

### 구조적 제약 — 이것이 핵심이다

`RQ_CHIP_QTY`·`RQ_CHIP_EQ`·`RQ_MODULE` 은 `EDITABLE_SCENARIO_TABLES` 에 없다. 활성 리비전
(`reference_tables`)에서 읽기만 하므로 **세션에서 행을 추가할 방법이 아예 없다.**
리비전 저장도 `rev_data` 의 테이블별 물리 테이블에 하므로, 편집 대상에 넣으려면
`rev_data.rq_chip_qty`·`rq_chip_eq` 를 만드는 **새 번호 마이그레이션과 Repository
저장·복원 확장**이 필요하다. (기존 마이그레이션은 체크섬 때문에 수정 금지.)

즉 지금 구조에서 신규 제품은 **계획 편집 사건이 아니라 원천 데이터 사건**이다.
계획 편집기는 "이미 존재하는 제품 집합 안에서 수량을 조정하는" 도구로 설계돼 있다.

### 제안 — 3단계로 나눈다

- [x] **1단계. 기준정보 미비를 오류가 아니라 진단으로 바꾼다 (선행 필수)**
  지금은 계획 행 하나에 `RQ_YLD` 가 없으면 `RQ_YLD가 연결되지 않는 기준이 있습니다` 로
  페이지 전체가 멈춘다. 이를 **해당 제품만 계산에서 제외하고, 무엇이 없는지 목록으로
  보여주는** 방식으로 바꾼다. 신규 제품 기능을 하지 않더라도 이것만으로 가치가 있다.
  `unit_capacity` 가 이미 쓰는 `CAPACITY_EXCLUSIONS_ATTR` 패턴을 그대로 확장한다.

- [x] **2단계. 기존 제품 복제 등록 (권장 진입점)**
  신규 제품은 대개 "기존 제품과 같은 공정을 타되 Chip 수·수율·용량이 다른" 형태다.
  기준 제품을 고르면 그 제품의 모든 기준정보 행을 새 키로 복제하고, **달라지는 값만**
  입력받는다. 완결성이 구조적으로 보장되고 입력량이 최소가 된다.
  복제 대상 12개 테이블을 한 번의 `apply_month_updates` 로 원자 반영한다(토큰 1회 발급).

- [x] **3단계. `RQ_CHIP_QTY`·`RQ_CHIP_EQ` 를 편집 대상으로 승격**
  2단계가 실제로 동작하려면 필요하다. 새 번호 마이그레이션으로 `rev_data` 테이블을
  추가하고 Repository 저장·복원과 리비전 스냅샷 계약에 넣는다. `RQ_MODULE` 은 공정
  기준이라 제품 추가와 무관하므로 제외해도 된다.

### 결정 결과 (2026-09-04)

- 목적은 **시뮬레이션용 가상 제품**이다. 원천에 없는 실제 신제품은 BigDataQuery 등록이라는
  기존 경로를 쓰므로 앱에서 만들지 않는다. 그래서 **복제 등록만** 구현했다.
- 가상 제품 포함 여부는 **리비전 메타에 기록**한다. `app_meta.revision_virtual_product` 가
  어떤 제품이 어느 원본에서 복제됐는지 리비전별로 남기고, 저장 완료 메시지가 공식버전
  발행 전 확인을 요청한다.

3단계 모두 구현 완료. 1단계는 `LOAD_EXCLUSIONS_ATTR` 진단, 3단계는 마이그레이션 `0011`,

### [검토] 가상 제품과 실적 지표의 관계

실적 DB가 붙을 때 정해야 한다. 사용자 제기: 복제한 제품의 계획이 총 필요 생산량에 더해져
해야 할 양이 늘어나는데 실적은 그대로이므로, 늘어난 계획 대비 실적이 더 부족하게
표현되는 것이 맞지 않냐는 것이다. 방향은 맞지만 구분이 필요하다.

- **확보율(설비 관점)**: 가상 제품이 소요대수를 늘려 확보율이 떨어진다. 이것이 what-if 의
  목적 자체이고 지금도 자동으로 그렇게 동작한다. 그대로 두면 된다.
- **효율·UPEH 실적**: 공정 단위로 측정되므로 어떤 제품을 계획했는지와 무관하다. 가상 제품을
  넣어도 **실적 값 자체는 변하지 않는다.** 변하는 것은 "그 실적 수준으로 늘어난 계획을
  감당할 수 있는가" 다. "실적이 나빠졌다" 가 아니라 "계획이 늘어 갭이 벌어졌다" 이며,
  화면 문구가 이를 구분하지 않으면 설비가 실제로 나빠진 것으로 오해된다.
- **재공 현황**: 가상 제품은 실제 재공이 0이라 "재공 100% 부족" 으로 뜬다. 실제로 뒤처진
  것이 아니라 존재하지 않는 제품이다.

- [ ] 실적 대조 화면(재공 현황·효율/UPEH 실적)에서 가상 제품을 기본 제외하고 토글로
  포함하게 한다. 부하량·소요대수·확보율은 그대로 반영한다.
- [ ] 가상 제품 기여분을 분리 표시한다. 예: `확보율 92% · 가상 제품 제외 시 104%`.
  이래야 실제 갭과 가정된 갭이 섞이지 않는다.

### Stack 이후 Wafer 공정 — 설명과 현 데이터의 차이

사용자 설명: Stack(Buffer 위 Core·Top·Dummy Bonding)이 끝난 Wafer 를 투입하는 공정이
Mold Wafer 이고, 그 이후 Wafer 단위 투입 공정도 대체로 같다. Stack 완료 Wafer 를 따로
네이밍하지 않으므로 그 공정의 부하량에는 Buffer 만 들어온다.

현재 `RQ_REQB` 실측은 이렇다.

| 소요기준 | 공정 수 | 공정 |
|---|---|---|
| WF | 6 | AVI-CoW, Laser Grooving, Wafer Grinding, Wafer Mount, Wafer Saw, Wafer_Sorter |
| CHIP | 24 | Mold 포함 나머지 전부 |

- WF 기준 6개 공정은 **전부 Stack 이전** 단계이고, 각각 Buffer·Core·Top·Dummy·Master
  5종을 모두 갖고 있다. 설명한 "Buffer 만 들어오는" 형태가 아니다.
- **`Mold` 의 소요기준은 `CHIP`** 이다. 설명대로라면 Wafer 단위여야 한다.
- 즉 "Stack 이후 Wafer 단위 투입 공정" 에 해당하는 행이 현재 원천에 하나도 없다.

- [ ] 위 차이가 (a) 원천 `RQ_REQB` 가 아직 그 공정들을 Wafer 기준으로 싣지 않은 것인지,
  (b) `Mold Wafer` 가 `Mold` 와 다른 별도 공정인지, (c) 현 CHIP 기준이 맞고 설명은 물리
  흐름에 대한 것인지 확인이 필요하다. 확인 전까지 코드는 그대로 둔다 — 사용자가 "특별히
  분류하거나 매핑하지 말라" 고 했고, 매핑은 산식이 아니라 `RQ_REQB` 기준정보 행이 정한다.
