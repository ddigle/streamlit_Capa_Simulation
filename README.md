# Capa Simulation

DuckDB 시나리오 기준정보로 HBM·EDP-TSV PKG 라인의 월별 부하량, 대당 Capa, 소요대수,
확보율과 Bottleneck 공정을 계산하는 Streamlit 프로젝트입니다.

새 웹 세션은 가장 최근에 발행한 공식 시나리오 리비전을 기본으로 불러옵니다. 웹에서
수정한 계획·수율·Capa 기준정보는 사용자별 활성 시나리오에 반영되고, 저장하면 새 불변
리비전으로 보존됩니다.

GitHub에서 소스만 받은 빈 환경은 첫 실행 시 DuckDB 스키마를 만들고, Git에 포함된
공용 표시순서 시드와 `DEMO_*` 합성 Core Data로 초기 시나리오·리비전·공식버전을 자동
생성합니다. 기존 시나리오나 공식버전이 있으면 이 시드는 생성하거나 덮어쓰지 않습니다.

## 현재 구현 범위

- PKG·Chip·Wafer·Density 월별 부하량 환산
- PKG PLAN 및 EDS·BE 수율 웹 편집
- UPEH·효율·여유율·Lot/WF측정률·일수·PKG PLAN·수율·보유/대여/가용 설비대수의
  월별 Wide CSV 양식 다운로드와 Excel 표 붙여넣기 일괄 적용
- UPEH·ST·효율·여유율·가동일수·측정률 기반 STEP·MCP 경로별 상세 대당 Capa와
  `원수요 부하량 ÷ STEP별 소요대수 합` 기반 공정별 대당 Capa 산출
- 공정·제품 경로의 STEP 구성 복제·추가·삭제와 Capa Code·Customer·CS 수요 변형 일괄 적용
- `RQ_REQB`의 Area·STEP·MCP 공정 경로별 소요대수 산출
- 보유·대여·가용 설비대수 조회
- 공정별 확보율 및 월별 B/N 공정 산출
- 월간 공정별 대당 Capa를 일 단위로 환산하고 Excel 붙여넣기의 주차별 가용대수를 적용하는
  표준 목표 Capa 산출과 단일 공정·주차의 제품·Stack·WF 속성별 Mix 로직 분석
- Density·Wafer Capa 요약과 계획·B/N 상세표를 `Main` 탭에 함께 그리는 HOME 대시보드
- 탭을 처음 열 때 첫 로딩을 덮는 입장 화면(웨이퍼 심볼·`S.PKG CAPA` 인트로, 진행 단계, `Detail`)과
  최신 공식버전 6개월을 모션으로 그리는 `Summary` 요약 화면
- 기존 제품의 기준정보를 복제해 what-if 에 쓰는 가상 제품 등록
- 제품타입별 WF 구분 분리(EDP-TSV 의 `Top`은 앱 안에서 `Top_e`로 표시)
- DuckDB 불변 리비전 캐시와 사용자별 활성 시나리오
- Core Data 78컬럼 계약, pandas Power Query 대체 변환과 typed DuckDB raw 적재
- DuckDB 기반 시나리오·불변 리비전·조회/판정 프리셋 저장 및 복원
- 사이드바의 시나리오·리비전 선택·불러오기·신규 리비전 저장과 독립 `시나리오 관리` 페이지
- 공식버전 발행·기본 자동 로딩과 시나리오 공용 표시순서의 Excel 붙여넣기·웹 편집
- 빈 DB의 비민감 합성 시나리오·초기 리비전·공식버전 자동 부트스트랩
- 사내 BigDataQuery 등록 탭과 CSV 없는 DataFrame 적재 어댑터 초안
- 기존 보유대수, Qual 확정상태를 포함한 36컬럼(`투자Capa`·`반입/Qual 이력`·`Main 설비`·`메모1~3` 은 선택) 호기 마스터와 운영 비가동의 DuckDB 이력 저장
- 옛 머리 이름(호기·라인구분·활용구분·분류1~3·모델·입고일정·비고·장기보관여부·모체호기·이설일)의 엑셀·CSV 도
  그대로 올리면 새 이름으로 바꿔 읽는다. 빠진 `투자기준` 열은 읽지 않고 알림 한 줄을 남긴다
- 모듈로 관리하는 설비(CoW Bonder 등)는 모듈마다 한 행을 두고 `Main 설비` 로 묶는다. 대수는
  묶음을 1대로 세고(모듈 하나가 멈추면 0.25대 비가동), 능력은 모듈 행의 환산비(0.25)를 더한다
- 호기 마스터·비가동 일정 Excel 붙여넣기 Import와 자연키 기준 추가·대체
- 공정·분류별 주차 단위 총대수·가용대수·비가동대수 대시보드
- HOME 하단 독립 메뉴의 `Capa Chatbot` 대화형 분석 화면 초안
- `Static Capa` 상위 화면의 경고·확보 기준별 월간 설비 부족 현황과 하위 `생산 계획`·
  `기준 정보`·`산출 결과`·`표준 목표` 페이지
- `Dynamic Capa` 아래 표준 대비 재공 현황·가용설비 현황·효율 실적·UPEH 실적·Space 현황
  페이지와, 사이드바 맨 아래 별도 박스의 `Admin Area` 페이지
- 전체 공정 우선순위와 공정·제품·Stack·WF 속성별 표준/실효/실적 Capa 비교 프로토타입
- 공정·제품·STEP별 일일 보유 재공·유입·Flow와 표준 가능량을 비교하는 Plotly 격자
  프로토타입

`Capa Chatbot`과 `Dynamic Capa` 영역의 상위·하위 페이지 제목에는 실제 실적 DB 연결과
운영 기준 확정 전임을 명확히 하기 위해 `(구현중)`을 표시합니다.

`Static Capa` 상위 화면은 월·공정별 확보율에서 경고 기준까지 필요한 대수와 경고 기준에서
확보 기준까지 추가로 필요한 대수를 분리해 표시합니다. 두 단계의 합계는 확보 기준을
충족하기 위한 최소 정수 대수이며, 기간 전체 합산 대신 월별 상세와 월 최대치를 사용합니다.
확보·경고 기준(기본 109.5%·99.5%)은 시나리오와 무관한 공용 설정이며 `HOME → Preference` 의
`확보율 판정 기준` 한 곳에서 정합니다 — 기본값 한 짝과, 특정 달만 다른 기준을 쓸 때의 월별 표(빈칸은
기본값)입니다. 모든 판정(HOME 색·결론·B/N 공정 선택, 히트맵, Static Capa 추가대수, 공식버전 Summary)은
달마다 **그 달의** 기준을 씁니다. 판정에는 정확한 값을 쓰고, 기준선 이름표·캡션처럼 화면에 기준을 적을
때는 사사오입한 정수 퍼센트(110%·100%)로 적습니다. 판정 색 범례는 「확보 · 경고 · 부족」 세 이름만
적고 숫자는 적지 않습니다. 확보율이 기준과 **같으면 확보**입니다(경고 기준도 같은 쪽 — 이상). 기준을 고치는 입력 칸은 정확한 값을 그대로 보여 줍니다.
`Dynamic Capa` 상위 화면은 데모 데이터로 `표준 Capa → 효율 반영 → UPEH 반영 →
Rundown 차감 → 실제 실적`의 손실 구조, 일별 추이와 제품 Mix 상세를 확인할 수 있습니다.
`효율 실적`과 `UPEH 실적`은 기준 대비 Gap, 공정·제품 개선 우선순위와 개선과제 관리
구조까지 화면 초안으로 구현했으며 실제 실적효율·생산실적 DB 연결은 후속 단계입니다.
`표준 대비 재공 현황`은 오늘 기준 -7일~+3일의 11일 구간을 제품 행과 STEP·공정 열의
정사각형 Plotly 셀로 배치합니다. 보유 재공·유입·Flow 세로 막대와 현재 `표준 목표 Capa`
산식의 제품별 일 표준 가능량 기준선을 함께 표시하며 Flow 충족은 초록색, 부족은 빨간색으로
구분합니다. 재공 값은 실제 DB 연결 전 결정론적 샘플이고 주차별 가용대수가 없으면 표준을
임의 생성하지 않습니다.
`Admin Area`는 화면 표기·정렬순서 같은 운영 관리 설정을 모으는 자리이며 `Proc Rename`과
`표시순서 관리` 두 탭입니다. `Proc Rename`은 공정 A를 화면에서만 A'로 바꿔 표시하는 공용 프로필을
CSV 다운로드·Excel 붙여넣기·직접 편집으로 관리합니다. 원본 공정과 표시명은 항상 1:1이고,
매핑에 없는 공정은 원본 이름 그대로 나오며 보유하지 않은 공정에 지정한 표시명은 무시합니다.
표시명이 매핑 밖 보유 공정의 원본명과 같으면 화면에서 두 공정이 같은 이름으로 보이므로
경고로 건수를 알립니다. 보유 공정 목록은 시나리오마다 다르므로 저장은 막지 않습니다.
규칙은 한 문장입니다 — **화면은 표시명, 파일은 원본.** 조회 표·편집기 분류 컬럼·선택
위젯·Figure 축과 안내 문구까지 화면에서 사람이 읽는 공정명은 모두 표시명이고, `RQ_*`
저장값과 내려받는 CSV(보고용·붙여넣기 왕복 양식 모두)는 원본 공정명을 그대로 유지합니다.
표시순서 관리와 이 `Proc Rename` 탭 자체는 원본 키를 편집·확인하는 화면이라 예외입니다.
가용설비대수처럼 시나리오와 분리된 공용 DB 프로필이라 저장해도 시나리오 리비전을
만들지 않습니다.
`Capa Chatbot`은 추천 질문, 대화 영역, 연결 상태와 답변 근거 표시 구조만 구현했으며
LLM API·Capa 데이터·권한 및 대화 이력은 아직 연결하지 않습니다.
`Space 현황`은 가용설비 현황과 동일한 설비 리비전을 사용해 `S.PKG FAB 전체 → 층 상세 배치`
2단으로 탐색합니다. FAB 전체도 층 도면과 같은 편집기의 보기 전용이라 층 블록을 누르면(또는 Tab 으로
고르고 Enter) 그 층이 열리고, 경로 줄의 `층 바로 가기`·아래 층 목록 표로도 엽니다. 연 층은 주소
(`?floor=C1-1F`)에 남아 새로고침해도 그 층에 머뭅니다. 설비별 동·층·X/Y 좌표와 X/Y 크기를 사용해
렌더링합니다. 레이아웃표시는 도면 대상만 가릅니다 — Y 인데 좌표가 없으면 미배치이고(크기만
있어도 됩니다), X·Y 를 넣으면 크기와 동·층도 넣습니다. 층 상세의 `배치 편집` 을 켜면
드래그앤드롭 편집기로 호기 자리·크기·층과 반입구·문·영역 같은 도면 요소를 고치고, 가용설비 RawData 와
같은 편집본을 한 번에 저장합니다(겹침은 경고만 합니다). FAB 전체 머리 줄의 `배치 편집` 을 켜면 층
블록(연결 층 필수, 자리 구분 색)·영역·글자·동선을 고치고 같은 `배치 저장` 으로 저장합니다 — FAB 배치는
설비 리비전과 무관한 현행값(설비 마이그레이션 `0013`)이라 설비 저장본이 없어도 고칠 수 있고, 샘플
화면을 보는 중에만 꺼집니다. S.PKG 가 아닌 자리는 블록 대신 영역과 글자로 그립니다. 층 도면은 열 폭을
채우고 아래 손잡이로 높이만 바꿉니다(브라우저가 기억, 다시 실행 없음). 편집 때 미배치 트레이는 도면 오른쪽의 접히는 서랍이고,
호기를 끌어 놓아도 열린 채라 이어서 놓습니다(서랍 아래에 놓이면 도면이 옆으로 비킵니다). 도면 요소(층 블록 포함)는
이름표의 글자 크기(자동·9~24px)와 글자 색(기본·여섯 색)을 고를 수 있고 기둥 이름은 기둥 위에 섭니다(설비 마이그레이션 `0017`). 기준일의 입고 예정·셋업 진행중·가용·반출·이설·보관·운영 비가동 상태를
색으로 구분하고 운영 비가동은 우선 표시합니다. 실제 층별 레이아웃 이미지와 Space Capa
계산 연결은 후속 단계입니다. 이 화면은 배치·공간만 봅니다 — 카드 없이 도면 도구 줄 한 줄 요약으로
배치 설비·미배치(레이아웃표시 Y 인데 좌표 없음)·레이아웃 제외(N) 대수와 층 점유율(호기 면적 ÷ 캔버스
면적)을 보이고, 상태별 대수는 층 배치도 범례에 붙입니다(FAB 층 블록은 배치·미배치 대수만 셉니다). 기간 안의 단계별 완료·예정 호기(단계 전환)는 `가용설비 현황` Main 의
`단계 전환` 에서 조회합니다.

## 구조 요약

```text
Core_Data DataFrame (BigDataQuery / 개발용 CSV / 내장 합성 시드)
        ↓ 78컬럼 검증·pandas RQ 변환
data/capa_simulation.duckdb
        ├─ 시나리오별 Core Data 78컬럼 raw 스냅샷
        ├─ 시나리오별 독립 RQ 16개 데이터셋
        ├─ 리비전별 편집 테이블·프리셋
        ├─ 시나리오 공용 표시순서 프로필
        └─ 공식버전 발행 이력
                ↓ 최신 공식 또는 사용자가 선택한 활성 리비전
사용자별 활성 시나리오 (세션) ↔ 불변 리비전 캐시 (서버)
                ↓
부하량 → 대당 Capa → 소요대수 → 확보율 → B/N
                ↓
Streamlit 페이지 및 HOME 대시보드

data/equipment_availability.duckdb
        └─ 기존 보유대수·호기 마스터·비가동 일정의 불변 저장 이력
                ↓
가용설비 주차 집계·대시보드 ↔ Space 단계·배치 현황

향후 실적효율 DB + 생산실적 DB
        └─ 주기적으로 갱신하는 누적 이력 (시나리오별 복제 없음)
                ↓ 일자·공정·제품·Stack·WF 속성 연결
시나리오별 표준 Capa ↔ Dynamic Capa 실적 비교
```

공통 사이드바의 조회기간은 시작 월과 종료 월을 각각 선택하는 월 캘린더로 제공되며,
선택한 범위는 모든 페이지의 월별 조회와 계산에 동일하게 적용됩니다. 사이드바 조회기간
상자는 고른 범위를 `선택 · 26.07–28.12` 처럼 보여 주고, 그 범위를 실제로 읽은 화면(HOME·계산
페이지)만 `✓ 적용` 으로 바꿉니다. 기준정보 오류로 계산이 멈추면 `계산 멈춤` 이 됩니다.
사이드바 `조회 조건 · 이 화면에 적용` 구역에는 그 화면이 실제로 읽는 조건만 모읍니다. 시나리오·
리비전과 조회기간 상자도 그 조건을 읽는 화면에서만 섭니다(예: VOC·Space 현황에는 없고, 가용설비
현황은 `Static/Dynamic` 탭에서만). 화면 고유의 설정은 **조건 카드**로 서며(예: `생산 계획` 의
`환산 조건`, `Static Capa` 의 `판정 기준` — 이 카드는 지금 기준을 보여 주기만 합니다), 기본은 접혀 있고 한 번 펴면 탭을 오가도 펴진 채입니다.
화면 설명은 헤더 밝게/어둡게 버튼 옆 `Guide` 버튼에 있습니다(가이드가 있는 화면에서만 보입니다).
밝게/어둡게는 앱 전체에 하나입니다. 어느 화면에서 바꿔도 다른 화면과 새로고침·즐겨찾기로 연 화면이
같은 테마로 열리고, 처음 여는 화면은 밝은 테마입니다. 테마를 바꾸는 곳은 헤더의 Light/Dark 버튼
하나입니다 — Streamlit 의 ⋮ 메뉴는 감췄습니다. 화면 인쇄는 그 버튼 바로 오른쪽의 `Print` 버튼으로
하며, 화면이 다 그려진 뒤 브라우저 인쇄 창이 열립니다. 인쇄(`Print` 버튼이든 Ctrl+P 든)에는
사이드바·헤더 띠·툴바 버튼·입장 화면/Summary 덮개가 늘 빠지고 본문이 종이 폭을 다 쓰며, 색은 화면
그대로 찍힙니다. Space 배치 보기·지표 카드는 쪽 사이에서 잘리지 않고, 월별 표(Plotly)는 빈 쪽이
생기지 않도록 쪽 경계에서 이어 찍힙니다. 용지 방향은 인쇄 창에서 고릅니다. 다만 `st.dataframe` 표는
화면에 지금 그려진 행만, 월별 표는 종이 폭에 드는 달만 찍힙니다(가로 스크롤 칸의 한계 — 가로 용지가
더 많이 담습니다). HOME `Capa LOB 현황` 처럼 가로로 넓은 표를 다 찍으려면 인쇄 창에서 가로 방향을
고르거나, 인쇄 전에 사이드바 조회기간을 좁히세요. 어두운 테마에서 `Print` 를 누르면 검은 바탕까지
찍히므로 먼저 묻습니다 — 확인하면 그대로 인쇄하고, 취소하면 아무 일도 없습니다(밝은 테마로 바꾼 뒤
인쇄하면 잉크가 덜 듭니다). 밝은 테마와 Ctrl+P 는 묻지 않습니다.
테마 전환은 화면을 새로 읽으므로 저장하지 않은 시나리오·설비 편집이 사라집니다 — 그런 편집이 있으면
버튼이 먼저 묻습니다.
화면 맨 위 띠에는 지금 보고 있는 시나리오가 적힙니다. 위 줄은 `시나리오명 · r번호 리비전명 · 상태`
(`공식 vN`·`저장된 리비전`·`미저장 변경`), 아래 줄은 시뮬레이션 코드·시나리오 기간(생산계획의 첫
달–끝 달)·원천과 등록일(공식버전이 아니면 리비전 저장일)입니다. 창이 1400px 보다 좁으면 오른쪽
단추 묶음이 실제로 쓰는 폭만 비워 두어 1100px 창에서도 두 줄이 대개 다 보입니다. 그래도 넘치는 아주
긴 이름은 말줄임(…)으로 끝나며, 전체 이름은 사이드바 `시나리오·리비전` 상자에 있습니다. 앱 버전·
개발자·인증 정보는 `Admin Area` 맨 아래에 있습니다.
브라우저 탭 아이콘은 앱에 든 SVG 파일(`static/icons/factory.svg`, Google Material Symbols Rounded
`factory`, Apache License 2.0)을 Streamlit 이 data URI 로 실어 보내므로, 외부 아이콘 서버
(fonts.gstatic.com)에 나가지 않고 사내의 URL 경로 접두에도 영향을 받지 않습니다.
페이지 제목·상자 제목·수치 카드의 큰 숫자는 영문·숫자를 Archivo, 한글을 Noto Sans KR(없으면 맑은
고딕)로 그립니다. Archivo 는 앱에 든 작은 글꼴 파일(`static/fonts/`, 영문·숫자만)을 Streamlit 정적
서빙(`.streamlit/config.toml` 의 `enableStaticServing = true`)으로 받으므로 외부 글꼴 서버에 나가지
않습니다. 본문·표·차트 숫자·사이드바 메뉴의 서체는 그대로입니다.
탭을 처음 열면 첫 로딩 동안 입장 화면이 앱을 덮습니다. 웨이퍼 심볼과 `S.PKG CAPA` 가 화면 전체로
펼쳐진 뒤 여섯 단계 막대가 요약 준비와 HOME 계산 진행을 따라 차고, 다 그려지면 `Detail`·`Summary`
가 켜집니다. `Detail` 은 원래 화면(상세)으로 들어가고, `Summary` 는 같은 자리에서 **최신 공식버전의
6개월 요약**(생산계획·B/N 확보율과 부족 대수·월별 Density·Wafer 계획·제품 비중)을 모션으로 그립니다.
원래 화면에서는 사이드바 왼쪽 위 `S.PKG CAPA` 라벨을 누르면 언제든 요약으로 돌아오고, 요약의
`Detail`(또는 Esc)로 다시 들어갑니다. 같은 탭에서는 새로고침·테마 전환을 해도 입장 화면이 다시 뜨지 않습니다(새 탭에서는 다시
뜹니다).
탭 이름 앞 아이콘은 그 탭이 하는 일이고, 적용하지 않은 편집이 남은 탭에는 이름 옆에 주황 점이
찍힙니다.
`생산 계획` 의 `PKG PLAN`·`수율` 탭은 작업 버튼(`변경사항 적용`·`Excel 붙여넣기`·`가상 제품
등록`)이 표 **위**에 있고, 붙여넣기와 가상 제품 등록은 팝업으로 엽니다. `기준 정보` 의 월별
편집표도 같습니다(`변경사항 적용`·`Excel 붙여넣기`·`편집 취소`, STEP 구성은 `STEP 추가·삭제`
팝업). 표 필터는 사이드바 `표 조건` 카드이고, 적용하지 않은 편집이 있으면 잠깁니다. 고친 뒤 다른
탭으로 옮겨도 편집은 남아 있습니다. `산출 결과` 도 집계 수준·상세·필터가 `표 조건`
카드이고(확보율 탭의 `히트맵` 은 그 필터를 거친 표와 같은 공정을 그립니다), `표준 목표` 는 조회·집계 설정이 `표준 목표 조건` 카드, 주차별 가용설비 입력이 결과 위
작업 줄(`가용설비 붙여넣기` 팝업·`입력 초기화` 확인 팝업)입니다. `가용설비 현황` 은 거르는
조건이 `설비 조회 조건` 카드(Main·Static/Dynamic), RawData 의 저장·보기 적용·일괄 삭제 버튼이 표
위이고, `Space 현황` 은 기준일·필터가 `Space 조건` 카드, 층 도면 편집이 팝업입니다. `Admin Area`
의 붙여넣기는 팝업, 저장은 편집표 위이고, `VOC` 는 글 목록 필터가 `VOC 필터` 카드입니다. 모든 기능
화면의 설명은 헤더의 `Guide` 에 있습니다.
적용하지 않은 편집은 시나리오에 들어 있지 않아 저장에 실리지 않습니다 — 편집이 남은 채 사이드바
`신규 리비전 저장`·`불러오기`를 누르면 어디에 남았는지 알리고 확인 체크를 받습니다. `변경사항 적용`
은 고친 것이 있을 때만 눌리고, `생산 계획` 의 PKG PLAN·수율에도 `편집 취소`가 있습니다.
부하량 페이지의 환산 결과는 고정된 분류 영역과 가로 스크롤되는 월별 영역으로 나누어
표시하며, 동일 분류값은 정렬 결과에 따라 계층적으로 그룹화됩니다. 각 제품 아래에는
`Total`, 각 양산구분 아래에는 양산구분 Total이 배치되고 전체 합계는 헤더 바로 아래 2행에 표시됩니다.
현재 소요기준·상세 여부·조회기간이 반영된 환산 결과는 UTF-8 CSV로 내려받을 수 있습니다.
대당 Capa, 확보율과 소요대수 결과도 현재 집계 수준·공정 및 분류 필터·상세 여부·조회기간을
반영한 UTF-8 CSV로 내려받을 수 있습니다.

**라인 전체가 서는 날은 `기준 정보 → 일수`(`RQ_RUN_DAY`)를 줄여서만 적습니다**(2026-10-06 결정).
라인 점검·공사로 라인이 통째로 쉬는 날은 그 달·공정의 가동일수를 줄이고, 호기 하나의 일(개발대여·

`표준 목표 Capa`는 공정·양산·제품·Stack·WF 속성 수준에서 중복되지 않은 원수요
부하량을 STEP별 소요대수 합으로 나눈 월간 공정별 대당 Capa를 `RUN_DAY`로 나누어

`대당 일 Capa × 가용대수`로 주차별 일 표준 가능량을 산출하고, ISO Weeknum
(`YY-W##`) 열의 Plotly 표와 UTF-8 CSV로 제공합니다. 월 경계 주차는 그 주에 더 많은 날이
들어간 달의 월간 Capa·RUN_DAY 기준정보를 사용합니다(7일이라 4:3 으로만 갈립니다). 수동 가용대수는 `data/equipment_availability.duckdb`에 별도
리비전 없이 공정·Weeknum 최신값으로 저장되며 일부 공정만 적용해도 나머지 공정은
보존됩니다. ER 계획은 집계 전에 항상 제외합니다. 상세 표시를 끄면 중복 없는 양산
원수요 부하량을 STEP별 소요대수 합으로 나눈 제품 Mix 가중 공정 단일값을, 켜면 선택한
제품 분류 수준의 값을 표시합니다. 향후에는 같은 입력 계약을 가용설비 현황 DuckDB의
산출 결과로 교체합니다.

결과의 `PKG 기준` 토글을 켜면 현재 공정·제품 Mix의 중복 없는 PKG PLAN 합계를 같은
Mix의 원수요 투입 Unit 부하량으로 나눈 환산계수를 적용해 일 표준 가능량을 PKG Kea로
역산합니다. 원래 소요기준 결과와 PKG 환산 결과는 계산 원본을 바꾸지 않고 화면과 CSV
출력에서만 전환합니다.

표준 목표 Capa에 한해 `Pre B/D` 공정은 `WF 구분 = Dummy`인 부하량과 STEP 소요대수를
제품 Mix 가중의 분자·분모에서 모두 제외합니다. 이 예외는 일반 부하량·소요대수·확보율
계산을 변경하지 않으며 페이지 하단의 `예외 처리 공정`에서 현재 조회범위 제외 행 수와
함께 확인할 수 있습니다.

`로직 분석`은 전체 결과를 다시 전개하지 않고 Weeknum·공정·소요기준·양산·제품·Stack·
WF 속성을 모두 선택한 뒤 공정·주차 한 건만 계산합니다. 공정 종합 원수요 부하량,
STEP 소요대수, 공정별 대당 Capa, RUN_DAY, 대당 일 Capa, 가용대수와 최종 일 표준 가능량을
연속 산식으로 보여주고, 같은 종합값을 구성한 제품·WF 속성별 부하량 비중·소요대수 비중·
분류 유효 Capa를 함께 제공합니다. 이 집계는 분류 Capa의 산술평균이 아니라 부하량 비중을
적용한 조화가중 결과입니다.

표준 목표 Capa의 공정 필터와 「조회·집계 설정」(시작일·종료일·상세 토글·제품 분류 수준·
출력 지표)은 리비전별 공용 기본값과 사용자별 임시 선택을 분리합니다.
리비전을 불러오면 저장된 값이 모든 사용자의 초기값으로 적용되고, 이후 변경은 현재
브라우저 세션에만 영향을 줍니다. 현재 선택을 공용 기본값으로 확정하려면 활성 시나리오의
신규 리비전을 저장해야 하며, 빈 목록은 전체 공정을 의미합니다. 사이드바 조회기간을 바꾼 뒤
과거 리비전을 열어 저장된 조회일이 범위 밖이면 오류 대신 범위 안으로 맞추고 그 사실을
설정 칸에 한 줄로 알립니다. 조회·집계 설정을 저장하기 전에 만든 리비전에는 이 값이 없으며
그때는 화면 기본값으로 열립니다.

입력 탭의 `Excel 붙여넣기 일괄 수정`에서는 현재 조회 범위의 화면과 같은 월별 Wide CSV
양식을 다운로드합니다. Excel에서 월별 값만 수정하고 헤더를 포함한 전체 셀 범위를
복사·붙여넣으면
활성 시나리오 편집본이 원자적으로 교체되어 다른 계산 페이지에 즉시 반영됩니다. 이 RQ
편집값은 기존 정책대로 사이드바에서 신규 리비전을 저장해야 서버 재시작 후에도 다시
불러올 수 있습니다. 설비대수의 `RQ_EQP_OWN`, `RQ_EQP_LENT`, `RQ_EQP_AVBL`도 활성
시나리오 및 리비전 소유 테이블에 포함됩니다.

설비대수는 붙여넣기 말고 **시트에서 칸을 직접 고칠 수도 있습니다.** `기준 정보 → 설비대수`
안의 `보유`·`대여`·`가용` 탭이 다른 기준정보와 같은 편집기이고, `현황` 탭이 셋을 합친 조회
표입니다. 합친 표는 편집 대상이 아닙니다 — 보유와 대여를 더한 값에 숫자를 쓸 자리가 없습니다.

자세한 개발 구조와 변경 규칙은 [AGENTS.md](AGENTS.md), 확정사항과 향후 계획은
[docs/TODO.md](docs/TODO.md)를 참고합니다. 직전 세션의 상태와 다음 할 일은
[HANDOFF.md](HANDOFF.md)를 참고합니다.

모든 Python·PowerShell 파일 최상단에는 그 파일의 단일 책임을 설명하는 `Purpose` 한 줄을
유지하고, 책임이 달라지면 같은 변경에서 함께 고칩니다. 변경 출처와 이력은 주석이 아니라
Git commit history를 단일 근거로 합니다. 적용 후 체크섬이 불변인 SQL 마이그레이션은 직접
수정하지 않고 `docs/migration_catalog.md`에서 목적과 문서화 출처를 관리합니다. 정확한 작성
형식은 `AGENTS.md`의 `소스 파일 Purpose 헤더 규칙`을 따릅니다.

예전 배포로 되돌려 DB 에 이 코드가 모르는 더 높은 마이그레이션 버전이 적용돼 있으면 앱은
막지 않고 계속 돌며, 경고 로그와 함께 화면 맨 위에 「시뮬레이션 DB(또는 설비 DB) 가 이 코드보다
새 버전입니다(DB n · 코드 m)」 경고를 띄웁니다. 설비 DB 경고는 설비 DB 를 여는 화면에만 뜹니다.

## 입력 데이터

앱 런타임의 고정 입력은 `data/capa_simulation.duckdb`입니다. 이 파일이 없는 GitHub
체크아웃에서는 앱 시작 시 마이그레이션을 적용한 뒤 `config/bootstrap_display_order.json`과
코드로 생성한 2026년 `DEMO_*` 합성 Core Data를 공통 78컬럼 파이프라인에 통과시켜
초기 공식버전을 만듭니다. 생성된 DuckDB는 계속 로컬 자산이며 Git에 포함하지 않습니다.
표시순서는 `app_meta.global_display_order*`의 공용 프로필에 저장되고 모든 시나리오에
동일하게 적용되므로 계산 페이지는 XLSB를 열지 않습니다. 공용 프로필이 처음 만들어질 때는
기존 시나리오의 유효한 규칙과 선택적 `data/input/RQ_DISPLAY_ORDER.csv` 중 더 완전한
구성을 사용하며 둘 다 없으면 비민감 JSON 시드를 사용합니다. 기존
`templates/structure_template.xlsb`는 초기 표시순서 이관과 과거 결과 병행 검증에만
사용합니다.

자동 부트스트랩은 저장소에 시나리오가 하나도 없을 때만 동작합니다. 생성과 공식 발행
사이에 프로세스가 중단된 내장 시드는 다음 시작에서 공식 발행 단계만 복구합니다. 반면
사용자 시나리오가 있으나 공식버전이 없는 저장소는 임의 변경하지 않으므로 `시나리오 관리`에서
사용할 리비전을 공식버전으로 지정해야 합니다. 수동으로 같은 안전한 초기화를 확인하려면
다음 명령을 사용할 수 있습니다.

```powershell
.\.venv\Scripts\python.exe scripts\bootstrap_builtin_seed.py
```

내장 데이터는 앱과 계산 경로를 실행하기 위한 합성 데모이며 운영 기준정보가 아닙니다.
운영 전 `BigDataQuery 등록`으로 실제 시나리오를 만든 뒤 새 공식버전으로 지정합니다.

신규 시나리오의 원천 적재 개발 검증에는 다음 파일을 사용합니다.

```text
data/input/Core_Data.csv
```

`BigDataQuery 등록` 탭은 두 단계입니다 —
① 시작일·종료일(기본값 오늘)로 기간 내 시뮬레이션 코드 목록을 조회하고 검색·표시범위로
좁혀 한 행을 고르면, ② 시뮬레이션 코드·원천 시뮬레이션명·시나리오명·등록시점·메모가 자동
입력된 등록 폼이 채워지고 확인·수정 후 저장합니다. 종료일은 화면 표시대로 포함이라 오늘
적재분까지 조회됩니다. 상세 조회 기간은 폼의 두 날짜 칸이고, 코드를 고르면 그 코드의 **원천
등록일 7일 전 ~ 3일 뒤**로 채워집니다(기간이 길수록 사내 조회가 느려 기본은 좁게 둡니다). 등록 뒤에도
계속 수정·재적재된 시뮬레이션은 종료일을 늘려 조회합니다. 코드를 직접 적을 때는 두 칸을 비우고
`원천 DB 등록시점` 을 채우면 같은 규칙이 적용됩니다. 조회한 기간은 리비전 메모에 남습니다. 같은
코드는 원천이 다르면 다시 등록되지 않으므로(원천 코드 불변) 계속 수정되는 시뮬레이션은 처음부터
종료일을 넉넉히 잡습니다. 이미 등록된 코드도 목록에 `등록됨`으로 함께 보여 줍니다.
저장 자체는 같은 계약의 DataFrame을 직접 받아 CSV 파일 없이 적재합니다. 두 경로 모두 원천 행·컬럼 프로파일·
RQ 16개·초기 리비전·화면 프리셋을 하나의 DuckDB 트랜잭션으로 저장하며, 화면 정렬에는
시나리오와 분리된 공용 표시순서를 적용합니다. 새 원천 시나리오의 초기 프리셋은 현재
화면의 필터를 복사하지 않고 내려받은 데이터의 전체 생산계획년월과 전체 B/N 공정을
활성화하며, 표준 목표 Capa의 빈 공정 목록도 전체 공정을 뜻합니다. 표준 목표 Capa의
조회·집계 설정도 함께 비워 새 원천이 남의 조회일을 물려받지 않게 합니다. 원천 `제품정보`는
typed raw에 그대로 보존하고, RQ 변환 단계에서는 BigDataQuery가 공백 대신 반환하는 모든
언더바(`_`)를 공백으로 치환한 뒤 연속 공백을 하나로 정규화합니다.
`RQ_UPEH`·`RQ_LOT_RATIO`·`RQ_WF_RATIO`는
`Area_Name + STEP_SEQ + MCP_SEQ`까지 포함한 경로 키로 생성하며 `RQ_REQB`와 정확히
일치하는 경로끼리만 대당 Capa와 소요대수를 연결합니다. UPEH·Lot/WF 측정률의
`Area_Name`은 Core Data 변환과 기존 리비전의 `RQ_REQB ↔ 대당 Capa` 런타임 연결에서
입력 대소문자와 앞뒤 공백을 정규화해 `Main`·`MI`로 통일하며,
Lot/WF 측정률의 빈 값과 `0`은 측정 대상이 아닌 경로의 기본값 `1.0`으로 계산합니다.
Dummy Chip·Wafer의 EDS Loss 보정은 `WF 구분` 하나가 아니라 `(제품타입, WF 구분)` 짝으로
판정하므로 현재 Dummy가 있는 HBM에만 적용되며, `Dummy`·`DUMMY`나 앞뒤 공백 같은 표기
차이에는 영향을 받지 않아 기존 리비전과 BigDataQuery 원천을 함께 다룰 수 있습니다.
Core Data에서 같은 RQ 업무 키에 서로 다른 값이 발견되면 전체 변환을 중단하지 않고
**값이 있는 첫 값**을 임시 적용합니다. 숫자 컬럼의 `0`과 빈 문자열은 값 없음으로 보므로,
형제 행에 실제 값이 남아 있으면 그 값이 저장됩니다(형제가 모두 `0`이면 `0` 그대로입니다). BigDataQuery 등록 화면에는 테이블별 충돌 건수와
임시 제외 행 수를 표시하고, 업무 키·후보값·선택값·원천행 번호를 UTF-8 CSV로 제공합니다.
이 우회는 원천 정합성 확인을 위한 임시 정책이며 실제 집계 규칙을 대체하지 않습니다.
`RQ_PKG_PLAN`은 예외입니다 — `Pack Code`가 업무 키라서 Pack Code별 생산수량은 충돌이
아니라 별도 행으로 저장되고, 합산은 부하량·소요대수·PKG 환산 같은 계산 계층이 합니다.

STEP·MCP 키 도입 전에 첫 행 선택 방식으로 저장한 사내 검증 시나리오는 경로별 값이
유실됐을 수 있으므로 호환 변환하지 않고 제거한 뒤 같은 시뮬레이션 코드를 다시 등록합니다.
개발용 `Core Data 초기 시나리오`를 현재 변환 계약으로 교체할 때는 아래 명령을 사용합니다.
새 시나리오를 공식 발행한 뒤 같은 원천 코드의 기존 시나리오는 스크립트가 건드리지 않고
목록에 남깁니다. 필요 없으면 `시나리오 관리 → 시나리오 관리 탭 → 목록 관리`에서 지웁니다.
시나리오명은 겹칠 수 없으므로(보관본 포함) 같은 이름이 있으면 스크립트가 이름 뒤에 만든
시각을 붙입니다.

```powershell
.\.venv\Scripts\python.exe scripts\bootstrap_initial_duckdb_scenario.py --replace-existing
```

합성 데모 CSV 자체를 다시 만들었으면 위 명령은 거부됩니다 — 원천 코드는 불변이라 같은
코드에 다른 원천 데이터를 저장하지 않습니다. 새 원천 코드로 적재하면 새 시나리오가 공식
발행되고 기존 시나리오는 그대로 남습니다. 생성기는 앞서 자기가 연장한 계획을 걷어내고
원본 계획부터 다시 연장하므로, 이미 연장된 파일에 다시 돌려도 결과가 같습니다.
실행 중인 앱이 DB 를 잠그고 있으므로 적재 전에 앱을 먼저 내립니다.

```powershell
.\.venv\Scripts\python.exe scripts\generate_sample_core_data.py data\input\Core_Data.csv
.\.venv\Scripts\python.exe scripts\bootstrap_initial_duckdb_scenario.py --source-code <새 원천 코드> --scenario-name <시나리오 이름>
```

`--replace-existing` 없이 돌렸는데 같은 원천 코드의 시나리오가 이미 있으면, 스크립트는 그
시나리오의 활성 리비전을 공식버전으로 지정합니다. 그 리비전에 가상 제품이 들어 있으면
화면의 공식버전 지정처럼 확인을 받습니다 — 제품 · Stack 목록을 찍고 지정하지 않은 채 0 이
아닌 코드로 끝납니다. 실적과 대조할 수 없는 값임을 알고도 지정하려면
`--allow-virtual-products` 를 붙여 다시 실행합니다.

사내 조회에 쓰는
`src/capa_simulation/io/company_bigdataquery_adapter.py`의 `QUERY_TEMPLATE`과
`SOURCE_COLUMN_MAPPING`은 실제 원천 테이블의 SQL·컬럼명으로 이미 채워져 있고, 남은
것은 사내 환경에서의 접속·조회 검증입니다. `bigdataquery`는 사내 전용
환경에서만 설치하고 `pyproject.toml`의 공통 의존성에는 넣지 않습니다.

XLSB, SQLite 및 DuckDB 파일은 로컬 데이터이므로 Git에 포함되지 않습니다. 시뮬레이션
DuckDB는 `data/capa_simulation.duckdb`, 설비 운영 전용 DuckDB는
`data/equipment_availability.duckdb`를 사용합니다.

## 캐시와 시나리오

- 사이드바 선택기는 실제 DuckDB 시나리오·리비전을 선택한 뒤 `선택 리비전 불러오기`로
  RQ와 프리셋을 계산 상태에 적용합니다. 현재 웹 편집본과 프리셋은 사이드바에서 활성
  시나리오의 신규 불변 리비전으로 저장할 수 있습니다.
- 새 세션은 `app_meta.official_release`의 가장 최신 발행 리비전을 자동으로 불러옵니다.
- 시나리오 저장소가 완전히 비어 있으면 새 세션 활성화 전에 내장 합성 공식버전을 한 번만
  생성합니다. 기존 시나리오는 자동 부트스트랩이 변경하지 않습니다.
- 불변 리비전 스냅샷은 서버 공통 캐시에 최대 32개까지 재사용합니다. Streamlit 캐시에는
  재로딩 시 클래스 식별자가 바뀔 수 있는 `ScenarioSnapshot` 객체를 직접 저장하지 않고
  기본형 메타데이터와 DataFrame payload만 저장한 뒤 캐시 밖에서 모델을 재구성합니다.
- 동일 입력의 부하량·Capa·소요대수·확보율과 HOME 전체 계산 그래프를 재사용합니다. HOME의
  상위 캐시는 리비전·조회기간·표시순서 해시로 만든 경량 키만 비교하므로 warm rerun마다
  전체 입력 DataFrame을 다시 해싱하지 않습니다.
- 대당 Capa·소요대수는 **시나리오 전체 기간으로 한 번 계산**하고 조회기간은 그 결과를
  잘라 씁니다. 조회기간을 바꿔도 다시 계산하지 않습니다. 대신 **어느 달이든 기준정보
  오류가 있으면 조회기간과 상관없이 계산 페이지가 멈춥니다.** 오류가 보는 기간 밖에만
  있으면 「조회기간(…) 밖의 달에 기준정보 오류가 있어 계산을 멈췄습니다」로 알립니다.
  기준 정보 페이지에서 그 달을 고친 뒤 새 리비전으로 저장하면 풀립니다. 기준 정보 편집
  페이지 자체는 이 계산을 쓰지 않아 막히지 않습니다.
- 같은 계산을 **리비전 저장과 공식버전 지정 전에** 한 번 돌립니다. 편집이 계산을 깨뜨리면
  저장하지 않고 그 자리에서 이유를 보여 줍니다. 편집 전부터 있던 오류는 저장을 막지 않고
  「공식버전으로 지정할 수 없습니다」라고 경고합니다(여러 오류를 하나씩 고쳐 저장할 수
  있게). 계산되지 않는 리비전은 공식버전으로 지정할 수 없습니다 — 공식버전은 모든
  사용자가 처음 여는 화면이기 때문입니다. BigDataQuery 등록은 검사하지 않습니다.
- HOME 본문은 `Main`·`Preference`·`Past Data` 세 탭입니다. `Main`이 계획·LOB·B/N Figure를
  모두 그리고, `Preference`가 공용 설정(비교 시나리오·확보율 판정 기준·선행 B/O·선행 입고 실적·
  Summary·Top5·주요공정·실행 Capa)을 받습니다. 보는 조건 토글(`선행 B/O`·`선행 입고`·`실행 Loss`·`GAP`·
  `상세 계획`·`EDP 포함`·`Past Data 포함`)은 사이드바
  `LOB 표시 조건` 카드에 있습니다(Main 탭에서만). 설명은 헤더의 `Guide` 입니다.
- `Capa LOB 현황` 맨 아래 `제품별 비중` 행은 월마다 도넛으로 제품 구성을 그립니다. 단위는
  `LOB 표시 조건` 의 `제품별 비중 단위`(Wafer·PKG)로 고르고, Wafer 의 분모는 같은 표의 `Wafer 계획`,
  PKG 의 분모는 그 달 PKG 생산수량 전체입니다. 같은 제품의 양산·ER 을 더해 비중을 내며, 같은 제품은
  모든 도넛에서 같은 색입니다(제품이 여섯을 넘으면 작은 제품을 `기타` 로 모읍니다).
- `EDP 포함`을 끄면 LOB로 표현되는 값(Density·Wafer 계획·Wafer Capa·B/N Capa
  막대·Top 5·상세 B/N의 Wafer Capa)과 계획 세부수량에서 EDP-TSV를 뺍니다. 설비가 받는 부하는
  전체 계획 그대로라 **확보율과 B/N 공정 순위는 바뀌지 않습니다.**
- `LOB 표시 조건` 의 `상세` 토글을 켜면 제품·Stack 아래에 거래선을
  분류로 더합니다. 거래선 수만큼 행이 늘어 표가 길어집니다. 거래선 정렬은
  `Admin Area → 표시순서 관리`에 `분류컬럼 = Customer` 규칙을 `부하량`·`PKG PLAN` 범위로
  넣으면 걸리며, 상세를 끈 화면에서는 같은 규칙이 아무 일도 하지 않습니다.
- `계획 세부수량`과 `상세 B/N 공정` 사이에 `주요공정 확보율` 격자가 있습니다. 한 줄이 끝까지
  같은 공정이라 **부족이 시작되는 달이 가로로 읽힙니다** — 상세 B/N 의 행은 순위라 같은 줄이
  매달 다른 공정이어서 그 질문에는 답하지 못합니다. 그릴 공정은 **이름 붙은 프리셋**
  (`Preference → 주요공정 히트맵 프리셋`, 예: `A 그룹`·`B 그룹`)으로 시나리오와 분리된 공용 프로필에
  저장하고, 사이드바 `주요공정 히트맵` 카드에서 그중 하나를 골라 봅니다(맨 앞 프리셋이 기본).
  **고른 차례가 곧 행 순서**이고(확보율로 다시 정렬하면 매달 행이 뛰어다닙니다), 프리셋이
  없으면 그 구획은 안내 한 줄만 남습니다. 칸 색은 확보·경고·부족 판정을 따르고 칸마다
  확보율 숫자를 함께 적습니다. 연간 Total 열은 비웁니다 — 확보율의 연평균은 부하량 가중이
  필요한데 이 화면에 그 근거가 없습니다.
- `Past Data` 탭에 과거 구간을 넣으면 화면이 이어 그립니다. 월별 Density·Wafer Total,
  계획 세부수량, 확보율 세 표를 CSV 양식으로 내려받아 Excel에서 채운 뒤 표마다 `Excel
  붙여넣기` 팝업에 붙여넣고, 맨 위 `과거 구간 저장` 으로 한 번에 저장합니다.
  Wafer Capa와 B/N Capa는 확보율을 곱해 만들고 B/N 순위는 확보율 오름차순이라 따로 넣지
  않습니다. **계산 결과가 있는 달은 계산이 이깁니다.** 과거 달에는 `선행 B/O`만 걸립니다
  (`선행 입고` 글자는 표시라 과거 달에도 적힙니다).
- 1~12월이 모두 조회범위 안에 있는 해는 그 해 12월 오른쪽에 `27년` 같은 연간 Total 열이
  붙습니다. Density·Wafer 계획·계획 세부수량만 합계를 적고 Wafer Capa·생산계획 LOB·
  B/N Top 5·상세 B/N은 비웁니다. 월별 Capa의 단순 합은 연간 Capa가 아니기 때문입니다.
- `Preference`에서 비교 시나리오와 리비전을 고르고 `LOB 표시 조건` 의 `GAP` 토글을
  켜면 Density·Wafer 계획·계획 세부수량 값 **아래**에 비교 대비 증감을 적습니다. 고른
  리비전에서 **계획만** 가져오고 환산에 쓰는 표는 현재 것을 씁니다.
  비교 시나리오에만 있는 제품·Stack 조합도 행으로 남겨 사라진 제품이 보이게 합니다.
  `선행 B/O`·`선행 입고`·`GAP`을 어떻게 켜도 **원래 숫자의 크기와 자리는 그대로입니다** — 증감
  두 줄이 들어갈 자리를 행 높이가 미리 비워 두기 때문입니다. 증감 글자는 표·막대·세부수량
  어디서나 같은 크기이고, 선행 B/O·값·GAP 사이 간격도 위아래가 같습니다. 선행 입고 실적은 칸
  오른쪽 끝, 값과 같은 높이에 증감 크기(12px)로 적힙니다(밝게 검정·어둡게 본문 글자색). 값이 길면 값과
  겹칠 수 있습니다(2026-10-07 사용자 결정) — 값과는 크기·자리로만 갈립니다.
- 시나리오를 바꾸면 HOME 토글이 **전부** 꺼집니다 — `선행 B/O`·`선행 입고`·`실행`·`GAP`·`상세`·
  `EDP 포함`·`Past Data 포함` 일곱 개입니다. 모두 기준정보 위에 무언가를 얹거나 빼는
  스위치라, 켠 채로 바꾸면 바꾸기 전 시나리오를 전제로 켠 것이 새 계획 위에 남습니다.
  새 시나리오를 있는 그대로 먼저 보고, 얹을 것은 다시 켜면 됩니다
  (`Past Data 포함` 만 기본이 켬이라 켜진 상태로 돌아갑니다).
  **보던 탭과 조회 조건은 그대로 남습니다** — 그것들은 값에 닿지 않습니다.
- `EDP 포함`의 기본값은 꺼짐입니다.
- 다른 탭을 보고 있는 동안에는 대시보드를 그리지 않습니다. 숨긴 채로 그리면 표 머리글이
  셀 가운데를 놓치고 그대로 굳기 때문입니다. 탭을 누르면 그때 그립니다.
  지금 보고 있는 시나리오도 고를 수 있어, 리비전이 달라지며 계획이 얼마나 바뀌었는지를
  같은 시나리오 안에서 견줄 수 있습니다.
- `Preference`의 `선행 B/O`(계획보다 앞서 만든 B/O 재공 — S.PKG FRONT 공정이 끝나는 Bond Out
  재공)에 앞서 만든 달은 `+`, 그만큼 줄어드는 달은 `-`를 억Gb로 넣고 `LOB 표시 조건` 의
  `선행 B/O` 토글을 켜면 계획과 확보율에 반영합니다. 생산계획에 없는 물량이라 그만큼 부하가
  늘어난 것으로 보되 설비를 늘린 것은 아니므로 **Capa는 정확히 그대로**이고 계획과 확보율만
  반비례로 움직입니다. 바뀐 칸에는 기존값 대비 증감을 작게 적고, 기존 계획은 표식·라벨 없는
  점선으로 함께 그립니다. 지금은 모든 공정에 같은 비율로 걸립니다(FRONT 공정만 고르는 분류는
  아직 없습니다). 선행 B/O 는 시나리오와 분리된 공용 프로필입니다.
- `Preference`의 `선행 입고 실적`(계획보다 앞서 입고한 물량, 억Gb, 부호는 넣은 그대로)은 이미
  생산계획에 든 물량이라 **계산을 바꾸지 않습니다.** `선행 입고` 토글을 켜면 Density 칸 오른쪽
  위에 `+1.2` 처럼 적고(마우스를 올리면 `선행 입고 실적 +1.2억Gb`), 연간 Total 칸에는 적지
  않습니다. 칸은 `Capa LOB 현황` 의 달 그대로라 `Past Data 포함` 을 켜면 과거 달에도 넣고 볼 수
  있습니다. 이것도 시나리오와 분리된 공용 프로필입니다.
- `Preference`의 `실행 Capa 반영`에 년월·공정·증감 확보율(%p)·비고를 넣고 `실행` 토글을 켜면,
  기준정보 밖에서 생긴 변수(비가동대수 증가로 인한 가용대수 축소·UPEH 실적 부진·재공 부진)를
  확보율에 바로 얹습니다. **퍼센트포인트 차감**이라 확보율 105%에 `-10`을 넣으면 95%가 됩니다
  (비율 곱셈이 아닙니다). 리비전을 새로 저장하지 않고 화면에서 즉시 봅니다.
- 실행 조정은 **원데이터 기준**이고 선행은 그 위에 얹힙니다. B/N 순위도 조정된 확보율로 다시
  매겨지며, 생산계획 LOB의 B/N 확보율은 재배치 뒤의 최종 B/N 공정 기준입니다. 줄거나 늘어난
  만큼은 색 영역으로 보입니다 — 감소는 밝은 적분홍, 증가는 밝은 연두이고 테두리는 감소면
  줄어든 결과값에만, 증가면 늘어난 결과값 전체에 두릅니다. 색 영역에 마우스를 올리면 조정량과
  비고가 뜹니다.
- 실행 조정은 확보율만 옮깁니다. **가용대수·소요대수는 기준정보 값 그대로**라
  `확보율 = 가용대수 ÷ 소요대수`가 성립하지 않습니다 — 조정 사유가 비가동·UPEH·재공으로
  제각각이라 어느 항으로 되돌릴지 정할 수 없기 때문이고, 차이의 출처는 hover가 밝힙니다.
  공정은 화면 표시명이 아니라 **원본 공정명** 기준으로 저장합니다. 실행 조정도 시나리오와
  분리된 공용 프로필입니다.
- HOME은 페이지 제목 오른쪽에 진행 막대를 띄워 지금 어느 단계이고 몇 퍼센트인지 알립니다.
  제목 줄 안이라 막대가 사라져도 아래 차트가 밀리지 않습니다. 누적 퍼센트는 단계 수를
  균등 분할한 값이 아니라 측정한 소요 시간 비율입니다.
- 확보·경고 판정 기준은 `Preference` 의 `확보율 판정 기준` 에서 `판정 기준 저장` 을 누를 때
  반영됩니다(사이드바에는 입력 칸이 없습니다). 기본값과 합쳐 어느 달이든 경고 기준이 확보 기준보다
  크면 저장하지 않고 그 달을 알리며, 편집하는 사이 다른 사람이 먼저 저장했으면 저장하지 않고
  알립니다. 한 번도 저장하지 않았으면 최신 공식버전 프리셋의 기준을 씁니다. 포함 공정은 사이드바
  `B/N 집계 공정` 의 `공정 선택` 팝업에서 `선택 공정 적용` 을 누를 때 반영됩니다.
- HOME `LOB 표시 조건` 의 `Past Data 포함` 토글은 **기본이 켬**입니다. 끄면 `Past Data` 탭에
  넣어 둔 과거 구간을 화면에서 빼고 활성 시나리오의 계산 결과만으로 화면을 구성합니다.
  과거 값 자체는 지워지지 않고 `Past Data` 탭에 그대로 남습니다.
- HOME 단계별 소요시간은 `scripts/benchmark_home.py` 로 잽니다. 화면에서 봐야 할 때만
  세션 키 `dashboard_show_performance` 를 켭니다 — 사이드바 토글이던 것을 뺐습니다.
  개발용 계측 하나가 모든 사용자가 늘 보는 자리를 차지할 이유가 없습니다.
- `기준 정보`의 UPEH·설비대수·효율·여유율·일수·Lot/WF측정률·STEP 구성 편집기는 선택한
  탭만 생성합니다.
  탭 전환 시 rerun되지만 입력 적용·세션 revision 계약은 기존과 같습니다.
- 편집기 탭마다 그 탭의 분류 컬럼 필터가 있습니다. **필터는 화면만 좁히고 `변경사항 적용`은
  필터와 무관하게 표 전체를 저장합니다.** 필터를 바꾸면 아직 적용하지 않은 편집은 사라집니다.
- 사이드바 맨 아래 `Support` 상자 안에 `Admin Area` 와 `VOC` 가 있습니다. 질문·개선 요청·오류 신고를
  남기고 답을 주고받는 자유 게시판이며, **시나리오·조회기간과 무관**합니다 — 시나리오를
  지워도 그때 나온 질문은 남습니다. 로그인이 없으므로 작성자는 직접 적습니다.
- `산출 결과` 의 `대당 Capa` 탭에서 표시 방식을 `STEP별` 로 두면 공정을 선택해야 그립니다.
  미선택이면 표와 CSV 버튼을 감추고 안내만 보여 줍니다 — 전 공정 STEP을 한 번에 그리면
  표가 수천 행이 되어 로딩이 길어지기 때문입니다. 전체 조망은 `공정별` 이 미선택 상태로
  그대로 제공합니다.
- Lot 측정률·WF측정률이 음수인 경로와 대당 Capa가 0 이하인 경로는 그 행만 계산에서
  빠지고 화면은 계속 그려집니다. 측정률 `0`은 제외 대상이 아니라 `1.0`으로 적용합니다.
  `산출 결과` 가 제외 건수를 경고로 알리고 사유가 붙은 제외 목록을 상세 표와 UTF-8 CSV로
  제공하므로, 문제 값은 `기준 정보` 의 해당 편집 탭에서 고칩니다.
- 소요기준 `PKG` 공정(스택·Mold·MPGA Saw 이후 PKG Chip 을 투입하는 공정)은 **Buffer 로만
  셉니다.** 부하량은 생산수량 그대로이고 수율을 걸지 않습니다(Good Die 만 들어온다).
  Core·Top·Dummy 는 Buffer 위에 쌓여 있어 따로 세지 않으므로, 그런 `RQ_REQB` 행은 소요대수에
  넣지 않고 제외 목록에 `PKG 기준은 Buffer 로만 계수` 로 남깁니다 — 고칠 값이 아니라 안내입니다.
- 저장하지 않은 웹 편집값은 브라우저 세션별 활성 시나리오에만 존재합니다.
- 페이지를 이동해도 편집값은 유지되고 다른 산출 페이지에 반영됩니다.
- `시나리오 관리`에서 신규 시나리오 또는 리비전으로 저장하면 서버 재시작 후에도
  DuckDB에서 다시 불러올 수 있습니다.
- 동일 시뮬레이션 코드는 원천 내용이 바뀌지 않는 불변 데이터로 취급합니다. 동일한 raw
  스냅샷의 새 시나리오 물리 복제는 허용하지만 내용이 다르면 등록을 거부하고 기존
  시나리오의 새 리비전으로 관리합니다.
- 리비전은 편집 가능한 14개 RQ 테이블과 조회기간·B/N 포함 공정·
  표준 목표 Capa 공정 기본값·확보율 판정 기준의 전체 스냅샷입니다. 과거 리비전은
  변경하지 않으며 과거 시점에서 분기할 수 있습니다. 리비전에 실린 판정 기준은 이제 판정에
  쓰지 않습니다(공용 `확보율 판정 기준` 이 정본) — 공용 기준을 한 번도 저장하지 않았을 때
  최신 공식버전의 값이 그 기본값이 될 뿐입니다.
- 표시순서는 시나리오와 분리된 공용 DB 설정입니다. `Admin Area → 표시순서 관리`에서 현재 전체 규칙을
  UTF-8 CSV로 내려받아 Excel에서 수정한 뒤 헤더 포함 전체 표를 붙여넣어 일괄 교체할 수
  있고, 페이지·탭 범위별 직접
  편집도 가능합니다. `정렬우선순위`는 행 정렬뿐 아니라 화면의 왼쪽 분류컬럼 배치에도
  적용하며, 경로 상세 표의 `STEP_SEQ → MCP_SEQ`는 항상 마지막 분류 계층으로 유지합니다.
  기존 공용 프로필에 이 규칙이 없으면 앱 시작 시 자동 보강합니다. 변경은 새 시나리오
  리비전을 만들지 않고 모든 시나리오에 적용됩니다.
- 공식 지정은 리비전을 수정하지 않고 발행 이력을 추가합니다. 최신 공식 시나리오는 다른
  공식버전을 먼저 지정하기 전에는 삭제할 수 없습니다.
- 고른 리비전에 가상 제품이 들어 있으면 공식 지정 전에 제품 · Stack 목록과 「실적과 대조할 수
  없는 값입니다」 경고를 보이고, 「가상 제품이 포함된 것을 확인했습니다」를 체크해야 지정
  버튼이 열립니다. 가상 제품이 없으면 지정 화면은 전과 같습니다.
- STEP·MCP 경로 키가 없는 옛 리비전은 불러오기 전에 막고 이유를 알립니다. 활성화한 뒤에
  계산이 멈추면 활성 시나리오가 이미 바뀐 뒤라 화면에서 되돌릴 수 없기 때문입니다. 같은
  원천 코드를 `BigDataQuery 등록`으로 다시 등록해 새 시나리오로 저장하세요.
- 목록에서 시나리오를 치우는 기본 수단은 **보관**입니다. 목록에서 숨겨지고 새 리비전
  저장·공식버전 지정이 막히지만 행은 그대로 남아 「보관된 시나리오」에서 되돌릴 수 있습니다.
  현재 최신 공식버전의 시나리오는 보관할 수 없습니다.
- **보관은 파일 크기를 줄이지 않습니다.** 행이 한 바이트도 사라지지 않으므로 오히려 지운
  경우보다 크게 유지됩니다. 보관이 사는 것은 용량이 아니라 되돌릴 여지입니다.
- 영구 삭제는 보관함 안에 있습니다. 물리 삭제이며 되돌릴 수 없고, 그 시나리오의
  리비전·원천 데이터·프리셋과 공식 발행 이력이 함께 사라집니다. DuckDB는
  지운 페이지를 파일에 되돌려주지 않아 파일 크기는 줄지 않습니다. 파일을 실제로 줄이려면
  `scripts/compact_duckdb.py`로 재구축합니다. 인자를 주지 않으면 운영 DB 두 개를 모두
  처리하고, `--dry-run`으로 줄어드는 크기만 먼저 재거나 `--keep-backup`으로 바꿔치기한
  원본을 남길 수 있습니다. **반드시 앱 서버를 내린 뒤에 실행합니다.** 앱은 rerun 이 끝나면
  DB 연결을 닫으므로 유휴 상태의 앱은 잠금이 없어 스크립트가 막지 못하고, 그 사이 앱이
  저장한 내용은 교체와 함께 사라질 수 있습니다. 스크립트는 원본 행 수를 세는 순간부터
  복사·검증이 끝날 때까지 원본을 읽기 전용으로 붙들어 그동안의 앱 저장을 오류로 막지만,
  Windows 는 열린 파일을 옮길 수 없어 닫고 바꿔치기하는 수 ms 의 틈은 남습니다.
  `managed` 모드에서는 앱의 심장박동이 살아 있으면 시작 전에 중단합니다. 다만 심장박동은
  rerun 때만 적히므로 최근 90초 안에 rerun 한 앱만 잡고, `managed` 모드라도 유휴 상태의 앱은
  보이지 않습니다. 실행 중인 앱을 찾지 못하면 스크립트는 서버를 내렸는지 직접 확인하라고
  알립니다.
- 오브젝트 스토리지 동기화를 켠 사내 환경(`managed` 모드)에서는 DuckDB 파일 옆에
  `<db파일명>.sync.json` 사이드카가 생겨 원격 세대와 아직 올리지 않은 변경 표시를
  기록합니다.

## 가용설비 현황 관리

- 설비 전용 DB가 비어 있으면 개발용 고정 샘플의 공정별 보유대수를
  기존 보유대수 초기 샘플로 표시합니다. 원본에 2차 분류가 없어 `분류=전체`로 표시하며,
  사용자가 첫 이력을 저장하기 전에는 DB에 기록하지 않습니다.
- 호기 마스터가 비어 있으면 현재 날짜를 기준으로 입고 예정·셋업 진행중·가용·반출 예정·
  이설 예정·보관 설비·운영 비가동 상태의 화면 검토용 호기 7대를 가용설비와 Space
  대시보드에 표시합니다. 이 샘플도 DB에 저장하지 않으며 실제 호기를 저장하면 사라집니다.
- 기존 보유대수와 공정명은 설비 전용 입력표에서 직접 등록합니다. 오래된 가동설비처럼
  호기별 양산전환 이력을 관리할 실익이 없는 설비를 공정·분류별 기준 대수로 유지합니다.
- 기존 보유대수는 전체 조회기간에 즉시 가용한 기준 대수입니다.
- 호기 마스터는 `설비명` 을 키로 구분·공정대·소분류, Maker·Model, 공정구분·투자Capa·투자구분·
  사용기준·담당자·설비가동현황 등 참고 속성, 동·층,
  Space X좌표·Y좌표·Xsize·Ysize, 제진대·물류·반입·Qual·반출·이설 일정과
  Qual 실행관리용 확정상태, 반입/Qual 이력·호기이력·설비이력,
  보관유무·기존설비여부·레이아웃표시, 환산비·Main 설비, 메모1~3 을 관리합니다. 공정소분류를 대시보드와
  레이아웃의 주 공정 기준으로 사용하며 반입일부터 보유대수, Qual일부터 가용대수에
  반영합니다. 반출·이설 실행일부터 보유·가용·레이아웃에서 제외합니다.
- 신규 호기의 반입·Qual 일정은 비워 둘 수 있습니다. 반입이 비면 입고 예정, 반입만 있고
  Qual 이 비면 셋업 진행중으로 남아 날짜가 들어올 때까지 가용대수에 들지 않습니다. 가용설비
  현황의 Main `가용대수`·`호기 현황` 과 Static/Dynamic 이 그런 설비를 「일정 미정 N대 (반입 미정
  a · Qual 미정 b)」 한 줄로 알립니다(모듈 설비는 지분으로 셉니다).
- 확정상태는 Qual 일정에만 적용하며 계획·확정·완료·지연으로 관리합니다. Qual 일정이 있는
  신규 호기에만 필수입니다. 이 값은 실행 모니터링 용도이고 가용대수는 기존과 동일하게
  Qual일정을 기준으로 계산합니다.
- 개발대여·공사·고장·이설 등 운영 비가동은 호기별 시작일·종료일로 별도 관리하며,
  가용 설비의 해당 기간을 가용대수에서 제외합니다.
- 기존 보유대수·호기 마스터·비가동 일정 세 표 모두 웹에서 행을 추가하거나 CSV 양식을
  Excel에서 수정한 뒤 헤더 포함 전체 표를 붙여넣을 수 있습니다. 입력 표는 각각
  공정 + 분류, 설비명, 설비명 + 비가동유형 + 시작일을 기준으로 현재 편집본에
  추가·대체됩니다. Import 전 신규·대체 행과 변경 컬럼을 미리 확인하고 편집본 적용을
  확정하며, DuckDB 저장은 별도 저장 버튼에서 수행합니다. 다운로드 양식의 2행에는 입력
  예시가 있고, 호기 마스터 양식의 3행부터는 설비명을 비운 채 허용값만 나열한 안내 행이
  이어집니다. 설비명이 빈 안내 행은 붙여넣기·업로드 때 자동으로 제외됩니다. 기존 보유대수
  양식에는 안내 행이 없습니다. 공정·분류·기존보유대수 중 하나라도 값이 있으면 행을
  남기므로, 일부만 채운 안내 행은 그대로 누락값 오류가 되기 때문입니다. 기존보유대수는
  소수 둘째 자리(모듈 단위 0.25대)까지 받고, 숫자가 틀리면 오류에 그 행의 공정·분류를 적습니다.
- 붙여넣기는 추가·대체만 하므로 행을 지울 때는 `직접 편집`을 씁니다. 세 표 모두 맨 앞
  `선택` 칸으로 행을 고르거나, 필터 조건을 고른 뒤 `필터에 맞는 행 모두 선택`을 눌러
  한 번에 고릅니다(보기를 적용하지 않아도 고른 조건대로 고릅니다). `선택 행 삭제` →
  `삭제 확정`을 누르면 편집본에서 빠지고, 호기를 지우면 그 호기의 비가동 일정도 함께
  빠집니다. 저장하기 전까지는 `방금 삭제 되돌리기`로 되돌릴 수 있고, `설비 데이터
  저장`을 눌러야 새 리비전이 됩니다.
- 주차는 월요일부터 일요일까지의 ISO Weeknum(`YY-W##`)으로 표시하며, 가용설비
  페이지 상단에서 시뮬레이션과 독립된 조회기간을 설정합니다.
- 대시보드 조회 조건은 `공정구분 → 투자구분 → 공정대분류 → 공정소분류` 순으로 제공하며,
  선택값을 호기 상태·비가동·주차 집계에 함께 적용합니다. 집계형 기존 보유대수에는 앞의
  세 속성이 없으므로 공정소분류 조건만 적용합니다.
- 저장은 현재 데이터를 덮어쓰지 않고 기존 보유대수·호기 마스터·비가동 일정 전체를 한
  DuckDB 리비전으로 추가합니다. 과거 리비전은 공정·동·층·설비명·비가동유형·기간으로
  필터링해 다시 확인할 수 있습니다.
- 설비 리비전 본문은 불변 revision ID별 서버 캐시에 저장해 가용설비와 Space 페이지가
  같은 DataFrame을 DB에서 반복 로딩하지 않습니다. 주차 집계도 설비 입력을 한 번만
  정규화한 뒤 주차별 상태를 공정 단위로 일괄 집계합니다.
- Space 현황은 가장 최근 저장 리비전의 호기별 좌표와 일정을 읽습니다. 집계형 기존
  보유대수는 호기·좌표가 없으므로 Space 배치에는 표시하지 않습니다.
- `Static/Dynamic → 분류별 내역` 은 `표시` 를 `호기 목록` 으로 바꾸면 월별 분류 대수를 이루는
  호기별 기여(기여일수·대수·환산대수)를 펼치고 CSV로 내려받습니다. `대수` 표에서 칸 하나를
  누르면 그 달·분류의 호기만 아래에 뜹니다. 같은 칸의 대수를 더하면 표의 값입니다.
  조건 카드의 `호기 필터` 에서 호기 마스터 컬럼(공정구분·Model·동 …)과 값을 고르면 공정과 함께
  **걸린 호기만** 분류대로 다시 더합니다(기존보유·Static·GAP 은 호기 속성이 없어 빠집니다).
- 이 대시보드의 운영 가용대수는 현재 `RQ_EQP_AVBL`을 사용하는 Capa·확보율 계산을
  대체하지 않습니다.
- 설비 페이지는 시뮬레이션 시나리오 DB, 활성 리비전, `RQ_*` 기준정보와 Capa 계산 캐시를
  읽지 않습니다. 향후 정합성 검증이 끝난 뒤 별도 연결 계층에서 공정명을 키로 연계합니다.

현재 `data/capa_simulation.db`는 과거 Excel/SQLite 병행 검증용이며 앱에서 읽지 않습니다.
두 DuckDB 파일은 서로 독립된 로컬 저장소이며, 단일 Streamlit 서버 프로세스 안에서 각
Repository의 쓰기를 별도 잠금과 DB 트랜잭션으로 직렬화합니다. 상세 모델은
[docs/data_model.md](docs/data_model.md)를 참고합니다.

## 초기 설정

처음 세팅하는 사람이 위에서부터 그대로 따라 하면 됩니다. **어느 환경인지부터 고르세요.**

| | 사외 (개발 PC) | 사내 (WebIDE) |
|---|---|---|
| 패키지 관리 | `uv` | `uv` |
| 추가로 필요한 것 | 없음 | `bigdataquery` (사내 인덱스) |
| 코드 수정 | 합니다 | **하지 않습니다** — `docs/dual_env_workflow.md` |

의존성 선언은 `pyproject.toml` 하나이고 **양쪽이 완전히 같습니다.** 개발 도구(mypy·ruff·
pytest)는 extra 가 아니라 PEP 735 의존성 그룹 `[dependency-groups]` 의 `dev` 에 있어
`uv sync` 가 기본으로 함께 설치합니다.

### 공통 — 0단계. 준비물 확인

```powershell
git --version
py -3.10 --version     # 3.10.11 이 나와야 합니다
uv --version
```

- **Python 3.10.11 64-bit 고정입니다.** 다른 마이너 버전은 씁니다만 권장하지 않습니다.
- `uv` 가 없으면 `pip install uv` 또는 [astral.sh/uv](https://docs.astral.sh/uv/) 안내를 따릅니다.
- `py -3.10` 이 없다면 Python 3.10.11 을 먼저 설치합니다.

### 사외 (개발 PC)

**1. 받기**

```powershell
git clone <저장소 주소> C:\dev\streamlit_project
cd C:\dev\streamlit_project
```

**2. 환경 만들기**

```powershell
uv sync
```

`.venv` 가 만들어지고 `dev` 그룹까지 설치됩니다. 이후 명령은 `.\.venv\Scripts\python.exe ...`
또는 `uv run python ...` 둘 다 됩니다. **사내에서는 `uv run --no-sync python ...` 을 씁니다** —
`uv run` 이 돌기 전에 하는 동기화가 락을 다시 잡고 빠진 것을 설치하는데, `--no-sync` 는 그
일이 아예 일어나지 않게 못박습니다.

> 지우는 것은 **맨 `uv sync`** 입니다. 맨 `uv run` 은 지우지 않습니다 — uv 0.12.13 에서 락에
> 없는 패키지를 넣어 두고 재 보면 `uv sync` 만 `Uninstalled 1 package` 를 찍고, `uv run` 은
> 락이 낡아 다시 잡는 경우에도 넣기만 합니다. `uv sync --inexact` 와 `uv run --no-sync` 는
> 둘 다 지우지 않습니다.

**3. 확인**

```powershell
.\.venv\Scripts\python.exe -m pytest
.\.venv\Scripts\python.exe -m streamlit run app.py
```

빈 `data/` 상태에서도 앱이 뜹니다 — 시뮬레이션 DB 와 내장 데모 공식버전이 첫 실행에
만들어집니다. Excel·Core Data CSV·사내 DB 없이 HOME 과 계산 페이지를 열 수 있습니다.

여기까지가 사외 세팅의 전부입니다.

### 사내 (WebIDE)

사외와 **1~3단계가 같고**, 그 뒤에 두 단계가 더 있습니다.

**1~3. 사외와 동일**

배포 ZIP 으로 받았다면 `git clone` 대신 그 폴더에서 시작합니다. 최초 1회는 ZIP 을 손으로
풀고, 그 다음부터는 `scripts/apply_deploy_package.py` 가 대신합니다(아래 5단계).

**4. 사내 전용 패키지 넣기**

```powershell
uv pip install -r requirements-company.txt
```

`bigdataquery` 를 사내 Artifactory 인덱스에서 받습니다. 인덱스 주소는 그 파일 안에 있으니
따로 칠 것이 없습니다.

> **C-DEP WebIDE 에서는 위 한 줄이 그대로 안 됩니다.** 이 계열 이미지는 `UV_DEFAULT_INDEX`
> 를 공개 PyPI 미러로 고정해 두어 파일 안의 `--index-url` 보다 먼저 이기고, uv 가 사내 CA
> 를 몰라 TLS 에서도 막힙니다. 추가 인덱스로 넣고 시스템 인증서를 쓰게 하세요.
>
> ```bash
> export UV_EXTRA_INDEX_URL="https://<AD 계정>:<Artifactory API 토큰>@artifactory.samsungds.net/repository/dataservice-devsecops-pypi/simple"
> uv pip install bigdataquery==2.5.0 --system-certs
> ```
>
> 설치 뒤 조회까지 되려면 로그인과 요청자 계정이 더 필요합니다 —
> [`docs/bigdataquery_webide_setup.md`](docs/bigdataquery_webide_setup.md) 를 보세요.

> **이 뒤로는 `uv sync` 대신 `uv sync --inexact` 를 씁니다.**
> 그냥 `uv sync` 는 **락에 없는 패키지를 지웁니다** — `bigdataquery` 가 그렇습니다.
> 실수로 지웠으면 위 명령을 다시 돌리면 됩니다.

패키지가 없어도 앱은 뜹니다. 사내 조회(BigDataQuery) 화면만 안내 문구를 띄우고 멈춥니다.

**왜 `pyproject.toml` 에 적지 않나** — uv 락파일은 universal 이라 extra·group 을 가리지
않고 전부 해석합니다. `[project.optional-dependencies]` 에 두면 `--extra` 를 고르지 않아도
사내 인덱스를 찾으러 가고, 닿지 못하는 개발 PC 에서는 `uv lock` 이 그 자리에서 죽습니다
(실측: `dns error`). 파일로 빼 둔 덕분에 선언과 락이 양쪽에서 같고, 그래서 **배포 ZIP 에서
빼야 할 파일이 없습니다.**

**5. 배포 적용 도구 자리 잡기 (최초 1회)**

`scripts/apply_deploy_package.py` 는 사내에서 도는데 사외에서 만듭니다. 첫 ZIP 은 손으로
풀어야 하고, 그 다음부터는 이 스크립트가 적용을 맡습니다.

```powershell
uv run --no-sync python scripts/apply_deploy_package.py <내려받은 ZIP> --dry-run
```

`--dry-run` 은 아무것도 바꾸지 않고 무엇이 지워지고 덮일지만 보여 줍니다. 처음에는 꼭
이것부터 돌려 보세요.

**6. 사내 규칙 걸기 (최초 1회)**

```powershell
New-Item -ItemType Directory .claude -Force
Copy-Item docs\internal_claude_settings.json .claude\settings.json
New-Item -ItemType Directory review -Force
```

- `.claude/settings.json` — 사내 에이전트가 `review/` 밖을 고치지 못하게 막습니다.
- `review/` — 리뷰 문서를 두는 자리입니다.
- 둘 다 배포가 **보존**하므로 다음 ZIP 이 덮지 않습니다. 템플릿이 바뀌면 그때 다시 복사합니다.

전체 운영 절차와 리뷰 문서 양식은 `docs/dual_env_workflow.md` 에 있습니다.

### 막힐 때

| 증상 | 까닭과 조치 |
|---|---|
| `uv lock` 이 `dns error` 로 죽는다 | `bigdataquery` 가 `pyproject.toml` 에 들어갔습니다. 빼고 `requirements-company.txt` 에 두세요. |
| `bigdataquery` 가 사라졌다 | `uv sync` 를 그냥 돌렸습니다. 4단계를 다시 하고 이후 `--inexact` 를 씁니다. |
| `duckdb.IOException` | 앱 서버가 떠 있는 채로 스크립트·테스트를 돌렸습니다. DuckDB 는 프로세스 배타 잠금입니다 — 앱을 끄고 다시 돌리세요. 가상환경 손상이 아닙니다. |
| 활성화 스크립트가 차단된다 | 활성화하지 않고 `.venv\Scripts\` 의 실행 파일을 직접 쓰면 됩니다. |
| 에디터가 `import streamlit` 을 못 찾는다 | 인터프리터를 `.venv` 로 지정하세요. 실행·테스트에는 영향이 없는 표시상의 문제입니다. |
